What it actually proved, by inspecting the downloaded bytes rather than trusting that a download fired:

  correctly falling back to the collection's own series (`DIN26-0001`) — tier-specific and collection-level
  reference scoping both work.

- ₦ renders correctly in the CSV.

**Verified by direct code reading, independent of the browser run** (Part 2A's remaining specific asks):

- **Formula injection.** `packages/domain/src/csv.ts`'s `csvField()` quotes and single-quote-prefixes any value
  starting with `=`, `+`, `-`, `@`, tab or carriage return — the exact set spreadsheets treat as the start of a
  formula. A dedicated unit test (`packages/domain/test/csv.test.ts`, `"defuses a value a spreadsheet would run as
  a formula (CSV injection)"`) is part of the passing domain suite.
- **Correct column selection.** `ExportPanel.tsx`/`export-actions.ts` build the CSV from exactly the field keys the
  organiser checked; the passing browser test confirmed three specific checked columns (Reference, Option, Hall of
  residence) and no others were asserted, matching a deliberate selection rather than a fixed dump.
  Row count is bounded by `MAX_ROWS = 20_000` with `tooMany` reported back rather than silently truncating.
- **Authorization.** Both CSV and PDF paths gate on `hasPermission(access, "member.export")`, re-checked
  server-side in `export-actions.ts`, and a request for contact fields additionally requires
  `member.view_contact` — the same permission an export cannot exceed even if the requester's role holds
  `member.export` alone. This matches the RBAC matrix in §10 exactly: owner, admin and treasurer hold

## 7. Packages per-order-limit — RESOLVED (Part 2D)

**The question, restated:** an organiser can set a per-order limit on a Packages option in the creation wizard, but
a contributor to a Packages collection can only ever choose one package total, so the limit has no visible or
functional effect there.

**Evidence used, per this milestone's instruction not to guess:**

- **Current domain behaviour.** `ContributeForm.tsx` has exactly two tier-rendering modes. Packages
  (`amountModel: "tiers"`, `!allowMultipleTiers`) renders exclusive radio buttons with no quantity field at all.
  Ticketing (`allowMultipleTiers`) renders checkboxes, and only a checked one reveals a quantity field.
- **Existing flow definitions.** `flows.ts`'s own hint text for the Packages step already says "A contributor picks
  one" — the single-choice design was already stated as intentional, just not connected to the per-order-limit
  control's presence in the same flow's editor.
- **Legacy product behaviour**, read directly from `kolekto-be-old`/`kolekto-fe-old` rather than assumed:
  `ContributeFlow.tsx`'s non-ticket tier branch used `setSelectedTier(tier)` — a single selection, a filled-circle
  radio affordance, no quantity stepper anywhere. The quantity stepper (`ticketSelections`, +/- buttons,
  `MAX_TICKETS_PER_ORDER`) existed **only** inside the `if (isTicket)` branch. The legacy system never let anyone
  take more than one package either.
- **Existing tests.** No test anywhere in the suite exercised more-than-one-package-per-order, because the feature
  never existed on either system.

**Decision: Option 1** — a per-order limit is meaningless for a single-choice Packages selection, so the control
that configures it should not be offered there. This is not a guess between three equally-plausible options; it is
the option the current architecture, the flow's own documented intent, and the legacy product's actual behaviour
all agree on.

**The smallest coherent change**, made this session:

- `apps/web/app/c/[slug]/collections/TiersEditor.tsx`: the per-order-limit `TextField` is no longer rendered when
  `vocabulary === "package"`. It remains for `"ticket"` (which genuinely allows several of one type per order) and
  for the neutral `"option"` vocabulary Settings uses (see the note below).
- `tests/e2e/collection-creation.spec.ts`, `"a per-order limit set during creation is enforced by the server"`:
  rewritten to use the ticketing flow instead of Packages — the same server-side guarantee
  (`resolveContribution`'s per-tier check), now exercised on a flow where it can actually be triggered, rather than
  a flow where the assertion could never have passed. This is not a weakened test; it proves the same thing on the
  flow where the thing is real.
- **Verified, not assumed:** `npm run typecheck` passes clean after the change. The rewritten E2E test was not
  re-run in a browser this session (queued behind the memory constraint documented throughout); the change is a
  straightforward conditional removal of one field plus a same-shape test rewrite using a helper (`fillTier`) and
  vocabulary (`"ticket"`) already exercised successfully elsewhere in the passing suite (§9 of the M7.8 report).

**A related observation, not acted on:** `SettingsPanel.tsx` still uses `TiersEditor`'s neutral `"option"`
vocabulary regardless of whether the collection underneath is Packages or Tickets, so a Packages collection edited
from Settings (rather than during creation) would still show the now-meaningless per-order-limit field there. This
is a real, narrower inconsistency, left alone this session because closing it would require passing the
collection's actual type context into Settings' tier editor — a larger change than "smallest coherent," and outside
what this specific finding asked to fix.

## 8. Multi-tab drafts (Part 2E)

**Assessed from the write functions, not from a live two-tab session**, and stated with confidence for a specific
reason: every collection-draft write function this session read (`app.set_collection_*`, `app.update_collection_*`,
the tier/item/audience/code-settings setters) performs a plain `UPDATE ... WHERE id = ...` with **no** version
column, no `updated_at` comparison, and no optimistic-lock check of any kind. This is not an inference from
behaviour observed once; it is the mechanism, read directly, and it is the same for every write function in this
surface — so a single confirmation generalises here in a way a UI click-through would not add confidence to.

**What this means concretely:**

- **Two tabs editing different steps** (e.g. Tab A on "Amount," Tab B on "Audience") do **not** collide, because
  each step's Continue click writes only the columns/rows that step owns. Nothing is silently corrupted across
  configuration areas.
- **Two tabs editing the identical step** produce ordinary last-write-wins: whichever tab's Continue click commits
  last is what persists for that step, with no warning to the tab that "lost." This is a narrow, low-severity case —
  an organiser overwriting their own concurrent edit of one field, not cross-contamination between unrelated
  settings.
- **`collections.draft_step`** (which step "Continue setting this up" resumes to) is itself written on every step
  transition with the same no-guard pattern, so two tabs at different steps will leave the draft resuming at
  whichever tab advanced last — a minor UX quirk (you land on a different step than you expected), not a data-loss
  risk.

**Decision, per this milestone's explicit instruction not to over-engineer collaborative editing:** last-write-wins
is the current, undocumented-but-real behaviour. It is being documented here, in this report, as the first place it
has been stated plainly. No conflict-detection mechanism is recommended: the failure mode is narrow (one person's
own overwritten edit of one field, in the rare case they have the same draft open in two tabs and edit the same
step in both), not the kind of important-configuration corruption the brief asks to guard against with new
machinery. If this changes — for example, if drafts become commonly co-edited by two officers rather than one
person in two tabs — a cheap `updated_at`-based check-and-warn (not a merge, not real-time collaboration) would be
the proportionate next step, not before there is evidence it is needed.

## 10. Internal RBAC matrix (Part 2F) — verified at the server boundary

**Note on role names.** The brief's OWNER/ADMIN/FINANCE/COLLECTOR/VIEWER maps to the codebase's actual
`public.officer_role` enum: `owner`, `admin`, **`treasurer`**, `collector`, `viewer`. "Treasurer" is used throughout
below; it is the same role the brief calls FINANCE.

This matrix was built by reading every `app.require_permission(...)` call across the collection-management server
functions (grepped, not sampled) and the `role_permissions` seed data that grants each permission to each role —
the actual enforcement layer, not the UI. RLS confirms the same boundary independently: no `INSERT`/`UPDATE`/
`DELETE` policy exists on `collections`, `collection_tiers`, `collection_fields`, or any collection-money table for
any client role (re-confirmed this session, same grep as M7.8's §5), so every action below is refused by the
database itself if the permission check is somehow bypassed in application code — defence in depth, not a single
point of failure.

| Action | Permission key | Owner | Admin | Treasurer | Collector | Viewer |
|---|---|:-:|:-:|:-:|:-:|:-:|
| View collection | `community.view_dashboard` | ✅ | ✅ | ✅ | ✅ *(scoped)* | ✅ |
| Edit draft / configure fees | `collection.draft` | ✅ | ✅ | ✅ | ❌ | ❌ |
| Configure contributor references | `collection.configure_codes` | ✅ | ✅ | ❌ | ❌ | ❌ |
| Manage audience / assign obligations | `obligation.assign` | ✅ | ✅ | ✅ | ❌ | ❌ |
| Export (CSV/PDF) | `member.export` | ✅ | ✅ | ✅ | ❌ | ❌ |
| Manage members | `member.create` / `member.edit` | ✅ | ✅ | ✅ | ✅ *(scoped)* | ❌ |
| Event check-in / check-out | `attendance.check_in` | ✅ | ✅ | ✅ | ✅ *(scoped)* | ❌ |
| Publish / pause / close | `collection.publish` | ✅ | ✅ | ✅ | ❌ | ❌ |
| Change amount after first payment | `collection.change_amount` | ✅ *(2nd approver)* | ✅ *(2nd approver)* | ✅ *(2nd approver)* | ❌ | ❌ |
| Archive a specific collection | *(no dedicated permission exists — see below)* | — | — | — | — | — |

**A real finding, not a guess about a gap:** there is no `collection.archive` permission and no dedicated
"archive this collection" server action was found in `actions.ts`. `archived` is a real, enforced value of
`collections.status` (it appears in the same status-guard every draft-editing function checks — `closed`,
`archived`, `suspended` all block further edits identically), but nothing in the current codebase exposes a
button or server action that sets a collection to it. Only `community.archive` (archiving the whole community,
reversible) exists as a first-class, permissioned action. Whether a collection needs its own archive action, or
whether `archived` is reachable only through some path this session did not find (a scheduled job, a future
Settings action), was not resolved — recorded as an open question, not silently closed either way.

**Owner** holds every permission in the catalogue by construction (`select 'owner', key, ... from public.permissions`
— a single seed statement, not enumerated per-permission, so a new permission added later is owner's automatically
and cannot be missed). Two owner actions still require a second owner's approval regardless:
`collection.change_amount`, and — outside the collection surface — `refund.initiate`, `withdrawal_account.change`,
`officer.remove_owner`, `community.archive`.

**Collector** is scoped (`requires...scoped` in the seed data) to whatever the officer's own term restricts them
to, and holds no money-adjacent or configuration permission at all: view (scoped), member create/edit/view-contact
(scoped), invite creation (scoped), sharing links (scoped), sending announcements/reminders (scoped),
`transaction.view` and `report.download` (both scoped), and `attendance.check_in` (scoped, added specifically so a
collector can run an event door without also being able to edit the event).

**Viewer** holds exactly six permissions, all read-only: `community.view_dashboard`, `member.view_contact`,
`transaction.view`, `balance.view`, `report.download`, `audit.view`. A viewer cannot export member CSV/PDF data
(that needs `member.export`, which viewer does not hold) but can download whatever `report.download` covers —
worth noting as a real, narrow distinction rather than assuming "download" means the same thing everywhere.

**Not independently confirmed by a fresh browser session this session**, though the mechanism is identical to
what M7.8 already live-confirmed for the owner-vs-outsider and owner-vs-anonymous-contributor boundaries (same
`app.require_permission` pattern, same RLS pattern): a live attempt, as each of the five roles, at each of the
actions above, by direct URL or direct server-action call. The server-code verification above is complete and
precise; a browser walk of it would confirm the same mechanism five more times rather than add new information,
and was not prioritised over the sessions' other blocked items given the shared memory constraint.

## 16. Financial invariants

**Already true today, re-verified this session by running `npm run invariants`, not by reading the script and
assuming it still passes:**

1. Money is `bigint` kobo everywhere — enforced across every migration.
2. RLS exists on every table.
3. No money write happens outside the database (no service-role money mutation in application code).
4. Exactly one caller of the Paystack-facing code exists (currently the settlement-provider seam only; Phase 4 will
   add the payment-facing counterpart at exactly one call site, per DEC-02's already-made decision).

**Specified by the existing architecture, not yet enforceable because the code they protect does not exist yet**
(re-stated here per this milestone's Part 9, each traced to where the architecture document derives it):

- No `UPDATE`/`DELETE` grant exists on ledger tables for any client role, plus a blocking trigger (the same
  mechanism already protecting `audit_logs` and `contributor_references` today — confirmed those two are already
  protected this way; the ledger tables that would need the same protection do not exist yet).
- Every journal balances (`Σ debits = Σ credits`), a deferred constraint trigger at commit.
- A capture is recorded before any validation and cannot be un-recorded; a failed validation parks money in
  `needs_review`, never a 4xx that could make captured money simply disappear from view.
- Idempotency is a unique index, never a read-then-write race.
- A webhook is a trigger to verify, never evidence on its own — a payment is believed only after a server-side
  `verify()` against the provider.
- Provider events are stored before the response is sent, so a failed event is never silently lost.
- Corrections are reversing journals; nothing financial is ever edited or deleted.
- One fee function (`calculateFees`), one call site — **already true today** for the collection wizard (§11); the
  architecture's `N5` invariant would extend the same rule to the payment path.
- `N6`: no `balance` column exists in any migration — a balance is always a sum over entries, never an
  incrementable field, because `wallet += delta` is exactly the bug class the old system's ₦46m arrangement traced
  back to.
- `N7`: no money query ever references a `migration.*` table — imported/preserved history is never treated as
  financial truth.
- Every money row stores the `fee_schedule_version` it was computed under, so a later rate change cannot restate
  history.
- A withdrawal and a payout are separate entities, because a withdrawal may need several payout attempts.
- A payout timeout is recorded as `unknown`, never `failed` — retrying an unknown-state payout risks paying a bank
  twice.
- Reconciliation records verdicts and evidence and **cannot** correct anything — a reconciler that could write
  truth would be a second, competing writer of truth.

**This session's own contribution to the invariant list:** none of the above were found to be violated, because
none of the code they govern exists yet (§21) — this section is a verification that the *design* is complete and
internally consistent, not a scan of running code for violations that cannot yet occur.

**The actual provider fee Paystack reports must be treated as provider-side financial truth once M8 exists** —
this matches the architecture's own existing design (§13/§16: `provider_fee_kobo` is "the gateway's fee — an
**estimate** on the attempt, the **fact** on the provider transaction," and the two are compared, never merged).
This commercial figure is an input to closing DEC-11 (the real fee schedule), not a rate this session has enabled
anywhere.

### D. Both fee-bearer models must become financially authoritative

Collection creation already supports **contributor pays** and **organizer absorbs** as a configuration choice
(`collections.fee_mode`, verified live and at the code level throughout this report — §11, §12 of the M7.8 report).
Today this is a stated *policy*, illustrated with an estimate. A future M8 must make both models **financially
authoritative** — the actual amount captured, the actual amount credited to the organiser, and the actual platform
fee recognised must all follow whichever policy the collection recorded, not merely display an estimate consistent
with it. This is what step 1 and step 6 of the implementation sequence (§17) actually wire up; recorded here as an
explicit requirement so it is not treated as already done because the configuration and the estimate already exist.

### E. Refund policy (future, not decided beyond what is stated here)

Recorded as stated, without extending it or deciding the parts left open:

- The **organiser** decides whether to approve a refund. Kolekto does not adjudicate whether the underlying
  service or event deserved one.
- A refund may be full or partial.
- A refund carries **another 3%** refund charge under the current business model (i.e., a second instance of the
  modeled cost in §C, not a special reduced rate).
- **Who economically bears the refund charge is explicitly not decided.** This report does not assume the
  organiser, the contributor, or Kolekto bears it — that remains open, alongside DEC-08 (§13), until stated
  explicitly by whoever owns that decision.

### F. Flexible / partial payment is NOT implemented, and must not be described as implemented

Stated plainly because this report cites several places where partial-payment *architecture* already exists as a
design (§13's A18: "`obligations` never gains `amount_paid`; partial payment is derived," and
`2026-09-22-phase4-money-architecture.md` §13) — **none of it is built**. No table, function, or code path in the
current repository processes a partial payment. Design work is not implementation.

The future model must support, as first-class concepts once built:

- a required amount
- a paid amount
- an outstanding amount (derived, per A18 — never a stored, incrementable field)
- multiple payment events against one obligation

**The exact rules for which collection types allow partial payment, and under what conditions, are not decided by
this report** and must be settled before implementation begins — the architecture document's existing installment
design (DEC-23, §13) is the closest existing precedent, but flexible payment as a general capability across
collection types is a broader question than one plan type's own installment rule, and this report does not
conflate the two or assume one answers the other.
