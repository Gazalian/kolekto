# M7.7 — Collection creation finalization: pricing, fee configuration and type-specific creation

**Date:** 2026-09-23
**Companion document:** [`2026-09-23-m7.7-collection-creation-audit.md`](./2026-09-23-m7.7-collection-creation-audit.md)
**Status:** implementation complete; **browser suite not yet run to completion** (§20, §21, §24).

---

## 1. Executive summary

M7.7 finishes the collection configuration and creation experience so that Phase 4 receives a complete, intentional
and unambiguous collection configuration. It implements no payment.

Four things changed.

**The wizard stopped being one form.** It had a single fixed seven-step sequence for all seven collection types;
everything type-specific happened inside a `switch` in step 2. It is now seven flows defined as ordered lists of
step *kinds*, rendered by kind. The sequences differ, the lengths differ (8 to 11 screens), and the vocabulary
differs. A ticketed event opens on the event — name, date, venue and flyer together — and is never asked for a
"contribution amount". A recurring plan has no closing date, because a plan that repeats does not close.

**The fee policy became configurable, for the first time.** `collections.fee_mode` has existed since the first
migration and **nothing could ever write it**. `app.set_collection_fee_mode` now can, behind `collection.draft`,
audited, idempotent, and refused on a closed collection. The creation flow stores the organiser's chosen *policy*
and nothing else — no amount, no fee, no net.

**Contributor reference configuration moved into creation.** Same M7.6 architecture, same function, same permission,
same freeze-on-issue. The only change is where it is offered, which restores parity with the legacy system.

**Two long-standing gaps closed.** `collection_tiers.per_order_limit` was enforced server-side and had never been
settable in any UI; it is now. And every browser spec walked the wizard by counting Continue clicks — a design that
had already left four specs silently red for a whole milestone — replaced by a helper driven by the flows' own data.

One defect found by the browser suite and fixed: a mid-step draft creation raced itself and could freeze the wizard
permanently (§23). That fix has not yet been re-verified in a browser, which is why this report does not say
"complete".

Specifically preserved by design:

- **ADR 0010** — tiers are rows with stable ids that survive edits and reordering.

- **Draft-as-rows** — there is no serialised wizard blob; every step writes real rows.

## 4. Fee configuration architecture

### The database

`supabase/migrations/20260923100000_collection_fee_mode.sql` — additive, one function, no table altered.

```
app.set_collection_fee_mode(p_collection_id uuid, p_fee_mode public.fee_mode)
```

- `SECURITY DEFINER`, `set search_path = ''`, revoked from `PUBLIC`, granted to `authenticated`
- tenancy read **from the row**, never from the caller
- gated on `collection.draft` — the same permission that sets a collection's amount
- refuses `closed`, `archived`, `suspended`: those terms are history
- **idempotent** — re-sending the same answer returns without writing, so a step that saves on every Continue does
  not fill the audit log with changes that did not happen
- audits `collection.fee_mode_set` with before and after state

Path: `FeeConfigurator` → `setCollectionFeeModeAction` → `setCollectionFeeMode` (`packages/db/src/write.ts`) →
`app.set_collection_fee_mode`.

### One representation, one calculation

The domain already had the abstraction Part 2 asks to reuse: `FeeSchedule`, `SCHEDULE_2026_09_PROVISIONAL`,
`FeeBearer`, `FeeBreakdown`, `calculateFees`. M7.7 added **no second implementation** and **no rate in `apps/web`**.

This matters because the legacy had four, and they disagreed: on ₦10,000 the creation wizard said ₦200 of fees and
the edit dialog said ₦350; on ₦500,000 two contribute screens differed by ₦8,500 because one applied the caps and
the other did not. That drift shipped.

### What is stored

Exactly one thing: `collections.fee_mode` ∈ {`community_absorbs`, `contributor_pays`}. No amount, no fee, no net.
Phase 4 will compute actual figures from the authoritative schedule at payment time and record the schedule version
with them (the versioning already exists — `SCHEDULE_2026_09_PROVISIONAL.version`).

## 5. Fee UX

### The choice

```
Who should cover payment fees?

( ) Contributor pays
    The contributor pays the collection amount plus applicable fees.

( ) You absorb fees
    Contributors pay the collection amount. Applicable fees are deducted from what you receive.
```

### The example asserts no figure Kolekto has not committed to

Part 3 forbids showing fake exact numbers while the schedule is unfinalised — and it is unfinalised (DEC-11), with
DEC-12 (whether a platform fee may lawfully be passed to a contributor in Nigeria) still a legal question. So the
default is:

```
Contributor pays    ₦10,000 + applicable fees
You receive         ₦10,000
```

or, when the organiser absorbs them:

```
Contributor pays    ₦10,000
You receive         ₦10,000 − applicable fees
```

The only number is the organiser's own amount.

### The estimate is available, and marked as one

Behind **"Show an estimate of the fees"**, collapsed by default, an organiser can see the computed split. It opens
with an explicit banner naming the schedule version and stating it is an estimate, not a settlement amount, and that
online payment is not switched on. Within it the two fees are named separately — *Estimated payment processing fee*
and *Estimated Kolekto service fee* — and never summed into one line, because somebody deciding whether to absorb
them is entitled to know which is the processor's and which is Kolekto's.

**This is an earlier instruction corrected, not a feature removed.** The previous revision led with computed figures
(₦20,400 / ₦19,600); that asserted pricing the business has not decided.

### One example per priced thing

Where a flow prices several things — packages, ticket types, items — each gets its own example, because absorbing
fees on a ₦2,000 souvenir and a ₦90,000 table are different decisions. An open collection with no fixed price is
illustrated at the organiser's own suggested amounts, or at a clearly labelled *"For example, on ₦10,000"*.

### The property that cannot be seen but is tested

`feePreviewRows` returns only *contribution* amounts — what the organiser typed as the price of a thing. Never a
payable, never a previous breakdown's total. `flows.test.ts` walks every flow, prices whatever it offers, feeds each
result back through `calculateFees` and asserts the payable does not move. A fee charged on a fee would creep upward
on every recalculation; it cannot.

## 6. Contributor reference integration

A `reference` step in **all seven flows**, writing through `saveCodeSettingsAction` → `setCollectionCodeSettings` →
`app.set_collection_code_settings` — M7.6's function, M7.6's permission (`collection.configure_codes`, owner and
admin), M7.6's guarantees. No second reference system; a second doorway to the same one.

Configurable: enable/disable, prefix, style (sequential or random), digits, starting number, separator, and
tier-specific prefixes.

Live examples as the format is typed — `DIN26-0001`, and per-tier `GOLD-0001` beside `SILVER-0001`, or `VIP-0001`
beside `REG-0001` for tickets.

Rules, unchanged and all enforced by the database: server-generated; immutable once issued (trigger); unique within
the collection (`unique (collection_id, reference)`) and per obligation (`unique (obligation_id)`); concurrency-safe
via `UPDATE … RETURNING` on `collection_code_sequences`, never `count(*) + 1`; format frozen after first issuance.

The four concepts stay separate: `members.member_code`, the community's primary identifier attribute,
`contributor_references.reference`, and `collection_tiers.code_prefix`.

**Two honest disclosures added to the UI:**

- without `collection.configure_codes`, the step explains rather than offering a control that would be refused
  (the function re-checks regardless — ADR 0008)
- with a **public** audience, it states that nothing will be issued until people are added to the roll, because a
  reference attaches to an obligation and an open collection has none

## 7. Fixed experience

*Everyone pays the same amount — an annual levy, a membership fee, a joining fee.*

**Basics → Amount → Fees → Image → Who pays → Their details → References → Closing → Review** (9 + intent).

Managed participation, `fixed`, one-time. Vocabulary: collection / contribution / members. The audience defaults to
the whole roll, which is what makes the collection able to answer "who has not paid". Timing: one optional closing
date. Review leads with the amount and "The same amount from everyone". Placeholder: *Ikoyi Residents Annual Levy
2026*. No ticket, item or fundraiser questions are asked.

## 8. Open experience

*Let contributors choose how much to give — a welfare fund, a condolence collection, a community project.*

**Purpose → Giving → Fees → Image → Who can give → Their details → References → Closing → Review** (9 + intent).

The second step is the point of the type and is not a fixed collection with an empty amount box: a minimum, a
maximum, suggested amounts and an optional target, together, because they are one decision. The fee example prices
the organiser's own suggestions. Review: "People give between ₦X and ₦Y", the one-tap suggestions, the target.
Placeholder: *Ilorin Traders Welfare Fund*.

## 9. Tiered experience

*Different contribution levels or packages — sponsorship tiers, membership grades, table packages.*

**Basics → Packages → Fees → Image → Who can choose → Their details → References → Closing → Review** (9 + intent).

`TiersEditor` runs in its **package** vocabulary: "Package name", "Add another package", "Remove package", a `GOLD`
prefix example. Each package supports name, description, price, quantity limit, **per-order limit**, and its own
reference prefix. One fee example per package. The reference step's hint is written for packages. Placeholder:
*Lagos Business Forum Sponsorship 2026*.

The UI does not call these "tiers" — they are packages here, tickets in the ticketing flow, options in Settings.

## 10. Item experience

*Orders for products or merchandise — aso-ebi, branded kit, a conference pack, an anniversary souvenir.*

**Basics → Items → Order rules → Fees → Cover → Who can order → Their details → References → Orders → Review**
(10 + intent).

Vocabulary: **catalogue** / order / customers / items. The first step asks "What is this catalogue called?" — which
also means a draft exists by the time the items step renders, so **item images can be added during creation**, not
only afterwards in Settings.

Each item supports name, description, price, image, available quantity, maximum per order, and ordering. Images
upload through a server action to the existing scoped storage, validate type and size, display on success, and
support replace and remove. The known failure — saving a local object URL before the upload finished — was fixed in
M7.6 with an explicit "Uploading…" state and is preserved.

Order rules are their own step: building a catalogue and deciding how people may buy from it are two different
thoughts. Timing is an **order window** — orders open *and* close. Review shows the catalogue as a grid of
photographs, prices and stock, and flags items still missing a photo.

Totals remain the server's: `resolveContribution` prices a basket from the collection's own rows.

## 11. Ticketing experience

*An event and its tickets — a conference, a dinner, a workshop, a product launch.*

**The event → Tickets → Buying → Fees → Who can buy → Their details → References → Sales → Review** (9 + intent).

**Step 1 is event identity**, as Part 9 requires: event name, description, start, end, venue — **and the flyer**,
here, not hidden in Settings. Naming the event creates the draft mid-step so the upload has a collection to scope
to; until then the panel says so rather than failing.

**Step 2 is ticket types**, in the language of tickets: "Ticket type name", "How many exist", "Most one person may
buy", "Add another ticket type", a `VIP` prefix example. Price, description, quantity available, per-order limit and
reference prefix per type.

**Step 3 is purchase rules**, and it states the thing plainly: *"One contributor can purchase multiple tickets for
other people."* It carries the attendee-details toggle — one name per ticket rather than only the buyer's — which
moved off `EventEditor` because "how many names do you need?" is a question about selling tickets, not about when
the dinner is.

**Step 6 separates ticket sales from the event date.** Timing is a `sales_window` with its own open and close, and
the step says explicitly that this is when people can buy, *not when the event is*, repeating the event's own date
underneath. There is no generic collection deadline doing both jobs.

The word "contribution" never appears in this flow, and there is no amount step. Review leads with the flyer, the
title, the date and venue on one line, and whether a name is asked per ticket. The preview is the real public event
page.

## 12. Fundraising experience

*A cause or project — a medical appeal, a building fund, a relief drive.*

**The story → Goal → Fees → Who can give → Their details → References → Timing → Review** (8 + intent).

**Step 1 is the story**, structured as Part 10 asks — what you are raising money for, why it matters, what the
money will accomplish — **with the campaign image on the same screen**. Its hint says why: it is the first thing a
supporter reads and it is what decides whether they give.

*Deliberate deviation:* Part 10 suggests the cover image as its own step between story and goal. It is on the story
step instead, because the image and the story are one editorial decision and splitting them adds a screen without
adding a choice. The requirement behind the suggestion — that it is in the creation flow and not discoverable only
in Settings — is met.

Step 2 is a **goal**, never a price: target, suggested amounts, optional minimum. Vocabulary throughout: campaign /
donation / supporters. Timing is a campaign end. Review reads the story back with "Working toward ₦X" and what a
gift funds in its own box. The public preview leads with story, goal, impact and the give action, because it is the
real renderer. Placeholder: *Rebuild the Community Health Post*.

## 13. Recurring experience

*Recurring dues or charges — monthly service charge, quarterly subscriptions, annual dues.*

**Basics → Amount → Frequency → Fees → Image → Who pays → Their details → References → Review** (9 + intent) —
and **no timing step at all**.

Vocabulary: **plan** / payment / members. "What is this plan called?", "Amount per period". The frequency step
carries frequency, interval, first-period start and due-after-days, and says that each period is asked for
separately and paying one does not settle the next.

**No fake deadline**, and no implication of automated card debits: the review states that the organiser opens each
period themselves and nothing is charged automatically. `flows.test.ts` asserts a timing step exists for every flow
whose shape is not `none` and for no other. Placeholder: *Estate Service Charge*.

## 14. Timing model

Every use of "deadline" was audited. One generic field became five shapes:

| Shape | Flows | Fields written | Wording |
|---|---|---|---|
| `closing_date` | fixed, open, tiered | `deadline_at` | "When does it close?" |
| `campaign_end` | fundraiser | `deadline_at` | "When does the campaign end?" |
| `order_window` | items | `starts_at` + `deadline_at` | "Orders open" / "Orders close" |
| `sales_window` | ticketing | `starts_at` + `deadline_at` | "Sales open" / "Sales close" |
| `none` | recurring | — | no step |

**No schema change was needed.** `starts_at` and `deadline_at` have both existed since `20260917120700`; the wizard
had simply never written `starts_at`. The underlying safe model is preserved and only the user-facing
representation changed, exactly as Part 12 directs. The event's own `event_starts_at` / `event_ends_at` / `venue`
remain separate fields and are not conflated with sales dates.

The review's timing sentence is written per shape by `describeTiming`, so a plan reads "No closing date — a plan
that repeats does not close" and an event reads "Sales open … · close … · event …" with all three dates named.

## 16. Draft persistence

Preserved from M7.5/M7.6 and extended.

Every meaningful step persists. `persistStep(stepKind)` replaced `persistStep(position)`; every prior save path is
preserved and two are new — `fees` (via `setCollectionFeeModeAction`) and `reference` (via `saveCodeSettingsAction`).

The audience still saves **first and for every mode**, before the collection row, because `audience_mode` and
`participation_mode` are paired by `collections_audience_matches_participation` and `app.set_collection_audience` is
the one place that writes both in a single statement.

Restored on resume: the flow (derived via `flowKeyFor`), name, description, `starts_at`, `deadline_at`, amounts,
suggested amounts, story, tiers (**including per-order limit**), items, event, recurrence, questions, audience,
visibility, cover, **fee mode**, **code settings**, and whether the reference format is already frozen.
`draft_step` is clamped to the resumed flow's length, because the flows are no longer all the same length.

A draft reopens **in its own flow**: a ticketed event comes back as an event, at the step it was left on, with the
event flow's own length and vocabulary.

## 17. Preview

The review step links to `/c/[slug]/collections/[collectionSlug]/preview`, which renders **`CollectionView` — the
same component the published public page renders** — from the draft's own rows, inside `PreviewFrame` (phone and
desktop toggle, "Contributor view", "Nothing here can be submitted").

No second preview implementation was created. The preview is type-specific because the real renderer is. The link's
wording is the flow's own: "See what your supporters will see", "See what your attendees will see".

The **review** is also type-specific (`ReviewPanel.tsx`): seven headline components, so a catalogue is reviewed by
looking at the catalogue, an event by looking at the event, a campaign by reading its story back — rather than by
reading a table of which fields were filled in. Only fields relevant to the type are shown.

## 18. Security

No new trust was granted.

| Never trusted from the client | Decided by |
|---|---|
| amount | `app.create_collection` / `app.update_collection` |
| fee | `calculateFees` server-side; the UI sends none |
| tier price | `collection_tiers.price_kobo` |
| item price | `collection_items.price_kobo` |
| stock / per-order limit | `collection_items`, `collection_tiers`, checked in `resolveContribution` |
| reference number | `app.issue_contributor_reference`, server-generated, DB-unique |
| community | resolved from slug through RLS |
| collection | resolved inside that community |
| audience membership | `app.set_collection_audience` |

Specific to this milestone:

- `app.set_collection_fee_mode` reads tenancy from the row, requires `collection.draft`, is revoked from `PUBLIC`,
  refuses a closed collection, and is audited.
- `canConfigureCodes` is a **UI-level** signal only; `app.set_collection_code_settings` re-checks
  `collection.configure_codes` whatever the screen offered (ADR 0008).
- No service-role client was introduced into browser code. `FeeConfigurator`, `ReviewPanel` and the wizard are
  client components receiving already-authorised props.
- Public contributors cannot modify fee policy, reference configuration, collection configuration, member records
  or obligations: none of those paths are exposed to `anon`, and every `app.*` write requires `authenticated` plus
  a permission check.

Proven by `supabase/tests/18_fee_configuration.sql`: a viewer cannot set the fee mode; another community's owner
cannot reach into this one **and cannot even read the row they were refused**; a missing collection is `NOT_FOUND`;
a closed collection is `COLLECTION_NOT_EDITABLE`; `anon` holds no execute privilege.

A browser journey (§21, journey Q) additionally checks that a signed-in outsider cannot open the community
dashboard, its collections list, the creation wizard, a specific collection, its continue route, its preview, its
settings or its members.

## 19. Database migrations

**One, additive, applied to the local stack only.**

```
supabase/migrations/20260923100000_collection_fee_mode.sql
```

## 23. Defects discovered and fixed

**1. A mid-step draft creation raced itself and could freeze the wizard permanently.** *(found by the browser
suite; the most serious of the three)*

The ticketing flow creates its draft mid-step, because Part 9 puts the flyer on the first event screen and an
upload must be scoped to a real collection id. `ensureDraft()` fires when the event name loses focus and guarded on
`draftId` — **React state**, which does not update inside the closure that set it. So `ensureDraft` and the
subsequent `advance()` both read `null` and both called `app.create_collection` for the same event. The loser
collided on the slug, and that rejection escaped into `startTransition`, which leaves `isPending` true for good —
disabling Continue *and* Back together, showing "Saving…" forever, with the organiser's work apparently lost. The
captured page proved the draft had in fact been created.

Fixed in `NewCollectionForm.tsx`: the draft is held in a **ref**, written synchronously, so a second caller sees the
first one's work; an in-flight creation is held in `creationRef`, so a caller arriving during one waits and then
performs its own *update* rather than starting a second create (returning the shared promise would silently drop a
description typed after the first create began); and every transition's work runs through `guard()`, which turns an
unexpected throw into a message rather than a frozen wizard.

**2. `SettingsPanel` would have silently dropped the new per-order limit.** Adding the field to `TiersEditor` made
it appear in Settings too, which loads and saves tiers independently — and its mapping included neither. An
organiser would have set a limit, saved, and watched it vanish. Caught before shipping by checking every consumer
of the edited component; both the load (line 98) and the save (line 313) were fixed.

**3. A test defect of mine.** `getByRole("textbox", { name: "Price", exact: true })` matched nothing: a required
field's accessible name carries the asterisk from its label, so it is `"Price *"`. Fixed in the helper and its call
sites.

**4. An environmental failure, classified rather than labelled.** Sign-in failed with *"Processing this request
timed out, please retry after a moment"* — Kong's upstream timeout on `POST /auth/v1/otp`; the request never
reaches the application. It reproduced precisely when a typecheck, a lint and a vitest run were competing with the
browser suite for the same four cores. Not a flake of unknown origin: an environment finding with a known cause.

**5. Collateral damage I caused, and fixed.** Running `next build` in the same tree as a running `next dev` left
production artefacts (`BUILD_ID`, `prerender-manifest.json`, `routes-manifest.json`) in `apps/web/.next`. A dev
server started on top of them served 404s for app routes — which is what the user hit. Diagnosed from artefact
timestamps versus the dev server's start time, fixed by clearing `.next` and restarting; the data was never
involved (816 communities intact throughout). See §24 for the standing risk.

## 24. Known limitations

**The browser suite has not been run to completion, and M7.7 is therefore not complete.** Three partial runs were
made; the first two surfaced defects 3 and 4 and were re-run after fixing them; the third — the full suite on a
quiet machine — was **killed part-way by the host for system memory pressure**, not by a test failure. The Supabase
stack, a Next production server and Chromium together exhaust the 7.9 GB available. Defect 1's fix typechecks,
lints and builds but **has not been re-verified in a browser**.

**`next build` and `next dev` share `apps/web/.next`.** Until that is separated (a `distDir` keyed off an env var
would do it), running a build while a dev server is up will break the dev server again. Not changed here because it
touches shared config and Playwright's `webServer`; recorded as the first item in §27.

**References do not issue on a public audience.** They attach to obligations, and a collection open to anyone has
none until members are added to a roll. The UI now says so, and the product question is logged as DEC-25.

**Fundraising's cover image is on the story step**, not its own step as Part 10 suggests. Rationale in §12.

**`docs/prd/` is empty.** The `PRC-02/09/12` requirements cited in `fees.ts` have no document behind them in this
repository. Recorded rather than invented.

**The fee estimate is collapsed by default.** Deliberate, per Part 3 — but it means an organiser who never opens it
sees no numbers at all beyond their own amount. That is the correct trade while DEC-11 is open; it should be
revisited when the schedule is fixed.
