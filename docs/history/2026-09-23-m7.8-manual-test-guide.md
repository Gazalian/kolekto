# M7.8 — Manual testing guide

**Purpose:** a practical, click-by-click guide to test the M7.7 collection-creation work yourself, without reading
source code. Every field label, button name and message quoted below is copied from the application's own code or
from the automated browser tests that assert on the real rendered page — not paraphrased.

**Companion document:** [`2026-09-23-m7.8-real-time-product-qa-report.md`](./2026-09-23-m7.8-real-time-product-qa-report.md),
which records what I actually ran, what passed, what failed, and why.

---

## 1. Start the local environment

From the repository root (`Kolekto-codebase/kolekto`):

```
npm run db:start        # starts the local Supabase stack (Postgres, Auth, Storage, Kong, Studio, Mailpit)
npm run dev              # starts the app at http://localhost:3000
```

`npm run db:start` prints a `Mailpit` URL (usually `http://127.0.0.1:54324`) — this is where sign-in codes land
instead of a real inbox, because there is no real email server locally. Keep that tab open; you will read every
one-time code from it.

Do not run `npm run build` in the same `apps/web/.next` while `npm run dev` is running — until this milestone that
corrupted the dev server's build output (§27 of the M7.7 final report). This is now fixed: `npm run build` reads
`NEXT_DIST_DIR` and, when the automated suite sets it, writes to `.next-e2e` instead. Left unset (the normal case
for you running `npm run build` by hand), it still writes to `.next`, exactly as before — so avoid running a manual
build alongside your dev server, the same as always.

## 2. Sign in

Kolekto has no password. Go to `http://localhost:3000/login`, choose **Email**, enter any address (a made-up one is
fine — nothing is sent anywhere real), click **Send code**. Switch to the Mailpit tab, open the newest message, copy
the 6-digit code, paste it into the **6-digit code** field, click **Verify and sign in**. You now have a fresh
account with no communities.

There is no seeded "test account" — every sign-in with a new address creates a new person. If you want to return to
the same account later, use the same email address again (the code changes each time; the address is your identity).

## 3. Which community to use

Create a new one for this testing pass so you are not mixing test data into anything real: click **+ New community**,
give it any name (e.g. "M7.8 Manual QA"), pick a **Type** (any option), and click **Create community**. You land on
its dashboard.

## 4–5. Choosing a collection type, and what each one asks

Click **Collections** in the left rail, then **New collection**. The first screen is the same for every type:

> **What are you collecting for?**

Seven cards, each with a title, one line of description and a neutral example. Clicking one starts that type's own
flow — a different number of screens, in a different order, asking about the thing that type is actually about
first. This is the headline change M7.7 made: before it, every type walked the same seven screens with a different
label on the second one. Confirm this yourself by starting two different types (say, **Fixed contribution** and
**Tickets**) and comparing what step 1 (after the intent card) asks — one should ask **"What are you collecting?"**,
the other should ask **"Tell us about the event"**, with the flyer upload alongside the event's name and date, not
a separate screen.

The seven cards, and the step-by-step shape of each:

### A. Fixed contribution
*"Everyone pays the same amount."* Example: an annual levy, a membership fee, a joining fee.

1. **What are you collecting?** — Name (`What is this collection called?`), description.
2. **How much does each person pay?** — Field labelled `Amount each person pays`.
3. **Who should cover payment fees?** — see §8 below.
4. **Add an image** — optional cover, JPG/PNG/WebP up to 5 MB.
5. **Who is expected to contribute?** — audience (see §7 below; this flow only offers *managed*, named members).
6. Questions (optional extra fields to ask a contributor).
7. Contributor references (optional; see §9).
8. **When does it close?** — an optional closing date.
9. **Check this over** — review, then **Open this draft**.

**Try it:** name it "Ikoyi Residents Annual Levy 2026", amount `20000`. On the fee step, click **Contributor pays**
and confirm you see **"₦20,000 + applicable fees"** — not a computed number — until you click
**"Show an estimate of the fees"**. That distinction (no invented figures by default) is deliberate; see §8.

### B. Open contribution
*"Let contributors choose how much to give."* Example: a welfare fund, a condolence collection, a community
project.

1. **What are people giving to?** — name, description.
2. **What may people give?** — a minimum, a maximum, and suggested amounts, all optional (hint on screen: "Leave the
   limits empty to accept any amount").
3–9. Same shape as Fixed, except the audience step asks **"Who can contribute?"** and this flow's audience allows
   *public* (anyone with the link) as well as managed.

**Try the edge cases:** set minimum above maximum; set a suggested amount below the minimum or above the maximum;
leave everything blank and confirm the public page still accepts any amount.

### C. Packages (tiers)
*"Offer different contribution levels or packages."* Example: sponsorship tiers, membership grades, table packages.

1. **What are you offering packages for?**
2. **What packages are you offering?** — add rows, each with a name (`Package name`), price (`Price`), an optional
   limit, and an optional **`Reference prefix`** of its own. Click **Add another** to add a row.
3. Fees, image, audience (**"Who can take a package?"**), questions.
4. References — this step's own heading is **"Give each contributor a reference?"**, with the hint that a package
   with its own prefix gets its own numbering series (GOLD-0001 beside SILVER-0001).
5. Closing date, review.

**Try it:** "Lagos Business Forum Sponsorship 2026" with Bronze/Silver/Gold/VIP, each with a distinct price and a
distinct reference prefix. Reorder them (drag or whatever control is present), delete one, try a zero price and a
negative price and confirm both are refused before you can continue.

### D. Items
*"Collect orders for products or merchandise."* Example: aso-ebi, branded kit, a conference pack.

1. **What are you taking orders for?**
2. **What is in the catalogue?** — each item: a photo, a price, how many are available.
3. **How may people order?** — a per-order rule for the *whole* order (per-item limits live on the item itself).
4. Fees, cover image, audience (**"Who can place an order?"**), questions, references.
5. **When are orders open?** — an order window, not a single closing date.

**Try it:** at least 5 items, each with a *different* photo (a crossed-wire upload is the one bug class that looks
fine in a screenshot and wrong in the database). Replace one image, remove another, leave the draft, close the
browser, come back (§11) and confirm the surviving items still have the right photos.

### E. Tickets
*"Create an event and sell tickets."* Example: a conference, a dinner, a workshop.

1. **Tell us about the event** — this is the one screen that is genuinely different in kind: name, description,
   date, venue **and the flyer**, all together, because that is what an organiser has in their head first. Upload
   the flyer here and confirm it appears before continuing.
2. **What tickets are you selling?** — each type: name (`Ticket type name`), price, `How many exist`, and an
   optional prefix.
3. **How may people buy?** — purchase rules, including whether to ask a name per ticket.
4. Fees, audience (**"Who can buy a ticket?"**), questions.
5. References — heading **"Give each ticket a reference?"**.
6. **When are tickets on sale?** — a sales window, explicitly separate from the event's own date (the hint on
   screen says so directly: "This is when people can buy — not when the event is").
7. Review — **"Check the event"**.

**Try it:** buy two ticket types in one order as a contributor (e.g. VIP × 2, Regular × 1), turn on "ask for a name
per ticket", and confirm the form asks for exactly the right number of names, one per ticket, not one per type.

### F. Fundraising
*"Raise money for a cause or project."* Example: a medical appeal, a building fund, a relief drive.

1. **Tell your story** — this is the first screen, and the cover image lives here too (a deliberate deviation from
   a separate image step — see the QA report's known-limitations section).
2. **What are you working toward?** — a target and suggested amounts.
3. Fees, audience (**"Who can donate?"**), questions, references, **"When does the campaign end?"**, review.

### G. Recurring
*"Collect recurring dues or charges."* Example: monthly service charge, quarterly subscriptions, annual dues.

1. **What is being charged for?**
2. **How much per period?**
3. **How often, and when is it due?** — frequency and due-after rule. The hint states directly: "Each period is
   asked for separately. Paying one does not settle the next" — confirm there is **no** "closing date" step anywhere
   in this flow, and nothing on screen implies a card will be charged automatically. Both are deliberate product
   rules, not omissions.
4. Fees, image, audience (**"Who is expected to pay?"**), questions, references, review — **no timing step**, which
   is correct: a plan that repeats does not close.

## 6. What proves each flow actually works

Two things, together, on every flow: (1) the review step's summary genuinely reflects what you entered — not a
generic template — and (2) clicking through to the collection's own preview shows the *same* renderer a contributor
would see, not a mock-up. If you see placeholder text, a wrong number, or a field you filled that is not reflected
in the review, that is a real defect — report it with the flow, the step, and what you typed.

## 7. Audience

Every flow's audience step offers a subset of: **all members**, **a specific group**, **selected members**, and
(open/fundraiser/items/ticketing/tiered flows only) **public — anyone with the link**. Test:

- A group with one member, then a group with several.
- A member who belongs to more than one relevant group.
- An archived member — confirm they do not appear as an eligible target.
- Switching between audience types and confirming the choice survives a draft resume (§11).

## 8. Fee configuration

Every flow's fee step asks the same question, once, in the same component: **"Who should cover payment fees?"**,
with two options:

- **Contributor pays** — "The contributor pays the [contribution] amount plus applicable fees."
- **[You/the community] absorb fees** — "Contributors pay the [contribution] amount. Applicable fees are deducted
  from what you receive."

**What you should see by default:** for a ₦20,000 amount, "Contributor pays" shows **"₦20,000 + applicable fees"**
— no computed number. This is deliberate: Kolekto's real fee schedule is not finalized (DEC-11), so the default view
never states a number it cannot stand behind.

**Click "Show an estimate of the fees"** to see the computed split, which should appear behind an explicit
disclosure reading something like *"An estimate only, using Kolekto's provisional rates... not a settlement
amount."* Two fees are shown **separately** — "Estimated payment processing fee" and "Estimated Kolekto service
fee" — never summed into one figure. For ₦20,000: absorbing should show the community netting **₦19,600**; passing
the fee on should show **₦20,400** (fees computed on the ₦20,000 contribution) and specifically **not ₦20,408**,
which is what you would see if the fee had wrongly been computed on the ₦20,400 payable instead (a compounding
bug). Somewhere on the step you should also see confirmation that **nothing has been charged** — this is
configuration only.

**What proves it is real configuration, not decoration:** leave the wizard mid-flow (navigate to the collections
list), come back through "Continue setting this up", step back to the fee screen, and confirm the radio you chose
is still selected.

## 9. Contributor references

On the reference step, check **"Give each [contributor/ticket holder/etc.] a reference?"**, then set:

- **Prefix** — free text (e.g. `REG`).
- **Style** — sequential or random.
- **Number of digits** — how many digits the counter pads to.
- **Starting number** — sequential only; not offered for random.

For a tiered or ticketed flow, each package/ticket type can carry its own **Reference prefix** on its own row, which
gives it its own numbering series — e.g. `REG-0001` and `VIP-0001` existing side by side, both starting at 1,
independently.

**What should NOT be possible:** once a reference has actually been issued to a real contributor, the format fields
(prefix, digit count, style) should be locked — you should see them disabled, not merely discouraged. If you can
still edit a locked reference format, that is a real defect.

**Public collections:** a reference attaches to an obligation, and a collection open to "anyone with the link" has
no obligations until members are added to a roll. Confirm the UI says this rather than silently doing nothing.

## 10. Draft persistence and resume

For any flow: fill roughly half of it, then navigate away (click **Collections** in the left rail) without finishing
or clicking Publish. Go back into the community's collection list and you should see the draft with a **"Continue
setting this up"** link. Click it and confirm every value you entered is still there — including anything in an
editor (a tier row, an item, an event date), not just plain text fields.

Also worth trying, because these are exactly where drafts have broken before:
- Close the whole browser (not just the tab) and reopen it, then navigate back to the draft by URL.
- Refresh mid-upload (start a flyer/image upload, refresh before it finishes).
- Open the same draft in two separate browser tabs, change something different in each, and see which value wins —
  there is no invented conflict resolution here, only whichever write lands last.

## 11. Preview

From the review step or from the collection's own page, use the preview link. It should render through the *same*
public page a contributor would see, including your chosen fee-mode presentation, cover image, and vocabulary
(an event should say "attendees", a fundraiser should say "supporters", and so on — the vocabulary is flow-specific,
not generic "collection" language everywhere).

## 12. The contributor side

Publish a collection, then open its public URL (shown on its Overview page, or `http://localhost:3000/{community
slug}/{collection slug}`) in a private/incognito window so you are not signed in as the organiser.

**For a managed collection** (named members): you should be asked to identify yourself *before* anything about
money appears. Try:
- Searching by a name two members share (e.g. two "Grace Adeyemi" entries with different phone numbers) — you
  should see a count and a prompt to narrow it down (by member ID or phone), never a list of the actual matches.
- Searching for an archived member — you should get "nobody matches", not their record.
- Confirming your identity, then clearing your browser's cookies for the site and trying to submit again — the
  server should refuse ("Find yourself on the list before continuing"), because your identification is a signed
  cookie the server checks, not something the page merely remembers.

**For an open/public collection**: no identification step at all — go straight to choosing/entering an amount.

**For any collection with a per-order or per-ticket limit**: try to order/buy more than the limit or more than what
remains in stock, both in the browser (the input should refuse) and, if you can, by editing the request directly
(the server should refuse too — client-side refusal alone is not enough).

## 13. Ticketing specifics

Buy more than one ticket type in a single order (e.g. 2× VIP, 1× Regular). If "ask for a name per ticket" was
turned on, confirm you are asked for exactly 3 names, each labelled with which ticket it belongs to.

## 14. Item baskets

Add multiple different items to the basket, in different quantities. Confirm the total shown is computed
server-side (it should not be possible to change the price by editing anything client-visible) and that ordering
more than the per-item or per-order limit is refused.

## 15. Fundraising

Confirm the public page reads like a campaign — the story is prominent, there is a visible goal/progress framing —
not like a generic contribution form with extra text.

## 16. Recurring

On the public page, confirm you are shown the *current period only* ("a recurring charge shows the period it is
asking about") — not a payment schedule, not an implication that a card will be charged automatically for future
periods.

## 17. Authorization — what you should NOT be able to do

Sign in as a second, unrelated account (a different email address) that has never been invited to your test
community. As that account, try to open, directly by URL, each of:

- `/c/{your community slug}`
- `/c/{slug}/collections`
- `/c/{slug}/collections/new`
- `/c/{slug}/collections/{a real draft's slug}`
- `/c/{slug}/collections/{slug}/continue`
- `/c/{slug}/collections/{slug}/preview`
- `/c/{slug}/settings`
- `/c/{slug}/members`

Every one of these should refuse the outsider — either a 403/404, or a redirect away from any page that would
reveal the community exists. If any of them opens and shows real data, that is a serious defect — report it
immediately, in plain terms, with the exact URL.

## 18. Mobile

Resize your browser window (or use its device-emulation mode) to 390px wide — an iPhone-sized viewport. Open a
published collection's public page and confirm: nothing scrolls sideways, the amount field and identification form
are usable, and text is not cut off. The organiser-facing wizard has not been checked this way in this round of
testing (recorded as a gap, not a pass) — if you try it yourself, watch the tier/item/ticket editors and the fee
step in particular, since they have the densest layouts.

## 19. What counts as a failure worth reporting

- Anything in §17 that opens for an outsider.
- A number on the public page that does not match what you configured (amount, fee split, stock, limit).
- A draft that loses data you entered after leaving and returning.
- The wizard getting stuck on "Saving…" with Continue and Back both disabled and no way forward (this exact
  symptom was a real, now-fixed defect — see the QA report — so if you see it again, it is a regression).
- A reference format that can still be edited after a reference has been issued.
- Any screen implying a payment has happened, will happen automatically, or has been recorded — Phase 4 does not
  exist yet, and nothing should suggest otherwise.

## 20. What is expected to be occasionally slow or flaky, and is not a product bug

This local machine runs a full Supabase stack (Postgres, Auth, Storage, Kong, Realtime, Studio) alongside the app
and, if you are testing in a browser, the browser itself — on limited RAM. Under load you may occasionally see
**"Processing this request timed out, please retry after a moment"** on sign-in, an image failing to load once, or
a step taking longer than usual. Waiting a few seconds and retrying is the correct response; this has been traced
(this round and the previous one) to Postgres itself timing out under host resource pressure, not to the
application. It is documented in the QA report as an environment finding, not swept under a "flaky test" label.

## 21. A defect this round found and fixed — worth testing yourself

Before this round, resuming a draft **before ever reaching its reference-configuration step** crashed the page
entirely — "Something went wrong," no wizard, no way forward. This is now fixed (the QA report's §10, Finding 3),
but is worth your own confirmation: start any flow, fill in the first one or two screens, leave before reaching
the "Give each [contributor/ticket holder] a reference?" step, close the browser, come back through "Continue
setting this up." If you see the crash screen again, that is a regression — report it immediately.

## 22. What has zero coverage from this round, and is worth your attention first

Two things were not verified at all this round, by browser test or by hand:

- **Tier/package reference prefixes together with the CSV and PDF exports** — the journey in §9 above (REG-0001 /
  VIP-0001, downloading and opening both files, checking a non-Latin name like "Ẹniọlá Adéṣínà" survives correctly
  in both). If you only have time for one manual pass, make it this one.
- **The organiser-facing wizard at a mobile width** — §11's mobile check only covers the public contributor page.
  Nobody has checked the tier editor, item editor, ticket editor or fee step at 390px this round.
