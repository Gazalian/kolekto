# M7.6 — what the old Kolekto did, and what this one does instead

**Date:** 2026-09-22
**Scope:** M7.6 part AG. Read-only inspection of `kolekto-fe-old` and
`kolekto-be-old`, plus the diagnostics those repositories carry about
themselves. No legacy system was run, changed or connected to. Production was
not accessed.

The old application is a product reference, not an architecture reference.
People used it for two years; the behaviour they learned is worth keeping and
the structure underneath it is the reason this rebuild exists.

---

## 1. Contributor codes

### Legacy behaviour

`src/components/collections/form/UniqueCodesSection.tsx` — a switch, a prefix
box, and a live example rendered as `` `${codePrefix || 'PREFIX'}-001` ``. The
helper text says the thing that matters: *"A prefix is required to generate
codes — no prefix means no code is assigned, even with this enabled. If
someone pays for multiple people, each person will get their own code."*

Generation lived in the Paystack verification edge function. From that
repository's own diagnostic, `KOLEKTO_CONTRIBUTOR_CODE_NUMBERING_DIAGNOSTIC.md`:

> contributor-code sequence allocation (`next_contribution_code_number`) is
> committed independently of, and strictly before, the `contributions` insert
> it numbers.

A counter that commits in its own transaction and an insert that may then fail
is a number issued to nobody. The same document records production reaching a
gap of 1,650 and growing on one collection, and a cron retrying a permanently
failing insert every five minutes with no retry cap.

### New behaviour

| Legacy | New | Verdict |
|---|---|---|
| Toggle + prefix, live example | Toggle + prefix + separator + digits + starting number, live example | **Improve** — the example was the right idea; the old one was hard-coded to three digits and a hyphen, and could not show what the collection would actually issue |
| Prefix required, no prefix means no code | Same rule, enforced by the database (`NO_PREFIX`) rather than by a sentence | **Keep** |
| Per-tier prefix (`unit.prefix || collection.code_prefix`) | Same fallback rule: an option's prefix if it has one, the collection's otherwise | **Keep** — this is the behaviour that makes REG-0001 and VIP-0001 coexist, and it was right |
| Counter committed in its own transaction, before the row | Counter incremented inside the same transaction as the insert (`app.issue_contributor_reference`) | **Remove and replace** — this is the defect the legacy diagnostic was written about |
| No uniqueness constraint behind the counter | `unique (collection_id, reference)`, enforced by the database | **Improve** |
| Codes minted at payment | References issued when somebody joins the roll | **Change, by necessity** — see §5 |
| Code could in principle be regenerated | Immutable and undeletable once issued, by trigger | **Improve** |

The retry loop in the new function deliberately does **not** return a number
to the counter when an insert loses to the unique index. That is the same
"burn" the legacy diagnostic complains about, and here it is correct: a
counter that gave numbers back would eventually reissue one already printed on
a ticket. The difference is that a burn is now bounded to a real collision
inside one transaction, rather than being the normal outcome of any failed
payment. If the whole call fails, the increment rolls back with it.

Proven under 24 and 60 simultaneous writers by
`scripts/verify/reference-concurrency.mjs`, which is a thing the legacy system
had no equivalent of.

## 2. PDF export

### Legacy behaviour

`src/pages/dashboard/CollectionDetailsPage.tsx`, `exportPDF()`. A template
literal of inline-styled HTML is appended to the live document, handed to
`html2pdf.js`, rasterised by html2canvas at scale 2, and saved as A4
landscape.

What it got right, and what this milestone kept:

- a branded header with the collection title and the generated date, written
  in `en-NG` long form ("21 September 2026")
- a summary block above the table
- a confidentiality line in the footer
- ₦ rendered properly
- landscape by default, because contributor tables are wide
- refusing to export nothing: *"No contributor data to export"*

What it got wrong:

| Legacy | New | Verdict |
|---|---|---|
| html2canvas rasterises the page | Real PDF text objects via pdf-lib | **Remove** — a rasterised report cannot be searched, selected or copied, and a printed attendance list is a document people search |
| Built in the browser | Built on the server | **Remove** — html2canvas at scale 2 over a thousand rows is tens of megabytes of canvas on a phone |
| No pagination control | Explicit pagination, tested for row conservation | **Remove** — html2canvas splits wherever the image runs out, which cuts rows in half |
| Total collected in the header | Absent | **Remove, for now** — nothing has been received in this phase, and a total of ₦0 is a claim (see §5) |
| Landscape always | Landscape past six columns, portrait below | **Improve** |
| Header row once | Header row repeated on every page | **Improve** |
| Filters not recorded | Filters printed under the heading | **Improve** — a report without its filters on it is a report somebody reads as the whole list |
| No page numbers | "Page 3 of 11" | **Improve** — a dropped sheet is otherwise invisible |

The font problem the legacy system did not have to solve, because a rasterised
page inherits the browser's fonts: the fourteen standard PDF fonts are
WinAnsi-encoded, and WinAnsi has neither ₦ nor the ẹ ọ ṣ ị ụ that Nigerian
names are full of. DejaVu Sans is embedded for that reason.

## 3. CSV export

The legacy front end had no CSV export of contributors at all — the CSV files
in that repository (`FINANCIAL_DRIFT_CLASSIFICATION.csv`,
`user_financial_breakdown.csv`) are forensic artefacts produced by
investigators, not a product feature. Hosts who wanted a spreadsheet got a
PDF and retyped it.

**New:** RFC 4180 with a byte-order mark and CRLF, plus formula-injection
defence, in `@kolekto/domain`'s `csv.ts`. Not a comparison — an absence
filled.

## 4. Field selection

### Legacy behaviour

`exportPDF` used `visibleContributorFields` — whichever custom fields the host
had defined on the collection — plus a tier column and a unique-code column
when any row had one. The host chose nothing at export time; the columns were
whatever the collection happened to have.

| Legacy | New | Verdict |
|---|---|---|
| Columns derived from the collection | Columns chosen per export, grouped by Identity / Collection / Membership / Event / Custom fields | **Improve** — the caterer wants dietary answers, the treasurer wants amounts, and they are two ticks apart |
| Unique-code column appears if any row has one | Reference is a column like any other, ticked by default | **Keep the intent, change the mechanism** |
| Custom fields under their own labels | Same | **Keep** — "Matric number", never `custom_field_1` |
| No filters at export time | Status, group, option, period, door state, date added | **Improve** |
| No record that an export happened | `collection.export_created` in the audit log, with the column names and the row count, never a value | **Improve** — an export is a disclosure of member personal data |

## 5. What legacy had that this milestone deliberately does not

Three exports the old product offered and this one does not: contributions,
payments, and totals collected.

They are not missing because they were forgotten. Nothing in this system
records a contribution, a purchase or an order — ADR 0012 rejected a
pending-contribution table on purpose, and ADR 0006 gates the real one until
Phase 4. An export named "Contributions" that produced an empty file would
read as *nobody has paid*, which is a materially different and much worse
statement than *this does not exist yet*. The export screen says so in a
sentence instead.

The same reasoning governs the rest of this milestone:

- a contributor reference attaches to an **obligation** — a member an officer
  put on the collection — because that is the only participation record that
  exists. A public collection has no obligations and therefore no references,
  and the screens say so rather than showing an empty column.
- check-in admits somebody on the roll, not a purchased ticket.
- the fundraiser page shows what the appeal is working toward and states that
  what has been raised will appear when online giving is switched on, rather
  than drawing a progress bar at zero.

When Phase 4 records a confirmed contribution, each of those becomes a second
thing the same structure points at: a nullable `contribution_id` beside
`obligation_id`, the same sequence, the same format, the same uniqueness, the
same audit trail. None of it needs rewriting.

## 6. Architectural problems deliberately not reintroduced

| Legacy pattern | Why it is not here |
|---|---|
| Code minted in an edge function, outside the insert's transaction | `app.issue_contributor_reference` does both in one transaction, and a unique index stands behind it |
| `price_tiers` as a jsonb array, resolved by name-or-id `.find()` | Tiers are rows with identity (ADR 0010); the 2026-08-06 duplicate-name incident is structurally impossible |
| `collections.user_id` as the root | A collection belongs to a community (ADR 0004) |
| Five Paystack call sites | One, enforced by an invariant script |
| Mutable `wallets` numbers | No stored balance; everything is derived |
| Retry cron with no cap | No cron in this milestone at all |
| PDF assembled from a template literal in a React page | A typed report model in `@kolekto/domain`, rendered by a server module, both unit-tested |

## 7. Behaviour a returning host will recognise

Worth listing explicitly, because familiarity is a feature:

- the codes switch, the prefix box, and a live example beside it
- "REG" as the example prefix, and per-option prefixes
- a prefix being required before any code is issued
- one code per person, including when one person pays for several
- a branded PDF with the collection title and a long-form Nigerian date
- landscape tables
- a refusal to export an empty list, phrased as a message rather than an empty file
