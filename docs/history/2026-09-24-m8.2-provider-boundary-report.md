## 1. Implementation report

M8.2 built the boundary between Kolekto's money model and a payment gateway, a
deterministic offline provider to exercise it, the append-only structure that
resolves M8.1's event-processing tension, the sixth security invariant, and the
migration and environment foundations. **No gateway was contacted and no money
path was built.**

Five things are worth drawing out.

**The provider boundary is about type ownership, not tidiness.** Everything
crossing it is a Kolekto-owned type. The previous estate had Paystack's field
names reaching the ledger, the wallet refresh and the reconciliation script, and
the consequence was not ugliness — it was that FIN-02's settlement swap was not
achievable and a change in the provider's response shape was a change to
financial code.

**Uncertainty is a value, not an exception.** Every call that can leave Kolekto
not knowing what happened returns `{ outcome: "unknown", reason, safeToRetry }`.
A thrown error invites a `catch` that treats "we do not know" as "it failed",
which on a transfer is how a bank gets paid twice. `safeToRetry` distinguishes a
timed-out *verify* (a read; safe) from a timed-out *initialize* (a checkout may
exist; not safe).

**The fake is deliberately unmistakable.** `name` is `"fake"`, every identifier is
prefixed `FAKE_`, and the checkout URL points at `fake-provider.invalid` — a
domain RFC 2606 reserves so it can never resolve anywhere. The failure mode being
guarded against is somebody believing payments work.

**Processing state never bought an `UPDATE` path onto the evidence table.**
`financial_events` is still strictly immutable. Attempts are their own append-only
rows, so "what happened on the third try, and why?" is answerable — which a
mutable counter would have destroyed.

**Two migration findings came from running fixtures, not from reading schema.**
Both are in §7, and one of them the schema handles correctly in a way I had not
anticipated.

## 4. Provider contract summary

Every type is Kolekto's. No Paystack name appears anywhere in the domain.

| Contract | Purpose |
|---|---|
| `ProviderName` | `"paystack" \| "fake"`. Part of every external identity, because two gateways may issue the same id. |
| `ProviderPaymentStatus` | `pending \| succeeded \| failed \| abandoned \| unrecognised`. `unrecognised` is never treated as either success or failure. |
| `ProviderResult<T>` | `ok \| not_found \| unknown \| refused`. The uncertainty carrier. |
| `PaymentInitializationRequest` | Server-derived and already frozen. No field may originate from a browser. |
| `PaymentInitialization` | Checkout URL plus the echoed reference. |
| `ProviderTransaction` | The provider's statement of fact: its id, status, raw status word, amount, currency, **nullable** fee, timestamps, channel, authorization token, raw payload. |
| `ProviderEventIdentity` | `(provider, providerEventId, providerEventType)` — the webhook idempotency key. |
| `WebhookAuthentication` | `authentic \| rejected`, with four named rejection reasons. |
| `ProviderEventSubject` | `transaction \| transfer \| unsupported`. A reference and a kind, deliberately **not** an amount. |
| `PaymentProvider` | `initialize`, `verify`, `authenticateWebhook`, `parseWebhookSubject`. |
| `ProviderSettlement` | `transactionIds` is **nullable**, because PA-10 is UNKNOWN. |

Four design decisions worth naming:

1. **`providerFee: Kobo | null`.** `null` means *not reported*, which is not zero.
   PA-05 — whether verify returns a settled fee or an estimate — is UNVERIFIED, so
   an unreported fee is a legitimate state (D-11).
2. **`rawPayload` is for storage and evidence only.** No domain code may read a
   field out of it. It goes to `financial_events.payload`, which no client role
   can read.
3. **`authenticateWebhook` is synchronous and total.** "This body is not
   authentic" is an expected outcome on a public endpoint; an exception invites a
   catch that turns it into a 500.
4. **`createPaymentProvider()` throws**, naming M8.9 and its prerequisites.

## 5. Fake provider behaviour

12 scenarios, selected per reference so one test can drive several payments
through different outcomes at once.

| Scenario | Behaviour |
|---|---|
| `success` | initialize ok; verify `succeeded` with a reported fee |
| `success_without_reported_fee` | succeeded, `providerFee: null` |
| `initialization_refused` | `refused` with a provider code |
| `initialization_timeout` | `unknown`, **`safeToRetry: false`** |
| `pending` | verify `pending`, no paid time, no fee |
| `payment_failed` | verify `failed` |
| `abandoned` | verify `abandoned` — distinct from a refusal |
| `amount_mismatch` | succeeded, amount 100 kobo off what was requested |
| `currency_mismatch` | succeeded, currency `USD` |
| `unrecognised_status` | `unrecognised`, raw word preserved |
| `verify_timeout` | `unknown`, **`safeToRetry: true`** (a verify is a read) |
| `not_found` | `not_found` |

**Determinism:** identifiers are an HMAC of the reference, not a counter, so a
failing test is reproducible from its output and expected ids do not depend on how
many tests ran first. Timestamps are a fixed epoch. Two separate instances produce
identical output for the same reference.

**Signature verification is real.** HMAC SHA-512 over the raw bytes, hex,
constant-time comparison after a length check, and the body is parsed **only
after** the signature passes. That ordering is tested from both sides: an
authentic malformed body fails on the parse, an unsigned malformed body fails on
the signature.

**What it does not do:** imitate Paystack's JSON. Payloads are labelled
`__fake: true` with a note. Paystack's exact shapes are not established, and a
"recorded" fixture written from a guess would put an invention about a provider
into the place tests treat as ground truth.

## 6. Event processing design

```
financial_events                      immutable. What the provider SAID.
      │
      └──< financial_event_processing_attempts    append-only. One row per attempt.
                     │
                     └── v_financial_event_processing    the current state, derived
```

`event_processing_outcome` is `succeeded | failed | unknown | ignored`. The middle
two carry the weight: `failed` means we know it did not work and retrying is safe;
`unknown` means we do not know, a side effect may have happened, and it is resolved
by **querying** the provider rather than retrying (D-27). `ignored` is terminal and
not a problem — an event type Kolekto does not handle is stored and passed over.

Constraints that keep the record unambiguous: a success carries no error; a failure
or unknown must carry a reason; a terminal outcome schedules no retry; an attempt
cannot finish before it started; attempts number from 1; `(event, attempt_no)` is
unique, so two concurrent processors cannot both be attempt 3.

The view answers the brief's eight questions — received, attempt count, latest
outcome, processed, failed, needs retry, what error, when — plus
`awaiting_provider_resolution`, which surfaces the `unknown` case separately
because it is the one that must not be retried blindly. An event with **no**
attempt reports `needs_retry = true`: never-attempted and failed are both
unprocessed.

Neither the table nor the view is readable by any client role. An error message may
quote a payload, and a payload may carry contributor PII (ADR 0009).

## 7. Migration compatibility findings

### The §15 checklist, for the one new structure

`financial_event_processing_attempts` is the only new schema object.

| # | Question | Answer |
|---|---|---|
| 1 | Can legacy records coexist? | **Yes.** It describes processing of a *new-system* provider event. Legacy events were never received by this system and get no rows — correctly. |
| 2 | Can imported history be represented without falsifying it? | **Yes, by not being used.** Fabricating attempt rows for legacy events would invent processing that never happened. `23_migration_fixtures.sql` imports a full fixture set and creates zero attempts. |
| 3 | Can legacy IDs be preserved? | **N/A.** No legacy row maps here. |
| 4 | Can provenance be retained? | **N/A**, and deliberately: there is no `is_imported` column, because an imported attempt would be a fiction. |
| 5 | Can records be marked historical? | **N/A.** |
| 6 | Can future migration scripts populate it deterministically? | **They must not.** Only a live processor writes here. |
| 7 | Does it require data legacy records lack? | **No** — it requires nothing of them. |
| 8 | Does it overwrite or reinterpret legacy financial truth? | **No.** It touches no legacy table and posts no journal. |

### Findings

**F-M1 — a phone-less legacy person cannot be an `active` member.**
`members_active_has_phone` requires an active member to have a number. For a
historical **contributor** the schema already handles this correctly and better
than I expected: `unclaimed` is exactly the right status — on the roll, claimable
later, not an account — and the constraint usefully forces the migration to say
which historical contributors are claimable rather than marking the population
active. For a legacy **authenticated user with no phone**, a category the brief
names explicitly, the migration must choose a roll status. **FOUNDER.** Encoded as
a passing assertion so the constraint's effect is a checked fact rather than a
surprise during a rehearsal.

**F-M2 — there is no destination table for legacy withdrawals.**
`migration.legacy_deposit` and `legacy_contribution` exist; `legacy_withdrawal`
does not. The architecture's own historical-data table says withdrawals are
"preserved as history", so the intent exists and the table does not. Additive and
straightforward, but it is a migration-architecture addition and the brief says not
to redesign migration casually, so **I did not add it.** ENGINEERING, for the
migration-engine milestone.

**F-M3 — no overflow destination for legacy auth users or tiers.** Both are
representable in target tables, so this may be deliberate — but a legacy tier whose
shape does not fit `collection_tiers` has nowhere to go. Confirm before the
transform is written.

### What the fixtures prove

43 assertions over synthetic records covering: an organiser with a preserved auth
UUID; a user with no phone; a contributor who never had an account; seven
collection shapes (fixed, tiered, open, fundraiser, ticketed, recurring,
archived); legacy tiers as rows; a legacy custom field; a paid and a pending
historical contribution; a historical deposit; an unattributed payment; three
legacy link kinds. Plus: imported rows immutable, provenance mandatory and never
invented, re-import refused by the partial unique index, legacy statuses kept
verbatim, and the legacy archive timestamp **carried rather than replaced with
`now()`** — otherwise every historical collection would appear to have been
archived on migration day.

**And the assertion the file exists for:** importing all of that created **zero
ledger entries, zero journals, and zero accounts.** Every imported collection
reports a position of zero. The old `wallets` table's five mutable numbers are the
most tempting thing to carry across because they look like balances; they were a
cache, and turning them into opening balances would put figures in the ledger that
no entry explains (D-23).

## 9. Security findings

**S1 — the M8.1 report's account of the PUBLIC EXECUTE problem was imprecise, and
this milestone corrects it.** M8.1 said the schema-wide revoke "was not a standing
rule". There *is* a standing rule —
`alter default privileges in schema app revoke execute on functions from public` —
and it is the right mechanism. The real cause is that `alter default privileges` is
recorded **per grantor role**, so it covers objects created by the role that ran
it and not necessarily others. The repository already knew this; `20260919120100`'s
own comment says so. The corrected explanation is in the new migration's header.

**S2 — the durable fix is the sixth invariant, not the SQL.** The migration's
retroactive revoke is a no-op today (verified: zero `app.*` functions were
PUBLIC-executable). What prevents recurrence is a source-tree rule: every
`app.*` function must carry an explicit `revoke execute` or `grant execute`, so
reachability is a decision on the record. 31 pre-M8.2 internal helpers — all
currently unreachable by `anon` and `authenticated` — are grandfathered in a
**frozen** list that may shrink and must never grow. Verified by probe that the
rule catches a new undeclared function.

**S3 — `packages/adapters` declared an entry point that did not exist.**
`package.json` pointed `exports["."]` at `./src/index.ts` and the file was absent,
so any `import … from "@kolekto/adapters"` would have failed. Nothing imported the
package yet, so nothing had noticed. Created as part of this milestone.

**S4 — the legacy live key finding from M8.1 is unchanged and still needs
action.** A full live Paystack key value sits in `kolekto-be-old/.env`,
`.env.bak.pre-email-fix`, and in **two historical diffs** of that repository's git
history (commit `1f82604`, 2025-12-31, added a `prod.env`). No tracked file at
`HEAD` contains it. Rotation is a live-environment action this milestone did not
and must not perform. Re-verified: no key value exists anywhere in the new
repository, in its working tree or its full history.

**Security posture preserved:** RLS enabled and forced on the new table; deny-all
policy; no client grant; append-only by both withheld privilege and trigger; the
new view is `security_invoker`; the grant allowlist did not need to change,
because nothing new is client-readable.
