### What the audit found

The pattern from earlier milestones held again: **the schema was provisioned
and the UI was never wired.** `collections.codes_enabled`,
`collection_code_settings` and `collection_tiers.code_prefix` had existed
since the first migration on 2026-09-17. Nothing read them, nothing wrote
them, no function generated a code, and no screen mentioned one. Most of part
H–N was completing a design that was already there, not inventing one.

Two things the previous report described as done were done: per-step draft
persistence, and a preview that renders the real public component. Two were
not: a draft could be started and never reopened, and the wizard called every
step the same thing whatever kind of collection it was.

## 2. What was implemented

### Implemented

**Contributor references (parts H–N, AB, W)**
- `collection_code_settings` extended with `separator`, `digits`,
  `start_number`
- `collection_code_sequences` — one counter row per numbering scope, moved by
  `UPDATE … RETURNING` under a row lock
- `contributor_references` — one row per participation, unique per collection,
  immutable and undeletable once issued
- `obligations.tier_id` — which option a member is on, which is what makes
  per-option series possible
- `app.build_contributor_reference`, `app.next_collection_code_number`,
  `app.issue_contributor_reference`,
  `app.issue_contributor_references_for_collection`,
  `app.set_collection_code_settings`
- `collection.configure_codes` permission (owner, admin)
- a settings panel with a live example; a reference column on the roll; a
  reference on each door row; a reference prefix field on each option; a
  reference column in both export formats; and the reference shown to the
  contributor themselves once they have found themselves on the list, which
  is what makes it a reference rather than an internal number
- references issued automatically as the roll is built, and a button to fill
  in any that are missing
- format frozen once anything has been issued

**Exports (parts D, E, F, G, W, Y, Z, AC, AD)**
- an export builder: subject, filters, grouped field selection, two formats
- four subjects — everyone on the collection, still expected to pay, guest
  list, only those who arrived — with the last two offered only on an event
- filters: status, group, option, period, door state, date added
- fields grouped Identity / Collection / Membership / Event / Custom fields,
  with only what this collection can answer offered, and personal fields
  marked and warned about
- CSV (RFC 4180, BOM, CRLF, formula-injection defence) and PDF
- server-side PDF: heading, organiser, generated date, the filters it was
  produced under, repeated table header, page numbers, landscape past six
  columns, an embedded font so ₦ and Yoruba and Igbo names render
- paged fetching, so a roll over a thousand rows is a whole roll
- a hard ceiling at 20,000 rows that refuses rather than truncates
- `collection.export_created` in the audit log: who, which collection, which
  columns, how many rows, what format — never a value out of any row

**Draft persistence (parts A1–A4)**
- per-intent step names, so a ticketed event's third step is "Tickets" and a
  fundraiser's is "Story and target"
- `collections.draft_step` and `app.set_collection_draft_step`
- `/c/[slug]/collections/[slug]/continue` — reopens a draft into the same

- drafts offer "Continue setting this up" from the list and from the detail page

**Preview (part B)**
- phone and desktop frames, and one click to the host view

### Partially implemented

- **The tab set (part C).** The brief's suggested structures add Items,
  Tickets, Story, Progress, Outstanding and Transactions as sections of their
  own. Three of those cannot exist: Transactions and Progress have no rows
  behind them, and a progress figure of zero is a claim. Outstanding is
  implemented as a filter on the roll rather than a tab, because it is the
  same people, the same columns and the same actions. Items, Tickets and Story
  are reachable, but they live inside Settings with the rest of the
  configuration rather than having tabs of their own. That is a deliberate
  decision not to reorganise a working screen for its own sake, and it is the
  clearest remaining gap against part C.

- **Item multi-basket (parts T, U).** Already complete before this milestone
  (M7.5): several items, quantities, server-authoritative totals, stock and
  per-order validation, no premature stock decrement. Nothing was added, and

  that M7.6 built it.
- **Wizard step *sequences* (part A1).** The names differ per kind; the
  positions do not. The brief's example flows regroup the same questions
  (Ticketing: Event / Ticket types / Ticket settings / Cover / …). What each
  step asks is already type-specific, and what it writes is shared, so the
  positions were left alone rather than restructured under working
  persistence. An organiser sees a different wizard; the code has one.
- **Export subjects (part E).** Contributors, outstanding, attendees and
  orders exist as views of the roll. Contributions, payments and item orders
  do not, because no such row exists in this phase — see §8.

### Deferred

- **`code_style = 'random'`** is implemented in the database and offered in
  the UI, but has no browser test; only the sequential path is covered end to

- **`collection_code_settings.attribute_basis`** (CODE-03, "CSC-300L-0015")

- **QR / barcode check-in (part S).** Not built, by the brief's own

- **Per-ticket sales windows** and **per-item visibility in the editor** —
  carried over unfinished from M7.5.

### Not attempted

- Anything in Phase 4: Paystack, webhooks, contributions, ledger, wallet,
  payout, withdrawal, settlement, reconciliation.
- The historical ₦19.8m unattributed-payment issue. Not reopened, not
  investigated, not referenced except where the legacy comparison quotes a

## 4. Contributor reference architecture

```
community
  └── collection                       codes_enabled
        ├── collection_code_settings   prefix, separator, digits, start_number, style
        ├── collection_tiers           code_prefix   (an option's own series)
        ├── collection_code_sequences  (collection_id, tier_id) → next_number
        └── obligation                 the participation
              └── contributor_reference  BIO26-0042
```

**Where prefixes live.** Two places, deliberately. The collection's prefix is
on `collection_code_settings`; an option's is on `collection_tiers.code_prefix`
(unique per collection). Resolution at issue time: if the obligation names a
tier and that tier has a prefix, use it and number in that tier's scope;
otherwise use the collection's prefix and the collection-wide scope. An option
without a prefix shares the collection's series rather than inventing one.

**Where sequences live.** `collection_code_sequences`, one row per scope. A
collection with no prefixed options has exactly one row and numbers straight
through; a collection whose options carry prefixes has one row per prefixed
option plus one for everything else.

**Where the generated reference lives.** `contributor_references`, one row per
obligation, carrying the reference, the number it came from, the tier scope it
was numbered in (denormalised, because the reference is immutable and so the
scope it was numbered in must be), who issued it and when.

**How uniqueness works.** Three layers, and the bottom one is the real one:

1. the counter hands out a number nobody else holds
2. the format turns that into a string
3. `unique (collection_id, reference)` refuses a duplicate whatever produced
   it — including a migration carrying old codes forward

If layer 3 fires, the function takes the next number and tries again, up to
ten times, then raises with a hint naming the likely cause.

**How concurrency is handled.**

```sql
update public.collection_code_sequences
set next_number = next_number + 1
where collection_id = … and tier_id is not distinct from …
returning next_number - 1 into v_number;
```

That `UPDATE` takes a row lock. A second transaction blocks on it until the
first commits, and then reads the moved value. It is never `count(*) + 1`,
which two concurrent transactions read identically and a deletion makes wrong
— the failure the legacy system's own diagnostic documents, with a production
gap of 1,650 and growing.

The increment is in the **same transaction** as the insert, which is the other
half of the legacy defect: there, the counter committed independently and
strictly before the row it numbered, so any failure downstream burned a
number. Here a failed call rolls both back together.

A number **is** spent when the insert loses to the unique index inside the
retry loop, because the increment sits outside the `begin … exception` block
and survives its rollback. That is deliberate: a counter that gave numbers
back would eventually reissue one already printed on a ticket.

**Proven, not asserted.** `scripts/verify/reference-concurrency.mjs` opens N
real connections, holds them at a barrier, releases them together, and
asserts: no failures, all distinct, correct format, numbers exactly 1..N with
no gaps, counter moved by exactly N. Then it fires the same N calls again and
asserts nothing new was issued. Passed at 24 and at 60 writers. `npm run
test:concurrency`.

**Four identifiers, kept apart (part M).**

| | Example | Answers |
|---|---|---|
| `members.member_code` | `KWASU/0042` | who this is, in this community, for years |
| a community attribute | `21/52/1234` | who this is, by the community's own rules |
| `contributor_references.reference` | `BIO26-0042` | this person's participation in **this** collection |
| `collection_tiers.code_prefix` | `VIP` | which option that participation is for |

## 5. Export architecture

**Where it runs.** `exportCollectionAction` is a server action.
`renderReportPdf` imports `server-only`, so putting it in a client bundle is a
build error rather than a habit. The browser receives a finished file and
saves it.

**CSV.** `@kolekto/domain`'s `toCsv` — RFC 4180 quoting, a UTF-8 byte-order
mark so Excel on Windows does not turn ₦ into mojibake, CRLF line endings, and
a leading apostrophe on any cell starting `= + - @`, because an export of
member data is exactly the file a CSV-injection payload travels in.

**PDF.** `apps/web/lib/pdf/report.ts` over `pdf-lib`. The layout decisions —
how many rows fit the short first page, how many fit the pages after it, which
page each row lands on, how wide each column is, whether the table should be
landscape — live in `@kolekto/domain`'s `report.ts`, pure and unit-tested,
because each of them is an off-by-one that is invisible until somebody prints
an attendance list and finds three people missing.

DejaVu Sans is embedded. The fourteen standard PDF fonts are WinAnsi-encoded;
WinAnsi has no ₦ and cannot write ẹ ọ ṣ ị ụ. pdf-lib subsets it per document,
so a thousand-row report is under a megabyte.

**Filtering.** Status, option, period and date range are applied in the
database, in the obligations query. Group and door state are applied in
memory, because both need a join the export builds anyway. The subject's own
meaning is applied on the server regardless of what the browser sent.

**Selectable fields.** A catalogue, not a switch statement of exports: a field
is a row in `EXPORT_FIELDS` with a key, a label, a group, a printed width and
an optional `needs`. Custom member fields are discovered per community and
appended with `attr:` keys under their own labels. Unknown keys are dropped
rather than trusted — the field list is a client-supplied array, and a column
name is not an instruction.

**Custom fields.** Read from `member_attribute_definitions` and
`member_attribute_values`, and fetched only when at least one is ticked.

**RBAC.** `member.export`, checked on the server against the community that
owns the collection: owner, admin and treasurer hold it; collector and viewer
do not. Hiding the tab is not a control. Selecting a phone number or an email
address additionally requires `member.view_contact` (RPT-06) — which every
holder of `member.export` currently also holds, so today it refuses nobody.
It is there so that the day the matrix changes, the columns follow it instead
of quietly outliving it.

**Large exports.** PostgREST caps a `select` at a thousand rows whatever the
query says — which meant the M7.5 export of a two-thousand-member roll was
silently half a roll. Everything is paged now. Past 20,000 rows the export
refuses with a sentence asking for narrower filters, because a register that
is quietly missing people is worse than one that would not generate. Only the
tables a chosen column or filter needs are fetched at all.

**Audit.** `app.record_collection_export` writes `collection.export_created`
before the bytes leave: actor, community, collection, subject, format, row
count, and the column names. Never a value out of any row — an audit trail of
an export must not become a second copy of the personal data it audits.

## 6. Ticket operations

**The attendee model.** An `obligation` — one member an officer put on the
collection, with what they are expected to pay and, now, which option. That is
the guest list. A purchased ticket is not a row anywhere in this phase, so it
cannot be one, and the check-in screen says so rather than showing an empty
table that looks broken.

**The ticket reference.** The contributor reference on that obligation,
numbered in the option's own series when the option has a prefix — so a VIP
guest's reference reads `VIP-0007` and a Regular's reads `REG-0031`, in the
same collection.

**Check-in.** `app.check_in_obligation` (M7.5, unchanged): SECURITY DEFINER,
re-checks `attendance.check_in` against the community derived from the
obligation, refuses an exempted person with a reason, and is idempotent — a
second tap at a busy entrance returns the existing open visit instead of an
error somebody has to read. A partial unique index enforces one open visit per
person.

**Check-out.** `app.check_out_obligation`, equally idempotent. Leaving and
returning is two visits, not a contradiction, because `event_check_ins` is a
history rather than a flag.

**Search (new in M7.6).** `searchAttendeesAction` — server-side, matching
name, member ID and contributor reference, capped at fifty matches, debounced,
with the previous results left on screen while the next query is in flight.
The door ships a first page of a hundred and asks the server for anything
else. ILIKE wildcards and PostgREST's `or` separator are escaped, so searching
for "50%" searches for "50%".

**Audit trail.** `attendance.check_in` and `attendance.check_out` audit rows,
each naming the actor, the obligation and the collection.

**Authorization.** `attendance.check_in`, held by owner, admin, treasurer and
collector — and `scoped = true` for collector, so ROLE-06 holds. A viewer
cannot work a door.

### Defects these tests found

Eight, each of which would have shipped:

1. **`assign_obligations` already had a five-argument signature.** The first
   draft of `20260921180200` added `p_tier_id` to what the repository's oldest
   migration showed, not to what the database actually had — creating a second
   overload and making every four-argument call ambiguous. pgTAP: `function
   app.assign_obligations(uuid, uuid[], unknown, unknown) is not unique`.

2. **`lpad` truncates.** `lpad('12345', 4, '0')` is `'1234'` — so the
   ten-thousandth member of a four-digit collection would have been handed a
   reference the 1,234th already held. Caught by a pgTAP vector, fixed in both
   the SQL and the TypeScript, and pinned on both sides.

3. **A trigger function inherited PUBLIC execute.** `app.enforce_reference_
   immutability` was callable by `anon` — the role whose key ships in the
   JavaScript of every published collection page. Caught by the grant matrix
   test, which exists for exactly this.

4. **PostgREST's thousand-row cap.** Found while rewriting the export, not by
   a test — but it means the M7.5 export silently truncated any roll over a
   thousand people.

5. **The PDF font did not survive a production build.** `new URL("./fonts/…",
   import.meta.url)` resolves against `.next/server/chunks` after bundling,
   where no .ttf is. The unit tests passed (they run from source); the browser
   journey downloaded the CSV and then hit an error page on the PDF. Fixed by
   making the font a public asset, and by removing the Helvetica fallback that
   would have hidden it behind a confusing encoding error. Reading it back
   through a loop variable then drew a build warning that the read "causes the
   whole project to be traced and included in the output" — every source file
   shipped as server code — so it is two statically-scoped reads instead.

6. **A floating server action left the wizard saying "Saving…" for ever.**
   `advance()` fired the new step-memory action inside `startTransition`
   without awaiting it; React kept the transition pending, so the Review step
   rendered with "Open this draft" permanently disabled. Caught by two browser
   journeys written for *earlier* milestones — not by the three written for
   this one, and not by the typecheck, the lint or the build.

7. **The wizard re-saved everything to open a draft.** `finish()` ran three
   more server round trips before navigating, rewriting rows every step had
   already written — at the single moment an organiser is least willing to
   wait, with the button disabled throughout. Under suite load that was long
   enough for journeys to give up with "Saving…" still on screen. Only found
   because the symptom looked like a hang and was chased rather than retried.

8. **An index that could never be used.** The reference lookup index was on
   `(community_id, reference text_pattern_ops)` while the door search filters
   by `collection_id` and used ILIKE, which `text_pattern_ops` does not
   support. Correct-looking and never chosen by the planner. Re-scoped, and the
   search now upper-cases its needle and uses LIKE — which the reference format
   constraint makes equivalent.

### Browser journeys

New in `tests/e2e/references-and-exports.spec.ts`:

1. **options with their own prefixes** — a tiered collection with REG and VIP
   prefixes, references switched on with a live example checked on screen, one
   member assigned to each option, `REG-0001` and `VIP-0001` asserted on the
   roll, the VIP row asserted at the VIP price, then **both files downloaded
   and read**: the CSV's bytes are searched for the references and for ₦, and
   the PDF's bytes are checked for `%PDF-`.
2. **a reference format is fixed once references are out** — issue one, then
   assert the prefix field is disabled and the reason is on screen.
3. **a draft survives closing the browser** — get several steps into an item
   collection, open a *new browser context*, continue the draft, assert it
   resumed at the step it was left on and that both items and their prices
   came back.

Updated for the renamed tabs: `collection-types.spec.ts` (Exports, Attendees),
plus an assertion that a dues collection is offered neither an Option column
nor a door filter.

**One thing worth recording about how these were run.** Playwright's
`reuseExistingServer: true` reuses whatever is already listening on port
3010. A suite started after a fix was committed therefore ran against the
build from before it, and reported the bug as still present — which is how
the "Saving…" hang appeared to survive its own fix. The port is now freed

## 8. Known limitations

State plainly rather than discovered later:

1. **No contributions, payments or orders export**, because no such row
   exists. ADR 0012 and ADR 0006. The export screen says so.
2. **A public collection issues no references.** They attach to an obligation,
   and a public collection has none. The screens say so. Phase 4's confirmed
   contribution becomes the second thing a reference can attach to.
3. **Check-in covers managed collections only**, for the same reason.
4. **The roll table still loads every obligation.** The door was fixed to page
   and search server-side; the Members/Attendees table was not. At a few
   thousand members that page will be slow.
5. **`attribute_basis` and `per_unit` are unimplemented**, now documented as
   such in the schema.
6. **The `random` style has no browser coverage.**
7. **Wizard step positions are shared across kinds**; only the names differ.
8. **Multi-tab drafts are last-write-wins.** No version check on field writes.
   `collections.version` exists if it is wanted.
9. **A reference is never withdrawn.** Cancelling an obligation leaves its
   reference attached to the record. That is deliberate (CODE-04) and it means
   a cancelled row still occupies a number.
10. **Export filtering is partly in memory** — group and door state. On a
    collection near the row ceiling that is more work than it needs to be.
11. **`npm audit` reports vulnerabilities in the vitest/vite/esbuild dev
    chain.** Pre-existing, development-only, and fixing them is a breaking
    major upgrade. Not touched in this milestone. `pdf-lib`, `@pdf-lib/fontkit`
    and `dejavu-fonts-ttf` introduced none.
12. **No QR scanning**, by design.

## 10. Recommendation

**Do not start Phase 4 yet.** Three things should be closed first, and none of
them is large.

1. **The roll table still loads every obligation.** The door was fixed to page
   and search on the server; the Members/Attendees table was not. It is the
   same shape of fix, and it is the one screen in this milestone that will
   fall over on a real association's membership.
2. **Item fields cannot be exported**, because no order is recorded. That is
   correct today and it will be wrong the moment Phase 4 lands, so the export
   catalogue should gain those columns in the same change that creates the
   rows — not afterwards, when somebody notices the file is missing them.
3. **The `random` reference style has no browser coverage**, and a style that
   is offered on screen should be exercised end to end before it is offered to
   somebody printing tickets.

After those, Phase 4 is the right next milestone, and this one was built for
it. The shape it slots into:

```
community → collection → participation → reference → tier/ticket/item
                              ↓
                        [ Phase 4: contribution ]
                              ↓
                   transaction → ledger → reconciliation
                              ↓
                      export / reporting
```

A confirmed contribution becomes the second thing a reference attaches to — a
nullable `contribution_id` beside `obligation_id`, a CHECK that exactly one
is set, the same counter, the same format, the same uniqueness, the same audit
trail. The same row becomes the second thing a door can admit, and the second
thing an export can be about. `BIO26-0042` identifies the same participation
before the money, during it and after it, which is what part AB's diagram
asks for.

What Phase 4 must not inherit from the old system, and what this milestone
already guards against: a counter that commits ahead of the row it numbers.
`app.issue_contributor_reference` does both in one transaction today, and the
contribution insert must be brought inside that same transaction rather than
handed a pre-minted code. The old system's own diagnostic is the argument, and
it is quoted in the legacy comparison.
