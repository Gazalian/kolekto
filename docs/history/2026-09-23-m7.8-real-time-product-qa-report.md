## 1. Executive summary

M7.7's collection-creation work reached this milestone implemented but browser-unverified — its own report said so
plainly. This gate finished that verification, on a machine that turned out to be the harder problem than the
application: a full 40-test browser suite was killed by host memory pressure twice (once in the M7.7 session, once
again in this one) before a one-test-at-a-time approach, gated on free memory, got it to run to completion.

**One real, previously-undetected defect was found and fixed.** Resuming any collection draft before its
contributor-reference step had ever been reached crashed the page entirely — a client-only function
(`emptyCodes()`) was being called from a server component, which Next.js refuses to allow, and the crash reached
the organiser as "Something went wrong" with no way forward. This is not an edge case: the reference step sits
near the end of every creation flow, so any organiser who saves a draft early and comes back later would have hit
it. Root-caused from the running server's own error log, fixed with the smallest change that addresses the actual
cause (moving two pure, side-effect-free declarations out of a `"use client"` file), and confirmed resolved by
direct server-log evidence — zero recurrences across every resume attempt against the rebuilt bundle, versus dozens
before the fix.

**One stale test assertion was found and fixed** (comparing two flows' total step counts, which had coincidentally
converged to the same number even though their actual step sequences remain completely different — the real
invariant, already correctly proven at the unit-test level).

**One real product question was surfaced, not guessed at.** A per-order limit can be configured on a Packages-flow
option in the creation wizard, but the Packages flow only ever lets a contributor choose one option in total, so
the limit can never have a visible or functional effect there. Not a security issue — there is nothing to bypass —
but a genuine gap between what the wizard configures and what the public page can express, left for a product
decision among three concrete options (§10).

**Every other test failure this session was individually checked against the running system's actual logs** —
Postgres, GoTrue, Kong, Storage — before being called environmental, not assumed. The evidence is consistent and
specific: genuine server-side timeouts (`canceling statement due to statement timeout`, `context deadline
exceeded`, real 504s and 544s) under combined load from a 9-container Supabase stack, a Next production server and
Chromium sharing a resource-constrained host, with `pg_stat_activity` confirming zero lock contention during the
stalls — resource starvation, exactly as the M7.7 session had already diagnosed, now reconfirmed independently.

Of 40 browser journeys: **23 passed cleanly**, 1 was the fixed test defect, 9 were confirmed environmental with
matching server-log evidence, and 7 were inconclusive on first pass and individually re-run — of those, 2 resolved
to PASS (confirming environmental), 1 resolved into Finding 3 (the real defect), 1 became Finding 2 (the product
question), and the rest remain honestly recorded as unresolved or blocked rather than assumed safe (§17).

Live browser evidence directly confirms four of this milestone's highest-stakes security guarantees: an outsider
cannot reach or modify another community's collection by URL; a contribution cannot be submitted after clearing the
identification cookie; a group-scoped collection cannot see another community's members; a contributor reference's
format cannot change once issued. All non-browser suites — typecheck, lint, production build, 249 unit tests, 453
pgTAP assertions, and the four Phase 4 boundary invariants — pass, re-run in this session rather than carried over
from memory of an earlier one.

**M7.7 is READY**, with the defect this gate exists to catch found and fixed, and **M8 is READY TO BEGIN**, with
the specific, named gaps in §17 — most importantly zero coverage on the reference-export/CSV/PDF journey and the
organiser wizard's mobile behaviour — carried forward explicitly rather than silently assumed covered.

## 5. Codebase audit (Part 2)

I did not take the M7.7 audit's findings on faith. Independently re-verified, against the live code, not memory of
the prior report:

- **`app.set_collection_fee_mode`** (`supabase/migrations/20260923100000_collection_fee_mode.sql`): tenancy is
  re-read from the collection row, never taken from the caller's input (SEC-18 pattern); gated on
  `collection.draft`; refuses on `closed`/`archived`/`suspended`; idempotent (no audit row on a no-op re-send);
  writes one audit row with before/after values on a real change. All of this matches what `18_fee_configuration.sql`
  asserts, and I read the function body myself rather than trusting the pgTAP result alone.
- **RLS on `collections`, `collection_tiers`, `collection_fields`:** I grepped every migration file for any
  `INSERT`/`UPDATE`/`DELETE` policy on these three tables. **There is none.** Only `SELECT` policies exist, scoped
  by `app.has_permission(community_id, 'community.view_dashboard')`. Postgres RLS defaults to deny, so an
  authenticated officer's client **cannot write to these tables directly at all** — every mutation must go through
  an audited `SECURITY DEFINER` function. This is independent evidence for "no authorization check that exists only
  client-side," not a restatement of the M7.7 audit's claim.
- **`app.has_permission` / `app.require_permission`:** single source of truth for every permission check in the
  codebase, keyed to *active* officer terms (`ended_at is null and started_at <= now()`), `SECURITY DEFINER` to
  avoid RLS self-recursion, `EXECUTE` revoked from `public`.
- **Contributor reference issuance** (`app.next_reference` in `20260921180100_contributor_reference_functions.sql`):
  the next number is taken under the row lock an `UPDATE` on `collection_code_sequences` takes — not `count(*) + 1`,
  which two concurrent callers would read identically. Genuinely concurrency-safe by construction.
- **`SettingsPanel.tsx` / `TiersEditor.tsx` diff:** confirmed the new `per_order_limit` field is wired into *both*
  the load (mapping `tier.per_order_limit` into local state) and the save (including it in the update payload) of
  `SettingsPanel`, which is the exact defect the M7.7 report's §23 finding 2 describes having caught and fixed.
- **`continue/page.tsx` draft-resume logic:** `codesLocked` is derived from a live `count` query against
  `contributor_references`, not a boolean the client could forge. `draft_step` clamping to the resumed flow's actual
  length happens in `NewCollectionForm.tsx` (`Math.min(Math.max(existing.step, 1), flow.steps.length)`) — confirmed
  present, not merely described in a comment.
- **The seven flows** (`flows.ts`): confirmed by direct evaluation (not just reading) that all seven have distinct
  step-kind sequences, distinct lengths where the product calls for it, and their own vocabulary. One finding from
  this: **`stepCount("ticketing")` and `stepCount("recurring")` are both 10** — see §10, Finding 1.

## 7. The environment finding: this machine cannot sustain a full browser run

This is the single most important finding in this report, because it determines how much confidence to place in
every browser result below, and because it happened **twice**: once in the M7.7 session (documented in that
report's §24) and again in this one.

**What happened.** A first attempt to run the full 40-test Playwright suite in one process was killed by Claude
Code's own background-pressure monitor — not a test failure, not a crash, a deliberate stop because the host was
critically low on memory while other work was in progress. Two tests had run by that point (both had failed both
their attempts). A second attempt, run test-by-test with a memory-gated driver script instead of one long process,
progressed further but still saw free physical memory swing between **130 MB and over 1 GB within seconds**, with
`Get-CimInstance` calls that normally return instantly taking over two minutes.

**Root cause, diagnosed rather than assumed.** `Get-Process` sorted by working set showed the actual composition:
seven separate `chrome.exe` processes (~2 GB combined — a separate Chromium-based browser the user had open, not
Playwright's own instance), VS Code (~480 MB across processes), Docker Desktop's backend (~105 MB), Windows
Defender (~193 MB), and Windows' own Memory Compression process already active (246 MB — itself a sign the OS was
already under pressure before any of my testing). Stopping the developer's `next dev` server (§4) barely moved the
number, which is what pointed at the browser rather than the application stack as the dominant consumer. The user
closed that browser mid-session, after which free memory recovered to a more usable ~500–650 MB band, though it
continued to fluctuate.

**How I verified failures were genuinely environmental rather than assuming it.** For every browser-suite failure
in this report, I checked the actual server-side logs (`docker logs`) for the failure's timestamp before
classifying it. Three separate, unrelated subsystems produced genuine server-side timeouts under this load, not
client-side flakiness:

- **GoTrue (auth):** `"error":"context deadline exceeded" ... "Database error finding user"` on `POST /otp` —
  confirmed by directly timing a `curl` to the same endpoint at a quiet moment (1.1 s, 200 OK) against the same
  request failing from the browser moments later with a real `504` **logged by Kong itself**, not a client timeout.
- **Storage:** a flyer upload's own `POST` succeeded (200, 3.6 s), but the browser's next request — fetching the
  public URL to render it — got a real `544 DatabaseTimeout` from the storage service: `"error":"The connection to
  the database timed out"`.
- **PostgREST:** `"ERROR: canceling statement due to statement timeout"` from the `authenticator` role during a
  community-creation journey.

`pg_stat_activity`, checked immediately after one of these, showed **zero active or waiting queries** — confirming
the M7.7 report's own prior diagnosis: this is host-level resource starvation (CPU scheduling contention across a
4-CPU box running a 9-container Postgres stack, a Next server and Chromium simultaneously), not database lock
contention, and not an application defect. The same failure, hitting three unrelated services in three unrelated
ways, is strong evidence the cause is generic host pressure rather than anything specific to auth, storage, or any
one code path.

**What this means for the results below.** Every FAIL in §9–§10 was individually checked against these signatures
before being classified. Where a failure's error matches one of the above — a generic timeout at an
otherwise-unremarkable point, different on each attempt — it is marked **ENVIRONMENTAL**, not APPLICATION DEFECT,
and is not evidence the underlying feature is broken. Where a failure was deterministic, reproducible, and
unrelated to timing (Finding 1, §10), it is marked as a real defect and fixed.

## 8. Real browser testing — method (Part 5)

Given §7, running the entire suite as one long-lived process was not viable twice in a row without being killed by
the same host-pressure mechanism. The approach that actually produced results: **one test at a time**, each its own
`npx playwright test <file> -g <test>` process (so memory is fully released between tests, not merely between
files), gated by a wait-loop that holds before starting a new test until free physical memory clears a threshold
or three minutes pass, whichever comes first. This is not a substitute for the full suite — it is what let the full
suite actually finish on this hardware, tracked test-by-test with the same server logs cross-checked for every
failure described in §7.

## 10. Defects and findings discovered during this milestone

### Finding 1 — stale test assertion, fixed (test defect, not an application defect)

`tests/e2e/collection-creation.spec.ts:116` asserted `expect(stepCount("ticketing")).not.toBe(stepCount("recurring"))`.
Directly evaluating `flows.ts` shows **both flows compute to 10 total steps** (9 + the intent picker) — this is
deterministic, not a flake; it fails on every run, on any machine.

Root cause: the ticketing flow gained a "timing" (sales window) step when M7.7 fixed audit finding F6 (a single
generic `deadline_at` that didn't fit every type); the recurring flow has no timing step by design ("a plan that
repeats does not close"). The two counts converged to the same total by coincidence.

This is **not evidence the flows are actually the same** — their step *kind* sequences are completely different
(`event, tickets, purchaseRules, fees, audience, questions, reference, timing, review` vs. `basics, amount,
schedule, fees, cover, audience, questions, reference, review`), and `apps/web`'s own unit suite
(`flows.test.ts`, 55 tests, all passing) already asserts the real invariant — "no two flows share a step
sequence" — correctly, at the step-kind level. The E2E test's specific proxy (comparing total *counts*) was never
the actual product requirement, and weakening or deleting the check entirely would have thrown away the thing it
was actually protecting.

**Fix (test-only, not application code):** replaced the count comparison with a comparison of the two flows' step
*kind* sequences, in `tests/e2e/collection-creation.spec.ts`. This is what the test's own docstring already claimed
to check ("two types... in a different order").

### Finding 2 — structural: a per-order limit has no visible effect in the Packages (tiered) flow's public page

Real, root-caused, but **not fixed unilaterally** — it needs a product decision, not a code guess.

`ContributeForm.tsx` has two rendering modes. When a flow lets a contributor take only one option
(`!allowMultipleTiers` — this is how the "tiered"/Packages flow works: flows.ts's own hint says "A contributor picks
one"), each option renders as a plain radio button with a name and a price. There is no quantity field, and
therefore no "Up to N per order." hint, because "how many of this package" cannot mean anything when a contributor
can only ever choose one package in total. That hint only exists in the *other* mode
(`allowMultipleTiers` — ticketing, and any flow that lets someone take several of a kind), where checking a box
reveals a quantity field whose hint is exactly that string.

The per-order-limit field itself ("Most one person may take") is offered in the *creation* wizard for Packages,
because `TiersEditor` is the same component and the same database column across Packages, Items and Tickets. An
organiser can set "2" on a package today and it will save, but it can never have any visible or functional effect
on that flow's public page, because a contributor there is structurally limited to one selection regardless.

This is not a security issue — nothing can be bypassed, because there is nothing to exceed. It is a genuine gap
between what the creation wizard lets an organiser configure and what the public page can ever express for that
specific flow. Three ways to close it, all product decisions:

1. Stop offering the per-order-limit field in the Packages flow's `TiersEditor` instance, since it configures
   something with no effect there.
2. Let Packages allow a contributor to take more than one of the same package (a real product change to that
   flow's shape), at which point the field would mean something.
3. Leave it as configuration that only matters for Items and Tickets, and say so in the field's own hint text in
   the Packages context, so an organiser is not left wondering why setting "2" changed nothing.

The E2E test asserting server-side enforcement of this limit (`collection-creation.spec.ts:245`) uses the Packages
flow, so it cannot pass as written regardless of environment — see the test matrix, row 6. Re-running it against
`items` or `ticketing` (both genuinely multi-select) would exercise the real guarantee; this was not done, since it
would change what the test proves, which is a call for whoever owns that test's intent.

### Finding 3 — CONFIRMED, FIXED: resuming a draft with no saved reference settings crashed the page entirely

The most serious defect this milestone found, and the reason two E2E tests (rows 8 and 16 in the matrix) kept
failing at the identical point across every attempt while everything else failed at random points.

**Root cause**, read from the running e2e server's own stdout, not guessed from the test failure alone:

```
⨯ Error: Attempted to call emptyCodes() from the server but emptyCodes is on the client. It's not possible to
invoke a client function from the server, it can only be rendered as a Component or passed to props of a Client
Component.
```

`continue/page.tsx` (a **server** component — no `"use client"` directive) imported `emptyCodes()` from
`NewCollectionForm.tsx` (a `"use client"` module) and called it directly whenever a draft had no
`collection_code_settings` row yet — i.e. whenever an organiser left a draft before reaching its reference step and
came back. Next.js treats every export of a `"use client"` file as a client reference and refuses to invoke it
during server rendering. The error propagated up to React's error boundary, and the organiser saw:

> Something went wrong
> An unexpected error happened. Nothing was silently retried or hidden.
> [Try again]

with no wizard, no draft, and no way forward except reloading. Confirmed directly from the actual page snapshot
Playwright captured at the moment of failure — not inferred.

**Why this matters for M8 readiness specifically:** the reference-configuration step sits near the end of every
flow (see the manual guide, §5). An organiser who leaves a draft *before* reaching it — which is a completely
ordinary thing to do, not an edge case — could never resume that draft again through the UI. This is exactly the
class of defect Part 1 of this milestone's brief exists to find before real organisers and real money are involved.

**Fix.** `CodeDraft` and `emptyCodes()` are pure data — a type and a function returning a plain object literal, with
no actual dependency on the browser. They had no reason to live in a `"use client"` file; they were only there
because that is where the wizard's own state initialisation needed them. Extracted both into a new file with no
directive, `apps/web/app/c/[slug]/collections/new/codeDefaults.ts`. `NewCollectionForm.tsx` now re-exports them (so
nothing importing from it needs to change) and imports its own copy for local use. `continue/page.tsx` now imports
`emptyCodes` from the new shared file directly. No behavior changed anywhere except that the server can now
actually call the function it needs.

**Verification, not assumption:**

## 12. Security testing (Part 17)

**Live, browser-confirmed this session:**
- An account with no role in a community cannot open, by direct URL, any of 8 configuration surfaces for that
  community (row 7).
- Identification cannot be forged: clearing cookies after identifying and attempting to submit is refused
  server-side with an explicit message, not silently accepted (row 27).
- A group-scoped collection's contributor search only ever returns that group's own members — a second
  community's members, created in the same test run, never appear (row 28).
- A contributor reference's format cannot be changed once a reference has been issued (row 38) — confirmed by a
  real attempt against a real issued reference, not inferred from the schema.

**Confirmed by direct code reading, independent of the browser run (§5):**
- `collections`, `collection_tiers`, `collection_fields` have **no** RLS write policy of any kind — every mutation
  must go through an audited `SECURITY DEFINER` function. Grepped across every migration file, not sampled.
- Every permission check resolves through one function (`app.has_permission`), keyed to active officer terms,
  revoked from `public`.
- Every write function that changes a collection re-derives its community from the row, never from caller input.
- Contributor references are issued under a real row lock, not `count(*) + 1`.

**Not attempted this session:** a systematic walk of every role (OWNER/ADMIN/FINANCE/COLLECTOR/VIEWER) against
every surface listed in Part 17 of the brief — the browser evidence above covers OWNER vs. an unrelated outsider
and OWNER vs. an anonymous contributor, which are the two highest-value boundaries, but not the full internal role
matrix (e.g., can a VIEWER configure fees; can a COLLECTOR change references). Recorded as a genuine gap, not
implied as covered.
