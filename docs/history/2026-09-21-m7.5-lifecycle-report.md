# M7.5 — Persistent drafts, real preview, exports, and the door

Continues the collection work recorded in
[`2026-09-21-collection-creation-audit-and-architecture.md`](2026-09-21-collection-creation-audit-and-architecture.md)
and the two reports beside it.

## 1. Executive summary

Four of the six M7.5 workstreams are implemented and tested: persistent
drafts (A), a real contributor preview (B), collection management additions
(C, as the Export and Check-in tabs plus a Preview link), configurable CSV
exports (D), and event check-in (E). Full lifecycle verification (F) ran
across pgTAP, domain, validation, invariants, typecheck, lint, production
build and targeted browser journeys.

Two things in the brief could not be built as written, because the data they
describe does not exist in this phase. Both are explained in §5 and §6
rather than faked:

- **Exports are of the collection's roll, not of contributors.** No
  contribution is stored anywhere (ADR 0012 rejected a pending-contribution
  table; ADR 0006 gates the real one), so "everyone who paid" has no rows
  behind it.
- **Check-in attaches to an obligation, not to a purchased ticket**, for the
  same reason. A managed event's roll is a real guest list; a public ticket
  sale has nobody to admit until Phase 4 records purchases.

## 2. Draft persistence (part A)

Every wizard step now writes when it is completed. The collection row exists
from the **Details** step onward, so the flow is:

| Step | What it writes |
|---|---|
| Purpose | Nothing — it only decides which questions get asked |
| Details | Creates the collection (name, description, deadline, type axes) |
| Contribution | Updates amounts, then writes tiers / items / event / suggestions / story / recurrence as the type requires |
| Cover image | Nothing of its own — the uploader already saved on upload |
| Who pays | Audience mode and groups, plus visibility |
| Questions | The collection's custom fields |
| Review | Re-saves anything edited after the fact, then opens the draft |

Three layers had to stop demanding a finished collection before one could be
saved, all stating the same rule:

- `collections_fixed_has_amount` → narrowed to published states
  (`20260921160000`)
- `app.assert_amount_model_config` → gained `p_allow_missing_amount`,
  default false, passed true only by `app.create_collection`
  (`20260921160100`)
- `checkCollectionConfig` (zod) → stopped requiring the amount up front

What still enforces it is `app.transition_collection_status`, which has
refused to publish a fixed collection with no amount since `20260919120000`.
The rule moved from save-time to publish-time; it did not go away, and a
pgTAP test now proves both halves.

**Stable ids.** `setCollectionTiersAction` and `setCollectionItemsAction`
return the saved rows' ids in display order, and the wizard carries them back
into its drafts. Editing an option three times leaves one option (ADR 0010).

**Multi-tab.** Not implemented. `collections.version` exists and
`app.transition_collection_status` already does compare-and-set on status,
but the field writes do not. Two tabs editing one draft is last-write-wins
today. Recorded in §11 rather than half-built.

## 3. Preview (part B)

`CollectionView` was extracted from the public page. Both render it:

- `/[communitySlug]/[collectionSlug]` — `mode="live"`
- `/c/[slug]/collections/[collectionSlug]/preview` — `mode="preview"`

There is one component, so the preview cannot drift from the page. It is
type-aware for free: the cover, the framing sentence, the fundraiser story,
the event block, the description and the lead line are the same tree in both
modes.

The contribution form is the one difference. In preview it is replaced by a
description of what will be asked — the ticket types or items with their
prices and stock, the amount model, the attendee-details setting, and the
list of questions. Submitting a preview would be the organiser contributing
to their own collection, and later a payment attempt against it.

The preview reads the draft through the officer's own session (RLS), because
`app.get_public_collection` deliberately cannot see a draft.

The detail page gains: a **Preview as a contributor** link, an **Export**

## 5. Export (part D)

**Filters:** everyone / still expected / exempted, and by group. Payment
status is not offered, because it does not exist.

**Fields:** full name, member ID, phone, email, groups, expected amount,
waived amount, status, due date, period, checked in — plus every custom
member field the community defined, under its own label. Select all / clear
all. Unknown keys sent by a client are dropped, not trusted.

**CSV:** `packages/domain/src/csv.ts`, pure and separately tested. RFC 4180
quoting, doubled inner quotes, a UTF-8 BOM so Excel on Windows does not
mangle ₦ or "Adéṣínà", CRLF endings, and a leading-quote defence so a cell
like `=1+1` or `@SUM(...)` cannot execute in a spreadsheet.

**Authorization:** `member.export`, the permission that already existed for
taking member data out (owner, admin, treasurer; not collector, not viewer).
Checked in the server action against the community that owns the collection.
Hiding the button is not a control, and the button is hidden as well.

**Scoping:** the collection is resolved by community id *and* slug, and every
query filters on the collection id.

**Large exports:** generated server-side; the browser receives finished text
and saves it, so nothing assembles a roll in page memory.

Example shape:

```csv
Full name,Member ID,Phone number,Expected amount,Status,Matric number
Ada Obi,MIC/0001,+2348011112222,"₦10,000",unpaid,21/SCI/456
"Obi, Bola",MIC/0002,+2348011113333,"₦10,000",Exempt,21/SCI/457
```

**Audit:** not recorded for exports. The audit function writes against a
community and an object, and an export is neither a row nor a state change;
adding an entry would have meant inventing an object id for it. Recorded in
§11.

## 6. Ticket operations (part E)

**The model.** `event_check_ins` — one row per visit, referencing an
obligation, the collection and the community, with `checked_in_at/by` and
`checked_out_at/by`. A partial unique index on `(obligation_id) where
checked_out_at is null` allows a history of visits while forbidding two open
ones.

**Why an obligation.** A purchased ticket is not a row anywhere in this
phase. An obligation is — it is the roll an officer built, which for a
managed event *is* the guest list. When Phase 4 records purchases, a
purchased ticket becomes a sibling column with a CHECK that exactly one is
set, and it uses the same function, permission and audit trail. A QR code
would resolve to the same obligation id and call the same function; no QR
infrastructure was built.

**States.** `Not arrived` → `Inside` → `Left`, derived from the latest visit
rather than stored as a flag.

**Idempotency.** Admitting somebody already inside returns their open visit.
Checking out somebody already outside does nothing. Both are silent, because
an error at a busy door is worse than a no-op.

**Permissions.** A new `attendance.check_in`, granted to owner, admin,
treasurer and collector — the collector being this schema's existing
field-agent role — and scoped for the collector per ROLE-06. Enforced inside
the SECURITY DEFINER function, not in the UI.

**Search.** One box, matching name or member ID, filtering in the page over
a list the server already scoped. Counters show expected / inside / not
arrived, all derived.

**Mobile.** One search box, large rows, one button each; no table to scroll
sideways.

**Audit.** `attendance.check_in` and `attendance.check_out` entries against
the obligation, with the actor and the collection. No personal detail in the
payload.

## 8. Security

- Export and check-in both re-check permission server-side against the
  community derived from the row, never from the caller's claim (SEC-18).
- Export queries are scoped by community id and collection id; a collection
  slug alone is not unique across communities and is never used alone.
- `event_check_ins` has RLS scoped to `attendance.check_in`; an officer of
  another community can neither admit a guest nor read the visits, and a
  pgTAP test asserts both.
- The grant matrix's `authenticated` allowlist was updated deliberately to
  name `event_check_ins`; the test caught it appearing silently, which is
  what it is for. The same test previously caught a new function inheriting
  PUBLIC execute.
- Unknown export column keys are dropped rather than interpreted.
- Preview writes nothing.

It took three runs to get there, and the first failure was not the test's
fault. It was a real product bug: the wizard wrote `participation_mode` on
the collection row before the audience rows existed, so Postgres rejected
the row on `collections_audience_matches_participation`. The fix is
`3afedfc` — the audience is written first, for every mode. The second and
third failures were the test's own fault: an assign dialog on a tiered
collection has no headline amount to inherit, and the door's counters use
the same three words as its badges, so each assertion matched twice. Both
corrected in `271bc35`.

**E2E honestly stated:** the suite is flaky on this machine (4 CPU / 3.7 GB,
documented in `kolekto-local-stack`), and this session also lost the Docker
daemon partway through. Targeted journeys were run individually and pass;
the full suite has not produced a single all-green run here, and the
failures that remain are timeouts at sign-in and community creation that
differ from run to run, not assertion failures. Every defect reported below
was confirmed by an independent method — a direct database query, a
production build, or rendered HTML — never by a red test alone.

## 11. Known limitations

- **Multi-tab drafts are last-write-wins.** No version check on field
  writes. `collections.version` exists if it is wanted.
- **Export is not audited.** See §5.
- **Ticket sales windows** (per-ticket-type start/end) are still not
  implemented — §41 of the brief allowed deferring it, and it was deferred.
- **Per-item visibility** is still not a control in the editor; `hidden`
  remains reachable only for published collections in Settings.
- **Check-in covers managed collections only.** A public ticket sale has no
  obligations, so it has nobody to admit. The UI says this rather than
  showing an empty list.
- **No QR scanning**, by design; the model is shaped so it can be added.
- **The full browser suite has not gone green on this machine.** See §9.
- Two files were corrupted by an interrupted write during this session
  (`page.tsx`, `CollectionDetailClient.tsx`) and were restored from git and
  re-applied. Both are in the commit and verified by build and typecheck.
