# M7.6 — closure report

**Date:** 2026-09-22

**Preceded by:** [the M7.6 final report](2026-09-22-m7.6-final-report.md) and
[the legacy comparison](2026-09-22-m7.6-legacy-comparison.md)

This closes the ten hardening items raised against that report. Phase 4 was
not started, and nothing in it was implemented.

---

## 1. The roll is paged and searched by the database

The final report's own first recommendation. The collection's
Members / Attendees / Orders table read **every** obligation and **every**
member of the community, then filtered them in the browser. Two defects in
one: a five-thousand-member association shipped five thousand names to a
phone, and PostgREST caps a select at a thousand rows whatever the query
says — so past a thousand members it was not even the whole roll.

Now:

- `loadRollAction` returns a page of 50 with a total, or a search capped at
  50 that says so. Filters (`Everyone` / `Outstanding` / `Exempt`) are applied
  in the query; their counts are three `head: true` counts, not an array
  nobody fetched.
- `searchAssignableMembersAction` replaces handing the assign dialog the whole
  community. It also excludes people already on the collection **for the
  period in question**, which is the rule a recurring collection needs.
- The door's counters moved into the database as
  `app.collection_door_totals`. "Not arrived" needs `DISTINCT` over a visit
  history — somebody may leave and come back — which no count query expresses.
- The page's remaining reads are bounded: a 50-row first page for the roll, a
  100-row first page for the door, and `range(0, 999)` on the decorating
  reads.

Security is the door's, deliberately and identically: community resolved from
the slug through RLS, collection resolved *inside* that community, every
subsequent query filtered by collection id. Reading obligations additionally
requires `transaction.view` for that collection, which RLS enforces.

One trap avoided twice now: `roll-actions.ts` is `"use server"`, so its
constants and types live in `roll.ts`. A `const` exported from a server-action
module fails the **production build**, not the typecheck — the way it did in
M7.5.

## 2. `code_style = 'random'` has an end-to-end journey

`tests/e2e/references-and-exports.spec.ts` — *"a random reference style issues
unguessable codes that persist and export"*. It asserts, in a browser:

- the digits and starting-number fields are **not** offered, because a random
  reference has no position in a series
- three references are issued, all matching `RAF-` plus six characters from
  the unambiguous alphabet (no I, L, O or U)
- all three are distinct, and **not** a sequence with a prefix stuck on it
- they survive a page reload, which is what "issued" means
- searching for one finds it and not the others — through the new server-side
  roll search
- all three appear in the CSV, and the PDF is a PDF

## 3. The export layer is ready for Phase 4, and carries no invented money

Verified against the live database rather than asserted:

```
tables matching contribution|payment|ledger|wallet|payout|withdraw|settle|transaction|invoice|receipt : none
obligations with status = 'paid'                                                                       : 0
columns matching paid|received|balance|settled                                                         : none
```

There is no financial state to fake, and none was fabricated. Paystack appears
in this repository only in comments and in `packages/adapters`' design note.

Readiness is now **enforced rather than claimed**, by
`export-fields.test.ts` (16 assertions):

- no field key, field label or subject may contain `paid`, `payment`,
  `received`, `contribution`, `balance`, `settled`, `refund`, `wallet`,
  `payout`, `ledger` or `transaction`. A column added ahead of the rows behind
  it fails the test.
- the two money columns that do exist are pinned as `Expected amount` and
  `Waived amount` — what was *asked for* and what an officer *forgave*,
  neither of which is money that arrived.
- every field has a unique key, a group the builder renders and a printable
  width; every subject has a unique key; every subject's defaults name fields
  that exist.

So Phase 4 adds a subject and a few columns by appending rows to two arrays.
The builder, the filters, the CSV writer and the PDF renderer do not change.

## 5. Every remaining browser failure, investigated

The first full run on the restarted stack: **27 passed, 2 flaky, 4 failed**
out of 33, in 1.0 hour. Each failure was chased rather than labelled.

| Failure | What the page actually showed | Cause |
|---|---|---|
| `audience` — newly eligible members | members page rendered its shell with an **empty `main`** | contention |
| `auth-community-member` | Add-member dialog still open, name typed, submit never returned | contention |
| `contributor` — identification cannot be forged | "the local stack did not accept a sign-in request after two attempts" | contention |
| `contributor` — a group collection only knows its group | predicate timeout | contention |

First hypothesis — that the local database had grown slow after hundreds of
test communities — was **measured and rejected**:

```
explain analyze: members by community_id → Bitmap Index Scan, 50 ms
largest table: audit_logs, 2,754 rows
```

Then all four were re-run on an idle machine, on the same code:

```
audience.spec.ts + auth-community-member.spec.ts   2 passed (3.4m)
contributor.spec.ts (the two failing journeys)     2 passed (4.8m)
```

**The established cause is the suite competing with itself.**
`fullyParallel: false` only stops tests inside one *file* running together;
across files Playwright still defaults to half the cores — two here. A full
run therefore put two browsers and two Next request streams on the same four
cores as the Supabase stack they were testing.

The fix is `workers: 1` in `playwright.config.ts`, not a larger timeout —
and it did not even cost wall-clock time. See the result below.

## 6. CSV and PDF verified with references, custom fields, ₦ and Nigerian names

In a browser, with the files downloaded and their bytes read — not with the
buttons merely clicked:

- `Ẹniọlá Adéṣínà` and `Ngọzị Okoro` on the roll, with `Ṣàngó Hall` in a
  community field of the community's own
- the CSV contains all of those, plus `₦25,000`, plus the column under its own
  label (`Hall of residence`, never `custom_field_1`)
- `csvText.charCodeAt(0) === 0xFEFF` — the byte-order mark, which is what
  stops Excel on Windows reading the file as the system codepage and turning
  every one of those names into mojibake
- the PDF's first five bytes are `%PDF-`, and its unit tests assert
  `/FontFile2` and `/Identity-H` are present, because the fourteen standard
  PDF fonts cannot draw ₦ or ẹ ọ ṣ ị ụ at all

## 7. Tier references across several options, and the fallback

Both levels.

**In the database** (`16_contributor_references.sql`): a dinner with `Regular`
→ `REG`, `VIP` → `VIP`, and `Table` with no prefix produces exactly
`REG-0001`, `VIP-0001`, `DIN-0001`. Each prefixed option counts from one; the
option without a prefix falls back to the collection's series rather than
inventing one.

**In a browser** (`references-and-exports.spec.ts`): the same three options,
three members, `REG-0001` / `VIP-0001` / `DIN26-0001` asserted on the roll and
all three asserted in the CSV. The VIP row carries the VIP price, because the
tier supplies the amount.

## 8. RBAC, verified as a matrix and as a refusal

`17_operations_rbac.sql`, 28 assertions. Each permission twice: once as the
role matrix the UI mirrors, once as the function refusing a caller who does
not hold it.

| | Holds it | Refused, by the function |
|---|---|---|
| `member.export` | owner, admin, treasurer | viewer, collector, another community's owner |
| `collection.configure_codes` | owner, admin | viewer, another community's owner |
| `attendance.check_in` | owner, admin, treasurer, collector (`scoped`) | viewer, another community's owner |

Also asserted: the export audit row names the **columns** that left and
carries no value out of any row (SEC-26); `collection_door_totals` refuses a
viewer as firmly as `check_in_obligation` does.

Additionally, exporting a phone number or an email address now requires
`member.view_contact` as well as `member.export` (RPT-06). Every current
holder of the second holds the first, so it refuses nobody today — it is there
so the columns follow the matrix if the matrix changes.

## 9. Isolation, cross-community and cross-collection

- **Cross-community:** another community's owner cannot export this
  collection, change its reference format, admit one of its guests, read a
  single one of its references, or read a single row of its roll — the last
  being exactly the filter the paged roll query runs.
- **Cross-collection:** two collections in the *same* community, `OPS` and
  `LEV`. The same member holds `OPS-0001` on one and `LEV-0001` on the other:
  three distinct references, none shared. A reference identifies a
  participation in one collection and means nothing outside it.

## Remaining limitations

1. **A full browser run takes about 43 minutes** on this machine, serially.
   That is the floor for this hardware, not a cost of the fix in §5 — the
   two-worker run that failed four tests took longer.
2. **Item exports still have no item columns**, because no order is recorded.
   Correct today; it becomes wrong the moment Phase 4 lands, which is why
   `export-fields.test.ts` exists to fail when a column arrives ahead of its
   rows.
3. **Export filtering is partly in memory** — group membership and door state.
   Both need a join the export builds anyway; at the 20,000-row ceiling it is
   more work than it needs to be.
4. **Multi-tab drafts are last-write-wins.** No version check on field writes.
   `collections.version` exists if it is wanted.
5. **A reference is never withdrawn.** Cancelling an obligation leaves its
   reference attached to the record — deliberate (CODE-04), and it means a
   cancelled row still holds a number.
6. **`attribute_basis` (CODE-03) and `per_unit` (CODE-04) are unimplemented**,
   documented as such in the schema, and offered by no screen.
7. **No QR scanning**, by design. The model is shaped for it: a scan resolves
   a reference to an obligation through the same server call the door search
   already uses.
8. **`npm audit` reports vulnerabilities in the vitest / vite / esbuild dev
   chain.** Pre-existing, development-only, and fixing them is a breaking
   major upgrade. `pdf-lib`, `@pdf-lib/fontkit` and `dejavu-fonts-ttf`
   introduced none.

## Recommendation

The three things the final report said should come before Phase 4 are done:
the roll is paged and searched server-side, the random style has browser
coverage, and the export catalogue is both verified Phase-4-ready and guarded
against gaining a money column ahead of the rows behind it.

**M7.6 is closed. Phase 4 is the right next milestone.**

`BIO26-0042` identifies the same participation before the money, during it and
after it. A confirmed contribution becomes the second thing a reference
attaches to — a nullable `contribution_id` beside `obligation_id`, a CHECK
that exactly one is set, the same counter, the same format, the same
uniqueness, the same audit trail — and the second thing a door can admit and
an export can be about.

One thing Phase 4 must not inherit, and which this milestone already guards
against: a counter that commits ahead of the row it numbers.
`app.issue_contributor_reference` does both in one transaction today, and the
contribution insert must be brought **inside** that transaction rather than
handed a pre-minted code. The old system's own diagnostic is the argument, and
it is quoted in the legacy comparison.
