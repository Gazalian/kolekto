## 1. What this milestone did

Phase 4 had an unusually good starting position: a 932-line money architecture,
state machines for seven entities, a reconciliation design, a test matrix and a
234-line decision register, all written 2026-09-22 and audited against live code
by M7.9. The architecture was accurate. What it lacked was decisions — and the
one decision it named as blocking everything, DEC-01, was genuinely blocking,
because the two settlement models it described produce different charts of
accounts.

The founder closed DEC-01 and twenty-odd other questions. This milestone
recorded those decisions, resolved six places where they conflict with the
2026-09-22 design, and built the ledger the design had been waiting to build.

## 5. The Phase 4 gate was narrowed, deliberately

`18_fee_configuration.sql` asserted that no table named `ledger_accounts` or
`ledger_entries` existed, and that no `app.*` function matched `%ledger%`.
Building the ledger trips both. That tripwire was installed so the boundary could
not be crossed unnoticed, so crossing it is recorded here rather than left to be
discovered in a diff.

What replaced it is narrower, not weaker. The gate now asserts:

1. no payment, contribution, wallet, withdrawal, payout, settlement, refund,
   dispute or hold table exists (18 names, up from 12)
2. `communities` has no balance column, under any name
3. no `app.*` function initiates a payment, settles, withdraws, pays out,
   refunds or creates a contribution
4. **no database function anywhere inserts into a ledger table** — the ledger
   exists and nothing can write to it
5. the ledger is empty: no opening balances, no imported history

Assertions 4 and 5 did not exist before. The boundary is checked more precisely
now than it was.

## 6. A security finding, from this milestone's own migrations

`02_grant_matrix.sql` failed when the new migrations were applied, and it was
right to.

**Finding.** Postgres grants `EXECUTE` to `PUBLIC` on every newly created
function. `20260917121100_grants.sql` revoked that across the `app` schema, but
that revoke applied to the functions existing at the time — it is not a standing
rule. All six trigger functions M8.1 added were therefore executable by `anon`.

**Severity: low, but the class is not.** All six are trigger functions; calling
one directly fails for want of a trigger context. The same default, on three
`SECURITY DEFINER` functions, is how the previous system let an anonymous caller
holding the publishable key drive its payment state machine.

**Fixed** by `20260924150000_financial_function_grants.sql`, which revokes
`EXECUTE` from `public`, `anon` and `authenticated` on all six. A trigger
function does not need an EXECUTE grant to fire, which `20_ledger.sql` and
`21_financial_idempotency.sql` demonstrate by still passing.

**Worth acting on beyond M8.1:** every future migration that adds an `app.*`
function has this same hazard, and the only thing that catches it is
`02_grant_matrix.sql` failing. A default-deny at schema creation, or a rule in
the invariant script, would catch it at authoring time instead. Not done here —
it is outside this milestone and affects every migration, not just financial
ones.

## 8. What needs a founder or counsel decision

Nothing here blocks M8.1. Each blocks something later, and all thirteen are in
`financial-decisions.md` §12.

**The one to act on first is not on that list, because it is a provider
question:** [PA-04](../phase-4/provider-assumptions.md#pa-04--subaccount-settlement-timing-is-controllable).
D-01 assumes a Paystack subaccount can be operated so the organiser's share does
not auto-settle on Paystack's schedule, letting Kolekto control the timing. If
that is false, then withdrawal, withdrawal fees, daily limits, approval
thresholds, the 24-hour target and the 48-hour cooling-off all have nothing to
act on — Paystack would already have paid the organiser. That would invalidate a
product decision rather than an implementation detail, and it is verifiable in
sandbox before any withdrawal work starts.

The ledger built here survives either answer, which is why M8.1 proceeded. ADR
0015 §4 says why.

**Needing the founder:** the ₦100–₦500 withdrawal fee brackets (O-2, and the
schedule is deliberately empty until they exist); what "security checks" and
"manual review" mean operationally (O-3); the refund policy (O-6); partial
payment rules (O-7); recurring overpayment roll-forward (O-11); stored-card
charging (O-12); unfinished installment plans (O-13).

**Needing counsel:** whether Kolekto may hold or control the timing of
third-party funds, and whether that needs a licence (O-1 — this is DEC-03, and it
gates going live, not building); whether a platform fee may lawfully be passed to
a contributor (O-4); who bears a lost dispute after withdrawal (O-5); payload
retention and data residency (O-10).

**Needing an accountant:** whether Kolekto's fee is VAT-able and whether a
receipt must show it (O-8).

## 9. Known limitations

1. **Nothing posts to the ledger.** By design, and asserted by the gate. Every
   writer — capture, fee, release, withdrawal, payout — is a later milestone.
2. **The chart of accounts is created per collection by nothing.** Accounts are
   inserted by migration or by hand today; the function that provisions a
   collection's accounts on first payment belongs with the capture writer.
3. **`financial_events` has no processing state, deliberately.** The table is
   immutable, so "processed" cannot be a column on it. When a receiver exists,
   its outcome should be an append-only row, not a mutable flag — noted in the
   migration so the shortcut is not taken later.
4. **No staff read path for raw payloads.** `financial_events` is readable by
   nobody: ADR 0009's staff realm is not built. That is honest rather than
   convenient, and it means a payload can only be inspected by a service-role
   session today.
5. **The T+1 release is a calculation, not a job.** `availableAt()` says when a
   release is due. Nothing posts one.
6. **`nairaFromKobo` in `SettingsPanel.tsx` duplicates `formatNaira`** from the
   domain. Found because the new fee invariant flagged it as a false positive
   (the rule was narrowed; the duplication was not touched). Not a money-path
   defect — it is a display conversion and it is correct — but it is a second
   implementation of something the domain owns, and worth collapsing when that
   file is next edited.
