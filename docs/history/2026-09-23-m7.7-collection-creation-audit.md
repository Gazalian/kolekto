## 1. Collection creation routes and components

```
apps/web/app/c/[slug]/collections/
├── new/page.tsx                    server component: community, access, member count, groups
├── new/NewCollectionForm.tsx       the wizard (client)
├── [collectionSlug]/continue/page.tsx   resume a draft
├── [collectionSlug]/preview/       PreviewFrame + the real CollectionView
├── AudiencePicker.tsx   CoverUploader.tsx   EventEditor.tsx
├── ItemsEditor.tsx      QuestionsEditor.tsx RecurrenceEditor.tsx
├── StoryEditor.tsx      SuggestedAmountsEditor.tsx  TiersEditor.tsx
└── actions.ts                      server actions
```

**F3 — the wizard was one sequence.** `NewCollectionForm.tsx` held a single seven-entry step array used by every
type: *Intent → Basics → Contribution → Cover image → Who pays → Their details → Review*. Everything
type-specific happened inside a `switch` on `amountModel` within step 2. A ticketed event, an aso-ebi catalogue and
an estate levy walked identical screens in identical order; the only differences were a heading string and which
editor rendered in the middle.

This is the defect the milestone exists to correct, and it cannot be fixed by renaming steps.

## 2. Collection type definitions

There is **no `collection_type` column** and there should not be (ADR 0013). A "type" is a preset over four
configuration axes the database actually constrains:

| Axis | Column | Values |
|---|---|---|
| participation | `collections.participation_mode` | `open`, `managed` |
| amount model | `collections.amount_model` | `fixed`, `open_amount`, `tiers`, `per_member`, `items` |
| schedule | `collections.schedule` | `one_time`, `recurring` |
| category | `collections.category` | `dues`, `contribution`, `event`, `fundraiser`, `items`, `other` |

Constraint `collections_audience_matches_participation` pairs `audience_mode` with `participation_mode`, which is
why `app.set_collection_audience` writes both in one statement.

**Consequence for this milestone:** a flow key must be *derived* from these axes, never stored. A stored key would
be a second source of truth able to disagree with what the database enforces.

## 3. Draft persistence

Sound, and to be preserved.

- `collections.draft_step` (migration `20260921190000_draft_step.sql`) records position.
- Every step writes **real rows** — the collection, its tiers, its items, its event fields, its audience, its
  questions — so a draft *is* the state. There is no serialised wizard blob anywhere, which is correct.
- `continue/page.tsx` reads those rows back.

Two defects found in the existing implementation:

- `rememberStepAction` was dispatched inside `startTransition` and **left floating** in an earlier revision; that
  had already been fixed (it is awaited) but the fix left `advance()` reading `draftId` from **state**, which does
  not update inside the closure that set it — so the very first step recorded no position at all.
- `continue/page.tsx` restored neither `starts_at`, nor `fee_mode`, nor the code settings.

## 4. Contributor reference schema, functions and UI

M7.6's architecture, and it is correct. **Do not rebuild.**

| Object | Migration |
|---|---|
| `collection_code_settings` (+ `separator`, `digits`, `start_number`) | `20260921180000_contributor_references.sql` |
| `collection_code_sequences (collection_id, tier_id, next_number)`, `unique … nulls not distinct` | same |
| `contributor_references`, `unique (collection_id, reference)`, `unique (obligation_id)` | same |
| immutability trigger; `collection.configure_codes` permission | same |
| `app.set_collection_code_settings`, `app.issue_contributor_reference` | `20260921180100` |
| trigger revoked from `PUBLIC` | `20260921190200` |

Properties already guaranteed: server-generated, DB-enforced uniqueness, concurrency-safe via
`UPDATE … RETURNING` (never `count(*) + 1`), immutable once issued, collection- and tier-level scopes.

**F5 — the gap is purely where it is offered.** The only UI is `CodeSettingsPanel` on a published collection's
Settings tab. An organiser setting up a ticketed dinner meets the option only after finishing.

**Four concepts are distinct in the schema and must stay distinct:** `members.member_code` (community member ID),
the community's primary identifier attribute, `contributor_references.reference`, and
`collection_tiers.code_prefix`.

**Honest limitation.** A reference has `unique (obligation_id)` — it attaches to an obligation. A collection open to
anyone has no obligations until members are put on a roll, so such a collection issues **no** references until then.
The creation UI must say so rather than let it be discovered.

## 5–6. Fee-related types and domain code

`packages/domain/src/fees.ts` — exports `FeeBearer`, `FeeSchedule`, `SCHEDULE_2026_09_PROVISIONAL`, `FeeBreakdown`,
`CalculateFeesInput`, `calculateFees`, `netForCommunity`.

It is the abstraction Part 2 asks to be reused. Its properties:

- integer kobo (ADR 0003), rates as integer basis points
- rounding half away from zero, applied exactly once per fee
- each fee capped independently
- **fees computed on the contribution, never on the payable**, so a contributor-borne total cannot compound
- the schedule is **versioned** (`SCHEDULE_2026_09_PROVISIONAL.version`) — PRC-09's fix for the previous system's
  worst property, where balances were recomputed nightly against current constants and changing a rate silently
  restated history

`money.ts` supplies `Kobo`, `fromNaira`, `formatNaira`, `add`, `subtract`, `applyRate`, `bps`, `min`.
`contribution.ts` resolves what is owed **server-side** from the collection's own rows.

**F2 — `calculateFees` had no caller in `apps/web`.** It was written, tested, and never shown to anybody. An
organiser published a ₦20,000 levy with no way to know whether they would receive ₦20,000 or ₦19,600.

**F1 — `collections.fee_mode` could not be changed.** The column has existed since `20260917120700` and
`communities.default_fee_mode` since `20260917120300`. `app.create_collection` copies the community default onto the
collection (`20260919120000` line 221, and again in `20260921160100` line 157) and **no function, action or screen
could ever alter it afterwards.**

**The rates are provisional.** `fees.ts` says so in its own header: they are what the previous system charged,
carried across so the arithmetic could be tested against known behaviour. The real numbers are DEC-11's. Any UI
must therefore not present computed figures as settlement amounts.

## 7. Phase 4 architecture documents

Five, all design-only, all in `docs/history/`:

`2026-09-22-phase4-money-architecture.md`, `-state-machines.md`, `-reconciliation-design.md`, `-test-matrix.md`,
`-open-decisions.md`.

Relevant constraints they set for this milestone:

- the ledger is the sole source of truth for money, and it does not exist yet (ADR 0006)
- **DEC-11** — the real fee schedule — is unanswered
- **DEC-12** — whether a platform fee may lawfully be passed to a contributor in Nigeria — is a **legal** question,
  unanswered. Both `fee_mode` enum values exist precisely so the engine can express either answer.

**Therefore:** M7.7 may store the organiser's chosen policy and illustrate it. It may not decide the schedule, and
it must not imply the illustration is final.

## 10. Legacy collection creation implementation

`Kolekto-codebase/kolekto-fe-old`.

### 10.1 The legacy already had per-type flows

`src/components/collections/wizard/wizardTypes.ts`:

```ts
export const STEP_FLOWS: Record<CollectionType, StepId[]> = {
  fixed:       ['type-selection', 'basic-info', 'pricing', 'charges', 'contributor-fields', 'unique-id', 'review'],
  tiered:      ['type-selection', 'basic-info', 'pricing', 'charges', 'contributor-fields', 'unique-id', 'review'],
  open_pool:   ['type-selection', 'basic-info', 'pricing',            'contributor-fields', 'unique-id', 'review'],
  ticket:      ['type-selection', 'basic-info', 'pricing', 'charges',                       'unique-id', 'review'],
  fundraising: ['type-selection', 'basic-info', 'fundraising-goal', 'fundraising-story', 'fundraising-verification', 'review'],
};
```

Five types, four of them sharing a sequence — but the *idea* is right and the fundraising row is genuinely its own
flow. The rebuild had replaced this with one fixed list. Part of M7.7 is recovering a design the previous system
already had.

### 10.2 F8 — four fee implementations that disagreed

| File | Platform rate | Gateway rate | Capped |
|---|---|---|---|
| `components/collections/form/PricingSection.tsx` | 3% / 2.5% / 2% / 1.5% banded | 1.5% | gateway only |
| `components/collections/wizard/wizardTypes.ts` | 0.5%, 1% for fundraising | 1.5% | both at ₦2,000 |
| `components/contribute/ContributeFlow.tsx` | 0.5%, 1% for fundraising | 1.5% | both at ₦2,000 |
| `components/contribute/ContributionForm.tsx` | 1% | 1.5% | **neither** |
| `utils/dbHelpers.ts` | — | flat 1.5% | no |

On ₦10,000 the creation wizard said **₦200** of fees and the edit dialog said **₦350** — a 75% disagreement about
the same collection on two screens an organiser could have open at once. On a ₦500,000 donation `ContributeFlow`
said **₦4,000** and `ContributionForm` said **₦12,500**, because one applied the caps and the other did not.

This is exactly what Part 2 forbids, and it is not hypothetical — it shipped. **One implementation only.**

### 10.3 The legacy configured references during creation

`steps/Step6UniqueId.tsx` is a creation step with a live `{prefix}-001` preview and per-tier prefixes. Moving that
to Settings was a regression, not a simplification.

Not to be copied: it padded to a fixed three digits with no configurable width, and computed the value in the
browser. M7.6's server-generated, DB-unique version is better and stays.

## 14. Contradictory implementation

One, and it is in the briefs rather than the code: an earlier instruction asked for a **live fee breakdown** from
`calculateFees`, while this milestone's Part 3 says **"Do not show fake exact numbers if the actual fee schedule is
not finalized."** The schedule is not finalised (DEC-11).

**Resolution adopted:** the fee step leads with the Part 3 wording — *amount + applicable fees*, *amount − applicable
fees* — and the computed breakdown is available only behind an explicitly-labelled estimate that names the
provisional schedule version and states it is not a settlement amount. This satisfies Part 2's allowance ("may show
an illustrative preview only if it is clearly marked as an estimate") without asserting figures Kolekto has not
committed to.

No contradiction was found *within* the code itself: there is exactly one fee implementation in the rebuild, and
the legacy's four are not imported anywhere.
