# M13.2 P9-1 — Recipient Suppression and Pre-Send Enforcement, as built

**Branch:** `feat/p9-pr1-recipient-suppression` (from `origin/main` at `30e897a`, the PR #13 merge).
**Status:** Implemented for review. No provider dispatch, no SES adapter, no production sending.

## What P9-1 does

Before a worker calls a provider, the delivery must pass a recipient-suppression check
that comes BEFORE every rate limit. A suppressed address never reaches the provider
and never consumes a rate-limit slot.

- `public.email_suppressions` (table): one row per suppressed address. `address_key` is
  `lower(address)` — the same normalisation as `notification_send_attempts.address_key`,
  so the reserve function reuses the value it already has. Append-only via trigger
  (DELETE/UPDATE only through the operator-controlled setter/clear/purge functions,
  signalled by a transaction-local session variable). RLS enabled and forced, deny-all
  policy, no client role has any access or grant.
- `app.is_address_suppressed(p_address text)`: the sender's probe. Returns `true` when
  a permanent row exists (`expires_at IS NULL`) OR an unexpired transient row exists.
  Never raises on bad input (returns `false`); the caller — `reserve_email_attempt` —
  has already validated the delivery and the probe must never fail the sender tick.
- `app.set_email_suppression(p_address, p_reason, p_expires_at, p_source, p_source_event_id)`:
  operator-session only (`role = 'none'`), with the same role gate as `begin_notification_suppression`.
  Takes the same address-order advisory lock as `reserve_email_attempt`, so a race
  between a send and a block cannot both see "not suppressed" and both proceed.
  A permanent suppression is never downgraded by a subsequent transient request.
- `app.clear_email_suppression(p_address)`: operator-session only. Deletes every row
  (permanent and transient) for the lower-cased, trimmed address. Returns the count
  deleted.
- `app.list_email_suppressions_masked(p_limit, p_before)`: the ONLY read path for the
  table. Operator-only. Returns `recipient_address_masked` via the existing
  `app.mask_email_address`; the raw address never leaves the database through this
  function.
- `app.purge_expired_email_suppressions(p_grace_days integer default 30)`: deletes
  transient rows whose expiry is more than `p_grace_days` in the past. Permanent rows
  (`expires_at IS NULL`) are never touched. Operator-only.
- `app.reserve_email_attempt(uuid)`: AMENDED. A new terminal branch inserted
  immediately after `v_address` is computed and before the L1 check. Everything else
  is byte-identical to the previous body. On a suppression hit:
  - delivery → `skipped` with `error_code = 'address_suppressed'`
  - `recipient_address` erased (same convention as `recipient_rate_limited` /
    `community_backlog_full`)
  - attempt counter undone
  - no ledger row written

## Design decisions

### Suppression key: lower-cased raw address, not HMAC

The existing codebase stores `lower(address)` in `notification_send_attempts.address_key`
and raw addresses in `notification_deliveries.recipient_address`, both behind deny-all RLS
and a masked read function (`app.mask_email_address`, `app.list_email_delivery_log`). We
followed the same convention:

- Deny-all RLS and `REVOKE ALL ... FROM public, anon, authenticated` on the table.
- Append-only triggers that refuse DELETE/UPDATE unless the operator function signals
  via a transaction-local `app.email_suppressions_mutating` variable.
- Masked operator read via `app.list_email_suppressions_masked` reusing `app.mask_email_address`.

HMAC was considered. It would reduce the long-lived PII surface, but at material cost:
key management (how is the HMAC key stored, rotated, and shared between workers?),
divergence from a convention this codebase already enforces consistently, and lost
operator readability (an operator cannot answer "is `foo@bar.com` suppressed?" without a
hashing tool). The decision is to minimise access via RLS and the masked read function,
not via irreversibility, which matches `notification_send_attempts` and
`notification_deliveries`.

### Retention

- Permanent suppressions (`expires_at IS NULL`) live indefinitely — that is the point.
- Transient suppressions auto-prune at `expires_at + 30 days` via
  `app.purge_expired_email_suppressions`. The 30-day grace lets an operator audit a
  recently expired suppression.

### Operator-only setter

The `operator`, `ses_event`, and `sender_classification` sources are declared in the
check constraint, but the `set_email_suppression` function refuses to run outside an
operator session (`role = 'none'`). The webhook ingestion function that P9-2 will add
uses its own SECURITY DEFINER entry point that writes to the table under its own gate;
it does not route through this operator setter. This closes the "a stray `p_source`
value cannot create a row that pretends to come from a webhook" case.

## Transaction discipline

The amended reserve path:

```
BEGIN
  claim → reserve
         ├── advisory lock (address, community, platform)
         ├── NEW: is_address_suppressed → skipped/address_suppressed if hit  ◄─── P9-1
         ├── L1 (per-address 24 h) → skipped/recipient_rate_limited if hit
         ├── L2 (per-community 1 h) → deferred or backlog_full
         ├── L3 (platform 1 h) → deferred or backlog_full
         └── ledger insert → granted
COMMIT  (before any provider call)
```

The operator setter takes the same address advisory lock (lock domain `1`, key
`hashtext(lower(address))`). A concurrent "send-this-address" and "block-this-address"
transaction cannot both see "not suppressed" and both proceed: whichever grabs the lock
first finishes; the other then sees the correct state.

## Permissions

Every added function is `SECURITY DEFINER` with `SET search_path = ''`:

| Function | Executable by |
|---|---|
| `app.is_address_suppressed(text)` | owner connection only (worker). `anon`, `authenticated` revoked. |
| `app.set_email_suppression(text, text, timestamptz, text, text)` | operator session only (`role = 'none'`). Any client session is refused with `42501`. |
| `app.clear_email_suppression(text)` | same |
| `app.list_email_suppressions_masked(integer, timestamptz)` | same |
| `app.purge_expired_email_suppressions(integer)` | same |
| `app.block_email_suppressions_mutation()` (trigger) | not callable; the trigger is attached. |

Direct `SELECT` on `public.email_suppressions`: `anon` and `authenticated` are refused
by the deny policy AND by the revoked table grants.

## Worker surface

`apps/worker/src/notification-rate-limit.ts` adds `"address_suppressed"` to
`ReservationOutcome`. `apps/worker/src/notification-sender.ts` already routes any
non-`granted` non-`community_deferred` reservation into a `SendStep` with
`outcome = "skipped"` and the `reservation` field forwarded, so the health snapshot's
`skipped_by_code` naturally picks up `address_suppressed` once a real skip happens.
No change to the pause switch, claim semantics, retry policy, rate-limit numbers, or
provider behavior.

## What this intentionally does NOT do (later phases)

- No SES adapter, no SDK dependency, no registration of `"ses"` in `REAL_EMAIL_PROVIDERS`. **P9-4.**
- No SNS webhook, no bounce/complaint event ingestion, no automatic suppression
  writing. **P9-2.** When P9-2 lands, its security-definer entry point will call into
  the same table with `source = 'ses_event'`.
- No SES-quota-aware L4/L5 limits. **P9-3.**
- No crash-after-accept guard. **P9-4.**

## Rollback

Revert this migration to restore the previous `reserve_email_attempt` body from
`20261013200000_notification_rate_limits.sql`. The suppression table, functions,
triggers and indexes drop in the standard migration-reverse order.

## Operator runbook (quick reference)

```sql
-- Block an address permanently.
select app.set_email_suppression('user@example.com', 'manual_block');

-- Block for 24 hours only.
select app.set_email_suppression('user@example.com', 'transient_bounce_capped',
                                  now() + interval '24 hours');

-- Unblock.
select app.clear_email_suppression('user@example.com');

-- Read the list (masked).
select * from app.list_email_suppressions_masked(100, null);

-- Age-prune transient rows older than 30 days past expiry.
select app.purge_expired_email_suppressions();
```

Every call runs under the operator session; any attempt from `anon` or `authenticated`
is refused with `42501`.
