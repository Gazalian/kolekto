## Root cause

The worker successfully processed each message (created `notification_events` + `notification_deliveries`) but then **failed to delete/acknowledge it**, so every message stayed on the queue and was reprocessed on each visibility-timeout cycle. The delete call passed the message id as **text**, and `pgmq.delete` is overloaded, so Postgres could not resolve which overload to use.

## Exact affected code

`apps/worker/src/index.ts`, the consume loop:
- Line 34 types the `pgmq.read` result as `{ msg_id: string; ... }`. The `postgres` driver surfaces pgmq's `bigint` `msg_id` as a JavaScript **string**.
- Line 47 (old): `await sql\`select pgmq.delete('notification_events', ${msg.msg_id})\`` — the string is sent as an untyped/`unknown` parameter.

## Why PostgreSQL could not resolve the overload

`pgmq.delete` has two candidates:

```
pgmq.delete(queue_name text, msg_id  bigint)
pgmq.delete(queue_name text, msg_ids bigint[])
```

An argument of type `unknown` (what a bare string parameter is until typed) is implicitly coercible to **both** `bigint` and `bigint[]`, so neither candidate is uniquely best:

```
ERROR 42725: function pgmq.delete(unknown, unknown) is not unique
HINT: Could not choose a best candidate function. You might need to add explicit type casts.
```

The error fires *after* successful processing, so it was caught by the loop's per-message `try/catch`, logged as "Failed to process", and the message was left on the queue — reprocessed forever (deliveries stayed correct only because the delivery insert is idempotent).

## Exact fix

`apps/worker/src/index.ts:47` — add an explicit `::bigint` cast to the bound parameter (still a parameterized query, no string concatenation):

```ts
// msg_id arrives as text (pgmq.read's bigint, surfaced by the driver as
// a string). pgmq.delete is overloaded on (text, bigint) and
// (text, bigint[]), so an untyped argument is ambiguous (42725). The
// explicit ::bigint cast resolves to the single-message overload.
await sql`select pgmq.delete('notification_events', ${msg.msg_id}::bigint)`;
```

This is the only code change in this task. It matches the fix the QA proved works manually (`select pgmq.delete('notification_events', 107::bigint)`).

## How msg_id is now typed/conveyed

`msg_id` is still read as a string from the driver (unchanged), but at the delete it is passed as a **bound parameter with an explicit `::bigint` cast**, so Postgres receives a typed `bigint` and resolves unambiguously to `pgmq.delete(text, bigint)` — the single-message overload. No string interpolation of the id into SQL; it remains a `$n` parameter.

## Retry / failure behavior (preserved, not weakened)

The loop structure is unchanged: `try { process; delete } catch { log }`. The delete still runs **only after** `processNotificationMessage` resolves successfully. The fix only makes the previously-always-failing delete succeed; it adds no new delete-on-failure path and no duplicate-delivery risk.
