# M13.2 P4 — Recipient Eligibility, as built

**Branch:** `m13.2-p4-recipient-eligibility` (from `origin/main` at `ce66b01`, the PR #4 merge).
**Status:** Implemented for review. No provider dispatch, no production sending.

## What P4 does

Every processed notification event now files exactly one of three email outcomes,
inside the existing resumable worker transaction:

- `member.create` / `member.approve_join` → an email delivery row, `pending`
  when eligible or `skipped` with a stable reason when not.
- `officer_invitation.accept` / `officer_term.end` → the same, resolved through
  the officer term holder.
- `member.reject_join`, `member.join_via_invite`, `collection.publish` and
  everything unwatched → no email row at all.

## The decision

`app.evaluate_email_eligibility(p_event_type, p_object_id, p_asserted_user_id)`
(20261012100000) is the single authority. It takes the event's object id — a
member id or an officer-term id — plus an asserted user id that it verifies
against the record it reads. It never matches on email strings.

- Account path: current `auth.users.email` with non-null `email_confirmed_at`.
  Anything else skips as `unverified_account_email`. `public.users.email`,
  `members.email` and `identity_level` are never consulted (Q-FALLBACK).
- Non-account path (`member.create` / `member.approve_join` only): the supplied
  `members.email`, stored with assurance `unverified_supplied` and minimal
  confirmation content only. Never described as verified.
- Missing rows → `missing_membership_relationship`; null or mismatched asserted
  ids → `ambiguous_recipient_relationship`; missing/malformed addresses →
  `no_recipient` / `invalid_recipient_address`; non-evaluation events →
  `unsupported_event`. Skips store no address and no assurance.

EXECUTE is revoked from `public`, `anon` and `authenticated`; the sole caller is
the worker over its owner connection. Client roles cannot enumerate addresses
through it.

## What P4 deliberately does not do

- No rejection mail to unverified supplied addresses. Decision R-E3 is final:
  a non-account applicant rejected through `member.reject_join` receives no
  email and no sendable email delivery row; in-app behavior is unchanged.
- No provider dispatch, leases, retries, rate limits, bounce handling, or
  production sending — all P5. The P5 sender must re-read the Auth record
  inside its send lease; an evaluation-time address never overrides that read.
- No account linking, no email matching, no phone verification, no consent or
  preference UI, no `consent_messages_at` writes, no financial or
  authentication changes, no broad permission refactor.
- No `recipient_kind` column: `recipient_address_assurance` plus the id pair
  already distinguishes the classes.
- Delivery is at-least-once; exactly-once is not claimed.
