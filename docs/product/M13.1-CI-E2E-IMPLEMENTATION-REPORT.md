## 2. CI architecture

The new `e2e` job runs on `ubuntu-latest` and is self-contained and additive. It does not depend on (`needs`) the other jobs, so it runs in parallel and cannot restructure them. Flow:

```
checkout
  → setup Node (.nvmrc) + npm cache
  → supabase/setup-cli@v1 (version: latest)
  → supabase start                     # applies migrations + seed; brings up Mailpit
  → export local Supabase keys → $GITHUB_ENV (robust name mapping)
  → generate ephemeral KOLEKTO_SESSION_SECRET → $GITHUB_ENV
  → npm ci
  → npx playwright install --with-deps chromium
  → npm run build --workspace apps/worker       # esbuild bundle
  → node apps/worker/dist/index.js &            # background, PID captured
  → npm run test:e2e                            # Playwright builds+starts web itself
  → [always] upload playwright-report/ + test-results/
  → [always] upload worker.log
  → [always] kill worker
  → [always] supabase stop
```

It deliberately reuses the already-proven `database`-job pattern (`supabase/setup-cli@v1` + `supabase start` on `ubuntu-latest`) rather than inventing new stack setup. The only process the workflow starts by hand is the worker; the Supabase stack is the CLI's and the Next.js web server is Playwright's.

## 3. Exact workflow changes

A new job appended under `jobs:` in `.github/workflows/ci.yml`:

- `runs-on: ubuntu-latest`, `timeout-minutes: 30`.
- Job-level `env` holds only **static, non-secret local values**: `KOLEKTO_ENV=local`, `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321`, `SUPABASE_DB_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres`, `MAILPIT_URL=http://127.0.0.1:54324`.
- `KOLEKTO_PRODUCTION_PROJECT_REF` and `KOLEKTO_EXPECTED_PROJECT_REF` are intentionally **unset** (for `KOLEKTO_ENV=local`, `packages/config/src/env.ts` requires a loopback URL and no hosted ref).
- 15 steps, matching the requested outline. All artifact-upload and teardown steps carry `if: always()`.

The existing workflow-level settings (`on: [pull_request, push:main]`, `concurrency`, `permissions: contents: read`) are unchanged and apply to the new job as-is. `contents: read` is sufficient — `actions/upload-artifact@v4` does not require write permission.

## 4. Environment variables

| Variable | Provided by | Secret? |
|---|---|---|
| `KOLEKTO_ENV=local` | job `env` (static) | no |
| `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321` | job `env` (static) | no |
| `SUPABASE_DB_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres` | job `env` (static; fixed local creds) | no |
| `MAILPIT_URL=http://127.0.0.1:54324` | job `env` (static) | no |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | step → `$GITHUB_ENV`, from `supabase status` | no (disposable local demo key) |
| `SUPABASE_SERVICE_ROLE_KEY` | step → `$GITHUB_ENV`, from `supabase status` | no (disposable local demo key) |
| `KOLEKTO_SESSION_SECRET` | step → `$GITHUB_ENV`, generated per run (`randomBytes(32).toString("base64url")`) | ephemeral; never persisted |

**No GitHub repository secrets are required.** The only secret referenced anywhere in the workflow is the auto-provided `GITHUB_TOKEN` (used by the pre-existing `security` job's gitleaks step, not by `e2e`). The two dynamic keys and the session secret are written to `$GITHUB_ENV`, which makes them available to **all subsequent steps including `npm run test:e2e`** — important because Playwright's `webServer` runs `next build`, and the `NEXT_PUBLIC_*` values must be present at build time to be inlined into the client bundle. The dynamic values are passed through `::add-mask::` so they do not appear in logs.

## 5. Supabase setup

- Uses `supabase/setup-cli@v1` with `version: latest`, then `supabase start` — the exact pattern the `database` job already runs successfully on `ubuntu-latest`.
- Local stack only. No `supabase link`, no hosted project ref, no production credentials anywhere in the file.
- **No `db reset`.** `supabase start` applies all migrations and the seed on first start; the guarded `scripts/db/reset.mjs` wrapper (which demands `KOLEKTO_CONFIRM_RESET=yes` and takes a backup) is never invoked.
- Mailpit comes up as part of the stack on port `54324`, matching `supabase/config.toml` `[local_smtp]` and the default in `tests/e2e/helpers/mailpit.ts`.

### Supabase key mapping (robustness)

The CLI's emitted variable names are **not assumed** to match the app's names. The job runs `supabase status -o env`, then extracts keys with fallbacks:

- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` ← `PUBLISHABLE_KEY` if present, else `ANON_KEY`.
- `SUPABASE_SERVICE_ROLE_KEY` ← `SERVICE_ROLE_KEY` if present, else `SECRET_KEY`.

If neither candidate is found for a key, the step **fails loudly** (prints the raw output and exits non-zero) rather than letting the app start with an empty key. This handles both older CLIs (which emit `ANON_KEY`/`SERVICE_ROLE_KEY`) and newer ones (which may emit publishable/secret names). The documented alternative — `supabase status -o env --override-name auth.anon_key=…` — was deliberately **not** used, because it couples the workflow to the CLI's internal config-key spelling; the parse-with-fallback approach degrades more gracefully. The locally installed CLI is 2.109.1; CI pins `latest`, which is why version-independent parsing matters.

## 6. Worker setup

- Built with the production path: `npm run build --workspace apps/worker` (esbuild → self-contained `apps/worker/dist/index.js`).
- Started with **plain Node**: `node apps/worker/dist/index.js` — no `tsx`, no source-level execution.
- Launched in the background with `nohup … &`, stdout/stderr to `worker.log`, and its PID written to `worker.pid` so it survives across workflow steps and can be terminated deterministically.
- Terminated in an `if: always()` step (`kill "$(cat worker.pid)"`), so a Playwright failure or timeout still cleans it up.
- Its only runtime requirement, `SUPABASE_DB_URL`, is supplied by the job `env`.
- Worker **source is unchanged.** For the existing (non-notification) suite the worker idles against an empty `notification_events` queue; it is present so the environment is complete and matches what the later notification spec will exercise.

## 7. Playwright setup

- Uses the repository's existing `playwright.config.ts` **unmodified** — it was already authored for this scenario (production web build via `webServer`, `workers: 1`, `fullyParallel: false`, `channel: "chromium"`, `baseURL http://127.0.0.1:3010`, `NEXT_DIST_DIR=.next-e2e`).
- The workflow does **not** duplicate the Next.js web server startup. Playwright's `webServer` block owns it: `npm run build --workspace apps/web && npm run start --workspace apps/web -- -p 3010`.
- Chromium and its Linux system libraries are installed with `npx playwright install --with-deps chromium` (the one genuinely Linux-specific step the local Windows setup never needed).
- The suite is invoked with `npm run test:e2e` (= `playwright test`).

**Known limitation (not changed):** the config's reporter is `[["list"]]`, so no `playwright-report/` HTML directory is produced by default; the diagnostic artifact in CI is `test-results/` (traces retained on failure via `trace: "retain-on-failure"`, plus any screenshots). The artifact-upload step requests both paths with `if-no-files-found: ignore`, so it succeeds whether or not an HTML report exists. Adding an HTML reporter would require editing `playwright.config.ts`, which is out of scope for this task; it is noted as an optional follow-up in §13.

## 8. Security / production isolation

- **No hosted/production Supabase project** is referenced. Grep over the workflow confirms no `*.supabase.co`/`.in` URL. Only `127.0.0.1` loopback addresses appear.
- **`packages/config/src/env.ts` enforces this at runtime too:** with `KOLEKTO_ENV=local`, `assertEnvironmentTarget` refuses any non-loopback URL, and the legacy project refs are refused in every environment. The workflow cannot connect anywhere but the ephemeral local stack inside the runner.
- **No secrets committed.** All sensitive values are either the Supabase CLI's disposable local demo keys (regenerated on every `supabase start`) or the per-run ephemeral session secret; none are written to the repository, and dynamic values are masked in logs.
- **No deploy.** Consistent with ADR 0007, the workflow still has no deploy job; `e2e` adds none.
- **No DB reset, no production access, no stash change.**

## 12. Whether the E2E job should be promoted to required

**Not yet — promote after the first green run.** The job is currently **non-required**: it is not listed in branch protection (required checks are a GitHub repository setting, not part of this workflow file), so it reports its true status (red on failure, visible on the PR) **without blocking merges**. This satisfies "do not hide failures" while acknowledging this is a brand-new, inherently flakier job class on a newly-targeted OS. `continue-on-error` was intentionally **not** used, because that would mark a failed job as successful and genuinely hide the result.

Recommendation: once the `e2e` job has run green at least once (ideally 2–3 consecutive green runs to confirm stability under the single-worker config), add `e2e` to the branch-protection required checks for `main`. Until then, leave it non-required.

## Verdict

**CI E2E ENVIRONMENT READY.**

The additive `ubuntu-latest` `e2e` job is implemented, YAML-valid, additive (the four existing jobs are unchanged), isolated to the local stack with no production/hosted credentials, runs the production worker under plain Node, lets Playwright own the production web build, installs Chromium with Linux deps, and cleans up and uploads artifacts even on failure.

**M13.1 is NOT closed.** The browser suite has not yet been executed in CI; closure depends on the first `e2e` run completing the onboarding-driven journeys green on Ubuntu. This task delivers the environment in which that run can finally happen — it does not by itself constitute the passing E2E that FINAL-2 requires.
