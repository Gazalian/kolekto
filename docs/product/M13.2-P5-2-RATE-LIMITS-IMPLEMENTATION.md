## What P5-2 does

Before a worker sends an email, the delivery must pass three rolling-window
rate limits and a per-community backlog cap — all checked atomically inside
the claim transaction using advisory locks that prevent concurrent bypass.

- `notification_send_attempts` (table): an append-only rate-limit ledger.
  One row per granted reservation, keyed by `address_key`
  (`lower(recipient_address)`) for case-insensitive counting. RLS
  enabled and forced, deny-all policy, no client role has any access
  (risk U7: short-lived PII surface). Rows purged after 48 hours.
- `app.notification_send_limits()`: returns the approved configuration as a
  single row — L1 (3/address/24 h), L2 (100/community/1 h), L3
  (1,000/platform/1 h), backlog cap (500), max attempts (3). Changed
  only by a reviewed migration.
- `app.reserve_email_attempt(delivery_id)`: the concurrency-safe
  reservation. Called inside the same transaction that claimed the delivery
  (P5-1). Takes advisory locks in a fixed order (address → community →
  platform) so concurrent workers cannot deadlock. Checks L1, L2, L3 and
  the per-community backlog cap. Returns one of:
    - **granted** — ledger row inserted, delivery stays `sending`.
    - **address_limited** — delivery `skipped` with `recipient_rate_limited`,
      address erased, attempt undone.
    - **community_deferred** — delivery returned to `pending` with
      `next_retry_at`, attempt undone. Covers both L2 and L3 breaches.
    - **backlog_full** — delivery `skipped` with `community_backlog_full`,
      address erased, attempt undone.
- `app.purge_stale_send_attempts()`: deletes ledger rows older than
  48 hours, using a session variable to bypass the append-only trigger.
  Called by the sender loop or a scheduled task.

## Transaction discipline

The claim-then-reserve pattern:

```
BEGIN → claim(delivery) → reserve(delivery) → COMMIT → [provider call if granted]
```

Both functions run inside one transaction. The claim's `FOR UPDATE` lock
on the delivery row and the reserve's advisory locks are all released when
the transaction commits. The provider call happens after commit, never
inside the transaction.

## Concurrency argument

- **Advisory lock ordering** (address, community, platform): two workers
  reserving for the same address acquire locks in the same order. No
  circular dependency is possible, so deadlock cannot occur.
- **Count-then-insert atomicity**: the advisory lock is held for the entire
  check-and-insert sequence. Worker 1 counts, inserts, commits, releases
  the lock. Worker 2 then acquires the lock and sees the committed row.
  Two workers cannot both see "2 of 3 used" and both proceed.
- **Hash collisions**: two unrelated addresses may hash to the same lock
  tag. This only serialises; it cannot let either through, because the
  count query uses the actual address text, not the hash.
- **Rollback safety**: if the transaction rolls back, the advisory lock is
  released and the ledger row is not committed. The delivery returns to
  `pending` with attempt_count unchanged.

## Attempt-count invariant

The claim function increments `attempt_count` by 1. For non-granted
outcomes, the reserve function decrements it back: a deferral or a
rate-limit skip never consumes an attempt. The net effect:

| Outcome             | attempt_count change | Ledger row |
|---------------------|---------------------|------------|
| granted             | +1 (from claim)      | Yes        |
| address_limited     | 0 (claim +1, reserve −1) | No    |
| community_deferred  | 0 (claim +1, reserve −1) | No    |
| backlog_full        | 0 (claim +1, reserve −1) | No    |

## What P5-2 deliberately does not do

- No sender loop, no provider call, no tick. The reserve function is
  called by the sender (a later phase) inside the claim transaction.
- No pause switch, heartbeat, or health monitoring view. The monitoring
  view (`private.v_notification_send_health`) is deferred to the sender
  milestone that owns the heartbeat column.
- No 72-hour expiry housekeeping. Deferred deliveries live at most 72
  hours and then become dead with `event_too_old`, handled by the sender's
  expiry loop (a later phase).
- No held-queue interaction.
- No financial, payment, withdrawal, settlement, refund, authentication
  or consent changes. Production sending remains structurally disabled
  (no real provider exists).

## Known issue (outside P5-2 scope)

P5-1's `resolve_notification_claim` for the `sent` outcome does not clear
`error_code`/`error_message`. A delivery that was previously retried with
an error code and then succeeded on a later attempt would violate the
`notification_deliveries_sent_has_no_error` constraint. This is a P5-1
latent issue and should be fixed in the resolve function, not in P5-2.
