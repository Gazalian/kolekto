## 1. Bugs fixed

| ID | Severity | Fix | Verified |
|----|----------|-----|----------|
| **BUG-1** | Blocker | Enqueue trigger and worker now key off the audit actions the domain actually writes: `collection.publish`, `member.approve_join`, `member.join_via_invite` (were `member.approve`, `invite_link.redeem`). Domain actions were **not** renamed. | pgTAP 16–19 + live replica |
| **BUG-2** | Blocker | The personal bell no longer relies on RLS alone. A shared provider queries deliveries scoped explicitly to `recipient_user_id = <signed-in user>` (and `channel='in_app'`). The officer RLS policy is unchanged, left for a future officer-history view. | pgTAP 20–22 (RLS isolation) + code |
| **BUG-3** | Should-fix | Delivery dedup index now keys on `coalesce(recipient_member_id, recipient_user_id, 0)`, so distinct in-app recipients (e.g. several officers with NULL member_id) each get a delivery while a true duplicate is still blocked. Worker `ON CONFLICT` matches. | pgTAP 23–24 + live replica |
| **BUG-4** | Should-fix | `processNotificationMessage` runs the event insert + all delivery inserts inside one `sql.begin()` transaction and is resumable: on a replayed message it reads the existing event id instead of returning early, so missing deliveries are completed and none are duplicated. | live replica (PASS 1 = 2, replay = 2) |
| **BUG-5** | Should-fix | `member.join_via_invite` recipients resolved by the existing `invite.approve` permission (held by admin/owner/treasurer — the membership gatekeepers). No new permission invented. Decision documented in `notification-processor.ts`. | live replica (owner+treasurer, not collector) |
| **BUG-6** | Blocker (red test) | `31_notification_foundation.sql` rewritten: `plan(24)`, runs to completion, behavioural not just structural. The invalid `row_security_active(schema,table)` call (absent in this pgTAP build) replaced with a `pg_class.relrowsecurity/relforcerowsecurity` catalog check; `throws_ok` switched to the 4-arg form. | `db:test` → 24/24 |
| **BUG-7** | Low | Polished empty state ("You're all caught up" + bell icon + subtext). | build + code |
| **BUG-8** | Low | Unread count is a dedicated `count: exact, head: true` query on `read_at is null`, not a slice of the first 30. | build + code |
| **BUG-9** | Low | A single `NotificationProvider` holds one 15s poll; both the desktop and mobile bells consume it, so only one interval runs regardless of how many bells are mounted. | build + code |

**Not changed (by design / accepted, per the QA report):**
- **NOTE-A** — notification copy still omits amount/due-date (money is Phase-4 gated).
- **NOTE-B** — the enqueue trigger remains coupled to the domain transaction (transactional-outbox; a `pgmq.send` failure would roll back the domain action). Low-probability; left as-is for M13.1.
- No dead-letter queue — a permanently failing message still retries on the pgmq visibility timeout (acceptable per "no complex retry in M13.1").
- The officer-wide SELECT policy on `notification_deliveries` is intentionally retained for a future officer notification-history surface; the personal bell no longer depends on it.

## 6. Live behavioural test results

- `member.approve_join` → **1** delivery to the approved member. ✅
- `app.mark_notification_read` by the recipient → `read_at` set. ✅; by a different user → refused. ✅
