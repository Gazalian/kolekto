## 1. Design decision (from the actual lifecycle)

The sender's only database work before a provider call is one transaction:

```
BEGIN → app.claim_next_notification_delivery   (FOR UPDATE SKIP LOCKED; pending → sending; lease; attempt+1)
      → app.reserve_email_attempt              (suppression, L1–L5, ledger row)
COMMIT → provider.send (no transaction, no lock) → app.resolve_notification_claim
```

So the recheck lives **inside `app.reserve_email_attempt`, first**, while the claim transaction holds
the row lock:

- **Ineligible** → the row is settled `skipped` with a stable code, address erased, attempt undone, lease
  cleared, no ledger row; reservation `ineligible`. Existing workers already treat any unknown
  non-granted reservation as a terminal skip, so this is safe with the current worker too.
- **Withdrawal race.** The recheck takes **shared** advisory locks on the keys the opt-out writer and the
  attestation writers take **exclusively**, then reads (VOLATILE, READ COMMITTED: fresh snapshot after
  the locks). A withdrawal committing concurrently is either seen or waits for the claim to commit.
  **Residual window:** a withdrawal committed after the claim commits and before the provider accepts
  (one provider call) cannot stop that one message.
- **Deferrals.** A bulk row deferred by L2–L5 returns to `pending` and is rechecked on every later claim,
  so withdrawals during the up-to-72-hour deferral are honoured.
- **Duplicates and concurrency** are unchanged and still enforced by the existing mechanisms: `SKIP LOCKED`
  claims, lease tokens on settle, lease recovery by provider idempotency, the per-event/member/channel
  unique index, and `skipped` being terminal (never re-claimable — tested).
- **No new grant.** `CREATE OR REPLACE` keeps the function's identity; the least-privilege worker role
  still holds EXECUTE (verified on the isolated stack). The recheck itself is callable by no client role
  and by no worker role; only the definer path runs it.
- **Fail closed in the worker.** If the database has no `app.recheck_delivery_eligibility(uuid)` (an
  environment without R3), the worker refuses to send any non-essential or unclassified row:
  `dead / eligibility_unverifiable`, no provider call. Essential mail is unaffected. Invariant: the
  recheck function and the new reserve body ship in one migration (pgTAP asserts the reserve calls it).

## 2. N-AUD dependency (assessed before implementing)

R3 does **not** need N-AUD first, and does not entrench the payment audience:

- The recheck is keyed by **delivery → member, community, category, channel, event object**. It never
  asks whether the member is in the collection's (payment) audience. N-AUD can replace fan-out
  (`app.evaluate_collection_email_recipients`) with a request-scoped resolver without touching it.
- Category comes from the event type (`app.communication_category_for_event`) or the stored
  `communication_category`; a new N-AUD event type (e.g. a general community announcement) needs one row
  in that map and one in the worker policy — the parity test fails until both agree.
- Reachability is checked only for `object_type = 'collection'` events.

Deliberate consequence: a member removed from a group after an announcement was queued still receives
it (they were chosen when it was sent), unless they are archived/merged, opted out, or the notice is
revoked. Organiser "unsend" is not provided.
