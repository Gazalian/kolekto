# M13.1 — Notification Foundation: Post-Implementation QA Report

**Date:** 2026-10-07
**Branch:** `m13.1-notification-foundation`
**Reviewer:** Independent QA / code-review pass (implementation report not trusted; verified directly)
**Scope:** M13.1 only. No M13.2 work; no email/WhatsApp/SMS; no payments/Paystack/withdrawals; no legacy migration; no password reset. Unrelated issues documented, not fixed.

---

## 1. Executive Summary

### Verdict: **NOT READY**

The notification *foundation* — schema, enums, RLS, append-only enforcement, idempotency, the pgmq queue, the audit-log→queue trigger, and the worker loop — is well-designed and, where it fires, works correctly. Those parts were verified live.

However, the feature does **not deliver its stated behavior**. Two of the three advertised event types can never fire, and the notification bell leaks other members' notifications to officers. Concretely:

- **BLOCKER 1 — Two of three event types are dead on arrival.** The queue trigger filters audit-log rows on actions `member.approve` and `invite_link.redeem`. The domain code never writes those actions; it writes `member.approve_join` and `member.join_via_invite`. Only `collection.publish` matches a real domain action. Result: the "New member joined" (host) and "You're in" (approved member) notifications are never created. These are explicit product requirements.
- **BLOCKER 2 — The bell shows officers everyone's notifications.** The bell query scopes results by RLS alone and does not filter on `recipient_user_id`. The officer SELECT policy returns the whole community's deliveries, so any officer's personal bell displays — and counts as unread — every member's in-app notifications. Verified live.
- **RED TEST — The delivered pgTAP suite for this feature does not run.** `supabase/tests/31_notification_foundation.sql` errors on a wrong `row_security_active(...)` call signature and aborts after 11 of 30 planned assertions ("Bad plan"). CI would be red.

Plus several correctness bugs (multi-officer delivery collapse, a non-existent permission in recipient resolution, non-atomic worker processing). Details in §13.

**This is a solid foundation with a broken last mile. It should not be marked CLOSED.** The single working path (`collection.publish`) is correct end-to-end; the remainder needs the fixes in §13 and a re-test.

## 3. Queue QA

- `select pgmq.create('notification_events')` creates the queue. ✅
- Enqueue is transactional: the trigger calls `pgmq.send` inside the same transaction as the audit-log INSERT, so a message only becomes visible when the domain transaction commits (a transactional-outbox property — good).
- **Architecture risk (note):** because the trigger is `AFTER INSERT` and `SECURITY DEFINER`, a failure inside `pgmq.send` would roll back the domain action itself (e.g., publishing a collection). `pgmq.send` is in-database and reliable, so this is low-probability, but the coupling is worth documenting.

**Verified live** (transaction, rolled back): inserting an `audit_logs` row with action `collection.publish` produced exactly **1** queue message; a non-listed action (`member.edit`) produced **0**.

## 4. Worker QA

Files: `apps/worker/src/index.ts`, `apps/worker/src/notification-processor.ts`.

- Loop reads a batch (10) with a 30s visibility timeout, processes each message, deletes **only on success**, sleeps when idle. ✅
- Failure behavior is correct: on a processing exception the message is **not** deleted, so pgmq redelivers after the visibility timeout. No complex retry system (as required). ✅
- Compiles: `tsc --build` builds `apps/worker` with no errors. ✅

**Defects:** see §13 BUG-4 (processing is not atomic / not fully idempotent on a mid-processing crash) and BUG-5 (recipient resolution keyed on action strings and a permission that do not exist).

No dead-letter / poison-message handling — a permanently failing message retries forever every ~30s. Acceptable for M13.1, noted for M13.2.

## 5. Event QA

The trigger enqueues for exactly three actions: `collection.publish`, `member.approve`, `invite_link.redeem`.

Cross-checked against the audit actions the domain actually emits:

| Trigger listens for | Domain actually writes | Fires? |
|---|---|---|
| `collection.publish` | `collection.publish` (collection transition fn) | ✅ yes |
| `member.approve` | `member.approve_join` | ❌ **never** |
| `invite_link.redeem` | `member.join_via_invite` | ❌ **never** |

Evidence (exact quoted-string search across `supabase/migrations/`): `'member.approve'` and `'invite_link.redeem'` appear **only** in the notification migration itself; the join/approval domain functions write `'member.approve_join'` and `'member.join_via_invite'`. This is **BLOCKER 1** (§13 BUG-1).

The `collection.publish` path is correct: the domain writes `object_type='collection'`, `object_id=<collection id>`, which the worker uses to resolve the audience. Append-only format checks (`^[a-z_]+\.[a-z_]+$`) accept all three names.

## 6. Audience QA

Recipient resolution reads the existing `app.resolve_collection_audience(collection_id)` (verified in `20260920150000_collection_audience.sql`), which already handles:

- `all_members` → every active/unclaimed/invited member ✅
- `selected_members` → members with an obligation on the collection ✅
- `groups` → members of the collection's audience groups ✅
- `public` → nobody (by design) ✅

The worker then joins `members` and filters `user_id is not null`, so **unclaimed members correctly receive no in-app notification** (step 9, Member C). Steps 9–11 (all-members / selected / groups targeting) are therefore correct **for `collection.publish`**, which is the one event type that fires.

Member-join audiences (steps 12 B/C) cannot be assessed as working because those events never fire (BLOCKER 1). Even if the action strings were corrected:

- `member.approve_join` → `resolveMemberSelf` (notifies the approved member) would work.
- `member.join_via_invite` → `resolveOfficersWithPermission(…, 'member.manage')` would still resolve **zero** recipients (§13 BUG-5), and multiple officers would collapse to one (§13 BUG-3).

Scenario A (host directly adds a member) is not wired to any event — this may be intentional; the absent M13 audit doc (see §15) would have been the authority.

## 9. Security / RLS QA

RLS is `enable`d and `force`d on all three tables. Policies verified live (transaction, rolled back):

- **Plain member isolation works.** A non-officer recipient sees only their own in-app delivery (1) and cannot see other users' (0). ✅
- **Anonymous is denied.** `anon` has no grant/policy → permission denied. ✅
- **Append-only works.** `UPDATE` and `DELETE` on `notification_events` both raise `NOTIFICATION_EVENT_IS_APPEND_ONLY`; privileges are revoked from `authenticated`/`anon`. ✅
- **`mark_notification_read`** enforces recipient ownership (`recipient_user_id = auth.uid()`, in-app only). Code path reviewed; a user cannot mark another user's notification read. ✅
- **SECURITY DEFINER hygiene:** all functions set `search_path = ''` and schema-qualify their references; execute is revoked from `public` and granted narrowly. ✅
- **Grants:** `authenticated` gets SELECT on exactly the three new tables (matches the updated grant-matrix test); writes go through SECURITY DEFINER functions. ✅

**Finding — officer over-exposure (BLOCKER 2 / BUG-2):** the `notification_deliveries_select_officer` policy returns *all* of a community's deliveries to any active officer. That is reasonable for a future officer "notification history" view, but the personal **bell** relies on RLS alone and does not add `recipient_user_id = <me>`. Verified live: officer `…001` saw **all 3** deliveries, including ones addressed to other users. Within-community leakage of other members' notification content and inflated unread counts.

No PII/tenant leakage across communities was found. Payloads carry only the subject community's data. No provider credentials anywhere.

## 10. Idempotency QA

Verified live (transaction, rolled back):

- Re-inserting the same `event_key` with `ON CONFLICT (event_key) DO NOTHING` → **1** row (dedupes). ✅
- A plain duplicate insert (no `ON CONFLICT`) → `unique_violation`. This confirms the worker's `ON CONFLICT` clause is **mandatory**; it is present in `notification-processor.ts`. ✅
- Delivery dedup: a second delivery for the same `(event, member, channel)` is dropped. ✅ — **but** when `recipient_member_id` is NULL (the officer case), distinct officers collapse to one row (§13 BUG-3).

**Gap:** idempotency holds for *message redelivery* but not for a *mid-processing crash* — see §13 BUG-4.

## 13. Issues Found

### BUG-1 — Two of three event types never fire (BLOCKER)
- **Severity:** High (blocker)
- **Problem:** The enqueue trigger filters on audit actions `member.approve` and `invite_link.redeem`, which the domain never writes. The real actions are `member.approve_join` and `member.join_via_invite`.
- **Evidence:** `20261007100000_notification_foundation.sql:346-350` (IN-list); exact-string search shows `'member.approve'` and `'invite_link.redeem'` appear only in the notification migration, while `'member.approve_join'` (`20260918140100`) and `'member.join_via_invite'` (`20260918140100`, `20260920120100`, `20260920140000`) are what the domain emits. The worker's `resolveRecipients`/`buildPayload` switch on the same wrong strings (`notification-processor.ts:92-101,154-196`).
- **Impact:** "New member joined" (host) and "You're in" (approved member) notifications are never created. Core product requirements unmet.
- **Recommendation:** Change the trigger IN-list and the worker's `switch`/`buildPayload` keys to `member.approve_join` and `member.join_via_invite`. Add a behavioral pgTAP test that inserts a real domain audit row and asserts a queue message appears.

### BUG-2 — Notification bell leaks other members' notifications to officers (BLOCKER)
- **Severity:** High (blocker)
- **Problem:** The bell query filters only by `channel='in_app'` and relies on RLS to scope to the user. The officer SELECT policy returns the whole community's deliveries, so any officer's bell shows and counts every member's notifications.
- **Evidence:** `NotificationBell.tsx:32-42` (no `recipient_user_id` filter) + migration `229-236` (officer policy, no channel/recipient restriction). Verified live: officer saw all 3 deliveries (§12).
- **Impact:** Within-community privacy leak (member names, approval notices) and wrong unread counts/items for every officer.
- **Recommendation:** Add `.eq("recipient_user_id", <session user id>)` to the bell query. Keep the officer policy for a separate, explicit officer "notification history" view — do not let the personal inbox depend on it.

### BUG-3 — Multi-officer in-app deliveries collapse to one
- **Severity:** Medium
- **Problem:** The delivery dedup unique index keys on `coalesce(recipient_member_id, zero-uuid), channel`. Officer deliveries (`invite_link.redeem` path) set `recipient_member_id = NULL`, so with ≥2 officers only the first delivery survives; the rest are silently dropped by `ON CONFLICT DO NOTHING`.
- **Evidence:** migration `120-125` + `notification-processor.ts:134` (`null as member_id`). Verified live: 2 distinct officers → 1 delivery (§12).
- **Impact:** Even after BUG-1/BUG-5 are fixed, only one officer would be notified of a new member.
- **Recommendation:** Include the user in the dedup key (e.g., `coalesce(recipient_member_id, recipient_user_id)` or a dedicated expression), since in-app recipients are identified by user.

### BUG-4 — Worker processing is not atomic / not idempotent on mid-processing crash
- **Severity:** Medium
- **Problem:** `processNotificationMessage` is not wrapped in a transaction and early-returns on event `ON CONFLICT` (`if (!event) return;`). If the worker crashes after the event insert but before all deliveries are written, redelivery sees the event already exists and returns **before** re-resolving recipients, leaving deliveries permanently incomplete.
- **Evidence:** `notification-processor.ts:37-56`; `index.ts:44-51` (no transaction around process+delete).
- **Impact:** Lost deliveries on an ill-timed crash; not caught by any test.
- **Recommendation:** Wrap event insert + delivery inserts in a single `sql.begin()` transaction; do not short-circuit recipient creation on event conflict (or re-run resolution regardless and rely on the delivery `ON CONFLICT`).

### BUG-5 — Recipient resolution uses a non-existent permission
- **Severity:** Medium
- **Problem:** `resolveOfficersWithPermission(communityId, "member.manage")` joins `role_permissions WHERE permission='member.manage'`. No such permission exists.
- **Evidence:** `notification-processor.ts:98`; permission catalog contains `member.create/edit/archive/export/view_contact` and `invite.approve` — not `member.manage`. Live query returned zero rows for `member.manage`.
- **Impact:** Even with BUG-1 fixed, the host "new member joined" notification resolves to zero recipients.
- **Recommendation:** Decide the intended audience (e.g., holders of `invite.approve`, or `member.create`/`member.edit`) and use an existing permission; add a test asserting at least one recipient for a seeded officer.

### BUG-6 — The feature's pgTAP test does not run
- **Severity:** Medium (blocks a green CI; hides the lack of behavioral coverage)
- **Problem:** `31_notification_foundation.sql` calls `row_security_active('public.notification_events', '<desc>')` — a signature that does not exist — so the file errors at line 61 and aborts after 11/30 planned assertions ("Bad plan").
- **Evidence:** `npm run db:test` output (§11).
- **Recommendation:** Use `ok(row_security_active('public','notification_events'), '<desc>')` (schema + table form). Then add behavioral tests: isolation, append-only block, idempotency dedupe, and enqueue-on-audit — the current file only checks existence.

### BUG-7 — Empty state is not the polished "caught up" state
- **Severity:** Low
- **Problem:** Panel shows a plain "No notifications yet" rather than the spec's icon + "You're all caught up" copy.
- **Evidence:** `NotificationPanel.tsx:70-71`.
- **Recommendation:** Match the spec empty state; functional regardless.

### BUG-8 — Unread count is approximate
- **Severity:** Low
- **Problem:** Unread count is computed from the fetched 30 rows (`limit(30)`), so it undercounts when a user has >30 unread; the query orders by `created_at` only, not unread-first (despite the `read_at nulls first` inbox index).
- **Evidence:** `NotificationBell.tsx:30,38-39`.
- **Recommendation:** Fetch the unread count separately (`head:true count` on `read_at is null`), or raise the limit and order unread-first.

### BUG-9 — Two bell instances poll simultaneously
- **Severity:** Low
- **Problem:** Sidebar and mobile-header bells are both always mounted (CSS-hidden per breakpoint), so two 15s polling intervals run at once (2× requests). No duplicate *visible* controls.
- **Evidence:** `AppShell.tsx` (bell in both the `sm:flex` sidebar and the `sm:hidden` header).
- **Recommendation:** Render a single bell, or gate polling to the visible instance.

### NOTE-A — Notification content is thinner than the spec examples
Collection copy is "X is now live" without amount/due-date. Money is Phase-4-gated, so this is acceptable for now; revisit when money fields are available.

### NOTE-B — Enqueue trigger is coupled to the domain transaction
A `pgmq.send` failure would roll back the domain action (see §3). Low-probability; document and monitor.

## 14. Final Closure Decision

**M13.1 is NOT READY. Do not mark CLOSED.**

Blockers:
1. **BUG-1** — `member.approve` / `invite_link.redeem` trigger filters don't match the domain's actual audit actions; 2 of 3 event types never fire.
2. **BUG-2** — the bell leaks other members' notifications to officers (missing `recipient_user_id` filter).
3. **BUG-6** — the delivered pgTAP suite for the feature errors out; CI is red and behavior is untested.

Should-fix before closing: **BUG-3** (multi-officer collapse), **BUG-4** (non-atomic worker), **BUG-5** (non-existent permission). Minors (BUG-7/8/9, NOTE-A/B) can follow.

What is genuinely done and verified: schema and enums; append-only enforcement; event and delivery idempotency; plain-member RLS isolation and anon denial; SECURITY DEFINER hygiene and grants; the audit→pgmq enqueue mechanism; the worker loop's delete-on-success / retry-on-failure behavior; and the `collection.publish` path end-to-end. No external channels are wired (step 21 satisfied). The architecture is sound; the wiring to real domain events and the inbox scoping are what fail.

**Recommended path:** fix BUG-1, -2, -6 (and ideally -3, -4, -5), add behavioral tests, re-run `typecheck` + `db:test` + a live worker publish/join/approve walkthrough, then re-assess for **CLOSED**.
