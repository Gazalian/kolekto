# M13.2 P9-5 — D-WORKER deployment plan (design)

**Status.** Design only. No code, no migration, no runbook action, no AWS
resource, no change to the pause switch. This document is the "written" half
of the D-WORKER release gate called out in
`docs/product/M13.2-EMAIL-NOTIFICATIONS-DECISION-RECORD.md` §11.2 and §17,
and in the P9-4 design doc §3.9 (gate 5). A separate operator-platform
follow-up slice adds the chosen deployment artefact (Dockerfile, systemd
unit, container manifest, or whatever the operator picks) once the platform
has been chosen; nothing here picks one for them.

**Scope.** Make the deployment contract for `apps/worker` explicit, so the
process model, environment surface, startup order, graceful shutdown,
restart policy, crash recovery, log shape, health-probe requirements and the
operator alert thresholds are written down in one place that an operator and
a reviewer can read side by side with the code.

**Explicitly out of scope for this slice.** No decision between container
platforms, no `Dockerfile`, no `Procfile`, no `fly.toml`, no systemd unit,
no helm chart. No new runtime code. No migration. No change to the SES
adapter. No change to the pause switch, the quota numbers, or any
`.env.example` entry. No touch to `apps/web`, `packages/db`,
`packages/domain`, or anything matching `*ledger*`, `*fee*`, `*withdrawal*`,
`*payment*`, `*settlement*`, `*refund*`, or `*auth*`.

- P9-1 through P9-4 merged on `origin/main` (recipient suppression, SES/SNS
  ingestion + hardening, L4/L5 quota controls, SES sending adapter with

## 2. Current-state findings (read from the live tree)

### 2.1 The worker as it stands today

- One Node 22 process (`"engines": { "node": ">=22.6.0" }` at the repo root,
  `--target=node22` in the worker's esbuild config).
- Entrypoint: `apps/worker/dist/index.js` (bundled from
  `apps/worker/src/index.ts` by `npm run build --workspace apps/worker`).
- One `while (running)` loop that interleaves two stages:
  1. **Event stage.** Polls `pgmq.read('notification_events', 30, 10)`, calls
     `processNotificationMessage(sql, msg.message)` for each row, deletes
     the message. Driven by in-app notification creation (M13.1) and
     eligibility (P4) which may queue email delivery rows.
  2. **Send stage.** `runSenderTick(sql, …)` claims up to `SENDER_BATCH=20`
     due pending email deliveries, calls the provider, settles each. Once
     per minute (`SENDER_MAINTENANCE_MS = 60_000`) it also runs the
     maintenance block: `recoverExpiredLeases` (routed by
     `provider.idempotency`, §10.6.4), `expireStaleDeliveries` (72-hour
     age-out), `purgeStaleSendAttempts` (L4/L5 ledger purge), and the
     per-minute health log line.
- Polling cadence: `POLL_INTERVAL_MS = 2_000` ms when the event queue is
  empty.
- Signals: `SIGINT` and `SIGTERM` flip `running = false`. The current
  iteration completes (including any in-flight send), the Postgres pool
  closes via `sql.end()`, and the process exits 0.
- Fatal errors in `main()` log and exit 1 (`main().catch(err => { … })`).

### 2.2 The sender tick is already crash-safe (what the deployment plan must preserve)

- **Transaction discipline** (`notification-sender.ts` §10 preamble): the
  claim and the rate-limit reservation commit before any provider call;
  the provider call runs with no row lock open; the outcome is recorded
  in a second short transaction. A process killed between a successful
  provider call and the outcome-recording commit leaves a `sending` row
  with an expired lease, which the next maintenance tick routes via
  `provider.idempotency`:
  - idempotent provider → `app.recover_expired_notification_lease` →
    `pending` (replay uses the same idempotency key, provider dedupes).
  - **SES / non-idempotent provider** → `app.resolve_lease_ambiguous` →
    `dead/outcome_unknown` (never silently retried, per Q-DUP and
    §10.6.4).
- **Pause switch.** `app.email_sending_enabled()` is checked each tick
  (`isEmailSendingEnabled`). When false the sender claims nothing while
  maintenance still runs; queued rows age out at 72 h and nothing is lost.
- **Startup refusals.** `loadEmailSender()` wraps provider construction in
  a try/catch; a startup refusal (SES `GetAccount` sandbox mismatch, L4/L5
  above provider quotas, missing config) produces `provider = null` and
  the event stage still runs. The worker never crashes because of email
  configuration.
- **Halt mid-run.** If the adapter signals `adapter_misconfigured` while
  running, `runSenderTick` returns `halted = true`; the worker sets
  `senderHalted = true` and keeps running maintenance, but makes no more
  provider calls this process. A restart is the recovery.

### 2.3 Observability already in the code

- One structured JSON log line per minute, built by `healthLogLine` in
  `apps/worker/src/notification-sender.ts`. Fields are ids, counts, codes
  and ISO timestamps only — no address, name, free text or error body.
  Includes the P9-3 `l4_last_24h_by_class` / `l4_utilisation_pct_by_class`
  / `l5_last_second_by_class` / `l5_utilisation_pct_by_class` fields, and
  the P9-4 `resolved_ambiguous_this_tick`.
- `app.notification_send_health()` is the single source for every field in
  that log line and in the staff-only view
  `private.v_notification_send_health`.
- `last_heartbeat_at` is stamped each tick (claimed or idle, so a quiet
  queue still looks alive), `last_claim_at` only on a tick that actually
  claimed something.

## 3. Proposed design

### 3.1 Process model

**Long-running, single instance per environment**, consuming the pgmq queue
over a direct Postgres connection. The decision is already made by ADR 0005
("Background work runs in `apps/worker`") and by the lease/heartbeat model
in migration `20261019140000`; this slice names the consequences explicitly.

- **One process at a time.** The L4 (per-class daily) and L5 (per-class
  per-second) counts in `app.reserve_email_attempt` are global per
  database (not per worker), so a second concurrent worker would not
  violate the quotas, but the §10.6.1 heartbeat alert ("heartbeat older
  than 5 minutes while backlog is non-zero") assumes one owner of the
  heartbeat. Two workers would both stamp the single
  `notification_sender_state` row, hiding a dead peer. The design keeps
  one instance per environment and documents that a second instance is a
  deliberate operator action (e.g. a safe hand-off during a rolling
  deploy), not an unplanned horizontal scale.
- **Long-running, not a cron.** A 60-second cron would miss the pgmq
  visibility-timeout semantics (30 s), run the maintenance block too
  rarely for the heartbeat alert, and never produce the per-minute health
  log line. The P9-4 release gate 5 explicitly asks for "long-running
  process, not a short cron"; this design confirms it.
- **Where it runs**: on a Node 22 runtime that the operator chooses.
  The design does **not** pick a platform (container platform, VM,
  managed worker service). The runbook lists the trade-offs so the
  operator can pick without this doc making the choice for them. The
  operator-chosen platform ships in a follow-up slice.

### 3.2 Startup order

1. Read env; call `loadConfig()` (fails fast on any missing or wrong
   `KOLEKTO_*`/`NEXT_PUBLIC_SUPABASE_*` var; refuses legacy project refs;
   refuses local pointed at a hosted project and vice versa).
2. Open the Postgres pool via `postgres(loadDatabaseUrl(), { prepare:
   false, transform: { undefined: null } })`. One connection pool, held
   open for the life of the process.
3. Log the connection line (`"Kolekto worker: connected. Polling
   notification_events queue."`).
4. Call `loadEmailSender(sql)` — this is where the SES adapter's
   `GetAccount` guard runs (see P9-4 §3.3). A startup refusal logs the
   reason and returns `null`; the worker then runs only the event stage.
   The pause switch is **not** checked here — the switch is checked each
   tick inside `runSenderTick`, so flipping it on without a restart takes
   effect at the next tick.
5. Install `SIGINT` / `SIGTERM` handlers that set `running = false`.
6. Enter the loop.

**No step above opens a network listener.** The worker has no HTTP
surface today. Section 3.7 discusses whether to add one.

### 3.3 Graceful shutdown

- `SIGTERM` (the orchestrator's normal stop signal) and `SIGINT` (operator
  Ctrl-C) both flip `running = false`. The current loop iteration
  completes:
  - a pgmq message already being processed finishes;
  - a send already in-flight runs to its outcome (claim is already
    committed; the provider call runs with no row lock open; the outcome
    is recorded in a second short transaction).
- After the iteration, the loop exits, `await sql.end()` drains the pool,
  and the process exits 0.
- **Drain window.** The worst-case iteration today is one SES send plus
  one settle statement. Bounded by `EMAIL_SES_SEND_TIMEOUT_MS` (default
  10 s, max 60 s), plus a few hundred milliseconds of settle. Add a
  margin for the pgmq message loop (up to one `VISIBILITY_TIMEOUT_S = 30`
  if a message had just been read but not processed). A drain budget of
  **≤ 90 s** fits every documented case.
- **Hard-kill upper bound.** The orchestrator may send `SIGKILL` after
  the drain budget. The ambiguous-lease recovery path (P9-4) is designed
  for exactly this: a `sending` row whose lease expires lands as
  `dead/outcome_unknown` on the next maintenance tick, surfaced to the
  operator rather than silently retried. No work is lost; at worst one
  row needs operator review.
- **Non-goal.** No "drain forever" mode. If the shutdown would exceed
  the budget, the hard-kill path is the recovery, by design.

### 3.4 Restart policy

- **Normal exit (0).** Shutdown was intentional (operator stop, deploy
  swap). Do not restart automatically.
- **Fatal exit (1).** `main().catch` logged the error. The orchestrator
  restarts with an exponential backoff starting at ~2 s, capped at ~5 min.
  The database is the source of truth; a short gap means a slightly older
  heartbeat and no lost work.
- **Crash loop.** Three fatal exits in five minutes is a crash loop. The
  orchestrator pages on-call; the worker stays stopped until an operator
  intervenes.
- **Deploy strategy.** Stop-then-start (brief downtime) is acceptable
  because the queue absorbs the gap and the 72-hour row life makes
  minutes of pause invisible. Blue/green with a second running instance
  is possible but trades downtime for the single-instance invariant
  (§3.1); when the operator wants it, the hand-off is: start the new
  instance, confirm it logs a `notification_send_health` line, stop the
  old instance, and watch `l4_last_24h_by_class` + `last_heartbeat_at`
  on the next tick.

### 3.5 Crash recovery (what each failure mode leaves behind, and how it heals)

| Failure | Row state when the worker dies | Who heals it | Guarantee |
|---|---|---|---|
| Process killed between claim and send | Row is `sending` with a lease (5 min, `SEND_LEASE_SECONDS`); no provider call made | Next tick's `recoverExpiredLeases` with `provider.idempotency = "provider"` → `pending`; with `"none"` (SES) → `dead/outcome_unknown` | No row lost; no silent duplicate against SES |
| Process killed between provider accept and settle | Same row state (`sending`, lease still ticking) | Same path | Idempotent provider dedupes on replay; non-idempotent (SES) surfaces as `outcome_unknown` for operator review |
| Postgres connection dropped mid-tick | The current loop iteration throws; `main().catch` or the inner `try/catch` logs; the loop keeps going on the next tick | Database re-check under row lock when the pool reconnects | No row lost |
| SES raises an unexpected 5xx | `classifyFailure` produces `provider_unreachable` with `ambiguous=true`; non-idempotent → `dead/outcome_unknown` | Nothing — the row is terminal with a stable code | Operator reviews |
| SES adapter `GetAccount` refusal at startup | `provider = null`; event stage still runs | Operator restarts after fixing the mismatch | No sends until operator acts |
| Pause switch flipped off during a tick | The pause check runs each iteration; next iteration claims nothing. In-flight send completes normally. | Nothing — the sender just stops claiming | Deliveries wait and age out at 72 h |
| Second worker started by mistake | Both stamp the heartbeat; one may win a claim another expected | Operator stops one. The database SKIP LOCKED + per-row lease still prevents double-claim; the risk is diluted heartbeat signal | Explicit §3.1 single-instance invariant |

### 3.6 Health probing

**Today the worker emits one `notification_send_health` JSON log line per
minute** (`healthLogLine` in `apps/worker/src/notification-sender.ts`). That
line is sufficient for an operator-side "liveness" check wired to log
collection: a missing line for 2 × SENDER_MAINTENANCE_MS (i.e. 2 min) means
the process is wedged or dead.

**Open question for operator decision**: whether an HTTP `/healthz` /
`/readyz` surface is required by the chosen platform.

- Platforms that only need "process is up" (systemd, long-running VM
  processes, Fly machines with `kill_signal=SIGTERM`) can rely on log
  liveness plus the process-exit-code check.
- Platforms that require an HTTP probe (Kubernetes-style liveness and
  readiness probes, Cloud Run's HTTP health check) need a small HTTP
  surface:
  - `/healthz` — 200 iff the Postgres pool reports open and the last tick
    completed within the last 2 minutes.
  - `/readyz` — 200 iff `/healthz` passes **and** either `provider` is
    null (event-stage-only mode) or `provider` is configured and the
    pause switch is being read successfully.
  - No request body is accepted; both endpoints are GET, no auth needed
    at a reverse proxy that is itself on a private network.

**Design position.** Do not add an HTTP surface in this slice. If the
operator picks a platform that needs one, add it as a small follow-up PR
whose only new code is an `http.createServer` wired to the already-existing
`SendHealth` object. The port is set via a new optional env var
`WORKER_HEALTH_PORT`; when unset the HTTP surface is not opened.

### 3.7 Log collection

- The worker emits structured JSON on `stdout` (`console.log(JSON.stringify(line))`)
  and plain text on `stderr` (`console.error`).
- Operator policy, named in the runbook (not here): where those streams
  are shipped, how long they are retained, who can read them.
- The code already asserts no PII in the health line; the runbook asserts
  the same policy for any `console.error` lines (which carry provider
  error codes but never message bodies or recipient addresses, by
  construction).
- Baseline retention target: 30 days. A shorter retention still works for
  operations but defeats trend charts; a longer retention needs a privacy
  review because the delivery-id tag + a correlating SES event could
  identify a recipient after the fact.

### 3.8 Named alert thresholds (operator contract)

The current prose scatters alert thresholds across §10.6.1 and §10.6.4 of
the decision record. The runbook (not this design doc) pins them to a
single table so on-call has one place to read:

| # | Metric | Source | Threshold | For | Severity | Suggested routing | Why |
|---|---|---|---|---|---|---|---|
| A1 | `l3_utilisation_pct` | per-minute health log line / `app.notification_send_health()` | ≥ 80 | 10 minutes | Page | On-call | L3 saturation squeezes every community; sustained saturation is a provider or deliverability problem (§10.6.1) |
| A2 | `oldest_deferred_age_s` | same | > 7 200 (2 h) | sustained | Page | On-call | Old deferrals mean the sender cannot drain the backlog; 2 h is 10× the per-attempt backoff (§10.6.1) |
| A3 | 24-hour dead-rate | derive from `dead_24h / (sent_24h + dead_24h)` on the log line, treating a zero denominator as "no attempts, no alert" (not divide-by-zero) | > 10 % | rolling 24 h | Page | On-call | A dead-rate spike is a reputation signal, often preceded by complaints (§10.6.1). **Approximation note.** §10.6.1 phrases this threshold as "dead exceeding 10 % of attempts in **an hour**". The health log line exposes only 24-hour counts (`sent_24h`, `dead_24h`, `skipped_24h`); the per-minute line itself cannot give a true rolling 1-hour attempt count, so this row uses the 24-hour window as the honest approximation. The 24-hour view does **not** satisfy §10.6.1's 1-hour wording — the two differ in how fast they react to a short burst. A faithful 1-hour alert needs either (a) a time-series store deriving the 1-hour rate from the per-minute line, or (b) an added 1-hour counter in `app.notification_send_health()`; both are deliberately out of scope for P9-5. `skipped_24h` is **excluded** from the denominator because a `skipped` row (address_suppressed, address_limited, community_backlog_full, community_deferred, provider_daily_limited, provider_rate_limited) made no provider attempt, so it is not an "attempt" in §10.6.1's sense. |
| A4 | `now() - last_heartbeat_at` + `pending_due > 0` | `app.notification_send_health()` row | heartbeat > 5 min while backlog is non-zero | — | Page | On-call | A silent worker with a backlog means mail is not going out (§10.6.1) |
| A5 | `resolved_ambiguous_this_tick` | per-minute health log line | > 0 | 3 consecutive minutes | Ticket | Engineering + on-call | A sustained non-zero means the worker is crashing mid-flight; isolated events are tolerated (§10.6.4, P9-4 §3.8) |

The runbook adds one informational metric (not an alert, just a dashboard
pin): `email_sending_enabled` from the same log line, so the operator
always knows whether the pause switch is on in the environment they are
looking at.

**Routing target type is operator-named**, not fixed by this document. Page
vs ticket, PagerDuty vs OpsGenie vs email, which rota — those decisions
belong to the on-call model the operator runs. The design asks only that
A1–A4 reach a human within 15 minutes and A5 within 1 hour.

### 3.9 Secrets

| Secret | Variable | Lives in | Never |
|---|---|---|---|
| SES send credentials | `EMAIL_AWS_SECRET_ACCESS_KEY`, optional `EMAIL_AWS_SESSION_TOKEN` | Operator secret store, injected at process start | Committed to the repo, printed in a log line (wrapped as `EmailSecret`), passed in a URL, passed on the command line |
| Direct Postgres connection | `SUPABASE_DB_URL` | Operator secret store, injected at process start | Committed, logged (the connection line prints a status, not the URL), exposed to the browser |

**The worker reads nothing else that is secret.** It does **not** read
`SUPABASE_SERVICE_ROLE_KEY` (the service role bypasses RLS and is reserved
for `apps/web`'s own server routes) and **does not** read
`KOLEKTO_SESSION_SECRET` (contributor cookies are a web concern). This slice
does not add any new secret.

### 3.10 Staging/production rollout order (sender restart)

**Precondition — this is not an authorisation to send email.** The
sequence below applies only in an environment where sending has
**already** been authorised, meaning: the pre-first-start checklist in
the runbook §6 has been signed off; the SES-sender runbook §7
(Q-CONFIRM) checklist is complete, dated and signed; every P9-4 §3.9
operator release gate is met in writing (D-PROVIDER, D-DOMAIN, D-LEGAL,
D-CONSENT, D-WORKER, Q-CONFIRM, AWS production access, IAM, monitoring
routing). Running step 4 in an environment that has not passed those
gates is a policy violation, not a procedure. P9-5 itself does **not**
flip the pause switch; the sequence is written so an operator does not
improvise once the gates are met.

When the operator wants to roll a change to the worker in a running,
**already-authorised** environment, the order is:

1. `app.set_email_sending_enabled(false)` from the owner connection. The
   next tick (≤ 2 s) stops claiming. Deliveries age out normally at 72 h.
2. Deploy / replace the worker process. Wait for the first
   `notification_send_health` log line.
3. Confirm the health line shows `email_sending_enabled: false` and a
   fresh `last_heartbeat_at` within the last minute.
4. `app.set_email_sending_enabled(true)` from the owner connection.
   Only reached when the preconditions above are already satisfied.
5. Confirm the next health line shows `last_claim_at` moving forward (if
   there is backlog) or just a fresh heartbeat (if the queue is empty).

Nothing above is in this slice's code. The runbook spells it out so the
operator does not improvise.

### 3.11 What a reviewer should check in the follow-up deployment-artefact PR

Platform-agnostic acceptance criteria for the slice that adds the chosen
container / VM / managed-worker artefact later:

1. The artefact runs `node dist/index.js` (the build output of
   `npm run build --workspace apps/worker`), not `node src/index.ts` and
   not `npm run start` wrapping a dev build.
2. The artefact passes exactly the environment variables listed in §2.4,
   from the operator's secret store. No secret appears in a committed
   file.
3. The artefact's stop signal is `SIGTERM` with a drain budget ≥ 90 s
   before `SIGKILL`.
4. The artefact's restart policy matches §3.4.
5. The artefact runs **one** replica per environment, enforced by the
   platform configuration (not by convention).
6. The artefact's logs reach the operator's log collector and are
   retained ≥ 30 days.
7. Alerts A1–A5 are wired to the on-call routing agreed with the operator.
8. The artefact does not add any new env var that the worker code does
   not read. If it does (e.g. the optional `WORKER_HEALTH_PORT` for an
   HTTP surface), that env var is also added to `.env.example` and
   documented in §2.4 in the same PR.

## 6. Decisions requiring approval

1. **No HTTP health surface in this slice (§3.6).** Add it only in the
   follow-up platform PR, and only if the platform needs it. Approve or
   revise.
2. **Drain budget of ≤ 90 s before SIGKILL (§3.3).** Chosen to cover
   `EMAIL_SES_SEND_TIMEOUT_MS` (default 10 s, max 60 s) plus one pgmq
   visibility timeout. Approve or revise.
3. **Restart policy — crash-loop threshold of three fatal exits in five
   minutes (§3.4).** Chosen as a soft default; the actual threshold is
   the operator's call once the platform is chosen. Approve or revise.
4. **Single-instance invariant per environment (§3.1).** A second
   instance is a deliberate hand-off during a rolling deploy, never a
   scaling action. Approve or revise.
5. **Alert routing target type (§3.8, A1–A5).** A1–A4 are "page", A5 is
   "ticket". Approve or revise.
6. **Log retention baseline of 30 days (§3.7).** Shorter defeats trend
   charts; longer invites a privacy review. Approve or revise.
7. **Decision-record section number (§4.2).** New section §10.6.5. If
   you prefer a different number, name it.
