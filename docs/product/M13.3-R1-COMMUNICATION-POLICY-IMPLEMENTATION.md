## 2. Policy decisions implemented

| R0 decision | Where enforced |
|---|---|
| 1 Four categories | `COMMUNICATION_CATEGORIES`; every watched action classified (`EVENT_POLICIES`); nothing is marketing |
| 2 Community operational default-on, no consent | `channelRequirement('community_operational','email') = default_on + notice`; `decide()` never asks for consent; worker never stores `consent_missing` |
| 3 Attestation required | `requiresCommunityNotice`; processor reads `app.community_communication_notice_attested` (R2) and treats absent/false/NULL as not attested |
| 4 Opt-out per category × channel; organiser limits | `decide()` puts the member's opt-out first; `mayRecordChoice('organiser', 'opt_in' / 'grant_permission') = false` (used by R2 write paths) |
| 5 WhatsApp opt-in only | `whatsapp` requires `whatsapp_permission` for every category; attestation never substitutes |
| 6 SMS disabled | `smsApproved: false` → `disabled(channel_disabled)` for every category |
| 7 Targeted payment reminders blocked | `payment` → `disabled(payment_attribution_unavailable)` on every channel; in-app plan agrees (tested) |
| Marketing separate | Only `marketing` requires `marketing_consent`; no send class; no event mapped |

## 3. Behaviour change (worker only)

| Situation | Before R1 | After R1 |
|---|---|---|
| Collection email, proposal functions not installed (every environment today) | no email row (`collection_unavailable`) | **unchanged** |
| Proposal installed, attestation function absent | pending if consent set (never), else `consent_missing` | `skipped / community_notice_missing` (or the member's `opted_out`) |
| Proposal installed, community attested, DB still withholds for consent | `consent_missing` | `legacy_consent_gate` |
| Proposal installed, attested, DB eligible | pending | pending |
| Membership confirmations, officer notices | unchanged | unchanged (essential, transactional) |
| Unpaid-targeted actions | no rows | unchanged (now also blocked by policy) |

Net effect today: no new email becomes sendable. Every path that could send still needs an applied
migration, a worker-role grant, R2's attestation store, `email_sending_enabled`, and non-zero bulk caps.

## 5. Unresolved issues

1. **The database proposal still applies the retired consent gate** (`MEMBER-ANNOUNCEMENTS.proposed.sql:255`).
   R1 neutralises it in the worker (`legacy_consent_gate`), but the database withholds the address,
   so the gate is only fully removed by R2.
2. **The attestation store does not exist.** Until R2, community operational email is always
   `community_notice_missing` once the proposal is installed.
3. **Opt-out granularity is not yet expressible in storage.** `notification_preferences` has
   channel-wide and topic-wide flags, not category × channel; the database reports any of them as
   `opted_out`. The policy is ready; the store is R2.
4. **No send-time recheck** of opt-out, archive, reachability or attestation (R3). Bulk rows can wait
   up to 72 h; a withdrawal in that window is not yet honoured at send.
5. **Web preview** still shows `skipped_consent_missing` (`packages/db/src/write.ts:675`); it changes
   with the R2 preview function.
6. **No unsubscribe link** (R4); templates still say "contact the organisers".
7. **Notification audience is tied to the payment audience** (review §10) — required capability, not built.
8. **Legal questions L1–L12 remain open.** The attestation is not proof of a lawful basis.
