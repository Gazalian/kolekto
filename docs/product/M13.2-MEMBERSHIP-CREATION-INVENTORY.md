## 1. How to read this

The notification pipeline is driven by **audit rows**: `app.write_audit_log()` inserts into
`audit_logs`, and the `AFTER INSERT` trigger `app.enqueue_notification_on_audit` enqueues the
actions it lists. Therefore **a membership produces an event only if the code path that creates
it writes an audit row with a listed action.** A direct `INSERT` into `public.members` that does
not call `write_audit_log` produces no event, by construction. The inventory below is organised
around that fact.

## 3. Findings the inventory surfaced

**F-1 — No member is linked to an account.** Nothing in `supabase/migrations`, `packages/db`,
`packages/migration` or `apps/web` ever sets `members.user_id` or `claimed_at`. The local
database agrees: 0 of 382 members have a `user_id`. Consequences:

- The "member **with** an account" branch of the eligibility matrix is, until a claim flow
  exists, reachable only through test fixtures. In practice every member is a non-account
  member, so membership confirmations will go to the supplied `members.email`.
- **M13.1's in-app notifications to members already depend on that link** (`resolveCollectionAudience`
  and `resolveMemberSelf` join on `m.user_id is not null`). In real use they currently reach
  nobody; only officers (who are users) receive `member.join_via_invite` alerts. This is an
  existing M13.1 limitation, not an M13.2 regression. It is out of scope here but should be on
  the roadmap, because it changes what "in-app is the default" delivers.

**F-2 — The audit rows do not carry what the worker needs.** `member.create` omits email;
`member.join_via_invite` omits status; `member.approve_join` has no state at all;
`member.reject_join` carries the whole member row. P3 must read current state from `members`
(for #1–#3) and forward only a **narrow** set of fields from `before_state` for #4, never the
whole row, into `pgmq`.

**F-3 — The worker reads state at processing time, not event time.** For #2 this is deliberate
(status decides E1b) but it means a long-delayed event can see a different state than when it was
written. P3 must define the outcome for each such race (approved before processing → send once;
rejected/deleted before processing → `member_unavailable`; archived → `member_unavailable`).

**F-4 — `pgmq` currently holds PII-bearing and unprocessed messages locally** (7 queued, 206
total in the local dev database; the worker is not running). Not a defect; noted because any P3
test that runs the worker against the dev database will process them.

## 4. Abuse and volume risks (need a decision)

**R1 — The invite form is an unauthenticated mail trigger.** Anyone holding an invite link (links
are shared widely by design) can submit an arbitrary email address, and with
`approve_joiners = false` the membership is created immediately, so E1b would email that
**stranger-chosen** address. That is a mail-bombing and reputation vector, and it undermines
the "supplied by the person themselves" reasoning behind E1b.

**R2 — One address, many members.** An officer (or compromised officer account) can create many
members that all carry the same victim address.

**R3 — Unbounded bursts.** No bulk path exists today, but a loop of #1, a leaked link with
`max_uses = null`, or a replay of a large queue could produce an unbounded number of emails.

**Proposed safeguards (for P3/P5; not built, need approval):**

1. **Per-address cap**: at most one membership-confirmation email per address per community per
   24 h, and at most *N* (proposal: 3) across all communities per 24 h. Over-cap → `skipped`,
   code `recipient_rate_limited` (appended to the reason-code list).
2. **Per-community send budget** (proposal: a rolling hourly cap, e.g. 100). Over-budget
   deliveries are **deferred** with `next_retry_at`, not dropped, and an operator-visible counter
   shows backlog.
3. **E1b is the only anonymous trigger**: apply the strictest cap there, and treat a null
   `invite_links.max_uses` as a configuration warning (a log line, not a block).
4. **Stale-event guard**: an audit event older than *H* hours (proposal: 72) at processing time is
   not emailed (`event_too_old`), so an outage, a restored queue or a replay cannot send old news.
5. **Explicit suppression for repairs**: the enqueue trigger honours
   `current_setting('kolekto.suppress_notifications', true) = 'on'`. Operators running data
   repairs or backfills that go through audited functions set it for the session, so no
   notification is generated. Default is unset (notify). This is the "not by default" control the
   product owner asked for; a repair that bypasses audited functions needs nothing.
6. **Defence in depth in the worker**: refuse any member with `is_imported = true` or
   `joined_via in ('import','migration')`.

## 6. Decisions requested before P3

1. Approve or amend the mapping in section 5.
2. **R1:** how should E1b treat an address supplied through the anonymous invite form? Options:
   (a) keep E1b and send, with the per-address cap only; (b) drop E1b, so the only invite-path
   email is E2 after an officer has approved the join (a human has looked at the request first);
   (c) as (b), but also decline to email invite-form addresses even on approval. **Recommendation:
   (b).** It removes the only unauthenticated mail trigger. The cost: a person who joins through a
   link that needs no approval gets no email, but they are shown their member code on screen at
   the moment they join (`redeem_invite_link` returns it for exactly that purpose), so no
   information is withheld from them.
3. Approve the caps in section 4 (numbers are proposals).
4. Approve the `kolekto.suppress_notifications` session control.
