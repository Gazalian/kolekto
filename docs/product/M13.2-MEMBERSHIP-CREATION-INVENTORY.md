## 1. The rule that makes this tractable

The pipeline is driven by **audit rows**: `app.write_audit_log()` inserts into `audit_logs`, and the
`AFTER INSERT` trigger `app.enqueue_notification_on_audit` enqueues the actions it lists. So **a
membership produces an event only if the path that creates it writes an audit row with a listed
action.** A direct `INSERT` into `public.members` that writes no audit row produces no event, by
construction. Two further facts, both verified live:

- `app.write_audit_log` is executable by **neither `anon` nor `authenticated`**; only server code
  reaches it.
- The importer role (`kolekto_importer`) holds `INSERT` on `public.members` but **no** `INSERT` on
  `audit_logs` and **no** `EXECUTE` on `write_audit_log` or on the enqueue function.

## 3. Findings

**F-1 — No member is linked to an account, and this is a separately scoped dependency (D-LINK).**
Nothing in the migrations, `packages/db`, `packages/migration`, `apps/web` or the live function
bodies assigns `members.user_id` or `claimed_at`. The local database agrees: 0 of 382 members are
linked. Consequences:

- Every member is, in practice, a **non-account member**. Confirmations go to the supplied
  `members.email`, recorded `unverified_supplied`.
- M13.1's in-app notifications to members join on `members.user_id` and so **reach nobody** outside
  test fixtures. That is an existing M13.1 limitation, not a regression, and M13.2 does not change it.
- **This must not be "solved" by matching a member's email to a user's email.** `members.email` is
  typed by a third party and is unverified; matching would let whoever controls a typed address
  take over a membership, and would treat a typed address as proof of ownership, which the product
  decisions forbid. Linking requires proof of ownership of the contact — the claim flow (MEM-08)
  together with a contact-verification mechanism (D-VERIFY). Until then, M13.2 does not link, match
  or infer.

**F-2 — The audit rows do not carry what the worker needs.** `member.create` omits email;
`member.join_via_invite` omits status; `member.approve_join` has no state;
`member.reject_join` carries the whole member row. P3 reads current state from `members` for #1 and
#3, and forwards only a narrow set of fields from `before_state` for #4. Forwarding the whole row
into `pgmq` is not allowed.

**F-3 — The worker reads state at processing time.** Defined outcomes: approved before the event is
processed → one E2; rejected or deleted before processing → nothing (`member_unavailable`);
archived → nothing. R1 removed the one race that depended on status (the old E1b).

**F-4 — `pgmq` holds unprocessed, audit-derived messages locally** (7 queued, 206 total on the
local database; the worker is not running). Client roles have no access to `pgmq` (verified).
Any P3 test that runs the worker against the dev database will process them.

**F-5 — `audit_logs.before_state` for `member.reject_join` stores the whole member row** (name,
phone, email, attributes), readable by `audit.view` holders. Pre-existing and unchanged; recorded
as unresolved issue U3 in the decision record.

## 4. Abuse and volume — resolved by the decisions of 2026-10-09

| Risk | Resolution |
|---|---|
| **R1 — the anonymous invite form was a mail trigger** | **Closed by decision (option b).** No email follows an anonymous submission. A confirmation follows only an officer's approval (E2). Links that need no approval send no email; the joiner sees their code on screen |
| **R2 — one address, many members** | **L1:** at most 3 attempts per address per rolling 24 h across communities; the 4th is a terminal `skipped` / `recipient_rate_limited` (decision record 10.6) |
| **R3 — unbounded bursts** | **L2:** 100 attempts per community per rolling hour, surplus deferred not dropped; **L3** (approved, provisional): 1,000 per hour platform-wide; a community may hold at most 500 deferred deliveries (then `community_backlog_full`); max 3 attempts per delivery; 72-hour life then `event_too_old` |
| Replays, outages, restored queues | The 72-hour stale-event guard; unique event key; unique `membership_confirmation` key |
| Maintenance and repairs | `kolekto.suppress_notifications` — operator sessions only, ≤ 15 minutes, logged, never for officer access changes (10.7) |

Limits are enforced in the database by one function with ordered advisory locks, so concurrent
requests cannot exceed them; the acceptance tests (including 50- and 200-connection concurrency
runs) are listed in decision record 10.6. They are built in P5, with the sender.

## 6. What approving this inventory commits you to

1. The mapping in section 5, including **no joiner email on the invite path**.
2. That account linking is out of M13.2 and is **never** done by matching typed contact details.
3. That historical imports, restores, migrations, seeds, repairs and backfills do **not** notify by
   default, with `kolekto.suppress_notifications` as the only supported way to run an audited repair
   silently.
4. That a future migration or script writing a watched audit action is rejected by a repository
   check unless it suppresses.
