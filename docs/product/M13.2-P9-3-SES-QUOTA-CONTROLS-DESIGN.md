The sender remains disabled (`notification_sender_state.email_sending_enabled
= false` by seed and by migration contract). No real provider is registered
in `REAL_EMAIL_PROVIDERS`. No AWS SDK dependency is introduced. No AWS
resource is provisioned. Nothing in this PR asks for a credential.

**Scope of PR #3 (P9-3).** Add two provider-aware safety limits — a daily cap
(L4) and a per-second rate cap (L5) — immediately before provider submission,
split by a new `send_class` dimension (transactional today, bulk reserved for
later). Keep every existing guarantee: idempotency on delivery id, lease-based
claim with a committed transaction before any provider call, suppression check
first, L1/L2/L3/backlog and 72-hour expiry unchanged. Document how a future
SES adapter (P9-4) must reconcile these app-side safety limits with the SES
account quotas (`Max24HourSend`, `MaxSendRate`) read from `GetAccount`.

## 2. Proposed implementation design

### 2.1 Dimensions and names

Two new limits, named consistently with L1/L2/L3:

| Code | Window        | Scope                              | Default (sandbox-safe) | Outcome on breach                                     |
|------|---------------|------------------------------------|------------------------|-------------------------------------------------------|
| L4   | 24 h rolling  | `send_class` + platform-wide       | 180 / class            | `provider_daily_limited` → defer with `next_retry_at` |
| L5   | 1 s rolling   | `send_class` + platform-wide       | 1 / class / sec        | `provider_rate_limited` → defer, short retry          |

Rationale for the defaults:

- SES *sandbox* account quotas, which every brand-new account starts with, are
  `Max24HourSend = 200` and `MaxSendRate = 1.0` per second. The P9-3 defaults
  sit strictly below sandbox so even an unapproved account cannot be throttled
  by SES. Operators requesting production access from AWS raise these numbers;
  Kolekto's L4/L5 are then raised in a reviewed migration, never above the
  provider's own numbers (see §2.6 and §5). The defaults are chosen in a
  migration, not read from the environment — same convention §10.6.1 enforces
  for L1/L2/L3.
- A single `send_class` ("transactional") is active today; adding the column
  now is additive and keeps the migration count low when bulk arrives.

### 2.2 `send_class` column — additive

New enum-like `text` column with CHECK, added to **both**:

- `public.notification_deliveries.send_class text NOT NULL DEFAULT 'transactional'`
  with `CHECK (send_class IN ('transactional','bulk'))`.
- `public.notification_send_attempts.send_class text NOT NULL DEFAULT 'transactional'`
  with the same check.

Why a check and not a Postgres enum: the project already stores category strings
with text + CHECK (see `email_suppressions.reason`, `.source`); the surrounding
tests follow the pattern; enum-add migrations are heavier and we never branch on
the ordering. The default handles existing rows without a backfill.

The processor
([apps/worker/src/notification-processor.ts:208](apps/worker/src/notification-processor.ts))
always inserts email deliveries with `send_class = 'transactional'` — explicitly
in the INSERT list, not relying on the column default, so the audit trail stays
readable. No code path today creates a `bulk` row; the value exists so L4/L5
counts can be split from the first commit.

### 2.3 The amended reserve function

Replace `app.reserve_email_attempt(delivery_id)` with a single new body (one
migration, one `create or replace`) that keeps every current check and adds L4
then L5 at the end:

```
1. Precondition:        delivery.status = 'sending' (unchanged)
2. Read limits:         app.notification_send_limits(send_class)
3. Compute v_address:   lower(recipient_address)
4. Advisory locks (fixed order, extended):
      (1, hashtext(v_address))
      (2, hashtext(community_id::text))
      (3, 0)                                 — platform (existing L3 lock)
      (4, hashtext(send_class))              — NEW class-platform lock
      (5, hashtext(send_class || '|daily'))  — NEW class-daily lock
5. Suppression check (existing, unchanged)
6. L1 per-address (existing, unchanged)
7. L2 per-community (existing, unchanged)
8. L3 platform (existing, unchanged)
9. L4 per-class daily:
      count(*) from notification_send_attempts
        where send_class = v_class
          and attempted_at > now() - make_interval(hours => l4_window_hours)
      if >= l4_daily:
        update delivery → pending, next_retry_at = oldest + 24h, attempt-1
        return 'provider_daily_limited'
10. L5 per-class per-second:
      count(*) from notification_send_attempts
        where send_class = v_class
          and attempted_at > now() - make_interval(secs => l5_window_seconds)
      if >= l5_per_second:
        update delivery → pending, next_retry_at = now() + 1s + small jitter
        return 'provider_rate_limited'
11. Insert ledger row (now includes send_class)
      return 'granted'
```

Why advisory keys (4) and (5) at the END and ordered: all existing callers
take (1)(2)(3) in that order and never (4)(5). Adding higher-numbered keys
to the end preserves the "fixed order prevents deadlock" argument for every
possible pair of callers. Two writers for the same class serialise on (4) and
(5); writers for different classes never contend on them, so bulk cannot
deadlock transactional even under load.

Why L5 defers rather than skips: per-second overshoot is the signature of a
healthy sender finishing a batch faster than the provider's declared rate; the
right response is a short, jittered wait, not a terminal drop. The outcome
pattern matches `community_deferred`. The caller's existing retry schedule
takes over if the delivery is deferred too many times before its 72-hour life.

Why L4 defers rather than skips: a daily cap is a smoothing control, not an
abuse control. A rejected daily attempt consumes no attempt budget (the
reserve function undoes the attempt, matching the L2/L3 pattern); the row ages
out at 72 h via the existing expiry function. A production operator who wants
delivery guaranteed before the next day raises L4 in a reviewed migration.

### 2.4 Transaction and concurrency strategy

Same model as P5-2:

- `reserve_email_attempt` is called from inside the claim transaction. Every
  state change (deferral, skip, grant) commits with the claim; the row lock on
  `notification_deliveries` taken by the claim stays held until commit.
- Advisory locks are transaction-scoped (`pg_advisory_xact_lock`); they vanish
  on commit or rollback, so a rolled-back reservation leaves no ghost lock.
- The ledger INSERT is the point at which another worker can observe the
  reservation. Because every reservation holds the daily and per-second locks
  during its own count-then-insert, two workers can never both see "L5 slot
  free" and both grant.
- Hash collisions on advisory keys only serialise; counts still use the true
  values (`send_class` string).
- Rollback safety is preserved: if any later step in the sender tick raises
  before commit, the ledger insert never happens, the delivery stays
  `pending`, and `attempt_count` returns to the pre-claim value. The existing
  integration test
  [apps/worker/test/notification-rate-limit.integration.test.ts](apps/worker/test/notification-rate-limit.integration.test.ts)
  "a rolled-back reservation leaves no ledger row" extends unchanged.

### 2.5 Deferred behaviour and retry-storm avoidance

L4 and L5 both set `next_retry_at` on the delivery and never schedule a retry
through the normal transient-error path. Concretely:

- L4 breach: `next_retry_at = min(attempted_at) + 24h`. The scanner
  (`claim_next_notification_delivery`) will not pick the row until the window
  slides. 72-hour expiry is checked by `expire_stale_notification_deliveries`;
  a row deferred for 48 h still has 24 h of life left even under worst case,
  so a deferred transactional row almost always sends before its L4 window
  closes. If it doesn't, it becomes `dead/event_too_old` by the existing
  expiry path — no new terminal code is introduced.
- L5 breach: `next_retry_at = now() + 1 second + jitter(0..200 ms)`. The
  jitter is computed in SQL via `random()` inside the reserve function — the
  worker-side `rng` is only for TypeScript backoff on *transient* failures.
  The jitter keeps 20 contending workers from re-colliding on the next second.
- Backlog cap still applies: a deferred row is counted toward the
  per-community `backlog_max` (500) — if a class is pushing a community over
  that cap, further rows become `skipped/community_backlog_full`, same as
  today. No new skip code is added.

Retry-storm avoidance (end-to-end):

- No ambiguous failure is retried without the provider's own idempotency
  (existing `notification-backoff.ts` rule).
- L4/L5 defer, they don't retry — so a 1 kreq backlog that trips L5 does not
  increment `attempt_count` and never approaches the 3-attempt cap because of
  rate limiting.
- `claim_next_notification_delivery` uses `FOR UPDATE SKIP LOCKED`; two
  workers waking at the same second cannot both grab the same row.

### 2.6 Transactional vs bulk/announcement separation

- `send_class` splits L4 and L5 (and the ledger counts behind them). It does
  not split L1 (one address's day-budget is one address, however many classes
  touch it) or L3 (the platform cap exists to protect sending-domain
  reputation across all classes).
- Defaults in P9-3:
  - `transactional`: L4 = 180/24 h, L5 = 1/s.
  - `bulk`: L4 = 0/24 h, L5 = 0/s. **A zero cap means "never granted":**
    the first bulk attempt deferrs forever and ages out. This is the "bulk is
    not opened yet" state. When the bulk-sender milestone lands, the cap is
    raised through a reviewed migration together with the bulk ingress path,
    campaign model, consent model and audit rules — none of which exist here.
- `L2` (per-community/1 h) stays class-agnostic: it is the fan-out brake for
  one community and does not care which class is driving it.

Why not introduce the bulk pathway in P9-3: the brief lists it as a *future*
concern; building it here would expand scope, add consent/legal gating that
is not resolved (`D-LEGAL`, `D-CONSENT`), and change the transactional
contract. P9-3 ships only the dimension and the zero-cap, so a later PR can
turn bulk on by changing numbers and adding the write path.

### 2.7 Config: the one place numbers live

Keep the §10.6.1 convention: numbers live in exactly one SQL function. Replace
`app.notification_send_limits()` (returns one row) with a per-class function:

```
app.notification_send_limits(p_class text)
  returns table (
    l1_address, l1_window_hours,
    l2_community, l2_window_hours,
    l3_platform, l3_window_hours,
    l4_daily, l4_window_hours,          -- NEW
    l5_per_second, l5_window_seconds,   -- NEW
    backlog_max, max_attempts
  )
```

Values are hard-coded in the function body (SQL stable), different for
`'transactional'` and `'bulk'`. Changing a number is a one-line migration
(`create or replace`) that updates this file and the tests that read the
function — the same discipline the current implementation already asserts.

**No environment variable** is added for the limits. Operators cannot change
L4/L5 by setting an env var or editing a UI; the only path is a reviewed
migration. This matches "the pause switch is the emergency control, not
editing a limit" (§10.6.1).

### 2.8 Future SES adapter — what P9-4 must do with this

P9-3 adds no SES code, but documents the obligation here so the design is
reviewable alongside the hooks:

- `AWS::SES::V2::GetAccount` returns `SendQuota.Max24HourSend` and
  `SendQuota.MaxSendRate`. The adapter must call it ONCE at startup, log
  (code + numbers), and refuse to start if `l4_daily >= Max24HourSend` or
  `l5_per_second >= MaxSendRate`. The adapter never *reads* these numbers at
  send time (we do not want a surprising mid-day quota change to turn into a
  retry storm); it refuses at startup instead.
- The adapter never asks SES to enforce quota for us. Kolekto's L4/L5 are
  **safety limits** that stay strictly below the provider's own numbers so
  SES's own `Throttling` / `DailyQuotaExceeded` paths are reached only in a
  code bug. If SES returns `Throttling` anyway, the adapter maps it to
  `provider_rejected_transient` (existing code) — a retry (not an L5 wait).
- The adapter also calls `GetAccount().ProductionAccessEnabled`: if false, L4
  defaults stay in the sandbox-safe range even if the migration raised them.
  This belongs in the adapter because it is provider knowledge, not database
  knowledge.
- Account-level suppression list and complaint policy already have a hook
  (P9-1 + P9-2 ingestion). P9-4 is where `REAL_EMAIL_PROVIDERS` gains `'ses'`
  and the factory grows an `SesEmailProvider` — not here.

  all rejections; row ages out at 72 h via the existing expiry function.
- `send_class = 'unknown'` is refused by the CHECK on insert.
- An old L4 window entry (24 h + 1 s) does not count; one 23 h 59 m old
  does.
- A clock skew by one second does not re-grant a just-breached L5 (the
  function uses `now()` consistently; test with `pg_sleep(1.1)` to pass).

### 3.5 Documentation

- New: `docs/product/M13.2-P9-3-SES-QUOTA-CONTROLS-DESIGN.md` (this report
  committed, together with the implementation, when the design is approved).
- New: `docs/runbooks/sender-quota-operator-guide.md` describing how to:
  - Change L4/L5 safely (migration-only; staging first; keep tests green;
    never above the provider's reported `Max24HourSend` / `MaxSendRate`).
  - Read quota utilisation from the health view and the per-minute log.
  - Diagnose a sudden deferral spike (common causes: AWS reduced
    `MaxSendRate` after a complaint spike; a new community is onboarding;
    the pause switch is off but L4 was raised too aggressively).
  - Recover from a backlog: never flip L4/L5 to extreme numbers to clear a
    queue (that is how reputation is lost). Use the pause switch to stop
    new deliveries, let the ingestion feedback drive suppressions, then
    raise L4 gradually.
- Update `docs/product/M13.2-EMAIL-NOTIFICATIONS-DECISION-RECORD.md`:
  Append a new section "§10.6.3 Provider-aware safety limits" documenting
  the L4/L5 numbers and the P9-4 contract (adapter refuses to start if its
  own `GetAccount` numbers disagree). Flagged under §4 as approval-required.

## 4. Failure scenarios and test plan

| # | Scenario | What proves it is handled |
|---|---|---|
| 1 | Two workers race one address, L1 is at 2/3, L5 full | Address lock + class-second lock serialise; exactly one grant, the other deferred by L5 or terminal by L1 depending on arrival; no deadlock. (Integration: §3.4 L5 race.) |
| 2 | Daily cap hits mid-batch | The granted ledger rows are committed; subsequent reservations defer with `next_retry_at = oldest + 24 h`. (pgTAP C.) |
| 3 | Per-second cap hits during a backlog drain | Deferred rows get `next_retry_at ≈ now + 1 s + jitter`, so 20 workers waking next second do not collide again. (Integration: §3.4 L5 race.) |
| 4 | Worker killed between provider accept and settle | Lease expires, `recover_expired_notification_lease` returns the row to `pending` with `attempt_count` kept consumed (existing P5-1 behaviour; unchanged). Suppression/L4/L5 do not interfere because recovery takes no new lock. |
| 5 | Suppressed address reaches L4 count | `is_address_suppressed` runs first; terminal skip, no ledger row, so suppressed sends never consume provider budget. (pgTAP I.) |
| 6 | Clock drift inside the DB server | `now()` is a single value within the transaction; L5 window uses `make_interval(secs => 1)`; a drift between DB nodes does not apply (one DB). |
| 7 | A migration raises L4 but the previous queue is not drained | A raise applies to the next reservation only; prior deferrals are unaffected (same guarantee as L1–L3; health snapshot shows a backlog drop as new reservations grant). |
| 8 | A migration *lowers* L4 while rows are deferred | Already-granted ledger rows stay; new reservations see the lower cap. No row is cancelled or re-queued. |
| 9 | Replay (same msg_id) in the queue after a crash | Delivery id idempotency still de-dupes at insert; no new L4/L5 impact. (Processor test unchanged.) |
| 10 | A `send_class = 'bulk'` row is inserted (future bulk sender ships) with cap still 0 | The row is deferred forever and ages out at 72 h as `dead/event_too_old`. No L4/L5 code change needed to open bulk later — only a reviewed migration raising the two numbers. |
| 11 | Attempted bypass: operator sets `app.app.send_attempts_purging` and tries to delete ledger rows | Append-only trigger refuses; `purge_stale_send_attempts` is operator-only; no client grant. (Existing P5-2 guarantee, unchanged.) |
| 12 | Pause switch flipped on, then L5 trips immediately | Sender does not claim while paused; so no L5 call. When the switch is flipped on, deferrals are picked up oldest-first; L5 behaviour as normal. |
| 13 | 72 h expiry versus a long L4 defer | A row deferred 48 h is still within life; a row deferred 70 h is close to expiry. The existing expiry function (`FOR UPDATE SKIP LOCKED` + status re-check) safely marks it `dead/event_too_old`. (pgTAP from P5-5 covers this; a new case asserts an L4-deferred row ages out correctly.) |

## 5. Design decisions requiring human approval

1. **Default numbers for L4 and L5 (transactional class).** Proposed:
   `L4 = 180/24 h`, `L5 = 1/s`. These sit strictly below SES's sandbox quotas
   (`Max24HourSend = 200`, `MaxSendRate = 1/s`) so they are safe even before
   production access is granted. A higher production number is a later,
   reviewed, environment-specific migration. **Approve or revise.**
2. **Bulk cap default: 0/0.** Making bulk unreachable until the bulk sender
   milestone ships is the safe default; it keeps the dimension in place
   without opening a path to actually send bulk mail. **Approve or revise.**
3. **No environment variable for the limits.** Keep the numbers in a reviewed
   SQL function per §10.6.1. **Approve or revise.**
4. **Scope split from P9-4.** This PR adds no `SesEmailProvider`, no AWS SDK
   dependency and does not register `'ses'` in `REAL_EMAIL_PROVIDERS`. The
   adapter's startup `GetAccount` check belongs to P9-4. **Approve or
   revise.**
5. **`send_class` enum values.** `'transactional'` and `'bulk'`, as text with
   a CHECK (consistent with `email_suppressions.reason`, `.source`). An
   additional class later (`'service_notice'`?) is a one-line migration.
   **Approve or revise.**
6. **Health snapshot additions.** Four new JSON-by-class fields on
   `app.notification_send_health()`; the staff-only view
   `private.v_notification_send_health` picks them up unchanged. **Approve or
   revise.**
7. **New stable error codes.** `provider_rate_limited`,
   `provider_daily_limited`. Both are reservation outcomes and new delivery
   `next_retry_at` deferrals (not skip codes); no change to the
   skipped-row-constraint vocabulary. **Approve or revise.**
8. **Documentation touches.** New operator runbook and a new §10.6.3 in the
   decision record. **Approve or revise.**

## 7. Safety requirements, point by point

- **No file modified in the repository as part of this task.** The design
  itself lives in the scratchpad; no commit, no push, no PR.
- **No real SES sending adapter.** None. The factory does not grow a case.
- **Sender pause switch untouched.** The seed row remains `false`. The P9-3
  migration adds no setter call and no `set_email_sending_enabled` write.
- **No AWS resources provisioned, no emails sent, no shared or live database
  modified.** The design is local-dev first; staging is explicitly deferred
  to a reviewed roll-out after approval.
- **No weakening of suppression, idempotency or retry protections.** L4 and
  L5 run *after* suppression and *inside* the same transaction as the claim;
  idempotency on the delivery id and the three-attempt cap are untouched;
  the `notification_send_attempts` append-only enforcement and the deny-all
  RLS stay in place.
- **No PR #4 (SES adapter) work started.** The design names the P9-4
  obligation (adapter startup `GetAccount` reconciliation) but implements
  none of it.
- **No destructive database operation.** The migration is additive:
  `alter add column`, `create index`, `create or replace function`. Rollback
  is explicit.
