# M13.2 P9-2.1 — SES ingestion hardening (implementation record)

## What this phase delivers

Follow-up hardening after PR #15 (M13.2 P9-2 SES/SNS event ingestion). The
receiving route is unchanged in its external contract, but four internal
behaviours are tightened:

- **A.** A verified event can never be acknowledged to SNS while its
  suppression or delivery-status side effect has silently failed. The
  ledger carries explicit per-event processing state; failed side effects
  return 500 to SNS so the Notification is redelivered, and the next
  attempt resumes safely because every side effect is idempotent.
- **B.** The request-body size limit is enforced per chunk during a
  streaming read, not after the whole body has been buffered. A chunked
  request with no Content-Length header cannot blow past the cap.
- **C.** The signing certificate's validity window is checked
  (`validFrom`, `validTo`) in addition to the hostname pin and HTTPS trust
  (issue #16). The decision record on offline X.509 chain validation sits
  in §C below.
- **D.** The adapter defaults to accepting only SignatureVersion 2
  (RSA-SHA256) and the route-side configuration opts in to v1 explicitly
  via `EMAIL_AWS_SNS_ALLOW_SIGNATURE_V1=true` (issue #17).

Addresses GitHub issues #16 and #17.

## What this phase deliberately does not do

- No SES sending adapter, no `ses` entry in `REAL_EMAIL_PROVIDERS`, no
  SES SDK dependency. P9-4 is still gated on D-PROVIDER.
- No AWS resource provisioning or configuration.
- No sender runtime, rate-limit, retry-policy, lease-semantics, or
  `notification_deliveries` schema change.
- No `app.record_ses_suppression` or `app.record_ses_delivery_event`
  change — the actual side-effect writers are untouched.
- The sender pause switch stays off (`notification_sender_state.
  email_sending_enabled = false`).
- No payment integration or contributor-receipt work.

## A. Reliable side-effect processing

### The gap closed

The P9-2 route order was: authenticate → insert ledger row (ON CONFLICT
DO NOTHING) → apply side effect in a try/catch that **swallowed** the
error → return 200. If `recordSesSuppression` or `recordSesDeliveryEvent`
threw during a transient DB blip, SNS would be acked, the Notification
would never be redelivered (unique index on `provider_event_id` catches
replays), and the row sat in the ledger with the full payload but no
suppression / no `sent → delivered` transition. The operator-visible
anomaly was a payload with no corresponding action, with no marker to
distinguish it from a "nothing to do" classification (`transient_bounce`,
`rejection`, `rendering_failure`).

### The design

`public.email_delivery_events` grows four processing-state columns plus
an `updated_at`:

| column | purpose |
|---|---|
| `processing_status` | `pending` (new) \| `succeeded` \| `failed` |
| `processing_attempts` | advances on every mark-succeeded / mark-failed |
| `last_processed_at` | stamp of the most recent mark call |
| `last_error_code` | stable snake_case for a `failed` row (null otherwise) |
| `updated_at` | advances via the shared `app.set_updated_at` trigger |

CHECK constraints:

- `processing_status` is in the three-value vocabulary.
- `processing_attempts >= 0`.
- `last_error_code` matches `^[a-z][a-z0-9_]{2,63}$` or is NULL.
- A `succeeded` row has NO `last_error_code`.
- A `failed` row MUST have `last_error_code`.

Pending rows may carry a NULL `last_error_code` (never processed yet).

### The trigger change

`app.block_email_delivery_events_mutation` previously refused all
UPDATE. The amended trigger allows UPDATE only when the session variable
`app.email_delivery_events_processing_marker` is `'true'` AND the row's
content columns (`provider`, `provider_event_id`, `provider_event_type`,
`normalized_event_type`, `payload`, `signature_verified`,
`recipient_address_key`, `ses_feedback_id`, `provider_message_id`,
`sns_topic_arn`, `received_at`) are byte-identical between OLD and NEW.
UPDATE outside the marker, DELETE, and TRUNCATE remain unconditionally
blocked.

The marker flag is set inside `app.mark_ses_notification_succeeded` and
`app.mark_ses_notification_failed`, both operator-only. External code
never sets it.

### The new functions

| function | purpose |
|---|---|
| `app.record_ses_notification(…)` | Insert-or-reuse the ledger row for a Notification; return `(event_id, inserted, previously_succeeded, processing_attempts)`. The webhook route's single orchestrator entry point. |
| `app.mark_ses_notification_succeeded(uuid)` | Transition pending/failed → succeeded. Idempotent (second call returns 0). Clears `last_error_code`, stamps `last_processed_at`, bumps `processing_attempts`. |
| `app.mark_ses_notification_failed(uuid, text)` | Transition pending/failed → failed with a stable snake_case error_code. **Never downgrades a `succeeded` row** — returns 0 in that case. |

All three are `SECURITY DEFINER`, `search_path = ''`, `role = 'none'`
operator-only, with EXECUTE granted only to the owner role.

### The route flow

1. Authenticate the SNS envelope. (Reject → stable snake_case code.)
2. Call `app.record_ses_notification(…)` → `{eventId, inserted,
   previouslySucceeded, processingAttempts}`.
3. If `previouslySucceeded` → ack `duplicate`, 200.
4. Classify and apply the side effect:
   - **Success** (including `no_op` / `no_recipient`): call
     `app.mark_ses_notification_succeeded(eventId)` → ack 200.
   - **Failure**: call `app.mark_ses_notification_failed(eventId,
     errorCode)` → return 500 so SNS retries.
5. If the mark call itself throws, return 500 so SNS retries. The ledger
   row stays `pending` and the next SNS redelivery sees
   `previously_succeeded = false` and retries the (idempotent) side
   effect.

### Why this is idempotent under retry

- `app.record_ses_suppression` delegates to `app.set_email_suppression`,
  which is a conditional upsert that is a no-op when the row already
  exists as `permanent`.
- `app.record_ses_delivery_event` only transitions `status = 'sent'` to
  `delivered` with the matching `provider_message_id`. Second call
  matches zero rows and returns 0.
- Marking succeeded on an already-succeeded row returns 0.
- Marking failed on an already-succeeded row returns 0 (never downgrades).
- The unique `(provider, provider_event_id)` index prevents duplicate
  ledger rows even under concurrent SNS deliveries.

## B. Request-body size limit (streaming)

### The gap closed

P9-2 did `const buf = await request.arrayBuffer(); if (buf.byteLength >
MAX) return 413;` — `arrayBuffer()` reads the full body before the size
check, so a chunked request without a Content-Length could buffer
unbounded memory before being refused.

### The design

A new `readLimitedBody(request, maxBytes)` helper reads
`request.body.getReader()` chunk-by-chunk, incrementing a byte counter
after each chunk, and cancels the stream as soon as the counter exceeds
`maxBytes`:

```ts
async function readLimitedBody(request, maxBytes): Promise<Uint8Array | "too_large" | "no_body" | "read_error"> {
  const reader = request.body.getReader();
  let total = 0;
  const chunks: Uint8Array[] = [];
  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;
    total += value.byteLength;
    if (total > maxBytes) {
      await reader.cancel();  // best-effort
      return "too_large";
    }
    chunks.push(value);
  }
  // concat...
}
```

The Content-Length pre-check remains (short-circuits honest clients).
The post-read check is removed — the stream-level cap replaces it.

- `apps/web/app/api/webhooks/ses/route.test.ts` — new test that posts a

## C. Certificate trust (issue #16)

### What AWS says

AWS's verify-signature best-practice list:

- Always retrieve the signing certificate using HTTPS.
- Check that the certificate is issued by Amazon SNS.
- Confirm that the certificate's chain of trust is valid.
- The certificate should come from an SNS-signed URL.
- Don't trust any certificates provided in the message without
  validation.

### What AWS does not publish

AWS does not publish:

- A stable root CA bundle specific to SNS signing certs.
- A stable, documented subject CN for SNS signing certs.
- A stable, documented issuer DN for SNS signing certs.

Every AWS SDK validator we inspected (`aws-sns-validator` Python
library, `boto3`'s internal verifier) stops at:

1. HTTPS hostname check for the SigningCertURL.
2. HTTPS fetch (TLS chain validated by the OS/Node trust store).
3. Signature verified with the fetched cert's public key.

They do NOT walk an offline X.509 chain against a hardcoded AWS root.

### What we add in P9-2.1

We **do** add:

- A `validFrom`/`validTo` check on the signing cert. A cert outside its
  validity window is rejected with `cert_fetch_failed` and a detail of
  `cert_expired`, `cert_not_yet_valid`, or `cert_dates_unparseable`. An
  expired cert is "chain of trust is not valid" in the plain sense of
  the words.

We **deliberately do NOT invent**:

- An offline X.509 chain walk against unspecified AWS roots. The task's
  "stop and report the unresolved issue instead of implementing an
  improvised trust check" rule applies here: we have no authoritative
  reference for the trusted issuer identities. A pinned subject CN or
  issuer DN would be a guess that could silently fail-closed on a
  legitimate AWS rotation, OR fail-open on a cert from a different
  Amazon-owned CA that happens to match the pattern.

### The composed trust model

The adapter's chain of trust is:

1. **Hostname pin.** SigningCertURL must sit on
   `sns.<EMAIL_AWS_REGION>.amazonaws.com[.cn]` over HTTPS, default
   port, no credentials, no fragment.
2. **TLS chain at fetch.** HTTPS fetch validates the SERVER's TLS cert
   chain against Node's bundled trust store. The fetch is called with
   `redirect: "error"`, so an unexpected redirect never silently
   relocates the trust.
3. **Validity window on the signing cert** (new in P9-2.1).
4. **Signature verification** with the cert's public key against the
   AWS canonical message.

Issue #16 is **partially addressed**. A full offline X.509 chain walk

## D. SignatureVersion policy (issue #17)

### The decision

Default: accept SignatureVersion 2 only (RSA-SHA256). The adapter
constructor refuses an empty `acceptedSignatureVersions` and refuses any
value outside the two AWS-published versions ("1", "2").

Operators who need to accept SignatureVersion 1 for a legacy topic they
cannot reconfigure can opt in explicitly:

```
EMAIL_AWS_SNS_ALLOW_SIGNATURE_V1=true
```

A new deploy that does not set the variable (or sets it to `false`)
accepts v2 only.

A value other than the literal `"true"` or `"false"` is refused at
config load (`EMAIL_AWS_SNS_ALLOW_SIGNATURE_V1 must be the literal
string "true" or "false"`). No silent coercion.

### Rationale

AWS still documents v1 but calls v2 the recommended option. SHA-1 is
deprecated for new signing use industry-wide. Kolekto controls its SNS
topic configuration end-to-end, so there is no legacy topic to
accommodate; v2-only is the clean posture.

The config flag exists so a future legacy integration (another AWS
account, a shared topic) can be onboarded without a code change.

### Tests

- `packages/adapters/test/ses-sns-webhook-provider.test.ts` — new tests
