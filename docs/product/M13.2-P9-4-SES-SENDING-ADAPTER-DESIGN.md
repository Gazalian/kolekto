**Scope.** Build the SES sending adapter and the one piece of safety plumbing
P9-1 left for this milestone (the "crash-after-accept guard"). The brief
"ambiguous-acceptance safeguards" is interpreted as the combination of:

- SES's `SendEmail` has **no client-supplied idempotency token**: the
  provider generates `MessageId` itself. The adapter is therefore
  `idempotency: "none"` by the P5 contract.
- Any ambiguous outcome (timeout, dropped connection at or after the DATA
  phase, worker crash while a lease is held) against a non-idempotent
  provider must land as `dead/outcome_unknown` and surface for operator
  decision — not silently retry (§10.6.2, Q-DUP).

### 2.1 Provider contract (`packages/adapters/src/email-provider.ts`)

- `EmailProvider` is `{ name, idempotency: "provider" | "none", send() }`.
- `EmailSendRequest` has `{ idempotencyKey, message: { to, subject, text, html? } }`.
- `EmailSendResult` is `{ providerMessageId: string }`.
- `EmailProviderError` carries `{ kind: transient|permanent, code, ambiguous: boolean }`.
- Error vocabulary: `invalid_message`, `provider_unreachable`,
  `provider_timeout`, `provider_rejected_transient`,
  `provider_rejected_permanent`, `provider_protocol_error`,
  `adapter_misconfigured` — **append-only** (never renamed, never reused).
- `assertValidEmailRequest` rejects header injection and oversized bodies
  with a *permanent* `invalid_message` before any adapter sees them.

### 2.2 Factory and config

- `packages/config/src/email.ts` — `REAL_EMAIL_PROVIDERS: readonly string[] = []`
  (empty on purpose). Startup guards refuse real providers in local/CI

### 2.3 Claim, lease, retry and ambiguous rules

- `supabase/migrations/20261013100000_notification_send_claims.sql`:
  - `app.claim_notification_delivery(id, lease_seconds)` → row lock,
    5-minute lease (`send_lease_token` 64 hex, `send_lease_expires_at`),
    status `pending → sending`, `attempt_count += 1`, 3-attempt cap.
  - `app.resolve_notification_claim(id, token, outcome, ...)` → the only
    way out of `sending`. `sent` is terminal; `retry` returns to
    `pending` with caller-supplied `next_retry_at`; `dead` is terminal
    with a stable `error_code`.
  - **`app.recover_expired_notification_lease(id)` returns a `sending`
    row with an expired lease to `pending`, clears the lease, and keeps
    the attempt consumed.** This is the bit that must change for
    idempotency-free providers (see §3.3).
- `supabase/migrations/20261019140000_notification_sender_controls.sql`:
  pause switch, heartbeat, 72-hour expiry, health view.
- `apps/worker/src/notification-backoff.ts` (`classifyFailure`):
  - permanent → `dead` with the code.
  - transient → `retry` with ≈5/30 min + ±20 % jitter, cap at attempt 3
    → `dead/retries_exhausted`.
  - ambiguous + `idempotency: "provider"` → retry (same key reused).
  - ambiguous + `idempotency: "none"` → `dead/outcome_unknown` on
    attempt 1 or any later — never retried.
  - `adapter_misconfigured` → sender halts.

### 2.4 Quota controls and suppression (post P9-1 and P9-3)

- `app.reserve_email_attempt(id)` (`20261022110000` + `20261024200000`):
  address lock → community lock → platform lock → class lock →
  class-daily lock. Suppression check first, then L1/L2/L3/backlog, then
  L4 (daily per class), then L5 (per-second per class). Any defer undoes
  the claim's attempt increment and keeps the address; terminal skip
  erases it.
- `app.is_address_suppressed(address)` consulted inside the reserve TX,
  under the address advisory lock, so a race between a send and a block
  can't both see "not suppressed".
- `app.email_delivery_events` (`20261023120000` + `20261024100000`)
  receives SES event feedback via SNS. `app.record_ses_suppression()`
  (SES-webhook-only entry point) writes permanent suppressions with
  `source = 'ses_event'` through the one P9-1 setter. The webhook route
  (`apps/web/app/api/webhooks/ses/route.ts`) is live but ingestion is
  only enabled when both env vars are set.

### 2.5 Sender runtime (`apps/worker/src/notification-sender.ts`)

- `sendOneClaimed(sql, {provider, now, rng})`:
  1. **Transaction 1 (committed before provider call):**
     claim → reserve. On non-granted outcomes the reserve function has
     already updated the delivery row; return early as `deferred` /
     `skipped`.
  2. **Provider call** with no transaction, no row lock open.
  3. **Transaction 2 (after the call):** `settleDelivery` with the lease
     token. On `sent`, stores `provider_message_id` and clears the lease.
     On `retry` or `dead`, records the error code (and `next_retry_at`
     for retry).
- `recoverExpiredLeases(sql, limit=100)` loops over expired-lease
  `sending` rows and calls `app.recover_expired_notification_lease(id)`.
- `runSenderTick` runs maintenance (recover + expire + purge) and emits
  one redacted health log line per minute.

## 3. Proposed design

### 3.1 SES adapter — contract and placement

A new `packages/adapters/src/ses-email-provider.ts` implementing
`EmailProvider`:

```ts
export interface SesEmailProviderOptions {
  readonly region: string;
  readonly from: string;
  readonly configurationSetName?: string;      // optional, for event destinations
  readonly accessKeyId: string;
  readonly secretAccessKey: EmailSecret;        // wrapped — reveal() only
  readonly sessionToken?: EmailSecret;          // for assumed-role / short creds
  readonly httpTimeoutMs?: number;              // default 10_000
  readonly httpFetch?: typeof fetch;            // injectable for tests
  readonly now?: () => number;                  // injectable clock
}
```

- `name: "ses"`.
- `idempotency: "none"` — SESv2 `SendEmail` does **not** accept a
  caller-supplied idempotency token; `MessageId` is server-generated.
  This is why the ambiguous-acceptance handling matters.
- `send(request)` posts a SESv2 `SendEmail` call. Delivery lineage is
  carried in two places so the P9-2 webhook ingestion can correlate:
  - `EmailTags: [{Name: "delivery_id", Value: idempotencyKey}]` — SES
    carries this in event-destination notifications. The delivery id
    cannot leak into recipient-visible mail (tags are server-side only).
  - An `X-Kolekto-Delivery-Id` custom header on the raw message, for
    deeper correlation in `email_delivery_events.payload`.

### 3.2 Transport decision — SDK vs hand-rolled

**Design decision (approval required).** The project's convention
(§2.4, hand-rolled SNS signature verification; §P9-2.1 implementation
record names it explicitly) has been to avoid an AWS SDK dependency and
hand-roll the signatures. Two viable paths:

- **A (recommended): add `@aws-sdk/client-sesv2`.** `SendEmail`'s
  request shape is complex (nested `Destination` / `Content` /
  `EmailTags` / `ConfigurationSetName`), and SigV4 for a signed POST
  with body is non-trivial. The modular v3 SDK (`client-sesv2` plus
  `credential-providers`) adds ~1 MB installed. We'd use it only in the
  worker, not in `apps/web`, so no bundle-size impact on the Next.js
  build. Set version in `apps/worker/package.json`, pin the exact minor,
  and add the advisory to `audit-exceptions.md` only if one appears
  (SES SDK has historically been clean).
- **B: hand-roll SigV4 and SESv2 `SendEmail`.** Matches the existing
  SNS adapter style and avoids the dep entirely. Needs ~400 lines of
  SigV4 code and careful handling of canonicalisation (particularly the
  SHA256 of the payload). Reviewable but higher per-review cost.

Pick A unless there's an operator objection to the SDK dep. The report
documents B as a fallback. Nothing in the rest of the design changes
with the choice — the adapter still implements the same
`EmailProvider` contract.

### 3.3 Startup checks and `GetAccount`

On adapter construction (NOT per-send):

1. Call SESv2 `GetAccount` once. Log, as plain code+number values:
   `MaxSendRate`, `Max24HourSend`, `ProductionAccessEnabled`,
   `SendingEnabled`, `DedicatedIpAutoWarmupEnabled` (if present).
2. Refuse to start when any of the following hold (plain language per
   the "security" / "irreversible-action" guidance in CLAUDE.md):
   - `SendingEnabled === false` on the account — the account is paused
     at AWS. Nothing we do will go through.
   - `ProductionAccessEnabled === false` AND `KOLEKTO_ENV === "production"`.
     Sandbox mode is a staging / preflight state, never production.
   - `l4_daily >= Max24HourSend` or `l5_per_second >= MaxSendRate`.
     Kolekto's own safety limits must sit strictly below the provider's
     own numbers (§10.6.3 contract).
3. Log the configured L4/L5 next to the AWS numbers so a reviewer can
   see the ratio.
4. The adapter does **not** re-read `GetAccount` at send time
   (§10.6.3): a mid-day quota change would become a retry storm.

If `GetAccount` itself fails (403, network), the adapter raises
`adapter_misconfigured`, which the sender maps to `halt`
(`notification-backoff.ts`). Maintenance (lease recovery, expiry,
health) keeps running; no sends happen.

### 3.4 Ambiguous-acceptance safeguards

The P5-1 lease model needs two targeted changes:

#### 3.4.1 New DB function `app.resolve_lease_ambiguous(p_delivery_id)`

Mirrors `app.recover_expired_notification_lease` with a different
terminal state. Signature:

```sql
app.resolve_lease_ambiguous(p_delivery_id uuid)
  returns table (resolved boolean, reason text)
```

Semantics (idempotent):

- Row lock the delivery row.
- Precondition: `status = 'sending'` AND `send_lease_expires_at <= now()`.
  A live lease (not expired) returns `(false, 'lease_still_valid')`.
  A terminal row returns `(false, 'not_leased')`.
- On success: `status = 'dead'`, `error_code = 'outcome_unknown'`,
  `send_lease_token = null`, `send_lease_expires_at = null`,
  `provider_message_id` left as it is (null, because the worker died
  before writing it). Attempts stay consumed.
- SECURITY DEFINER, `search_path = ''`, revoked from `public, anon,
  authenticated` — same pattern as every other `app.*` function.

#### 3.4.2 Worker chooses the recovery path by provider idempotency

`apps/worker/src/notification-sender.ts` `recoverExpiredLeases` becomes:

```ts
async function recoverExpiredLeases(sql, provider): Promise<RecoveryCounts> {
  const rows = await sql`select id from … where status='sending'
                         and send_lease_expires_at <= now()
                         order by send_lease_expires_at limit 100`;
  let recovered = 0, resolvedAmbiguous = 0;
  for (const row of rows) {
    if (provider.idempotency === "provider") {
      // De-duping provider — a replay reuses the same key and is safe.
      // Keep today's behaviour: return the row to pending so a worker
      // can finish the job.
      const r = await recoverExpiredLease(sql, row.id);
      if (r.recovered) recovered += 1;
    } else {
      // Non-idempotent provider (SES). A re-send might produce a second
      // copy. Surface the row as dead/outcome_unknown for an operator
      // to decide (per §10.6.2 ambiguous-outcome rule).
      const r = await resolveLeaseAmbiguous(sql, row.id);
      if (r.resolved) resolvedAmbiguous += 1;
    }
  }
  return { recovered, resolvedAmbiguous };
}
```

This routes crash-after-accept the same way the sender already handles
in-process `provider_timeout` with `idempotency: "none"`
(`notification-backoff.ts` → `dead/outcome_unknown`). The two paths
converge on one stable code (`outcome_unknown`), which the health view
already counts in `dead_by_code`.

#### 3.4.3 Why this is sufficient (and why nothing more is needed)

The lease itself IS the in-flight marker. A `sending` row with a live
lease means "a specific worker holds this and nobody else may touch
it". When the lease expires:

- **Idempotent provider.** Replaying is safe. Return to pending.
- **Non-idempotent provider.** Replaying may double-send. Mark
  `dead/outcome_unknown`. The operator looks at the delivery log and
  decides whether to re-queue manually, with a note.

No separate `send_in_flight_marker` table is required. The P9-1 doc's
reference to such a marker predates P5-5's lease work; the lease now
provides the same evidence.

Edge case: the `attempt_count` increment at claim time commits before
the SES call. If the SES call *definitely* didn't start (e.g. the
worker crashed between `commit` and `fetch`), the attempt counter is
still consumed. That is intentional — it's conservative, and the row
still ages out at 72 h if we somehow failed to resolve it. The worst
outcome is "one wasted attempt", never "silent duplicate".

### 3.5 Error mapping (SES → `EmailProviderError`)

Table authored for review and the adapter's tests:

| SES / HTTP condition | Error code | `kind` | `ambiguous` |
|---|---|---|---|
| 200 OK, `MessageId` present | n/a — resolve `sent` | — | — |
| `MessageRejected` (invalid recipient domain etc.) | `provider_rejected_permanent` | permanent | false |
| `MailFromDomainNotVerifiedException` | `provider_rejected_permanent` | permanent | false |
| `ConfigurationSetDoesNotExistException` | `adapter_misconfigured` | permanent | false |
| `SendingPausedException` (account-level pause) | `provider_rejected_transient` | transient | false |
| `ThrottlingException` / HTTP 429 | `provider_rejected_transient` | transient | false |
| HTTP 5xx (service unavailable, internal error) | `provider_unreachable` | transient | **true** |
| Connect refused / DNS failure | `provider_unreachable` | transient | false |
| TCP reset mid-body / stream dropped | `provider_unreachable` | transient | **true** |
| `AbortError` (our timeout) | `provider_timeout` | transient | **true** |
| Signature validation error (SigV4 broken) | `provider_protocol_error` | permanent | false |
| Everything unmapped | `provider_rejected_transient` | transient | false |

The `ambiguous` flag is set only when the TCP connection was
established and the request body sent (we can't rule out that SES
accepted it). Pre-connect failures (DNS, refused socket) are
unambiguous. The adapter must never read error prose to decide
`ambiguous` — only the SDK's own structured fields or network state.

New env vars (added to `packages/config/src/email.ts` as part of this
PR, and only read when `EMAIL_PROVIDER=ses`):

| Variable | Required when `EMAIL_PROVIDER=ses` | Purpose |
|---|---|---|

| `EMAIL_AWS_ACCESS_KEY_ID` | yes | SigV4 access key id. |
| `EMAIL_AWS_SECRET_ACCESS_KEY` | yes | SigV4 secret. Wrapped as `EmailSecret`; logs and dumps print `[redacted]`. |

Guards (mirroring the P9-1/P9-2 pattern):

- `EMAIL_AWS_*` must be server-only. The existing
  `assertNoPublicEmailVariables` already covers names matching
  `/(EMAIL|SMTP|MAIL)/i`; add a parallel guard for `/(AWS|SES)/i` so a
  stray `NEXT_PUBLIC_AWS_ACCESS_KEY_ID` is refused at startup.
- `EMAIL_PROVIDER=ses` is refused in local and in CI
  (`GITHUB_ACTIONS === "true"`), same as any real provider.
- The access key / secret pair must both be set, and neither must look
  short (minimum lengths, same shape as the existing `apiKey` check).
- Credentials are **not** supplied in `.env.example`. Instead,
  `.env.example` describes how to export them from the operator's
  password manager at run time; the file is public.

### 3.9 Operator release gates

Nothing in this PR flips the pause switch. The gates below must be
satisfied **in writing** before the first production send:

1. **D-PROVIDER.** SES selected (recorded in the decision record).
2. **D-DOMAIN.** Production sending domain approved, DKIM/SPF
   configured, verified in SES.
3. **D-LEGAL.** Transactional-only classification reviewed by a
   qualified person.
4. **D-CONSENT.** Consent model aligned with D-LEGAL.
5. **D-WORKER.** Worker deployment plan (long-running process vs
   cron) documented and matches the lease / heartbeat assumptions.
6. **Q-CONFIRM.** Operator check recorded for staging and production
   (date, operator name, test send to a verified address, Delivery
   event received, suppression ingested on a Complaint event).
7. **AWS production access** granted; `GetAccount.ProductionAccessEnabled
   === true` in production.
8. **IAM policy** limited to `ses:SendEmail` and `ses:GetAccount`,
   scoped to the sending identity. No `*` actions.
9. **Monitoring alert routing** wired to a human on-call.
10. **This PR** merged with the pause switch still `false`; a separate,
    reviewed, dated operator action turns it on.

## 5. Failure scenarios and test plan

### 5.1 Scenario matrix

| # | Scenario | Expected outcome | Where proved |
|---|---|---|---|
| 1 | SES returns `MessageId`, worker records sent | row `sent`, `provider_message_id` set, one message, no retry | unit (fake transport) + integration |
| 2 | SES returns `MessageRejected` | `dead/provider_rejected_permanent`, address kept, no retry | unit |
| 3 | SES returns `ThrottlingException` | `retry` with ≈5-min backoff, `provider_rejected_transient` | unit + backoff tests |
| 4 | SES returns 5xx | `provider_unreachable` (`ambiguous=true`), ambiguous handling applies | unit |

## 6. Decisions requiring approval

1. **AWS SDK versus hand-rolled transport (§3.2).** Recommend
   `@aws-sdk/client-sesv2` added only to `apps/worker/package.json`.
   Decision owner: engineering lead.
2. **SES event-destination correlation (§3.1).** Recommend both
   `EmailTags: delivery_id` and an `X-Kolekto-Delivery-Id` header.
   Confirm the delivery_id is not sensitive to echo in SES's own
   metrics (it's a UUID, so yes, safe).
3. **Credential source (§3.6).** Recommend static access-key/secret in
   the operator's secret store, not an EC2 instance role (keeps the
   worker's deployment story simpler and matches the current ADR
   0007 posture). Decision owner: operator.
4. **Configuration Set (§3.6).** Recommend creating one with event
   destinations pointing at the SNS topic that P9-2 already consumes,
   so sent-send events are correlated by delivery_id. Decision
   owner: operator, in the setup runbook.
5. **Timeout defaults (§3.6).** Recommend 10 s per request (SES p99 is
   well under 1 s for well-formed sends). Approve or revise.
6. **Resolve-ambiguous as a separate function vs. a flag on
   `recover_expired_notification_lease` (§3.4.1).** Separate function
   is cleaner and keeps the P5-1 contract unchanged (two functions,
   each one does one thing). Approve or revise.
7. **Signaling `resolved_ambiguous` vs `recovered` on the health log
   line.** Add both. The P5-5 alert thresholds say "ambiguous events
   are rare at steady state"; a non-zero count for several consecutive
   ticks is signal.
8. **Where to document AWS production-access gating.** Add §10.6.4 to
   the decision record *and* a runbook. The runbook is what an
   operator checks before touching the pause switch.
9. **IAM policy minimum.** Recommend `ses:SendEmail`, `ses:GetAccount`
   scoped to the sending identity. The webhook ingestion already needs
   nothing on AWS side beyond the SNS topic subscription that is
   outside the sender's IAM scope. Confirm with operator.
10. **Behaviour on `GetAccount` network failure at startup.**
    Recommend `adapter_misconfigured` → sender halts. Alternative is
    to retry `GetAccount` with backoff; rejected because startup
    retries delay the maintenance loop and the operator should see a
    clean "misconfigured" signal rather than a hang.

## 7. Explicit safety restatements

- The sender **stays disabled** throughout this PR. The migration
  does not touch `notification_sender_state`, the config change does
  not flip anything, and the factory refuses `ses` unless
  `REAL_EMAIL_PROVIDERS` lists it — which is itself the change the
  PR introduces, and the environment guards still refuse `ses` in
  local, CI and `KOLEKTO_ENV=production` until all §3.9 gates are

- **No real email is sent** by any test or build step.

- **No payment / wallet / withdrawal / settlement / ledger code**

- **No weakening** of suppression, idempotency, retry limits,
