# M13.2 P9-2 — SES/SNS event ingestion (implementation record)

## What this phase delivers

The receiving half of the email delivery-feedback loop. Amazon SES posts
events (Delivery, Bounce, Complaint, Reject, Rendering Failure) through
Amazon SNS. A new HTTP endpoint on the Next.js app
(`POST /api/webhooks/ses`) authenticates each SNS envelope, records it
durably, and applies the matching side effect: a permanent recipient
suppression for hard bounces and complaints, or a `sent → delivered`
transition on `notification_deliveries`.

The sender itself is not touched. No real email is enabled. No AWS resource
is created. The sender pause switch (M13.2 P5-5) stays off.

## What this phase deliberately does not do

- No SES sending adapter, no SES SDK dependency, no `ses` entry in
  `REAL_EMAIL_PROVIDERS`. That is P9-4 and is gated separately.
- No AWS resource provisioning: SES identity, SNS topic, subscription, IAM
  roles and policies are the operator's responsibility (see
  `docs/runbooks/ses-sns-webhook-operator-setup.md`).
- No change to the sender runtime: `app.reserve_email_attempt`,
  `app.claim_notification_delivery`, `app.resolve_notification_claim`,
  rate limits, retry policy, backoff, lease semantics — all untouched.
- No modification of the P9-1 recipient-suppression migration or the
  `app.set_email_suppression` setter. The new SES entry point delegates to
  that setter so the lock order and append-only guarantees stay in one
  place.
- No contributor payment receipts, no payment integration, no templates,
  campaigns, preferences, unsubscribe flows or later roadmap milestones.
  Payment integration still does not exist in this codebase; receipts
  remain a future product requirement outside this PR.

## Architecture

### Event ingestion sequence

```
POST /api/webhooks/ses
   │
   ├─ 1. method is POST — else 405 with Allow: POST
   ├─ 2. Content-Type is text/plain or application/json — else 415
   ├─ 3. Content-Length <= 256 KiB — else 413 (and re-checked after read)
   ├─ 4. adapter.authenticate(rawBody) — SNS signature over the exact bytes
   │     - rejects: 400 with a stable reason code
   ├─ 5. envelope.TopicArn equals EMAIL_AWS_SNS_TOPIC_ARN
   │     (adapter enforces this; route defends in depth)
   ├─ 6a. SubscriptionConfirmation → adapter.confirmSubscription(SubscribeURL)
   │      - 200 on confirmed, 400 on refused
   ├─ 6b. Notification → adapter.classifyEvent(envelope)
   │      - normalizes to delivery | bounce_permanent | bounce_transient
   │        | complaint | rejection | rendering_failure | other
   ├─ 7. db.insertEmailDeliveryEvent (ON CONFLICT DO NOTHING on
   │      (provider, provider_event_id))
   │     - duplicate → ack with outcome: duplicate, no side effect
   └─ 8. apply side effect:
          - bounce_permanent → db.recordSesSuppression(reason: hard_bounce)
          - complaint        → db.recordSesSuppression(reason: complaint)
          - delivery         → db.recordSesDeliveryEvent (sent → delivered)
          - everything else  → no_op (recorded in ledger only)
```

### Idempotency

The UNIQUE index on `public.email_delivery_events (provider,
provider_event_id)` IS the deduplication (D-25). A replayed SNS
Notification carries the same `MessageId`, conflicts on the index, and the
route returns 200 having applied no side effect. The suppression and
delivery-status entry points are themselves idempotent: a permanent
suppression that already exists is a no-op refresh, and
`app.record_ses_delivery_event` matches zero rows for a non-`sent` status
and returns 0.

### Security controls

- **SNS signature verification runs on real bytes.** The route reads
  `request.arrayBuffer()` and passes that to the adapter unchanged — no
  JSON re-serialisation between receive and verify.
- **Signing cert URL is allowlisted** to `sns.<EMAIL_AWS_REGION>.amazonaws.com`
  (or `.com.cn`) over HTTPS, default port, no credentials, no fragment,
  no redirects.
- **Topic ARN is matched exactly** against `EMAIL_AWS_SNS_TOPIC_ARN`
  (whose region segment must equal `EMAIL_AWS_REGION`, cross-checked at
  config load).
- **Signature versions 1 (RSA-SHA1) and 2 (RSA-SHA256) are supported.**
  Anything else is `unsupported_signature_version`. Operators should
  configure SNS topics to use v2 — v1 remains accepted because AWS still
  issues it on some paths, but production should prefer v2.
- **Timestamp skew bounded** to 15 minutes to defuse replay.
- **Cert fetch is bounded**: 3-second timeout, 32 KiB max body, 32-entry
  in-memory cache, 24-hour entry age.
- **No PII in logs or response bodies.** Rejection responses contain only
  a stable snake_case code (`missing_signature`, `bad_signature`,
  `untrusted_cert_url`, …). The event payload is written to the ledger
  (where no client role has read access) and never echoed back.
- **Operator-only DB entry points.** Both `app.record_ses_suppression` and
  `app.record_ses_delivery_event` are `SECURITY DEFINER` with the
  `current_setting('role') = 'none'` gate; they are reachable only from
  the webhook route over `withOwnerConnection`.
- **Append-only ledger.** `public.email_delivery_events` enforces append-only
  via a trigger (same model as `public.financial_events`).
- **SubscribeURL hostname is re-checked** against the allowlist before any
  fetch; a signed envelope that somehow carried an untrusted SubscribeURL
  is still refused.

### Delivery-status transitions

```
notification_deliveries.status:
  sent     → delivered    (allowed; only on matching provider_message_id)
  dead     → delivered    (REFUSED — a dead row is terminal)
  skipped  → delivered    (REFUSED — never sent in the first place)
  pending  → delivered    (REFUSED — not yet sent)
  sending  → delivered    (REFUSED — resolve_claim path owns this row)
  delivered → delivered   (NO-OP — idempotency)
```

The gate is implemented in SQL (`WHERE status = 'sent'`), so the
application cannot bypass it by passing wrong parameters.

### Suppression writes

Reason codes accepted at the SES entry point: `hard_bounce`, `complaint`.
Any other reason raises `INVALID_REASON (22023)` so a classification bug
cannot write a `manual_block`, `list_unsubscribe` or
`transient_bounce_capped` row through the webhook path.

Source identification: `source = 'ses_event'`. Source event id prefers
the SES `feedbackId` and falls back to the SNS `MessageId` when the event
does not carry a feedback id.

Transient bounces, rejections and rendering failures ARE recorded in
`public.email_delivery_events` but DO NOT suppress. A later milestone may
introduce `transient_bounce_capped` logic over counted events.

## Configuration

Two new server-only environment variables, both validated at config load.
Setting one without the other fails closed at startup.

- `EMAIL_AWS_REGION` — e.g. `eu-west-1`. Letters, digits and hyphens only.
- `EMAIL_AWS_SNS_TOPIC_ARN` — e.g.
  `arn:aws:sns:eu-west-1:123456789012:kolekto-ses-feedback`. Must be a
  well-formed AWS SNS Topic ARN whose region segment equals the configured
  `EMAIL_AWS_REGION`.

Both are rejected as `NEXT_PUBLIC_*` (same guard that rejects
`NEXT_PUBLIC_EMAIL_API_KEY`).

A proposed `EMAIL_AWS_SES_WEBHOOK_SECRET` from the earlier design is
**not** added: SNS signature verification uses the signed envelope plus a
cert fetched from a strict hostname allowlist, and adding a shared secret
would be security theatre.

Local-development seam: when `KOLEKTO_ENV=local` and
`SES_FAKE_WEBHOOK_SECRET` is set (≥ 8 chars), the route uses the
deterministic HMAC fake adapter instead of the real SES/SNS adapter. In
hosted environments the variable is ignored and the real adapter runs
unconditionally.

## Database migration

`supabase/migrations/20261023120000_email_delivery_events.sql`

Adds:

- `public.email_delivery_events` (append-only ledger, deny-all RLS,
  no client grant).
- Unique index `(provider, provider_event_id)` — the dedupe.
- `app.record_ses_suppression(address, reason, feedback_id, message_id)` —
  operator-only; delegates to `app.set_email_suppression` with
  `source = 'ses_event'`.
- `app.record_ses_delivery_event(provider_message_id, delivered_at)` —
  operator-only; `sent → delivered` only.
- Append-only trigger refusing UPDATE / DELETE / TRUNCATE on the ledger.

The migration does not modify the P9-1 recipient-suppression migration or
any sender migration.

## Outstanding risks and decisions

- **Retention policy** for `public.email_delivery_events` is not set. The
  previous design proposed 90 days; this record notes that retention
  belongs with the broader `financial_events.payload` retention review
  (O-10 in the decision record) and is deferred to a later operator-
  controlled migration. Rows are append-only until then.
- **SignatureVersion 1** is accepted. A follow-up may tighten to v2 only
  once operators have confirmed their topic is v2.
- **No E2E test** is included that exercises the full stack against a
  live Postgres plus a signed envelope. The migration pgTAP tests cover
  the database guarantees; the adapter tests cover signature verification
  against real RSA; the route tests cover branching with the DB mocked.
  Adding an integration test that pushes a signed envelope through the
  route to the DB is a sensible follow-up but is not required for the
  receive-only, no-sending phase.
