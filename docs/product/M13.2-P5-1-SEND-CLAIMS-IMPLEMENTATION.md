# M13.2 P5-1 — Atomic Claims and Leases, as built

**Branch:** `m13.2-p5-1-claims-leases` (from `origin/main` at `f6727d2`, the PR #6 merge).
**Status:** Implemented for review. No provider dispatch, no production sending.

## What P5-1 does

A worker can now take ownership of one due `pending` email delivery —
atomically, under concurrency — hold it under a five-minute lease, leave it
exactly once with the lease token, or hand an expired lease back to the
queue. Every state change is a database function; the worker module is a thin
typed caller that enforces nothing.

- `app.claim_notification_delivery(delivery, lease_seconds)`: row lock,
  eligibility re-check, 64-hex lease from `gen_random_bytes`, status to
  `sending`, one attempt reserved — one transaction. Anything ineligible
  returns `claimed = false` with a reason (`terminal`, `exhausted`,
  `not_due`, `already_claimed`, `not_email`, `not_found`), never a raise.
- `app.claim_next_notification_delivery(lease_seconds)`: oldest due `pending`
  email row across all communities via `FOR UPDATE SKIP LOCKED`, claimed
  through the by-id function. Empty queue returns `claimed = false`.
- `app.resolve_notification_claim(delivery, token, outcome, ...)` is the
  only way out of `sending`. (Named "resolve", not "settle": the fee
  invariant forbids any `app.*` function with "settle" in its name.) The stored token must match **and** the lease
  must be unexpired, otherwise nothing is written. `sent` is terminal and
  stores the provider id; `retry` returns to `pending` with a
  caller-supplied `next_retry_at` and the attempt kept consumed; `dead` is
  terminal with a stable `error_code`. Misuse (unknown outcome, a code where
  none belongs) raises: that is a worker bug, not a race.
- `app.recover_expired_notification_lease(delivery)`: an expired `sending`
  row returns to `pending` with the lease cleared, so the old token can never
  settle afterwards. A live lease is refused.

Table guarantees (CHECK-enforced, not conventional): only a `sending` row
holds a lease, every `sending` row holds a complete one, tokens are 64 hex
chars, attempts never exceed 3.

## Concurrency argument

- One id, two workers: the second blocks on the row lock, then re-validates
  after it and reports `already_claimed`. Only the first can succeed, because
  the status check happens after the lock is held in the same transaction.
- Queue scan, N workers: `SKIP LOCKED` skips rows another worker holds.
- Recovery vs. a slow worker: recovery clears the token in the same update
  that returns the row to `pending`; the old worker's settle then finds no
  matching token and changes nothing. Exactly one of them can move the row.
- Exactly-once email delivery is **not** claimed: the lease proves this
  worker holds the current claim, never that the provider accepted nothing.
  The provider-accepted-then-crash case stays residual (decision record
  §10.3) and is absorbed later by provider idempotency plus `outcome_unknown`.

## What P5-1 deliberately does not do

- No provider call, no sender loop, no tick. The claim transaction must be
  committed **before** any future provider call executes, never held across
  one — `notification-send-claim.ts` states this at the top.
- No rate-limit ledger (P5-2): only a successful claim reserves an attempt,
  so a deferral can never consume one.
- No backoff computation: `retry` takes `next_retry_at` from the caller.
- No 72-hour expiry housekeeping. Expired `pending` notifications must
  eventually become terminal with `event_too_old`, including while sending
  is paused — that belongs to the sender milestone with the pause switch
  (P5-5), which owns the queue's oldest-first order, the backlog cap and the
  health view (decision record §10.6.1). P5-1 only guarantees that nothing it
  builds blocks that later transition: recovered and retried rows stay
  ordinary `pending` rows any housekeeping query can see.
- No held-queue interaction: `notification_events_held`, release and discard
  are untouched. Held events are never auto-released or drained.
- No financial, payment, withdrawal, settlement, refund, authentication or
  consent changes; `consent_messages_at` never written. Fake/Mailpit
  restrictions unchanged; production sending stays structurally disabled
  (no real provider exists).
