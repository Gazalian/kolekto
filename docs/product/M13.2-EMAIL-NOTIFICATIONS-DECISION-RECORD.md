## 1. Purpose and scope

M13.2 adds an email channel to the notification system built in M13.1, for a deliberately small
set of important personal notices. In-app notifications remain the default channel for routine
events. The architecture must allow a WhatsApp adapter to be added later without rewriting event
processing, but WhatsApp, SMS, announcements, reminders, a preferences UI, delivery webhooks and
anything touching payments, ledger, withdrawals, settlement, refunds, partial payments, legacy
migration or password reset are **out of scope** (see section 13).

### 2.4 Delivery-record access (the M13.1 gap that must close before any email row exists)

`notification_deliveries_select_officer` (`20261007100000:229-236`) lets **any current officer of
the community**, of any role, `SELECT` every delivery row including `recipient_address`,
`error_code` and `error_message`. By contrast `members` rows are gated on
`app.has_permission(community_id, 'member.view_contact')`. Once email rows exist, the delivery
policy would leak addresses that the members policy deliberately protects.

**Rechecked against the actual role grants (rev. 2).** The original brief assumed collectors do
not hold `member.view_contact`. They do, and so do two other roles:

| Role | Holds `member.view_contact`? | Notes (`20260917120400`) |
|---|---|---|
| owner | Yes (owner receives the whole catalogue) | |
| admin | Yes (line 101) | |
| treasurer | Yes (line 127) | |
| collector | **Yes, `scoped = true`** (line 158) | |
| viewer | **Yes** (line 170) | read-only oversight role |

Worse, the `scoped` flag does not restrict this check: `app.has_permission(community, perm)`
(`20260917120400:325-346`) joins `officer_terms` to `role_permissions` on role and permission
**and never reads `rp.scoped`**. Scope is enforced only by a separate, collection-specific
helper (`20260917121000_rls_policies.sql:30-74`). Consequently the existing
`members_select_officer` policy lets a scoped collector and a viewer read **every** member's
email and phone in the community. That is a pre-existing finding, outside M13.2's remit to fix
(recorded as D-SECURITY-FINDINGS), but it settles the delivery-log design: **`member.view_contact`
(or `has_permission` of any permission held by collector/viewer) cannot be the gate for email
delivery rows.** See section 9.

## 3. Principles

1. **In-app is the default.** Email is reserved for important personal notices.
2. **Membership record ≠ user account ≠ verified email ≠ verified phone.** No one of these is ever
   treated as proof of another.
3. **A supplied address is not a verified address.** Nothing in M13.2 marks a contact verified.
4. **Never fabricate consent.** M13.2 never writes `consent_messages_at`.
5. **Skipped, not silent.** An email candidate that is ineligible produces a `skipped` delivery
   row with a stable reason code.
6. **Honest delivery semantics.** The queue is at-least-once. External delivery is at-least-once
   unless a provider's idempotency guarantee says otherwise. We do not claim exactly-once.
7. **Minimal content to unverified addresses.** The content permitted for an address is a function
   of how much we know about it (section 7).
8. **No parallel permission system.** Use the existing `permissions` / `role_permissions`
   catalogue and `app.has_permission`. `member.view_contact` is **not** the gate for delivery rows
   (section 9.1); a single new catalogue entry is proposed instead (9.2, Q-PERM).

## 4. Revised event-to-channel matrix

**Policy:** an audit action that exists is *not* a reason to email. An event is an email
candidate only if it appears with "Email = Yes" below. Events that are not email candidates
**never create an email delivery row** (they are not "skipped"; they were never candidates).

### 4.1 Email candidates (M13.2)

| # | Event (type) | Source audit action | Recipient | In-app | Email | WhatsApp (future) | Notice class |
|---|---|---|---|---|---|---|---|
| E1 | Member added to a community | `member.create` | The member (account email if confirmed account; else the supplied contact) | Only if the member has an account (`user_id`) | Candidate | Later, via adapter | Minimal membership confirmation |
| ~~E1b~~ | ~~Invite redemption that creates a membership (no approval required)~~ | `member.join_via_invite` | — | None for the joiner (officers keep their M13.1 in-app alert) | **Withdrawn by R1.** No email | — | — |
| E2 | Join request approved | `member.approve_join` | The member | Existing M13.1 in-app (accounts only) | Candidate | Later | Minimal membership confirmation |
| E3 | Join request rejected | `member.reject_join` | The requester, only if a contact survives in `before_state` | None | Candidate, **conditional** (see 4.2) | Later | Minimal decision notice |
| E4 | Officer appointed | `officer_invitation.accept` (creates the term) | The new officer's **verified account email** | Yes (new) | Candidate | Later | Account notice |
| E5 | Officer term ended | `officer_term.end` | The former officer's **verified account email** | Yes (new) | Candidate | Later | Account notice |

Notes:

- **Invite path (R1, decided).** `member.join_via_invite` continues to notify *officers* in-app
  (M13.1) and **never** produces a joiner email, whatever the link's approval setting. The
  anonymous invite form is therefore not a mail trigger: an address typed into it is not mailed
  unless an officer then approves that very request. For a link that requires approval, the later
  `member.approve_join` produces E2. For a link that does not, the joiner receives no email in
  M13.2; `redeem_invite_link` returns their member code, which is shown on screen at the moment
  they join. The worker does not read member status to decide anything on this path, which removes
  the race the earlier E1b design had.
- **One confirmation per membership.** E1 (manual add) and E2 (approval) are the two events that
  confirm a membership. They share one de-duplication key on the email delivery,
  `membership_confirmation:{member_id}`, enforced by a unique index (P2), so an event processed
  twice, or a membership that is somehow both added and approved, yields one email. Different
  actions still produce their own in-app events; only the **email** is collapsed.
- **E3** needs engineering work the other events do not: the member row is deleted, so the
  recipient and community name must come from the audit row, and the M13.1 trigger forwards only
  `after_state`. P3 must forward a *narrow* set of fields (contact email, display name, community)
  and must **not** copy the whole `to_jsonb(member)` (phone, attributes) into `pgmq`. The
  officer's free-text `reason` must **not** be emailed.
- **E4** is "officer appointed" at the moment the term is created (invitation accepted). Email at
  the moment an invitation is *sent* is excluded (4.3).
- **"Officer-term changes" (rev. 2).** The only term-lifecycle audit actions that exist are
  `officer_invitation.accept` (term starts) and `officer_term.end` (term ends). There is **no
  role-change action**; a role change would need a new domain function and is therefore not part of
  M13.2. E4 and E5 are the full set of officer emails.
- **E1 for officers adding members in bulk** (import, bulk add) is a separate path. P3 must
  inventory every member-creation path (`create_member`, `redeem_invite_link`, importer, any
  bulk/roll flow) and decide per path; only `create_member` is confirmed in scope by this record.

### 4.2 E3 recipient rule

Send only if (a) `before_state` contains a contact email, and (b) that email was supplied by the
requester through the invite form (`members.joined_via = 'invite_link'`), which is closer to the requester's own
intent than an organizer-typed address. If the row was not self-supplied, or no email exists,
record `skipped` with `no_recipient_address`. The rejection email states the decision only;
no reason, no member ID (the person was never accepted).

### 4.3 Explicitly **not** email in M13.2

| Event | Channel decision | Why |
|---|---|---|
| `collection.publish` (published) | In-app only | Routine lifecycle (Decision A). Already shipped in M13.1. |
| collection paused / resumed / closed | In-app only; **not built in M13.2** unless separately requested | Routine lifecycle. The original plan emailed resumed/closed; that is withdrawn. |
| `officer_invitation.create` (invite sent to a future officer) | Not in M13.2 | The message would carry a credential-bearing accept link. Needs its own security design and approval. |
| `officer_invitation.accept` → notify owners/admins | In-app only if desired | Optional; not an email candidate. |
| Announcements, reminders | Out of scope | M13.3 / M13.4. |
| Payments, receipts, withdrawals, settlement, refunds | Out of scope | Require separate financial-policy decisions. |

The original plan's "five additional lifecycle events" (`collection.closed`, `collection.paused`,
`collection.resumed`, `member.rejected`, `officer.term_ended`) are therefore reduced: three
withdrawn from email entirely, `member.rejected` kept as E3 (conditional), `officer.term_ended`
kept as E5.

## 5. Membership confirmation rules (Decision B)

When an organizer adds a person (E1) or an eligible join request is approved (E2):

1. The membership record exists and carries a `member_code`. If `member_code` is null at event
   time, the email is **skipped** with `member_code_missing`; it is never sent without the ID, and
   the code is never generated by the notification system (identity model stays owned by
   `app.next_member_code`).
2. The email may contain **only**: community name, the person's `member_code`, a statement that
   they have been added/approved, the date of the action (from the audit row `created_at`, not
   "now"), and a safe next step *if one exists* (the community's public contact route, if the
   community has one; otherwise none).
3. The email must **not** contain: `members.id`, any other member's data, collection or balance
   data, officer names beyond what the community has made public, or sensitive administrative
   details (audit reason, status internals).
4. The email wording must not claim the address or phone is verified, and must not imply the
   recipient has a Kolekto account. It should invite the recipient to tell the community if the
   message is not meant for them (see 7.3 on misdirected mail).
5. The `member_code` confirms the **membership record only**. It is not proof of ownership of the
   email or phone and is never treated as such by the system.
6. Event payload is a frozen snapshot (name, community name, `member_code`, action date) taken at
   event time, so a later rename does not change a sent message (consistent with M13.1 `payload`).
7. The event model is channel-neutral: one `notification_events` row, N delivery rows
   (in-app / email / future WhatsApp). A WhatsApp adapter later consumes the same event and
   snapshot and implements the same adapter interface; no processor rewrite.

Contact verification for non-account members (so that richer content could later be sent) is a
**separate mechanism** (OTP or verification link), not designed or implemented here. See Q-VERIFY.

## 6. Account verification dependency (Decision C)

This section answers the five questions the product owner required before recipient eligibility
is implemented. It is analysis and a minimal-remediation list. **M13.2 changes none of the
authentication behaviour described here.**

### 6.1 The five questions

**1. What is the authoritative source for email verification?**
GoTrue's own record: `auth.users.email_confirmed_at` (non-null = confirmed), read together with
`auth.users.email` (the address that was confirmed). `auth.users` is owned by the auth service;
application roles have no write access to it. Not authoritative:

| Field | Why it is not evidence |
|---|---|
| `public.users.email` | A copy written once by the `AFTER INSERT` trigger `on_auth_user_created` (`20260918140000_user_bootstrap.sql:148`, function body in `20260930110000`). There is **no `UPDATE` trigger**, so it never follows `auth.users`. It carries no verified flag. |
| `public.users.identity_level` | See question 3. |
| `members.email` | Typed by an officer or a joiner. Never verified (Q-MISDIRECT). |

**2. Can the server reliably check it?**
Yes, with one small addition, but this is **proposed and must be proven by a P4 test against the
local GoTrue**, not assumed. A `SECURITY DEFINER` function in the `app` schema
(working name `app.resolve_verified_account_email(user_id uuid)`) would return
`auth.users.email` only when `email_confirmed_at is not null`, and `NULL` otherwise. Properties
required of it: explicit `revoke execute … from public` (repo rule), execute granted only to the
worker's role, returns the address only (never other `auth.users` columns), and a row in the grant
matrix. The worker must not be given general read access to `auth.*`.
Residual conditions the test and the operator check must cover: (a) confirmation really is
required on the hosted projects (6.2); (b) the behaviour of an **email change** — the app
never calls `updateUser({ email })` (only `{ password }`, in `account/actions.ts:51` and
`ResetPasswordForm.tsx:46`), but a signed-in user can call GoTrue's email-change endpoint
directly, so P4 must verify that `auth.users.email` and `email_confirmed_at` remain consistent
through a change (the `secure_email_change` family of settings is not set in `config.toml`, so
GoTrue defaults apply and must be checked rather than assumed).

**3. Why can `identity_level = 'contact_verified'` not be trusted on its own?**

- It does not say **which** channel was verified. The enum comment is "phone OTP and/or email OTP"
  (`20260917120200_users.sql:26`).
- It is set by `app.set_contact_verified()`, which takes **no proof**: it upgrades the caller's own
  row from `none` whenever called (`20260930110000:165-189`). The function is granted to
  `authenticated` and invoked by a bare server action,
  `setContactVerifiedAction` (`apps/web/app/(auth)/verify/actions.ts`), which performs no check of
  its own. Any code path that reaches it, or any authenticated caller able to execute the
  function, can self-assert the level.
- Its column comment says the level's required checks are "per DEC-04 … not encoded here".
- It is a one-way, user-level flag; it does not track the address later changing.

It may remain useful as a coarse onboarding signal. It must never be consulted for email or phone
eligibility.

**4. What phone-verification capability is missing?**
Essentially all of it:

- `public.users.phone_e164` is written by `app.update_user_profile` from user input with only
  format normalisation (`20260930110000:121-155`); nothing proves ownership.
- GoTrue can record `auth.users.phone_confirmed_at`, but no phone-OTP sign-in or phone-change flow
  is wired in the app, and no SMS provider is configured (`config.toml:139-140`: the local stack
  "sends no SMS and prints codes to the CLI log"; hosted provider selection belongs to DEC-17).
- `members.phone_e164` is likewise officer- or joiner-typed.
- There is therefore **no field anywhere that means "this phone is verified"**.

**5. What is the minimal remediation before an account's email or phone can be called verified?**

| Item | Needed for | Minimal remediation | In M13.2? |
|---|---|---|---|
| Account email | Sending E4/E5 and account-addressed E1/E2/E3 | (a) `app.resolve_verified_account_email` as in 2 above; (b) hosted-confirmation check (6.2); (c) email-change consistency test | (a), (c) in **P4** as part of recipient eligibility; (b) is an operator task |
| Account phone | Any future SMS/WhatsApp to an account | Phone OTP via GoTrue phone change or sign-in; an SMS/WhatsApp provider; a derived read (`auth.users.phone_confirmed_at`) instead of trusting `users.phone_e164`; stop presenting an unverified `phone_e164` as a contact | **No.** Separate engineering requirement (D-PHONE) |
| `identity_level` | Not needed for email | Make `set_contact_verified` derive from `auth.users` evidence, or retire it | **No.** Separate reviewed change (D-SECURITY-FINDINGS) |
| Member (non-account) contacts | Notices beyond minimal confirmation | OTP or link verification of the contact | **No.** Separate mechanism (D-VERIFY) |

Statements that remain true in M13.2: email eligibility never depends on phone status;
membership confirmation is never treated as verification of any contact; `identity_level` is never
read.

### 6.2 Hosted-configuration check for email confirmation (Q-CONFIRM) — required before production

Local `supabase/config.toml` sets `[auth.email] enable_confirmations = true` (line 89), but that
file configures the **local** stack. Hosted staging and production are separate projects whose
settings are not proven to match. The operator check, to be recorded with date, project and
person in the production-readiness record before P9:

1. In each hosted Supabase project, confirm email confirmation is **required** (the Auth email
   provider setting commonly labelled "Confirm email"; labels vary by dashboard version) and that
   no auto-confirm is enabled.
2. Read-only data cross-check in each project (no writes): count users who have signed in without a
   confirmed email. A non-zero count would indicate confirmation was off at some point.
   ```sql
   select count(*) as signed_in_unconfirmed
   from auth.users
   where email_confirmed_at is null
     and last_sign_in_at is not null;
   ```
   A zero result is supporting evidence, not proof. Pre-existing users created before the setting
   changed may legitimately differ; investigate rather than assume.
3. Confirm the email-change settings (secure email change / double confirmation) are enabled.
4. Record the result for staging and production **separately**. A local-only pass is not
   acceptable.

Until this is recorded, `app.resolve_verified_account_email` is **not trusted for production
sending**, and M13.2 may not be declared production-ready.

## 7. Recipient eligibility matrix (Decision D) — approved with safeguards

### 7.1 Definitions

- **Minimal membership confirmation (N1):** the E1/E2 content in section 5.
- **Minimal decision notice (N1-R):** the E3 content (decision only).
- **Account notice (N2):** E4/E5; addressed to a user, content limited to community name, role
  and date. No financial or member data.
- **Sensitive/confidential (N3):** anything else (member lists, collection details, balances,
  credential-bearing links). **No N3 notice is sent by M13.2 to any address.**
- **Contact assurance** (recorded on every email delivery row, proposal for P2):
  `verified_account` (address confirmed by GoTrue), `unverified_supplied` (organizer- or
  joiner-supplied member contact). There is no third value until a contact-verification mechanism
  exists. The row never says "verified" for an address that is not `verified_account`.

### 7.2 Matrix

"Account" means `members.user_id` is set. The account email is the confirmed address from the
section 6 function; `members.email` is never used for a member who has an account.

| Recipient situation | N1 / N1-R (E1, E2, E3) | N2 account notice (E4, E5) | N3 sensitive | Outcome when not sent |
|---|---|---|---|---|
| **Account holder, email confirmed** | **Send** to the confirmed account address (`verified_account`) | **Send** | Out of scope | — |
| **Account holder, email unconfirmed** | **Skip.** No fallback to `members.email` (Q-FALLBACK) | **Skip** | Never | `skipped` / `unverified_account_email` |
| **Account holder, email confirmed, phone unverified** | **Send.** Phone status is irrelevant to email and is never consulted | **Send** | Out of scope | — |
| **Non-account member, email supplied** | **Send** minimal content to `members.email`, recorded as `unverified_supplied`; never described as verified | N/A (no account) | **Never** | If a consent condition applies and is unmet: `skipped` / `consent_missing` |
| **Non-account member, no email** | **Skip** | N/A | Never | `skipped` / `no_recipient_address` |
| **Non-account member, unverified contact** | Identical to "email supplied": **every** non-account contact is unverified until a verification mechanism exists | N/A | **Never** | as above |
| **Community or notice requiring stronger confidentiality** (Q-MISDIRECT) | **Skip** unless the contact has been verified | N/A | Never | `skipped` / `contact_verification_required` |
| *(Future)* Non-account member, contact verified | N1 allowed; richer content only after separate approval | N/A | Separate approval | — |

Rules that follow from the matrix:

a. For an account holder who is also a member, the **confirmed account email** is used for
   E1/E2/E3; it is not an either/or with `members.email`.
b. The "stronger confidentiality" row is a **hook, not a feature**: P4 implements the check as
   "this notice class requires contact assurance ≥ X" with N1/N1-R/N2 set to accept
   `unverified_supplied` for non-account members. A per-community setting to raise that bar, and
   the verification mechanism that would satisfy it, are separate work (D-VERIFY); nothing in
   M13.2 lets a community opt in yet.
c. The contact is **recorded** as unverified on the delivery row; nothing is written to `members`
   (no verified flag, no `consent_messages_at`).

### 7.3 Safeguards on sending to unverified member addresses (Q-MISDIRECT)

Organizer-entered addresses can be wrong or belong to someone else. Approved safeguards:

- minimal content only: community name, member ID, a plain confirmation of the membership action,
  date; no financial data, no other members' data, no sensitive community data;
- no claim, anywhere in the message, that the address or phone is verified;
- a "not you? tell the community" line, and no clickable account-creation or credential link;
- contact assurance recorded as `unverified_supplied` on the delivery row;
- one email per membership (de-duplication, section 4.1).

The residual risk — a stranger learns that a named person was added to a named community — cannot
be eliminated by engineering. It is accepted by the product owner on these terms, and the
classification is flagged for legal review before production sending (D-LEGAL).

### 7.4 Stable skip reason codes

Stored in `error_code` (Kolekto vocabulary, never provider text). Visible only to authorized
roles (section 9). Codes are append-only: a code is never renamed or reused once it has shipped.

|---|---|
| `unverified_account_email` | Member has an account; its email is unconfirmed, absent, or does not match the confirmed address (Q-FALLBACK) |
| `no_recipient_address` | No usable address on any permitted source |
| `consent_missing` | The notice class requires `consent_messages_at` and it is null |
| `contact_verification_required` | The notice or community requires a verified contact and the contact is `unverified_supplied` |

## 8. Consent and message importance (Decision E) — approved; legal review required

Current state: `members.consent_messages_at` is never written. The M13.1 schema comment says,
without it, "no announcement or reminder may be sent — only receipts, codes and security
messages, which are not optional (NOT-10)".

**Policy (approved):**

| Class | Examples | Requires `consent_messages_at`? |
|---|---|---|
| Transactional personal notice | E1/E2/E3 membership confirmation and decision; E4/E5 officer notices | **No**, but content is restricted to the minimal fields in sections 5 and 7 |
| General / optional community communication | announcements, reminders, collection updates | **Yes**; missing consent → `skipped` / `consent_missing` |

The distinction between the two classes is preserved in code as a property of the notice type, so
reclassifying a notice is a one-line, reviewable change rather than a hunt through the sender.

Rationale for treating membership confirmation as "codes" under NOT-10: the email delivers the
member's ID. This is a **technical reading of an internal requirement**, not a legal conclusion.
NDPR/NDPA (Nigeria) applicability and the lawful basis for contacting a person added by a third
party **must be reviewed by a qualified person before production email is enabled** (D-LEGAL).

M13.2 will:

- never write `consent_messages_at`, automatically or otherwise;
- record `consent_missing` skips where the policy requires consent;
- not build a consent-capture UI or a preferences UI.

Production dependencies (not built in M13.2): a consent-capture flow that sets
`consent_messages_at`; an unsubscribe/suppression mechanism honoured by the sender (including for
transactional mail where required); a decision on whether an unsubscribe link is mandatory in N1.
Without bounce/complaint webhooks (out of scope), automatic suppression is not available, so
repeated sends to a bad address are a known gap (D-SUPPRESS).

## 10. Reliability design (summary; detail lands with P5/P6)

### 10.1 Two stages

1. **Event stage (queue):** pgmq message → `notification_events` row → delivery rows
   (in-app `sent`; email `pending` or `skipped`). Keeps M13.1 behaviour and idempotency.
2. **Send stage (table-driven):** a sender claims due `pending` email rows
   (`… for update skip locked`), sends, records the outcome. The existing
   `notification_deliveries_retry_idx` is the starting point.

### 10.2 State machine (proposal)

`pending → sending → sent` · `sending → pending` (transient failure, `next_retry_at` backoff,
`attempt_count + 1`) · `sending → dead` (permanent error or `attempt_count` ≥ max) ·
`pending → skipped` (policy). `delivered` stays reserved for webhook confirmation (out of scope).
Adding `sending` and `dead` to `notification_delivery_status` is an enum migration (P2/P5).
A `sending` row with an expired lease is reclaimable (crash recovery).

### 10.3 Duplicate sends — what we can and cannot promise

Decision (Q-DUP, amended): **avoidable duplicates are not accepted.** Defence in depth, in order:

1. **Database de-duplication.** The event key (`{action}:{object_id}`), the existing delivery
   unique index, and the new `dedupe_key` unique index (section 9.3) mean a replayed message or an
   equivalent event cannot create a second email row. This closes the *avoidable* duplicates.
2. **Replay-safe processing.** Event processing stays transactional and resumable (M13.1). The
   sender claims rows with `for update skip locked` and a lease, so two senders never hold the
   same row, and a row already `sent` is never re-claimed.
3. **Provider idempotency where available.** The stable `notification_deliveries.id` is passed as
   the provider's idempotency key if the chosen provider supports one. A provider **without**
   idempotency support is not enabled for production until its duplicate mitigation is reviewed
   (P9 gate); it is not simply tolerated.
4. **Ambiguity is recorded, not hidden.** The attempt start is persisted before the provider call
   (`sending` with a lease), so a crash leaves an observable ambiguous row, not an invisible one.

**Residual risk (cannot be removed by this system):** if the provider accepts a message and the
worker crashes **before** the `sent` outcome is committed, the lease expires and the row is
re-claimed. With provider idempotency the second call is de-duplicated by the provider (within
whatever window that provider documents). Without it, the recipient may receive the message twice.
This is the standard external-call limitation. **Exactly-once external delivery is not claimed**
and will not be claimed without evidence from the selected provider's documented guarantees plus a
crash-injection test (P5/P8).

### 10.4 Retries and dead letters

Bounded attempts (**max 3 per delivery**, aligned with the per-address limit in 10.6) with exponential backoff and jitter; only transient errors
retry. Permanent errors go straight to `dead` with a stable code. For the **queue**, the worker
must use `pgmq.read`'s `read_ct`: past a threshold, archive (or move to a `notification_events_dlq`
queue) instead of leaving the message to reappear every 30 s forever, which is today's behaviour.
Dead rows and archived messages need an operator-visible count (a view or log line) so they are
not silently lost.

### 10.5 Provider abstraction and startup guards (as built in P1)

**Interface** (`packages/adapters/src/email-provider.ts`): `EmailProvider.send({ idempotencyKey,
message }) → { providerMessageId }`, plus `idempotency: "provider" | "none"` so the sender (P5) can
treat the two honestly. Failures are `EmailProviderError` with a `kind` (`transient` | `permanent`)
and a stable `code`; messages are written by us and never contain provider text, addresses or
credentials. Every adapter validates first (single valid recipient, no CR/LF or other control or
line-separator characters in any header-bound value, non-empty plain-text part).

**Adapters:**

- **fake** — deterministic, offline, records an outbox, models provider idempotency (or, with
  `{ idempotency: "none" }`, its absence), scripted transient/permanent failures for P5/P6 tests.
- **mailpit** — SMTP to a Mailpit on this machine, development and CI only. It is a small
  hand-written client rather than a library: production providers will be HTTPS APIs (P9), so SMTP
  is needed only for a local catcher, and a general SMTP/MIME dependency would add supply-chain
  surface to the only package allowed to make outbound calls (ADR 0001) in exchange for features
  (TLS, AUTH, relaying) it must not have. It connects to loopback only and refuses construction
  otherwise, validates before connecting, RFC 2047-encodes the subject, and base64-encodes bodies so
  no body line can terminate DATA or imitate a MIME boundary. A drop after the body is sent but
  before the server's reply is reported as transient and ambiguous (§10.3). *Not yet exercised
  against a real Mailpit*: P1 tests use an in-process SMTP server; the real-Mailpit check is P8.
- **Mailpit ports (correction to rev. 1 of this record):** `supabase/config.toml`'s
  `[local_smtp] port = 54324` is Mailpit's **web UI/API**, not SMTP. SMTP was not published to the
  host. P1 sets `smtp_port = 54325` so the host can reach it; the local stack must be restarted
  (`supabase stop` / `supabase start`) for it to take effect.
- **No real provider adapter** exists until a provider is approved (P9).

**Configuration** (`packages/config/src/email.ts`, server-only, no defaults):
`EMAIL_PROVIDER`, `EMAIL_FROM`, `APP_BASE_URL`, `EMAIL_API_KEY` (real providers only),
`EMAIL_SMTP_HOST` / `EMAIL_SMTP_PORT` (mailpit only). `loadEmailConfig(environment)` takes the
environment from the existing `KOLEKTO_ENV` (via `loadConfig()`), so no new "is this production"
signal is invented (ADR 0007).

| Environment | `fake` | `mailpit` | real provider |
|---|---|---|---|
| local | allowed | allowed (loopback SMTP) | **refused** |
| staging | allowed (delivers nothing) | refused | allowed *(none exists)* |
| production | **refused** | **refused** | allowed *(none exists)* |
| any, under `GITHUB_ACTIONS=true` | as above | as above | **refused** |

Further guards: `EMAIL_API_KEY` set beside a local provider is refused; any `NEXT_PUBLIC_*` variable
whose name mentions EMAIL/SMTP/MAIL, or whose value equals `EMAIL_API_KEY`, is refused;
`APP_BASE_URL` must be this machine in local and `https`, non-loopback elsewhere; `EMAIL_FROM` must
be one plain address. Because `REAL_EMAIL_PROVIDERS` is empty, **production cannot start email at
all** until P9 registers a provider. The key is wrapped so logging, JSON, string interpolation and
`util.inspect` print `[redacted]`, and no error message contains a variable's value (tested).
The CI signal is `GITHUB_ACTIONS` only, not the generic `CI` variable: some platforms set `CI` at
build time, and a false positive there would block a legitimate deploy.
### 10.6 Send limits (approved numbers; design — built in P5)

The product owner approved a maximum of **three email attempts per recipient address per day across
communities** and asked for a specific hourly community limit, server-side enforcement, and
protection against concurrent bypass. This section fixes the window, the unit, the numbers and the
outcomes. Nothing here is implemented yet: enforcement lives in the sender (P5), and the tests in
this section are its acceptance tests.

**Unit — what is counted.** One **attempt** is one *reservation* made immediately before a call to
the provider's `send`. A reservation is counted whether the call then succeeds, fails or times out,
and is **never refunded**: a timed-out call may still have delivered (10.3), so refunding would let
an attacker or a flaky network exceed the cap. Not counted: a delivery that is skipped by
eligibility, a delivery deferred by the community limit, a queue replay that finds the row already
`sent`. A retry is a new attempt and is counted.

**Window — rolling, not calendar.** Both limits use a **rolling window** ending now (24 hours and 1
hour). A calendar day resets at an arbitrary midnight and would allow six sends in two minutes
across the boundary; "midnight" is also ambiguous between UTC and the recipient's own day.

| Limit | Value | Window | Scope | On breach |
|---|---|---|---|---|
| **L1 — per recipient address** | **3 attempts** | rolling 24 h | one address, compared lower-cased, across **all** communities | **Terminal skip**: delivery becomes `skipped`, code `recipient_rate_limited`; the address is erased from the row (the skipped-row constraint requires it) |
| **L2 — per community** *(approved)* | **100 reservations** | rolling 1 h | one community | **Defer**: delivery stays `pending`, `next_retry_at` = when the oldest counted attempt leaves the window; no provider call, no attempt counted |
| **L3 — platform backstop** *(approved, provisional)* | **1,000 reservations** | rolling 1 h | all communities | **Defer**, as L2 |

Because retries are counted, **max attempts per delivery is 3** (this replaces the earlier "5"
proposal in 10.4): a delivery that fails transiently twice and succeeds on the third attempt uses
the whole allowance for its address that day, which is intended — a mailbox that needs three tries
should not then be hit by a fourth message from another community.

**Why 100 per community per hour.** The only fan-out in M13.2 is one email per person per officer
action (add, approve, reject, appoint, end term); there is no bulk path and no announcement. A
community of the largest size the schema is designed for (5,000 members) onboarding people by hand
is a few dozen actions an hour; an officer clearing a queue of pending joiners might approve
~200 in a sitting. 100 attempts/hour is well above any manual rate (reaching it takes one
send every 36 seconds, sustained), so ordinary use never sees it; a queue
of 200 approvals simply completes over two hours because the surplus is **deferred, not dropped**;
and a leaked invite link or a compromised officer account can cause at most 100 sends an hour from
one community. It is deliberately below any transactional-email provider tier we might choose.
No vendor limits are claimed, because no provider is selected (D-PROVIDER); the number must be
re-checked against the chosen provider's limits at P9. L3 exists because many communities each
under L2 can still, together, harm the sending domain's reputation.

**Why L1 skips and L2 defers.** L1 exists to stop one address being mail-bombed or used to harass;
a legitimate person is added to at most a couple of communities a day, so a breach is abuse or an
error, and waiting does not make it legitimate. L2 and L3 exist to smooth volume; waiting is the
right answer, bounded by the delivery's maximum age (72 h, then `dead` with `event_too_old`).

**Server-side and concurrency-safe.** The decision is made in the database by one function,
`app.reserve_email_attempt(delivery_id)`, called by the sender inside the transaction that moves the
row to `sending`; the browser, the web app and the worker's in-memory state decide nothing. Inside
the function: (1) take `pg_advisory_xact_lock` on a key derived from the lower-cased address, then
(2) on a key derived from the community, then (3) the platform key — **always in that order**, so
two concurrent reservations cannot deadlock; (4) count the ledger rows in each window; (5) insert
the reservation only if every limit has room; (6) return `granted`, `address_limited` or
`community_deferred`. Because the count and the insert happen while the lock is held, two sessions
can never both see "2 of 3 used" and both proceed. A hash collision between two keys only makes two
unrelated reservations wait for each other; it can never let one through. The ledger is
`notification_send_attempts` (append-only; row-level security enabled and forced; **no** grant to
any client role; rows purged after 48 h). It stores the lower-cased address so it can be counted —
a deliberate, short-lived, inaccessible PII surface (recorded as risk U7). A crash after the
reservation commits but before the provider call over-counts (conservative), never under-counts.

**Auditable outcomes.** Every outcome is a row, not a log line: `granted` → the delivery row
(`attempt_count`, `last_attempted_at`) plus the ledger row; `address_limited` → `skipped` +
`recipient_rate_limited`; `community_deferred` → `pending` + `next_retry_at`, visible as a backlog
count in the delivery log; provider-rejected → `dead` + `provider_rejected_permanent`; suppressed
by maintenance → a row in `notification_suppression_log` (10.7). Raw provider text and addresses
are never part of an outcome.

**Acceptance tests (P5, must pass before the sender is enabled anywhere):**

1. *Per-address boundary.* With 2 attempts in the window, a 3rd is `granted`; a 4th is
   `address_limited`. Attempts 24 h + 1 s old do not count; 23 h 59 m old do.
2. *Case and community independence.* `Ada@Example.com` and `ada@example.com` share one budget, and
   attempts in community A count against community B's delivery to the same address.
3. *Community boundary.* With 99 attempts in the last hour, the 100th is `granted` and the 101st is
   `community_deferred` with a `next_retry_at` when the oldest attempt expires; attempts 61 minutes
   old do not count. L3 likewise at 1,000.
4. *Deferred is not an attempt.* A deferral writes no ledger row and does not change
   `attempt_count`.
5. *Concurrency, per address.* 50 database connections reserve for the same address at once
   (a script in the style of `scripts/verify/reference-concurrency.mjs`): **exactly 3** are
   `granted`.
6. *Concurrency, per community.* 200 connections reserve for 200 different addresses in one
   community: **exactly 100** are `granted`; the rest are deferred.
7. *No deadlock.* The two runs above complete with no deadlock error, including a mixed run where
   some reservations contend on the address lock and others on the community lock.
8. *No client access.* `anon` and `authenticated` cannot read or write the ledger or execute the
   function (grant matrix + role-switched pgTAP).
9. *Safe outcomes.* An `address_limited` row satisfies the skipped-row constraint (no address) and
   appears in the masked delivery log with its code; a deferral appears as a pending row with
   `next_retry_at`.

### 10.6.1 Platform backstop: operation, monitoring and safe change (approved, provisional)

**Status.** The platform-wide limit of **1,000 reservations per rolling hour** is approved as a
*provisional* backstop: it is a ceiling chosen before any provider or real traffic exists, to be
re-checked against the selected provider's limits at P9 and after the first real traffic. It does
not replace L2 (100 per community per hour), which is the limit ordinary use could ever meet; at
most ten communities can be at their own cap before L3 binds.

**Deferred-message behaviour.** When L2 or L3 has no room, the delivery is **deferred, never
dropped**: it stays `pending`, no provider call is made, no attempt is counted, and `next_retry_at`
is set to the moment the oldest reservation counted in the *binding* window leaves it. When slots
free, due rows are claimed **oldest `created_at` first across all communities**, so no community is
starved by another. A deferred delivery lives at most 72 hours, then becomes `dead` with
`event_too_old`; it is never held indefinitely and never silently discarded.

**Backlog controls.**

1. *Per-community backlog cap — 500 deferred deliveries.* A delivery that would be the 501st
   deferred one in its community is not queued: it becomes `skipped` with the stable code
   `community_backlog_full`. This bounds the cost of a compromised officer account or a leaked link
   that creates deliveries faster than they can be sent.
2. *Pause switch.* A server-side setting, `email_sending_enabled`, **false by default in every
   environment** until P9 and true only for local/CI with the fake or Mailpit adapter. When false
   the sender claims nothing. Deliveries wait and age out at 72 hours; nothing is lost early. This —
   not editing a limit — is the emergency control.
3. *Bounded life.* The 72-hour life applies to everything, including a paused queue.

**Monitoring.** A staff-only view `private.v_notification_send_health` (ADR 0009: operational data
is not client-readable) reports: reservations in the last hour for the platform and for the ten
busiest communities; L3 and L2 utilisation as percentages; the deferred backlog count and the age of
the oldest deferred delivery; deliveries `skipped` and `dead` in the last 24 hours **by code**; and
the sender's last-claim time as a heartbeat. The sender writes one structured log line per minute
with the same numbers and **no addresses, names or error text**. Proposed alert thresholds:
L3 utilisation ≥ 80 % for 10 minutes; oldest deferred delivery older than 2 hours; `dead` exceeding
10 % of attempts in an hour; heartbeat older than 5 minutes while backlog is non-zero. **Alert
routing is not built and depends on the worker's deployment (D-WORKER)**; until then the view and
the log line are the monitoring, and that must be stated in any readiness review.

**Changing a limit safely.** The numbers live in exactly one place, a function
`app.notification_send_limits()` that returns the L1, L2, L3 and backlog values. They are changed
**only** by a reviewed migration (`create or replace`), never at runtime, by a UI, or by ad-hoc SQL.
A change must: update this record; keep the boundary tests, which read the configured numbers rather
than hard-coding them, green; be applied to staging first and observed for a full hour of the
monitoring above before production. A raise applies to the next reservation. A lowering applies to
the next reservation too, and **never** revokes past reservations or cancels queued deliveries —
the surplus simply defers. L1 (3 per address) is an abuse control; changing it needs product
approval, not just engineering review.

### 10.6.2 Attempts, retries and ambiguous outcomes (approved: at most 3 per delivery)

**Rules.** At most **three attempts per delivery**; an attempt is counted at reservation (10.6).
Every outcome is classified by the adapter's `EmailProviderError.kind` and `code`
(`packages/adapters/src/email-provider.ts`) and handled once:

| Outcome | What the sender does | Retried? |
|---|---|---|
| Provider accepted | `sent`, store `provider_message_id` | no |
| **Permanent** — `provider_rejected_permanent`, `provider_protocol_error`, `invalid_message` | `dead` with that code | **No. Never.** A permanent failure is not retried, however many attempts remain |
| **Transient** — `provider_unreachable` *before* the body was sent, `provider_rejected_transient` | back to `pending` with `next_retry_at` | Yes, with bounded backoff, up to attempt 3; the 3rd failure → `dead` / `retries_exhausted` |
| **Ambiguous** — `provider_timeout`, a connection dropped *after* the body was sent, or the worker dying while a row is `sending` (lease: 5 minutes) | depends on the provider's declared idempotency — below | depends |
| `adapter_misconfigured` | cannot arise after the startup guards; if it does, the sender halts and alerts rather than consuming deliveries | n/a |

**Adapter contract gap (a P5 prerequisite).** The ambiguous case must not be inferred from message
text. Today `EmailProviderError` carries only `kind` and `code`, and the Mailpit adapter reports a
drop after the body was sent as the same transient `provider_unreachable` as a refused connection
(it differs only in its message). P5 therefore extends the error with an explicit boolean
`ambiguous` (true for a timeout or drop at or after the DATA phase), sets it in the Mailpit and fake
adapters, and tests it, **before** the sender relies on it.
**Backoff.** After attempt 1 wait 5 minutes; after attempt 2 wait 30 minutes; each with ±20 %
jitter, so a mass failure does not retry in lockstep. All three attempts fit well inside the
72-hour life.

**Ambiguous outcomes — what is and is not claimed.** When the sender cannot tell whether the
provider accepted a message:

- *Provider with idempotency* (`idempotency: "provider"`): retry as a transient failure with the
  **same** idempotency key (the delivery id). The provider de-duplicates within its documented
  window, and that window must be at least as long as the retry horizon (verified at P9). A
  duplicate is then prevented by the provider, not assumed.
- *Provider without idempotency* (`idempotency: "none"` — SMTP/Mailpit, or any provider lacking it):
  **no automatic retry.** The row becomes `dead` with the stable code `outcome_unknown`, visible in
  the delivery log, for an operator to decide. This honours "no avoidable duplicates" (Q-DUP): the
  system reports a possibly-delivered message as unresolved rather than risk sending it twice. A
  production provider without idempotency is not enabled until this behaviour is reviewed (P9 gate).
- **Exactly-once delivery is not claimed anywhere.** What is claimed: no duplicate delivery *row*
  and no *avoidable* duplicate send; and that the residual case — provider accepted, outcome
  unrecorded — is surfaced (`outcome_unknown`) or absorbed by the provider's own idempotency, never
  hidden.
- A replayed queue message or a re-claimed row that is already `sent` is never sent again.

**Acceptance tests (P5):** (1) a permanent failure produces exactly one provider call and a `dead`
row; (2) a transient failure retries at ≈5 and ≈30 minutes (jitter within ±20 %) and the 3rd failure
is `dead` / `retries_exhausted`, with no 4th call ever; (3) an ambiguous outcome with
`idempotency: "provider"` retries with the identical key and the fake provider records one message;
(4) an ambiguous outcome with `idempotency: "none"` produces `dead` / `outcome_unknown` and **no**
retry; (5) crash injection — a worker killed holding a `sending` lease — never yields two sends with
a de-duplicating provider and never yields a retry without one; (6) a replay of a `sent` row makes no
provider call; (7) the 4th message to one address within 24 hours is never attempted at all.

### 10.6.3 Provider-aware safety limits — L4 daily and L5 per-second (approved; built in P9-3)

**Status.** Added in P9-3 (migration `20261024200000_notification_quota_controls.sql`), ahead of a
real SES adapter (still P9-4, still gated on D-PROVIDER). The sender pause switch stays off; nothing
in P9-3 enables real sending. The two new numbers sit strictly below SES's sandbox quotas
(`Max24HourSend = 200`, `MaxSendRate = 1/s`) so even an unapproved AWS account cannot be throttled
by SES at the configured rate.

**Why two more limits.** L1/L2/L3 (10.6) protect the recipient (abuse) and the sending domain's
reputation at an application level. They do not know whether a specific provider's own daily or
per-second quota is close to breach. L4 and L5 are provider-aware safety limits: they are set *below*
the provider's own numbers and defer traffic that would otherwise be refused by the provider. The
provider's own `Throttling` becomes a code bug surface, not an operational one.

**Dimensions.** Both limits are split by a new `send_class` column on `notification_deliveries` and
`notification_send_attempts` (`transactional` | `bulk`, text with CHECK). Today every delivery is
written as `transactional` (processor `notification-processor.ts`, two inserts); `bulk` exists only
so L4/L5 counts split cleanly when a bulk sender milestone later opens the path. Default `bulk`
caps are **zero**, which makes every bulk reservation defer forever and age out at 72 h — a safe
"closed" state until a reviewed migration raises the two numbers together with the bulk ingress
path.

| Limit | Window | Scope | Transactional default | Bulk default | On breach |
|---|---|---|---|---|---|
| **L4 — per class, daily** | rolling 24 h | one `send_class`, platform-wide | **180** | **0** | **Defer**: `pending` with `next_retry_at = oldest counted + 24h` (fallback `now()+24h` when the ledger is empty, so a zero cap defers to the far side of the window). No provider call, no attempt counted. Reservation outcome `provider_daily_limited`. |
| **L5 — per class, per second** | rolling 1 s | one `send_class`, platform-wide | **1** | **0** | **Defer**: `pending` with `next_retry_at = now() + 1 s + jitter(0–200 ms)`. No provider call, no attempt counted. Reservation outcome `provider_rate_limited`. |

**Where enforcement lives.** Inside `app.reserve_email_attempt`, immediately after the existing
suppression/L1/L2/L3 branches. The function body is one `create or replace`; every pre-existing
branch is byte-identical. The two new checks are the last ones before the granted-insert, and the
granted-insert now stores `send_class`. Reservation outcomes `provider_daily_limited` and
`provider_rate_limited` land on the sender as the existing `deferred` SendStep kind.

**Lock order (extended, deadlock-safe).** The P5-2 fixed order was address → community → platform.
P9-3 appends two keys at the end: class (`(4, hashtext(send_class))`) and class-daily
(`(5, hashtext(send_class || '|daily'))`). Appending preserves the deadlock argument for every
existing caller: no path takes a new key before an old one, so no cycle is possible.

**Deferred is not a retry, not an attempt.** Both new deferrals set `next_retry_at`, roll
`attempt_count` back from the claim's `+1`, keep the recipient address, and write no ledger row —
same pattern as `community_deferred`. Terminal skips (address_limited, address_suppressed,
community_backlog_full) still erase the address, same as today. The three-attempt cap and the
72-hour expiry are untouched.

**Config lives in one place.** `app.notification_send_limits(p_class text)` is the single source of
truth; the no-arg signature from P5-2 was dropped in the same migration (the new reserve body is
the only caller). The function is called inside `reserve_email_attempt` (binding limits for the
class the delivery row carries) and inside `notification_send_health()` (reading both classes to
report utilisation).

**Monitoring.** `app.notification_send_health()` gains four fields:
`l4_last_24h_by_class`, `l4_utilisation_pct_by_class`, `l5_last_second_by_class` and
`l5_utilisation_pct_by_class` (each a `jsonb` keyed by class). The staff-only view
`private.v_notification_send_health` picks them up unchanged. The worker's per-minute health log
line writes the same numbers verbatim (no address, name or provider text). Operator runbook:
`docs/runbooks/sender-quota-operator-guide.md`.

**Future SES adapter (P9-4) obligation.** When a real SES adapter is added, its startup must call
SESv2 `GetAccount` once, read `SendQuota.Max24HourSend` and `SendQuota.MaxSendRate`, log them (code
+ numbers), and **refuse to start** if `l4_daily >= Max24HourSend` or `l5_per_second >= MaxSendRate`.
The adapter must not re-read the quota at send time (a mid-day provider-side quota change would
become a retry storm); the invariant is enforced at startup instead. If SES returns `Throttling`
anyway, the adapter maps it to the existing `provider_rejected_transient` — a retry, not an L5
wait. P9-3 implements none of this; it ships only the application-side safety limits the adapter
will reconcile against.

**Changing a number safely.** Same discipline as L1/L2/L3 (10.6.1): numbers live only in
`app.notification_send_limits(p_class text)`; a change is a reviewed migration (`create or
replace`); staging first; keep the boundary tests green; never raise L4 or L5 above the provider's
own `GetAccount` numbers; the pause switch — not a limit edit — stays the emergency control.

**Acceptance tests (P9-3, pgTAP + worker unit + worker integration):**
1. *L4 boundary.* With 180 transactional attempts in 24 h, the 181st is `provider_daily_limited`;
   attempts 24 h + 1 s old do not count; `attempt_count` is undone.
2. *L5 boundary.* With one transactional attempt within the last second, the next transactional
   reservation is `provider_rate_limited`; `next_retry_at` lies in the ~1 s + jitter window.
3. *Class independence.* A full transactional L4 does not block a `bulk` reservation (and vice
   versa); bulk defaults to a zero cap, so every bulk reservation defers forever.
4. *Deferred is not an attempt.* L4 and L5 defers write no ledger row and leave `attempt_count`
   unchanged.
5. *Suppression precedence.* A suppressed address is terminally skipped before L4/L5 are
   consulted; no ledger row is written.
6. *Lock-order determinism.* Concurrent reservations across mixed classes, addresses and
   communities complete without deadlock in the real-DB integration suite.
7. *Config privilege.* `anon` and `authenticated` cannot execute
   `app.notification_send_limits(text)`.
8. *Health snapshot.* Carries `l4_last_24h_by_class`, `l4_utilisation_pct_by_class`,
   `l5_last_second_by_class`, `l5_utilisation_pct_by_class`; no address, name or provider text.

### 10.6.4 SES adapter and ambiguous-acceptance semantics (approved; built in P9-4)

**Status.** Added in P9-4 (migration `20261025100000_notification_lease_recovery_variants.sql`,
adapter `packages/adapters/src/ses-email-provider.ts`, worker routing in `recoverExpiredLeases`,
runbook `docs/runbooks/ses-sender-operator-setup.md`). The sender pause switch stays `false`
until the operator release gates below are met in writing. Nothing in this PR flips the switch,
creates an AWS resource or sends a real email.

**Why ambiguous acceptance is a safety problem for SES.** SES's `SendEmail` (both v1 and v2)
does *not* accept a caller-supplied idempotency token: `MessageId` is server-generated at
acceptance. The adapter is therefore `idempotency: "none"` by the §10.5 contract, and every
ambiguous outcome against it must be handled under the §10.6.2 non-idempotent rule — never
retried, surfaced as `dead/outcome_unknown` for an operator to decide. Q-DUP's "no avoidable
duplicates" guarantee holds the moment we never retry an ambiguous call.

**In-process ambiguity.** `classifyFailure` (`apps/worker/src/notification-backoff.ts`) was
already correct for SES: a `provider_timeout` or a 5xx with `ambiguous=true` against an
`idempotency: "none"` provider yields `dead/outcome_unknown`. P9-4 wires the SES adapter to
set `ambiguous=true` on timeouts, 5xx and `ECONNRESET`/`EPIPE`, and `false` on pre-connect
failures (DNS, refused). The mapping table is in `ses-email-provider.ts` `mapSendError` and
mirrored in the P9-4 design document.

**Crash-after-accept.** The remaining gap in the P5 model is a worker killed while holding a
lease: a replay against a non-idempotent provider might double-send. P9-4 closes it with a
single new DB function and a routing choice in the worker:

- `app.resolve_lease_ambiguous(delivery_id)` is the sibling of
  `app.recover_expired_notification_lease`. Same preconditions (row-locked, lease expired,
  status = `sending`), different terminal state: `status → dead`, `error_code →
  outcome_unknown`, lease cleared.
- `apps/worker/src/notification-sender.ts::recoverExpiredLeases(sql, providerIdempotency)`
  routes expired-lease rows by `providerIdempotency`:
  - `"provider"` → `app.recover_expired_notification_lease` → `pending`. A retry reuses the
    same key and the provider dedupes.
  - `"none"` → `app.resolve_lease_ambiguous` → `dead/outcome_unknown`. Reported to the
    operator; the row is never re-attempted automatically.

The lease itself is the in-flight marker. No separate `send_in_flight_marker` table is
needed. Attempts stay consumed either way: a timed-out call may have delivered, so refunding
would let a flaky network exceed the three-attempt cap.

**Startup-time quota reconciliation.** On construction, the SES adapter calls
`SESv2 GetAccount` once. It refuses to start if any of:

- `SendingEnabled === false` (SES has account-level sending paused).
- `ProductionAccessEnabled === false` AND `KOLEKTO_ENV === "production"` (sandbox mode
  cannot serve a production environment).
- `l4_daily >= Max24HourSend` or `l5_per_second >= MaxSendRate` (local safety ceilings must
  sit strictly below SES's own numbers; §10.6.3 contract).

A refusal becomes `adapter_misconfigured`, which the sender maps to `halt`: maintenance
(lease recovery, 72-hour expiry, ledger purge) keeps running, no provider calls happen. The
adapter does not re-read `GetAccount` at send time (a mid-day quota change would be a retry
storm). An operator who widens the account's limits re-starts the worker.

**Observability.** The health snapshot (`app.notification_send_health`) is unchanged — new
`outcome_unknown` counts land in `dead_by_code` automatically. The per-minute worker log
line adds `resolved_ambiguous_this_tick` alongside the existing `recovered_this_tick`. A
suggested alert: `resolved_ambiguous_this_tick > 0` for three consecutive minutes →
investigate (an operator looks at the delivery log and at SES's own Delivery/Bounce stream
to decide whether to re-queue a specific `outcome_unknown` row).

**Operator release gates.** Nothing in P9-4 flips the pause switch. Before the first
production send, these must be satisfied in writing (date, operator name):

1. **D-PROVIDER.** SES selected and recorded.
2. **D-DOMAIN.** Sending domain approved, DKIM/SPF configured, verified in SES.
3. **D-LEGAL / D-CONSENT.** Transactional-only classification reviewed by a qualified
   person; consent model aligned.
4. **D-WORKER.** Worker deployment plan documented and compatible with the lease/heartbeat
   model (long-running process, not a short cron).
5. **Q-CONFIRM.** Operator check recorded for staging and production: test send to a
   verified address; Delivery event received; a Complaint event ingested writes a
   permanent suppression (`source = 'ses_event'`).
6. **AWS production access** granted; `GetAccount.ProductionAccessEnabled === true` in
   production.
7. **IAM policy** scoped to `ses:SendEmail` and `ses:GetAccount` on the sending identity.
   No wildcard actions.
8. **Monitoring routing** wired to a human on-call for the four alert thresholds in
   §10.6.1 and the new `resolved_ambiguous` alert here.
9. A reviewed, dated operator action calling `app.set_email_sending_enabled(true)` on the
   target environment. P9-4 does not call this.

**Acceptance tests (P9-4, unit + pgTAP + integration):**

1. *GetAccount reconciliation.* The adapter refuses to start when `SendingEnabled=false`,
   when `ProductionAccessEnabled=false` with `requireProductionAccess=true`, when local L4
   is not strictly below `Max24HourSend`, or when local L5 is not strictly below
   `MaxSendRate`.
2. *Error mapping.* Every row of the SES-error table in `ses-email-provider.ts` is covered
   by a unit test, with the correct `(code, kind, ambiguous)`.
3. *Delivery-id lineage.* Every `SendEmailCommand` carries
   `EmailTags: [{Name: "delivery_id", Value: <idempotencyKey>}]`.
4. *Validation precedence.* `assertValidEmailRequest` runs before any provider call; an
   invalid request yields `invalid_message` with no HTTP traffic.
5. *Ambiguous recovery.* `app.resolve_lease_ambiguous` transitions an expired-lease
   `sending` row to `dead/outcome_unknown`; a live-lease row is refused; a non-sending row
   returns `not_leased`. (pgTAP suite 45.)
6. *Worker routing.* `recoverExpiredLeases(sql, "provider")` returns expired-lease rows to
   `pending`; `recoverExpiredLeases(sql, "none")` resolves them as `dead/outcome_unknown`.
   (Worker integration test.)
7. *No credential leak.* `JSON.stringify` of the config and of an SES-rejected error never
   contains the access-key secret or the recipient address.

### 10.7 Notification suppression — `kolekto.suppress_notifications` (approved; design — built in P3)

Purpose: let an operator run **maintenance or a data repair that goes through audited functions**
without those audit rows generating notifications. It is not a feature of the product and is
unreachable from it.

**Why it cannot be activated by public users.** The setting is honoured only when the session is an
*operator* session. The web app never runs queries as a bare connection: for every request it
switches to `anon` or `authenticated` first (`packages/db/src/client.ts`, `withCallerContext`:
`set local role authenticated` / `set local role anon`). Inside a SECURITY DEFINER function the
`role` setting still reflects that switch — verified on the local database: an operator session
reports `none`, a caller reports `authenticated` or `anon`. The trigger therefore **ignores the
setting whenever `role` is anything other than `none`**, so a signed-in user, an anonymous
joiner, and any code path running on their behalf cannot suppress a notification even if they
could set the variable. Setting it also requires a database login, which only operators hold.

**Format and lifetime.** The value is `v1|<expiry>|<reason>`: a version tag, an expiry as Unix
seconds, and a reason of 3–80 characters from `a-z 0-9 . _ -`. It is honoured only if the expiry is
in the future **and no more than 15 minutes ahead**, so a value left behind on a long-lived
session dies on its own. The supported way to set it is the helper
`app.begin_notification_suppression(reason)`, which calls `set_config(..., is_local => true)` —
the setting vanishes when the transaction ends — and which is executable by no client role
(`revoke … from public, anon, authenticated`).

**Scope — what can be suppressed.**

| Audit action | Suppressible? | Why |
|---|---|---|
| `member.create`, `member.approve_join`, `member.reject_join`, `member.join_via_invite` | yes | membership notices; a repair that re-runs these should not message people |
| `collection.publish` | yes | routine lifecycle |
| `officer_invitation.accept`, `officer_term.end` | **no** | they change who holds access to a community; an officer must always learn of it |
| anything not in the trigger's action list | n/a | not notified anyway |
| Supabase Auth emails (sign-in OTP, password recovery) | **not affected** | a different system; this variable is never read there |

**Behaviour.** When the setting is honoured for a suppressible action the trigger does **not**
enqueue, and writes one row to the append-only `notification_suppression_log` (audit log id,
community, action, reason, time, outcome `suppressed`; no names, no addresses). The audit row
itself, and every business and financial record, are untouched: suppression changes only whether a
queue message and a notification are produced. When the setting is present but **not** honoured the
outcome depends on who is asking. For a **public** role (`anon`, `authenticated`, `service_role`, the importer,
PostgREST) it is ignored, the notification proceeds normally and a log row `ignored_untrusted_role` is written, so
an attempt to use it from the product is visible rather than silent. For an **operator** session whose value is
well-formed but outside its window (expired, or more than 15 minutes ahead) the event is **held**, not sent and not
silently dropped: see 18.3. A value that is not even `v1`-shaped is ignored in either case.

**Other maintenance paths, stated explicitly.** `scripts/db/restore.mjs` runs with
`session_replication_role = replica`, which disables triggers, so restoring a backup never
notifies. The importer role has no right to write audit rows, so imports never notify. Direct
SQL that bypasses audited functions writes no audit row and notifies no one. The one supported
script that *does* write a watched audit action — `scripts/db/persistence-marker.mjs`
(`member.create`, actor `system`) — will call the helper in P3. A repository check (P3) fails the
build if a migration or script writes a watched action without it.

**Deduplication still applies to un-suppressed maintenance.** A repair that is *not* suppressed and
re-runs an audited function cannot resend: events are keyed `{action}:{object_id}` and the email is
keyed `membership_confirmation:{member_id}` (one per membership), both enforced by unique indexes.

**Acceptance tests (P3, pgTAP unless stated):**

1. *Honoured.* Operator session + valid value + `member.create` audit row → **no** queue message and
   exactly one `suppressed` log row.
2. *Default.* No value → the message is enqueued and nothing is logged (regression guard for M13.1).
3. *Untrusted roles.* The same valid value set under `set local role authenticated`, and under
   `anon`, is **ignored**: message enqueued, log row `ignored_untrusted_role`.
4. *Time bounds.* In an operator session: expired value → **held**; expiry 16 minutes ahead → **held**; 14 minutes
   ahead → suppressed. (Held, not enqueued: 18.3.)
5. *Malformed.* Missing version, empty or 2-character reason, disallowed characters, non-numeric
   expiry → enqueued.
6. *Non-suppressible actions.* `officer_term.end` and `officer_invitation.accept` are enqueued even
   with a valid value in an operator session.
7. *No business effect.* A hash of `members`, `obligations`, `ledger_journals` and `audit_logs` is
   identical with and without suppression apart from the one extra `audit_logs` row both cases
   write; only the queue and the suppression log differ.
8. *Helper reachability.* `anon` and `authenticated` cannot execute the helper; `PUBLIC` cannot.
9. *Lifetime* (script, two sequential psql sessions): a value set by the helper in one transaction
   is gone in the next.
10. *Log integrity.* `notification_suppression_log` rejects UPDATE and DELETE and grants nothing to
    client roles.

### 18.3 The suppression window and long maintenance transactions (review round 2)

**The question.** In 18.2 the review noted that suppression uses wall-clock time, so a maintenance
transaction longer than 10 minutes would silently stop suppressing partway through. Could any supported
operation actually be that long, and what should happen if one is?

**Evidence — can it occur today?** No supported operation is long enough *today*, and the control exists for
exactly the kind that would be.

| Fact | Evidence |
|---|---|
| The only supported maintenance caller of the helper is `scripts/db/persistence-marker.mjs`: `begin; helper; one audit write; commit;` — three statements, milliseconds | code search; transaction boundaries read at lines 85-88 |
| No migration, seed or other script executes a watched audited write (invariant 7 would fail the build) | the invariant passes on the whole tree |
| An audited `create_member` costs about 6.3 ms on this machine (200 calls, small community) — so about 95 000 fit in 10 minutes. The duplicate check slows as a community grows, so a repair of tens of thousands of members through audited functions in **one** transaction is plausible | measured, rolled back |
| The control's stated purpose is "controlled maintenance and data repair" through audited functions | decision record 10.7 |

So: not hit by any current path, reachable by design, and silent when reached. That warranted a fix.

**The failure, reproduced.** One transaction, window shortened to two seconds so the lapse happens in real time
(`pg_sleep`): write 1 was suppressed and logged; after the window lapsed **write 2 went into the live queue (it
would notify real people) with no log row**. The same transaction, the same operator, no warning.

**What happens now.** In an *operator* session (role `none`) holding a well-formed `v1|<expiry>|<reason>` value
that is **outside its window** (expired, or more than 15 minutes ahead), a suppressible event is:

1. **held** — sent, intact, to the durable queue `notification_events_held`;
2. **recorded** as `lapsed_held` in `notification_suppression_log` (with the operator's reason);
3. announced — **one WARNING per transaction** to the operator's session;
4. never a reason for the audited write to fail or roll back.

The operator then decides, explicitly and on the record, with two operator-only functions (both refuse any client
role with 42501, and write one log row per message): `app.release_held_notifications()` (move them to the live
queue; they will notify) or `app.discard_held_notifications(reason)` (the suppression the operator wanted).

**How it meets each requirement**

| Requirement | How |
|---|---|
| Operator-only | The lapse path exists only when `role = none`. Held events can be released or discarded only by an operator |
| Transaction-local | Unchanged: the helper still uses `is_local = true` |
| Approved maximum not silently bypassed | Unchanged ceiling: 10 minutes granted, 15 accepted. Past it the old authority is **not** extended — events are held, not suppressed. Nothing is made longer |
| Ordinary callers cannot activate it | Unchanged: `anon`, `authenticated`, `service_role`, the importer and PostgREST are untrusted, and for them an expired or any setting is **ignored** and their notifications go out as before (tested through the real `create_member`) |
| A long operation cannot silently start notifying | It cannot notify at all after the lapse: the event is held, logged and warned about. Officer access changes are the one exception — they are never suppressible, so never held, and always notify |
| Notification failures must not fail business writes | The lapse path is inside the same exception handler. A hold that cannot be both **recorded** and **queued** is not a hold: the event falls through and notifies (recoverable) instead of being lost; the write commits either way |
| No financial, payment, auth or unrelated change | The migration touches only notification objects; the PR file list is unchanged in kind |

**Why hold, and not the alternatives.** *Keep suppressing past the window* would bypass the approved ceiling.
*Notify* is the bug. *Raise an error* would fail an audited write, which the requirements forbid. Holding is the only
behaviour that is quiet, loud to the operator, recoverable, and inside every limit.

**A malformed value is deliberately not "lapsed".** A value that is not even `v1`-shaped is still ignored and the
event notifies. The helper validates strictly, so a malformed value only arises from hand-setting, which is not a
supported path; treating it as an activation attempt would let junk silently hold events.

**Operator runbook**

1. Prefer short transactions: batch a large repair into separate transactions, each calling
   `app.begin_notification_suppression('reason')` first. The window is per transaction.
2. If the WARNING `NOTIFICATION SUPPRESSION LAPSED` appears, events from that point are in `notification_events_held`.
3. Decide: `select app.release_held_notifications();` (they notify; the 72-hour stale rule still applies in the
   worker) or `select app.discard_held_notifications('why it is fine to drop them');`.
4. The record is in `notification_suppression_log` (`lapsed_held`, then `released_held` or `discarded_held`).
