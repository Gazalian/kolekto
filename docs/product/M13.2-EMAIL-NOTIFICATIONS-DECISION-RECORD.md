## 1. Purpose and scope

M13.2 adds an email channel to the notification system built in M13.1, for a deliberately small
set of important personal notices. In-app notifications remain the default channel for routine
events. The architecture must allow a WhatsApp adapter to be added later without rewriting event
processing, but WhatsApp, SMS, announcements, reminders, a preferences UI, delivery webhooks and
anything touching payments, ledger, withdrawals, settlement, refunds, partial payments, legacy
migration or password reset are **out of scope** (see section 13).

### 2.3 Identity and verification (this matters for recipient rules)

| Question | Finding |
|---|---|
| Where is **account email** verification recorded? | `public.users` has **no** verified flag. `users.email` is a copy of `auth.users.email` taken at sign-up by `app.handle_new_auth_user` (`20260930110000`). The only email-verification record is GoTrue's `auth.users.email_confirmed_at`. Local config has `[auth.email] enable_confirmations = true` (`supabase/config.toml:89`); the hosted setting is **unverified**. |
| Is `users.identity_level = 'contact_verified'` reliable? | **No.** It does not say which channel was verified ("phone OTP and/or email OTP", `20260917120200_users.sql:26`). It is set by `app.set_contact_verified()`, granted to any `authenticated` caller and invoked by a bare server action (`apps/web/app/(auth)/verify/actions.ts`) with no proof attached. It must not be used as an email- or phone-verified signal. |
| Where is **account phone** verification recorded? | Nowhere reliable. `users.phone_e164` is editable through `app.update_user_profile` with **no verification** (`20260930110000:121-155`). `auth.users.phone_confirmed_at` exists in GoTrue, but no phone-OTP sign-in flow or SMS provider is wired. **Phone verification is effectively not implemented.** |
| Can `users.email` drift from the verified address? | Possibly: it is a copy, not a view. The authoritative address is `auth.users.email` where `email_confirmed_at is not null`. |
| What is a member's contact? | `members.email` / `members.phone_e164`, entered by an officer or by the joiner. No verification mechanism exists for them. `members.consent_messages_at` is never written by any flow. |
| What does "active" mean for a member? | The schema comment says phone-verified (`members_active_has_phone`), but both `create_member` and `approve_pending_member` deliberately avoid setting it. |
| Community member ID | `members.member_code` (e.g. `KWASU/0021`), issued once by `app.next_member_code()` at creation or at invite redemption, unique per community. This is the "community member ID" in the product brief. Internal `members.id` (uuid) must never be shown. |

### 2.4 Delivery-record access (the M13.1 gap that must close before any email row exists)

`notification_deliveries_select_officer` (`20261007100000:229-236`) lets **any current officer of
the community**, of any role, `SELECT` every delivery row including `recipient_address`,
`error_code` and `error_message`. By contrast `members` rows are gated on
`app.has_permission(community_id, 'member.view_contact')`. Once email rows exist, the delivery
policy would leak addresses that the members policy deliberately protects.

**Correction to an assumption in the M13.2 brief:** the brief says collectors do not hold
`member.view_contact`. They do, **scoped** (`20260917120400:158`), and so does the `viewer`
role. So gating delivery rows on `member.view_contact` alone is necessary but is **not**
sufficient to hide addresses from a scoped collector. See open question Q-RLS.

## 3. Principles

1. **In-app is the default.** Email is reserved for important personal notices.
2. **Membership record ≠ user account ≠ verified email ≠ verified phone.** No one of these is ever
   treated as proof of another.
3. **A supplied address is not a verified address.** Nothing in M13.2 marks a contact verified.
4. **Never fabricate consent.** M13.2 never writes `consent_messages_at`.
5. **Skipped, not silent.** An email candidate that is ineligible produces a `skipped` delivery
   row with a stable reason code.
6. **Honest delivery semantics.** The queue is at-least-once. External delivery is at-least-once
   unless a provider's idempotency guarantee says otherwise. We do not claim exactly-once.
7. **Minimal content to unverified addresses.** The content permitted for an address is a function
   of how much we know about it (section 7).
8. **No new permission system.** Reuse `member.view_contact`; extend the grant matrix, not
   a parallel mechanism.

## 4. Revised event-to-channel matrix

**Policy:** an audit action that exists is *not* a reason to email. An event is an email
candidate only if it appears with "Email = Yes" below. Events that are not email candidates
**never create an email delivery row** (they are not "skipped"; they were never candidates).

### 4.1 Email candidates (M13.2)

| # | Event (type) | Source audit action | Recipient | In-app | Email | WhatsApp (future) | Notice class |
|---|---|---|---|---|---|---|---|
| E1 | Member added to a community | `member.create` | The member (contact on the member row) | Only if the member has an account (`user_id`) | Candidate | Later, via adapter | Minimal membership confirmation |
| E2 | Join request approved | `member.approve_join` | The member | Existing M13.1 in-app (accounts only) | Candidate | Later | Minimal membership confirmation |
| E3 | Join request rejected | `member.reject_join` | The requester, only if a contact survives in `before_state` | None | Candidate, **conditional** (see 4.2) | Later | Minimal decision notice |
| E4 | Officer appointed | `officer_invitation.accept` (creates the term) | The new officer's **verified account email** | Yes (new) | Candidate | Later | Account notice |
| E5 | Officer term ended | `officer_term.end` | The former officer's **verified account email** | Yes (new) | Candidate | Later | Account notice |

Notes:

- **E1/E2 vs. the invite path.** `member.join_via_invite` (a person joining through a link)
  continues to notify *officers* in-app (M13.1). Whether to email the joiner an
  acknowledgement "we received your request" is **not** in M13.2 (**NEEDS APPROVAL**, Q-ACK).
- **E3** needs engineering work the other events do not: the member row is deleted, so the
  recipient and community name must come from the audit row, and the M13.1 trigger forwards only
  `after_state`. P3 must forward a *narrow* set of fields (contact email, display name, community)
  and must **not** copy the whole `to_jsonb(member)` (phone, attributes) into `pgmq`. The
  officer's free-text `reason` must **not** be emailed.
- **E4** is "officer appointed" at the moment the term is created (invitation accepted). Email at
  the moment an invitation is *sent* is excluded (4.3).
- **E1 for officers adding members in bulk** (import, bulk add) is a separate path. P3 must
  inventory every member-creation path (`create_member`, `redeem_invite_link`, importer, any
  bulk/roll flow) and decide per path; only `create_member` is confirmed in scope by this record.

### 4.2 E3 recipient rule

Send only if (a) `before_state` contains a contact email, and (b) that email was supplied by the
requester through the invite form (`members.joined_via = 'invite_link'`), which is closer to the requester's own
intent than an organizer-typed address. If the row was not self-supplied, or no email exists,
record `skipped` with `no_recipient_address`. The rejection email states the decision only;
no reason, no member ID (the person was never accepted).

### 4.3 Explicitly **not** email in M13.2

| Event | Channel decision | Why |
|---|---|---|
| `collection.publish` (published) | In-app only | Routine lifecycle (Decision A). Already shipped in M13.1. |
| collection paused / resumed / closed | In-app only; **not built in M13.2** unless separately requested | Routine lifecycle. The original plan emailed resumed/closed; that is withdrawn. |
| `officer_invitation.create` (invite sent to a future officer) | Not in M13.2 | The message would carry a credential-bearing accept link. Needs its own security design and approval. |
| `officer_invitation.accept` → notify owners/admins | In-app only if desired | Optional; not an email candidate. |
| Announcements, reminders | Out of scope | M13.3 / M13.4. |
| Payments, receipts, withdrawals, settlement, refunds | Out of scope | Require separate financial-policy decisions. |

The original plan's "five additional lifecycle events" (`collection.closed`, `collection.paused`,
`collection.resumed`, `member.rejected`, `officer.term_ended`) are therefore reduced: three
withdrawn from email entirely, `member.rejected` kept as E3 (conditional), `officer.term_ended`
kept as E5.

## 5. Membership confirmation rules (Decision B)

When an organizer adds a person (E1) or an eligible join request is approved (E2):

1. The membership record exists and carries a `member_code`. If `member_code` is null at event
   time, the email is **skipped** with `member_code_missing`; it is never sent without the ID, and
   the code is never generated by the notification system (identity model stays owned by
   `app.next_member_code`).
2. The email may contain **only**: community name, the person's `member_code`, a statement that
   they have been added/approved, the date of the action (from the audit row `created_at`, not
   "now"), and a safe next step *if one exists* (the community's public contact route, if the
   community has one; otherwise none).
3. The email must **not** contain: `members.id`, any other member's data, collection or balance
   data, officer names beyond what the community has made public, or sensitive administrative
   details (audit reason, status internals).
4. The email wording must not claim the address or phone is verified, and must not imply the
   recipient has a Kolekto account. It should invite the recipient to tell the community if the
   message is not meant for them (see 7.3 on misdirected mail).
5. The `member_code` confirms the **membership record only**. It is not proof of ownership of the
   email or phone and is never treated as such by the system.
6. Event payload is a frozen snapshot (name, community name, `member_code`, action date) taken at
   event time, so a later rename does not change a sent message (consistent with M13.1 `payload`).
7. The event model is channel-neutral: one `notification_events` row, N delivery rows
   (in-app / email / future WhatsApp). A WhatsApp adapter later consumes the same event and
   snapshot and implements the same adapter interface; no processor rewrite.

Contact verification for non-account members (so that richer content could later be sent) is a
**separate mechanism** (OTP or verification link), not designed or implemented here. See Q-VERIFY.

## 6. Account verification requirements (Decision C)

- For an account holder, the **only** acceptable evidence that an email is verified is
  `auth.users.email_confirmed_at is not null` **for the same address** being used
  (`auth.users.email`). `public.users.email`, `public.users.identity_level` and
  `members.email` are **not** evidence.
- The worker must obtain this via a narrow, purpose-built `SECURITY DEFINER` function in the
  `app` schema (for example `app.resolve_verified_account_email(user_id)` returning the address or
  `NULL`), not by granting the worker broad read access to `auth.*`. The function is new database
  surface and therefore a **P4** item with its own grant-matrix entry; its exact shape is a
  proposal here.
- **Hosted configuration dependency:** the guarantee holds only if email confirmation is enabled
  on every hosted project. Local config enables it; staging/production settings are unverified.
  This must be checked before P8/P9 (Q-CONFIRM).
- **Account phone verification is not implemented** (section 2.3). M13.2 does not add it, does not
  pick an OTP/SMS provider, and does not treat membership confirmation as a substitute. It is
  recorded as an external dependency (section 11, D-PHONE). Accordingly, M13.2 never gates an
  email on phone verification and never claims a phone is verified.
- M13.2 does **not** change `set_contact_verified`, `update_user_profile`, or any auth behaviour.
  The self-callable `set_contact_verified()` and unverified phone editing are noted as
  pre-existing findings for a separate, reviewed change; fixing them is out of scope here.

## 7. Recipient eligibility matrix (Decision D) — NEEDS APPROVAL

### 7.1 Definitions

- **Minimal membership confirmation (N1):** the E1/E2 content in section 5.
- **Minimal decision notice (N1-R):** the E3 content (decision only).
- **Account notice (N2):** E4/E5; addressed to a user, content limited to community name, role
  and date. No financial or member data.
- **Sensitive/confidential (N3):** anything else (member lists, collection details, balances,
  credential-bearing links). **No N3 notice is sent by M13.2 to any address.**

### 7.2 Matrix

| Recipient situation | N1 / N1-R (E1, E2, E3) | N2 account notice (E4, E5) | N3 sensitive | Outcome when not sent |
|---|---|---|---|---|
| **Account holder, email verified** (`email_confirmed_at` set, same address) | Send to the verified account address *(see note a)* | **Send** | Not in scope | — |
| **Account holder, email unverified** | **Skip** to the account address. May fall back to `members.email` only under the non-account rule below *(note b)* | **Skip** | Never | `skipped` / `account_email_unverified` |
| **Account holder, email verified, phone unverified** | Send (phone is irrelevant to an email) | **Send** | Not in scope | — (phone status never gates email; document only) |
| **Non-account member, email supplied** | **Send** minimal content only, to `members.email`, subject to the consent policy (section 8). Address is **not** represented as verified | Not applicable (no account) | **Never** | If consent policy not met: `skipped` / `consent_missing` |
| **Non-account member, no email** | Skip | N/A | Never | `skipped` / `no_recipient_address` |
| **Non-account member, unverified contact** | Same as "email supplied" today — **all** non-account contacts are unverified until a verification mechanism exists | N/A | **Never** | Same as above |
| *(Future)* **Non-account member, contact verified** | N1 allowed; richer content only after separate approval | N/A | Separate approval | — |

Notes:

a. For an account holder who is also a member, E1/E2 go to the **verified account email**, not to
   `members.email`, so a mistyped organizer-entered address cannot receive mail for someone who
   has a verified one. (**NEEDS APPROVAL**, Q-PREFER.)
b. If the account email is unverified, falling back to the organizer-entered `members.email` would
   send to an address that is unverified on *both* sides; the proposal is to **skip** rather than
   fall back, unless product decides otherwise (Q-FALLBACK).

### 7.3 Risks accepted by sending to unverified member addresses

Organizer-entered addresses can be wrong or belong to someone else. Mitigations: minimal content
(no financial or other-member data), a "not you? tell the community" line, no claim of
verification, and the suppression/unsubscribe dependency in section 8. Residual risk — a stranger
learns that a named person was added to a named community — is real and is a **product decision**
(Q-MISDIRECT), not something engineering can eliminate.

### 7.4 Stable skip reason codes (proposal)

Stored in `error_code` (Kolekto vocabulary, never provider text). Visible only to authorized
roles (section 9).

| Code | Meaning |
|---|---|
| `no_recipient_address` | No usable address on any permitted source |
| `account_email_unverified` | Account exists but `email_confirmed_at` is null or address mismatch |
| `consent_missing` | Policy requires `consent_messages_at` and it is null |
| `member_code_missing` | N1 requires a member ID and none exists |
| `member_unavailable` | Member merged/archived/deleted in a way that leaves no valid recipient |
| `preference_opt_out` | Recipient preference disables email (only once preferences exist) |
| `address_suppressed` | Address on a suppression list (hard bounce/complaint), once one exists |

Permanent failure codes (P5/P6, proposal): `provider_rejected_permanent`,
`retries_exhausted`, `payload_invalid`, `template_error`. A skip and a failure are different
states: a skip is a policy outcome; a failure is a delivery attempt that did not succeed.

## 8. Consent and message importance (Decision E) — NEEDS APPROVAL

Current state: `members.consent_messages_at` is never written. The M13.1 schema comment says,
without it, "no announcement or reminder may be sent — only receipts, codes and security
messages, which are not optional (NOT-10)".

**Proposal:**

| Class | Examples | Requires `consent_messages_at`? |
|---|---|---|
| Transactional personal notice (proposed) | E1/E2/E3 membership confirmation and decision; E4/E5 officer notices | **No**, but content is restricted to the minimal fields in sections 5 and 7 |
| General / optional community communication | announcements, reminders, collection updates | **Yes**; missing consent → `skipped` / `consent_missing` |

Rationale for treating E1/E2 as "codes" under NOT-10: the email delivers the member's ID. This is
a **technical reading of an internal requirement**, not a legal conclusion; NDPR/NDPA
(Nigeria) applicability and the lawful basis for contacting a person added by a third party
**need review by someone qualified** before production email is enabled (D-LEGAL).

M13.2 will:

- never write `consent_messages_at`;
- record `consent_missing` skips where the policy requires consent;
- not build a consent-capture UI or a preferences UI.

Production dependencies (not built in M13.2): a consent-capture flow that sets
`consent_messages_at`; an unsubscribe/suppression mechanism honoured by the sender (including for
transactional mail where required); a decision on whether an unsubscribe link is mandatory in N1.
Without bounce/complaint webhooks (out of scope), automatic suppression is not available, so
repeated sends to a bad address are a known gap (D-SUPPRESS).

## 9. Security and database access (Decision F; before the first email row)

Required outcomes and the proposed approach (implemented in P2, tested with pgTAP):

1. **Replace** `notification_deliveries_select_officer`. For `channel <> 'in_app'` rows, readable
   only by officers holding `member.view_contact` (existing permission, no new one), and only the
   columns they need.
2. **Hide sensitive columns** from officers even when they can see the row: `recipient_address`
   and `error_message` should not be readable through the base table by officers.
   Because RLS is row-level only (the repo's own note, `rls_policies.sql:148-150`), this means a
   narrowly-scoped view or `SECURITY DEFINER` read function that returns masked address and the
   stable `error_code` only, with the base-table `SELECT` for officers revoked on those columns.
   Exact mechanism is a P2 design choice and is presented for review there.
3. **Scoped roles:** decide how `member.view_contact` *scope* (collector) maps to delivery rows
   (Q-RLS). Default proposal: scoped holders get **no** access to email delivery rows.
4. **Members** read only their own in-app deliveries (existing `…_select_own_inbox`, unchanged).
   Email deliveries are not exposed to members in M13.2.
5. **Anonymous:** no access (unchanged; no `anon` grant).
6. **Email rows require a valid address:** a table `CHECK` that `channel = 'email'` rows that are
   not `skipped` carry a syntactically valid `recipient_address`; skipped rows carry none.
7. **No raw provider text in the database.** The `failed_has_reason` constraint currently requires
   a non-null `error_message`; P2 will relax it to require `error_code` and store at most a
   Kolekto-authored, non-PII message.
8. **Grant matrix:** `supabase/tests/02_grant_matrix.sql` is extended for any new object (the repo
   rule: every new `app.*` function needs an explicit `revoke execute … from public`).
9. **Templates (P7):** all user-supplied text HTML-escaped; plain-text alternative for every
   template; adversarial-name tests. **Worker (P3+):** event payloads validated against a schema
   before use; unknown shapes → dead-letter, not best-effort send.
10. **Secrets:** server-only variables, never `NEXT_PUBLIC_*`, never logged; delivery failures do
    not log addresses or bodies.

## 10. Reliability design (summary; detail lands with P5/P6)

### 10.1 Two stages

1. **Event stage (queue):** pgmq message → `notification_events` row → delivery rows
   (in-app `sent`; email `pending` or `skipped`). Keeps M13.1 behaviour and idempotency.
2. **Send stage (table-driven):** a sender claims due `pending` email rows
   (`… for update skip locked`), sends, records the outcome. The existing
   `notification_deliveries_retry_idx` is the starting point.

### 10.2 State machine (proposal)

`pending → sending → sent` · `sending → pending` (transient failure, `next_retry_at` backoff,
`attempt_count + 1`) · `sending → dead` (permanent error or `attempt_count` ≥ max) ·
`pending → skipped` (policy). `delivered` stays reserved for webhook confirmation (out of scope).
Adding `sending` and `dead` to `notification_delivery_status` is an enum migration (P2/P5).
A `sending` row with an expired lease is reclaimable (crash recovery).

### 10.3 Duplicate sends — what we can and cannot promise

- Queue: **at-least-once**. Event/delivery inserts are idempotent, so replays do not create
  duplicate rows (already true in M13.1; extended to email).
- Provider call: the stable `notification_deliveries.id` is the idempotency key **if** the chosen
  provider supports one. If not, a crash between "provider accepted" and "row marked sent" will
  re-send once on lease expiry. That is documented residual risk, not hidden. Mitigations to
  evaluate before enabling any provider: provider idempotency key; a deterministic `Message-ID`
  derived from the delivery id; recording attempt-start before send so an ambiguous attempt is
  visible. For non-financial notices a rare duplicate is considered preferable to a lost message
  (**NEEDS APPROVAL**, Q-DUP).
- **Exactly-once external delivery is not claimed.**

### 10.4 Retries and dead letters

Bounded attempts (proposal: max 5) with exponential backoff and jitter; only transient errors
retry. Permanent errors go straight to `dead` with a stable code. For the **queue**, the worker
must use `pgmq.read`'s `read_ct`: past a threshold, archive (or move to a `notification_events_dlq`
queue) instead of leaving the message to reappear every 30 s forever, which is today's behaviour.
Dead rows and archived messages need an operator-visible count (a view or log line) so they are
not silently lost.

### 10.5 Provider abstraction and startup guards

Interface `EmailProvider` with `send(message, idempotencyKey) → {providerMessageId}` and a typed
error taxonomy (`transient` | `permanent`). Adapters: **fake** (deterministic, unit tests),
**SMTP→Mailpit** (local/CI; local Mailpit already exists on port 54324, `config.toml:41-43`).
**No real provider adapter** until a provider is approved (P9).

Config (server-only): `EMAIL_PROVIDER`, `EMAIL_API_KEY`, `EMAIL_FROM`, `APP_BASE_URL`
(`.env.example` already has the first two as unused placeholders). Guards, following ADR 0007
rules 3-4 (fail fast; non-production asserts it is not production):

- missing/invalid config → refuse to start (no default provider);
- `fake` is rejected in production; a real provider is rejected unless the environment is
  explicitly production (and in CI/local, always);
- Mailpit/SMTP adapter is rejected outside local/CI;
- secrets are never printed; errors name the variable, not its value;
- how "this is production" is determined must reuse the repo's existing environment signal
  (ADR 0007's `KOLEKTO_PRODUCTION_PROJECT_REF` comparison) rather than invent a new one — to be
  confirmed in P1.

### 11.3 Provider selection — framework only (no provider chosen)

No production provider is selected or implied by this record. Vendor facts (pricing, limits,
idempotency support, webhook features, regional deliverability) change and have **not** been
researched for this draft; they must be verified from current vendor documentation before
selection. Criteria the comparison must cover:

1. Idempotency-key support, or a documented duplicate mitigation (10.3).
2. Delivery reliability and deliverability to Nigerian mailbox providers.
3. Cost and pricing model at expected volumes.
4. Rate limits and burst behaviour.
5. Domain verification and DNS requirements.
6. Delivery-status/webhook capability (needed later; webhooks are out of scope now).
7. Data-residency and regional/regulatory suitability.
8. API ergonomics, SDK weight, and failure-mode clarity (transient vs permanent errors).
