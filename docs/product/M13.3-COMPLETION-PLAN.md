# M13.3 — Completion plan: community notifications, working end to end

**Date:** 2026-11-09 · Status of each phase is from the code and the isolated `kolekto-itest` stack, not
from earlier reports. Goal: members (no account needed) receive the right community email, organisers
control it, withdrawals always win, and it runs in production. One plan; no further design-only phases.

## Where things stand

| Done and verified on the isolated stack | Not done |
|---|---|
| Central policy (worker) and matching DB matrix; parity tests | Notification audience independent of payment (N-AUD) |
| Attestation, member choices, delivery category (proposal 1) | Signed accountless links / unsubscribe / List-Unsubscribe (R4) |
| Announcement eligibility without consent (proposal 2) | Organiser UI for attestation, audience, opt-outs, delivery log (R5) |
| Send-time recheck in the claim transaction; fail-closed worker (R3) | Real worker under its own role exercising M13.3 (needs grants + lane approval) |
| Web preview reads the new counts | Any proposal in `supabase/migrations`; any staging/production change |
| SES adapter, SNS bounce/complaint ingestion, suppression, quotas (M13.2, pre-existing) | Bulk caps above zero; `email_sending_enabled` anywhere |

Apply order for the three proposals (everywhere): `M13.3-COMMUNICATION-POLICY` → `MEMBER-ANNOUNCEMENTS`
→ `M13.3-R3-SEND-TIME-RECHECK`; then the N-AUD migration.

- **Files/objects:** `scripts/itest/itest.mjs` (`WORKER_ROLE_FUNCTIONS`), `apps/worker/test/integration/notification-worker-runtime.integration.test.ts`, new concurrency test in `notification-communication-policy.integration.test.ts`.
- **Dependencies:** R3 applied on the isolated stack (done). **Approval needed:** `npm run itest:worker-role` with three added grants, and running `--worker-runtime` (the harness temporarily writes the pause switch on the test stack and restores it).
- **Tasks:**
  1. Add to `WORKER_ROLE_FUNCTIONS`: `app.community_communication_notice_attested(uuid)`, `app.collection_announcement_context(uuid)`, `app.evaluate_collection_email_recipients(uuid, text)`. Nothing else: the recheck runs inside the already-granted reserve.
  2. Extend the runtime test: a collection announcement reaches Mailpit only for an eligible, attested member; an opt-out recorded between fan-out and send is skipped `opted_out` and never reaches Mailpit.
  3. Concurrency test with two connections and committed, quarantined fixtures: connection A holds an uncommitted opt-out; B's claim → reserve blocks on the shared lock and, after A commits, reserves `ineligible`.
- **Security:** worker role still has no table access to the evidence tables and no client-callable function beyond the list above.
- **Automated tests:** `--worker-runtime` lane green; new concurrency test green; unit/pgTAP unchanged.
- **Manual acceptance:** Mailpit shows exactly the expected messages; the delivery log shows the skipped ones with codes.
- **Exit:** real worker process, least-privilege role, M13.3 path green on the isolated stack; switch back to false (read-back in the harness).

## Phase 2 — N-AUD: notification audience independent of payment

- **Files/objects:** new migration proposal: `communication_requests` (or additive columns on `collection_reminder_requests`), `communication_request_groups`, `communication_request_members`, tenancy triggers, `app.resolve_notification_audience(request_id)`, `app.evaluate_communication_recipients(request_id, topic)`, preview variant; additive audience parameters on `app.publish_collection`, `app.send_collection_publish_reminder`, `app.announce_collection_update`. Worker: `notification-processor.ts` (in-app `resolveRecipients` and email fan-out by request), `notification-email-templates.ts` (variant for non-contributors). Web: `packages/validation/src/collection.ts`, `packages/db/src/write.ts`, `apps/web/app/c/[slug]/collections/actions.ts`, `CollectionDetailClient.tsx` (audience picker).
- **Dependencies:** proposals 1–3 applied together on the isolated stack (done). Product decisions: default audience per action (proposed: "collection audience" for reminders, "all members" for announcements); whether non-default audiences need `announcement.send`; members-only collections for non-contributors (G7: no page they can open — skip with `collection_not_reachable` until the personal link exists).
- **Tasks:** schema + resolver (never reads/writes obligations); request id in the audit `after_state` (counts, never member lists); processor resolves by request; preview by request; UI picker (All members / Collection audience / Groups / Selected members) with live counts; template copy that never implies an obligation to non-contributors.
- **Security:** same-community tenancy on groups and members; bounded list size (e.g. 5 000); permission `collection.publish` (+ decision on `announcement.send`); scoped collectors limited to their scope; no member lists in audit or queue payloads.
- **Automated tests:** pgTAP — cross-community group/member refused; archived excluded; a member outside the payment audience is notified **and no obligation is created**; counts = deliveries. Worker unit per mode; integration: 300-member community, 80-member collection, announce to all/group/selected and assert recipients.
- **Manual acceptance:** organiser announces a collection for 80 members to all 300; only the 80 have obligations; preview counts match Mailpit.
- **Exit:** the 300/80 scenario passes in pgTAP, integration and a manual run on the isolated stack.

## Phase 3 — R4: signed accountless links (unsubscribe, preferences, "not me")

- **Files/objects:** server-only token module (HMAC-SHA256 over delivery id, member id, community id, category, channel, expiry; key from server env, never `NEXT_PUBLIC_*`); routes `apps/web/app/u/[token]/…` (preference page, one-click POST); `app.record_member_communication_choice` gains its caller: a dedicated DB role used only by that route (or a SECURITY DEFINER wrapper that verifies a DB-side token hash), with **one** EXECUTE grant; email templates add `List-Unsubscribe` + `List-Unsubscribe-Post` (RFC 8058) and footer links for B/D2, "not me" for all.
- **Dependencies:** Phase 1 (grants process). Product/legal: link lifetime, wording (L3), whether "not me" removes the address or flags it.
- **Tasks:** token issue at send (worker) and verify (web); preference page showing per-category × channel state for that community; one-click unsubscribe; WhatsApp permission grant UI copy (opt-in wording versioned, `wording_version`); rate limiting on the route.
- **Security:** constant-time compare; expiry; single community scope; no PII in the URL beyond the opaque token; CSRF-safe POST; no account required; the grant is the only new privilege; replay is idempotent (no-op when already in that state).
- **Automated tests:** unit (token tamper/expiry/scope); web route tests; pgTAP for the caller grant (no other role); integration: a link from a real delivery opts the member out and the next queued row is skipped at send.
- **Manual acceptance:** click unsubscribe in a Mailpit message without signing in → next announcement not received; Gmail-style one-click header present.
- **Exit:** unsubscribe and preference changes work without an account; send-time recheck honours them in integration.

## Phase 4 — R5: organiser interface

- **Files/objects:** community settings page (attestation with the notice text and version, revoke, history via `app.community_communication_notice_status`); member page (communication state per category × channel, "record opt-out on request" with request channel — no opt-in control); publish/reminder/update dialogs (audience picker from N-AUD; counts and skip reasons from the preview); masked delivery log (existing `notification.view_delivery_log` function).
- **Dependencies:** N-AUD, R4. Product: final `community-notice-v1` wording (draft in the R3 report §6) after legal review.
- **Security:** buttons mirror permissions only; every action re-checked in the database; collectors scoped; no organiser path to opt a member in or grant a permission.
- **Automated tests:** web unit tests for components; Playwright flows (attest → publish → counts → revoke → counts change).
- **Manual acceptance:** an organiser who has never seen the feature can attest, announce to a group, see who will and will not be emailed and why, record an opt-out on request.
- **Exit:** all flows pass in Playwright against the isolated stack.

## Phase 5 — Worker permissions and runtime (all environments)

- **Files/objects:** worker-role SQL for staging/production (mirror of `itest:worker-role`: table grants on events/deliveries/queue, the function list incl. the three M13.3 additions, column-limited reads); `docs/runbooks/worker-deployment-operator-guide.md`.
- **Dependencies:** Phases 1–3.
- **Tasks:** one reviewed grant script per environment; health log and heartbeat monitored; lease-recovery mode set from the provider (`SES` = non-idempotent → `dead/outcome_unknown`, never a silent re-send).
- **Security:** worker role: no BYPASSRLS, no superuser, no client functions, no evidence-table access; secrets only in the worker's environment.
- **Tests:** `itest:status`-style read-back of grants per environment; worker-runtime lane on staging-like data.
- **Exit:** read-back shows exactly the approved grants; worker starts, heartbeats, and sends nothing while the switch is false.

## Phase 6 — Email delivery, retry, suppression, bounce and failure handling

- **Files/objects (exist; activate and verify):** `packages/adapters/src/ses-email-provider.ts`, `ses-sns-webhook-provider.ts`, `apps/web/app/api/webhooks/ses/route.ts`, `email_suppressions`, `app.reserve_email_attempt` (suppression + L1–L5), quota migration (bulk caps).
- **Dependencies:** Phase 5; SES domain verification, DKIM/SPF/DMARC, production access (outside the repo; operator runbooks `ses-sender-operator-setup.md`, `ses-sns-webhook-operator-setup.md`). Legal: L7 (cross-border transfer).
- **Tasks:** a reviewed migration raising bulk L4/L5 from zero to values below the SES account quota (`GetAccount`); verify bounce → suppression → next send skipped `address_suppressed`; complaint → suppression; retries with backoff; 72-hour expiry; dead-letter visibility in the delivery log.
- **Security:** webhook signature verification (exists); no raw provider text stored; addresses never logged.
- **Tests:** existing adapter/webhook suites; staging SES sandbox to verified addresses only; bounce/complaint simulator addresses.
- **Exit:** in staging, simulated bounce and complaint each suppress the address and the next send is skipped; quotas never exceeded.

## Phase 7 — End-to-end acceptance

- **Scope:** Playwright + Mailpit on the isolated stack, then the same script on staging with SES sandbox: create community → add 300 accountless members → attest → create an 80-member collection → announce to all → member unsubscribes by link → update announcement → member not emailed; confirmations still delivered; payment-targeted reminder unavailable; WhatsApp/SMS never sent.
- **Exit:** script green twice in a row on both environments; delivery log matches Mailpit/SES counts exactly.

## Phase 8 — Staging and production release

- **Order per environment:** backup → apply proposals 1–3 and N-AUD as migrations (moved into `supabase/migrations` in one reviewed change, tests to `supabase/tests/49–52`) → worker grants → deploy web and worker with `email_sending_enabled = false` → attest a pilot community → enable the switch for transactional only (existing quotas) → open bulk caps for the pilot → widen.
- **Rollback:** switch false (immediate stop); per-object rollback in each proposal header (announcements first, then policy; R3 by re-creating the 20261024200000 reserve body); evidence tables exported before any drop.
- **Gates:** pgTAP and integration green on staging; Nigerian legal sign-off on L1–L5, L7, L8, L12 and the notice text; operator runbook dry-run; monitoring of skipped/dead by code.
- **Exit:** pilot community receives announcements; withdrawals honoured; no complaint above threshold over an agreed period; then general release.
