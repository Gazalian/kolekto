### 3.2 Port semantics (investigated)

- `inet_server_port()` returns the port on which the **server** accepted the connection.
- `docker port supabase_db_kolekto` (container metadata only; no database connection) shows
  `5432/tcp -> 0.0.0.0:54322` and `[::]:54322` [V]. Postgres listens on 5432 inside the container; Docker
  publishes it on the host port. A host connection to 54322 is therefore reported as 5432 by the server [I,
  standard Docker NAT/proxy behaviour; not observed live, because no connection was allowed].
- Consequence: `inet_server_port()` is identical (5432) on the developer and the test stack and cannot identify
  either. It is now only checked as "a TCP connection to the expected container port"
  (`ITEST_CONTAINER_DB_PORT = 5432`, [U] for the test stack until Phase 3; any other value refuses).
- The host port is checked instead against a value the **test database itself** carries:
  the bootstrap must run `alter database postgres set kolekto.itest_db_host_port = '<host port>'` next to
  `kolekto.itest_stack`. The developer database has neither setting → `IDENTITY_PORT_UNDECLARED` +
  `IDENTITY_STACK_MISSING`.
- `inet_server_addr()` is not used: inside Docker it is the container address, not loopback.

### 3.3 The probe

`IDENTITY_PROBE_SQL` (one constant `select`):

```sql
select current_user::text as role_name, session_user::text as session_role_name,
       current_database()::text as database_name, inet_server_port() as server_port,
       current_setting('kolekto.itest_stack', true) as stack_id,
       current_setting('kolekto.itest_db_host_port', true) as declared_host_port,
       current_setting('transaction_read_only') as transaction_read_only
```

`createIdentityProbe(open)` opens a single-use session, runs the statement, closes the session (also on
failure) and maps the rows with `identityFactsFromRows`: exactly one row with exactly these seven columns,
values passed through uncoerced so a wrong type is `IDENTITY_INCONCLUSIVE`. The real session
(`openProbeSession`): `max: 1`, `fetch_types: false`, startup parameters `default_transaction_read_only = on`
and `statement_timeout = 5 s`, every statement wrapped in `begin read only`, and only the two constant probe
statements accepted (`PROBE_STATEMENT_REFUSED` otherwise). The gate bounds each probe at 10 s.

## 4. Pause-switch reader behaviour

- SQL: `select email_sending_enabled from public.notification_sender_state` (unchanged from Phase 1a), run
  through the same read-only session.
- `pauseSwitchStateFromRows` requires an array of rows with exactly the one column; `checkPauseSwitch` then
  requires exactly one row whose value is the boolean `false`.

| Result | Refusal |
|---|---|
| `[{ false }]` | passes |
| `[{ true }]` (before or after the file) | `PAUSE_SWITCH_ON` |
| `[]` | `PAUSE_SWITCH_ROW_MISSING` (a missing row reads as "off" in production code, so it is not trusted) |
| two or more rows | `PAUSE_SWITCH_INCONCLUSIVE` ("returned N rows") |
| non-array, `null` row, `"false"`, `0`, `null`, wrong or extra column | `PAUSE_SWITCH_INCONCLUSIVE` |
| query error or timeout | `PAUSE_SWITCH_READ_FAILED` (SQLSTATE/errno only, details withheld) |

There is no write path: the session refuses any statement other than the two probes, the reader never
repairs a missing or malformed row, and a unit test asserts the only statements issued are the two selects.
`email_sending_enabled` is never set by any code in this phase.

### 5.2 Factory (`itest-db.ts`)

- `connectVerified(env, { max })` → `assertVerifiedEnvironment(env)` first; the driver is never constructed for
  an unverified object (unit-tested with a spy driver). `max` must be 1–10.
- Options are built field by field: `host` (IPv6 brackets stripped), `port`, `database`, `username`,
  `password`, `ssl: false`, `path: undefined`, `prepare: false`, `fetch_types`, `max_lifetime: null`, explicit
  timeouts, `application_name`. **The URL string is never passed to the driver.** Reason (verified by reading
  postgres.js 3.4.9 `parseOptions`): the driver turns URL query parameters into startup parameters and falls
  back to `PG*` variables for anything not given explicitly.
- R10 startup parameters on test connections: `lock_timeout = 10 s`, `idle_in_transaction_session_timeout = 60 s`.
- Lexical repository guard: only `itest-db.ts` under `test/support/` imports `postgres`; no harness file imports
  `pg`, `@kolekto/adapters`, `@kolekto/db`, `node:net/tls/http(s)`, `nodemailer` or calls `fetch(`.

## 8. Secret exposure assessment (`KOLEKTO_SESSION_SECRET`)

Method: scripts read the value from the git-ignored `.env.local` into memory and reported only file paths,
counts, lengths and claim names. No value was printed in this session.

**Findings**

1. **Inside the repository the value exists only where it is meant to be:** the git-ignored `.env.local` and
   `apps/web/.env.local` (one occurrence each). It is in no tracked file, no document, and no build output
   (`.next-e2e` was scanned). `git log --all -S<value>` over all refs, including the stash, finds **0 commits**.
   It was never committed.
2. **It is persisted outside the repository, in 7 Claude Code session transcripts**
   (`C:\Users\USER\.claude\projects\C--Users-USER-Desktop-Kolekto-codebase-kolekto\*.jsonl`). The repository
   does not control these files. The commands that put it there:
   - Read-tool reads of `.env.local` / `apps/web/.env.local` (sessions on 2026-10-29, 2026-10-30 ×2, 2026-11-03 ×2);
   - `grep -E "^(SUPABASE|EMAIL|KOLEKTO)" .env.local` (2026-11-03);
   - a repository-wide `grep … SES …` that included `*.env*` files — `SES` matches inside `KOLEKTO_SESSION_SECRET`
     (2026-10-29);
   - **the Phase 1a session's `env | grep -iE "^(KOLEKTO|SUPABASE_DB|EMAIL_|MAILPIT|PG)"` (2026-11-04)** — the
     disclosure the previous report referred to. It printed values because the agent process environment
