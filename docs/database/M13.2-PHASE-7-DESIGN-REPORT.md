## 0. Summary

1. **The real loop can be exercised with no source change.** Run the esbuild bundle of `src/index.ts` as a supervised child process with an environment built only from the verified gate. `src/**` stays untouched, and the Q6-2 extraction is not needed.
2. **Failure recovery can be tested deterministically without touching worker code,** by holding row locks from the harness and detecting the blocked worker session (§7).
3. **The switch-ON path can only be proven by writing the switch on the test stack.** That contradicts R11′, so it needs an explicit amendment (§6). Everything else in this design runs with the switch `false`.
4. **Strict "Mailpit-only" cannot produce rejection or ambiguous cases.** A loopback fault proxy in front of the test Mailpit can, and no provider other than the test Mailpit is ever contacted (§8).
5. **No dedicated worker role exists.** The documented credential is the owner connection, so a pass as `kolekto_itest` says nothing about least privilege (§5).
6. **Budget is not the constraint now:** 22 of 180, one full design pass costs about 26 grants (§11). Wall-clock is, because the 30 s visibility timeout is a fixed constant.
7. **Reading the code found issues that are outside a test design.** They are listed in §2.3 and were not fixed.

### 1.2 Event stage (`index.ts:109-142`)

| Step | Behaviour | Class |
|---|---|---|
| Read | `select msg_id, read_ct, message from pgmq.read('notification_events', 30, 10)`, every loop iteration | VERIFIED |
| Visibility timeout | 30 s, compile-time constant (`index.ts:30`). Not configurable | VERIFIED |
| Read count | Live `pgmq.read` (pgmq 1.5.1) does `read_ct = read_ct + 1` in `UPDATE … RETURNING`, so **the first read returns 1**. It selects `vt <= clock_timestamp()` with `FOR UPDATE SKIP LOCKED`, so a row locked elsewhere is skipped and **not** counted | VERIFIED (live body) |
| Order | One message at a time within a batch. No `running` check inside the batch (`index.ts:116`) | VERIFIED |
| Dead-letter test | `read_ct > 5` → `pgmq.archive`, no processing. So up to 5 processing attempts, and the 6th read archives | VERIFIED |
| Process | `processNotificationMessage(sql, msg.message)` in one transaction. **The return value is ignored** (`index.ts:129`) | VERIFIED |
| Acknowledge | `pgmq.delete(…, msg_id::bigint)` after processing returns, including `skipped` outcomes. The boolean result is ignored | VERIFIED |
| Delete vs archive | **Success or skip → deleted, no copy kept. Only `read_ct > 5` → archived.** In production `pgmq.a_notification_events` therefore *is* the dead-letter store. There is no separate DLQ | VERIFIED |
| Throw while processing | Logged, message stays, reappears after 30 s | VERIFIED |
| Throw while deleting | Same catch: logged, message reappears, processing replays. Replay is idempotent through `event_key` and delivery uniqueness | Code VERIFIED, runtime NOT TESTED |
| Archive failure | Logged and skipped, so it retries at the next read with a higher `read_ct` | VERIFIED |
| Poll failure | Logged, sleeps 10 s, send stage still attempts | VERIFIED |
| Idle | 2 s sleep only if the read returned nothing (`index.ts:173`) | VERIFIED |

**Timing of an always-failing message (INFERRED):** reads at about t0, 30, 60, 90, 120 s fail, and the read at about 150 s archives. Budget 150–180 s per real poison test.

**What makes a message throw.** The processor skips bad input rather than throwing (`notification-rules.ts:115`), so only a database error throws. A real poison shape exists: `collection.publish` with an invalid `actor_type` passes `parseAuditMessage` and `admission` (the person-actor rule covers `member.*` only), then fails the `::public.audit_actor_type` cast at the event insert (`notification-processor.ts:111`). VERIFIED by reading; NOT TESTED. The trigger cannot generate it, so a seed is needed (§4.4).

### 1.4 Shutdown and restart

| Case | Behaviour | Class |
|---|---|---|
| SIGINT/SIGTERM | Sets `running = false` (`index.ts:102-103`), installed after `loadEmailSender` | VERIFIED |
| During a batch | Remaining messages in the batch are still processed | VERIFIED |
| After the event stage | The send stage still runs once: maintenance if due, zero claims (`shouldContinue` false), heartbeat | VERIFIED |
| Exit | Logs, `await sql.end()` with no timeout, exit code 0 expected | Code VERIFIED, exit NOT TESTED |
| Blocked statement | The worker sets no `statement_timeout` or `lock_timeout`. A blocked statement stalls the whole loop and the drain, until the platform's SIGKILL | INFERRED |
| Hard kill mid-event | Message reappears after the visibility timeout | INFERRED |
| Hard kill mid-send | Row stays `sending` until its 300 s lease lapses. With `idempotency: "none"` (Mailpit, SES) the next maintenance makes it `dead/outcome_unknown`, never re-sent | Code VERIFIED, runtime NOT TESTED |
| Restart | `lastMaintenance = 0`, so maintenance runs on the first iteration. `senderHalted` resets | VERIFIED |

### 1.5 How to exercise this exact path

Spawn `node <bundle>` from a new `test/support/itest-worker.ts`:

- **Build:** the same esbuild flags as `package.json`, output under `apps/worker/dist/itest/` (already ignored by `.gitignore:6`), SHA-256 recorded in the evidence.
- **Environment, built from nothing, never inherited:** `KOLEKTO_ENV=local`; `NEXT_PUBLIC_SUPABASE_URL` set to the test Kong loopback URL; `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` a constant placeholder (`env.ts` only requires non-empty); `SUPABASE_DB_URL` composed from `gate.verified().db`; `EMAIL_PROVIDER=mailpit`; `EMAIL_FROM`; loopback `APP_BASE_URL`; `EMAIL_SMTP_HOST=127.0.0.1`; `EMAIL_SMTP_PORT` from the gate or the proxy; `PGAPPNAME=kolekto-itest-worker` (`postgres/src/index.js:485` honours it); OS essentials only. Never `EMAIL_API_KEY`, `EMAIL_AWS_*`, `AWS_*`, `NODE_OPTIONS`, other `PG*`, or `--env-file`.
- **Target proof:** after spawn, the harness must see a session with that `application_name` on the verified test database within a bounded time, or it kills the child and fails.
- **Layered guards unchanged:** with `KOLEKTO_ENV=local`, `email.ts:244` refuses a real provider, and the adapter refuses a non-loopback host. The `kolekto_itest` password fails on any other database (28P01, VERIFIED in Phase 3).
- **Orphan safety:** a test-only preload (`--import`) exits the child when the parent's IPC channel disconnects, so a crashed test cannot leave a worker polling. No production file changes.
- **Logs:** stdout and stderr captured in memory, and every child gets the redaction scan in §4.5.

**Windows limit.** Node on Windows treats `child.kill('SIGTERM')` as a forced kill, so the handler never runs. On this machine graceful shutdown needs the same preload to call `process.emit('SIGTERM')` on an IPC message. That proves the handler and drain logic, not OS signal delivery. Real signal delivery stays NOT TESTED until run on Linux, which is the likely deployment platform (INFERRED; the platform is not chosen, runbook §2).

### 5.3 The RLS problem and the recommendation

Every `public` table above has RLS **enabled and forced**, with policies aimed at client roles (VERIFIED). A new role without BYPASSRLS sees no rows and cannot insert.

| Option | Change | Trade-off |
|---|---|---|
| A. `kolekto_worker` with BYPASSRLS plus narrow grants | One additive migration | **Recommended first step.** Grants, including column grants on `members`, still limit what it reaches. Smallest change |
| B. No BYPASSRLS, new policies `to kolekto_worker` | Policies on 8 tables | Slightly stronger, more surface, more ways to get a policy wrong |
| C. Move all direct SQL into `SECURITY DEFINER` `app.worker_*` functions | Source and migration | Cleanest end state; largest change. Not justified now |

Two invoker-rights trigger functions run on the worker's inserts: `app.sanitize_notification_event_payload` and `app.set_updated_at` (VERIFIED). Postgres checks EXECUTE on a trigger function when the trigger is created, not when it fires, but the body runs with the caller's rights (INFERRED). Only a real run settles this, which is what LP-1 is for.

**Rollback for any later production adoption:** repoint `SUPABASE_DB_URL` to the previous credential, then drop the role and its grants; nothing else depends on it. **No role or grant is changed by this report.**

## 7. Failure-recovery test design

### 7.1 Deterministic interruption with no source change

| Technique | How | Proves |
|---|---|---|
| **Processing gate** | Harness opens a transaction and inserts `notification_events` with the message's `event_key`, uncommitted. The worker's `INSERT … ON CONFLICT` waits on it. Always rolled back, so no residue | Worker is mid-processing with `read_ct = 1` |
| **Acknowledgement gate** | While the processing gate holds (read is finished), harness runs `select … from pgmq.q_notification_events where msg_id = $1 for update`, then releases the processing gate. Processing commits; `pgmq.delete` blocks on the row lock | Processed, not yet acknowledged |
| **Detection** | Poll `pg_stat_activity`: `application_name = kolekto-itest-worker`, `wait_event_type = 'Lock'`, query text matches. Never a fixed sleep. Bounded, then fail | The worker is exactly where the test says |

Limits: harness sessions have `lock_timeout` 10 s and `idle_in_transaction_session_timeout` 60 s, which fits. The blocking behaviour is INFERRED from Postgres semantics and must be proven by the first run. Sequence matters: commit the domain action and take the gate **before** spawning the worker, or it may finish first.

### 7.2 Scenario mapping (Section C)

| Required scenario | Test | Sequence and assertions |
|---|---|---|
| Successful processing | RT-2 | §3.1 |
| Interruption after read | RC-1 | Domain commit → processing gate → spawn → detect blocked → **SIGKILL** → roll back gate → assert still queued, `read_ct = 1`, no event → spawn again |
| Visibility timeout expiry | RC-1 | Message is not re-read before `vt`: sample `vt` and `read_ct` read-only until it passes, then completion within a bound of about 40 s |
| Retry and read-count increments | RC-1, RC-5 | `read_ct` 2 on redelivery; 1 → 5 sampled on poison |
| Maximum attempts | RC-5 | Exactly 5 "Failed to process" lines, read 6 does not process |
| Dead-letter archival | RC-5 | Archive row for this `msg_id` with `read_ct = 6`, `archived_at` set, gone from queue; no event row; one "Dead-lettering" line |
| Acknowledgement failure, by error | RC-2 | Acknowledgement gate → `pg_terminate_backend` on the worker's blocked session → worker logs and survives → release → redelivery → replay → deleted. 1 event, 1 delivery throughout |
| Acknowledgement failure, by crash | RC-3 | As RC-2 with SIGKILL, then restart |
| Replay and duplicates | RC-2, RC-3, RC-6, RC-7, PS-1 | Counts never rise. Sent row never re-sent |

`pg_terminate_backend` targets only sessions with the worker's `application_name`, re-checked in the same statement.

**Poison safety:** the seed uses the test's own `community_id`, `collection.publish`, a run-scoped object id and an invalid `actor_type`. It cannot create a delivery. `recoverOwnQueue` handles leftovers through the existing owner-checked archive.

### 8.1 What Mailpit can do

### 8.2 Fault proxy

`itest-smtp-fault-proxy.ts`: a TCP proxy on `127.0.0.1:0` (ephemeral port, in-process, per test). Its only upstream is the gate's verified SMTP port, with no configurable host. It reads client commands line by line and applies one script per test: pass through, answer a code itself, drop, hold, or reset on QUIT. It never relays anywhere else. Unit-tested against the existing SMTP test server first, with no database.

Real `MailpitEmailProvider`, real `sendOneClaimed`, real database. **The switch stays `false`, so none of these needs §6.** `timeoutMs` is set short for the timeout cases. Each test asserts the row and the proxy log, and matches Mailpit exactly.
