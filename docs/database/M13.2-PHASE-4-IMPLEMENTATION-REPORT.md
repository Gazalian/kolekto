## 6. How fixture ownership and cleanup are enforced

- **Ownership:** every id is a fresh random v4 UUID from the file's `RunScope`; slugs `itest-<tag>-<n>`, event
  keys `itest-<tag>-<file>-<n>`, addresses `itest+<tag>-<n>@<file>.example.test`. The scope refuses the P8
  residue ids and the old fixed-id shape. No test reuses another run's values (Verified by unit tests;
  Verified live: 4 runs, no unique-constraint collision).
- **No deletes:** no test deletes any row, toggles any trigger, sets the purge flag or replication role, or
  writes the pause switch (acceptance guard over the whole test tree, Verified; safety grep, Verified).
- **Rollback first:** 22 of the 36 run tests commit nothing at all.
- **Quarantine, not delete:** committed communities are tracked by the harness; `afterEach` runs the
  parameterised, ownership-checked `buildQuarantineStatement` (`UPDATE … SET status='dead',
  error_code='itest_quarantined' … WHERE community_id IN ($n::uuid …) AND status IN ('pending','sending')`).
  Errors are recorded, not thrown over a test's own failure, and reported by `finish()`.
- **Postflight:** `finish()` asserts the scope holds no open row and the whole test database holds no
  pending/sending email row, then releases the mutex; the gate's postflight then re-reads the switch.
- **Ledger fillers:** only in `insertLedgerFillers`. The acceptance guard allows exactly one ledger insert, only
  in `support/itest-isolation.ts`, only after `assertRollbackHandle(tx);` in the same function; every other
  ledger insert anywhere is still a violation (unit-tested both ways).
- **Committed residue (by design):** committed tests leave run-tagged communities, users, events, settled or
  quarantined deliveries and real ledger rows on the test stack. After 4 runs: 56 communities (all `itest-*`),
  84 events, 84 email deliveries (36 sent, 36 dead of which 12 quarantined, 12 skipped), 68 ledger rows,
  0 open email rows (Verified). Removing them would need `itest:reset` (separate approval); nothing in the tests needs it.

## 7. Concurrency and sender-claim isolation

- **Suite mutex:** each file takes session lock `(918273, 1)` with a bounded `pg_try_advisory_lock` poll (90 s,
  500 ms) on a dedicated connection taken out of its pool with `reserve()` (postgres.js starts the idle timer
  only for connections in the pool's open queue, and `max_lifetime` is null, so the session is not recycled —
  Verified by reading postgres.js 3.4.9). `beforeEach` checks the lock is still held by this session
  (`MUTEX_LOST` otherwise). Released in `after`; 0 advisory locks remained after every run (Verified).
- **Lane serialisation:** unchanged `--test-concurrency=1`, one file at a time.
- **Claim isolation (real, unscoped claim, no production change):** `start()` refuses if any pending or sending
  email row exists anywhere; `checkpoint()` refuses before **every** test unless that count is 0. So the real
  `claim_next_notification_delivery` can only ever see the current test's own rows, and every committed sender
  test asserts the claimed `deliveryId` is its own. Rows a test leaves open are quarantined before the next test.
- **Global rate limits:** L1/L2 are made independent by run-unique addresses and communities. L3/L4/L5 are
  global by design: serialised by the mutex; L5 respected by `waitForL5Headroom` before each reservation that
  must be granted (committed or rolled back — the frozen transaction clock cannot wait inside a transaction);
  committed filler rows no longer exist, so the per-run L4 cost is exactly the real grants: **17 per run**
  (Verified: ledger 0 → 17 → 34 → 51 → 68).
- **L4 headroom:** the preflight refuses a file when more than cap − 40 (140 of 180) transactional attempts
  occurred in 24 h. Today's use: 68.
- **Pause switch and sender state:** never written. The only committed sender-state effect a test could have
  is the heartbeat; every `runSenderTick` now runs on a rolled-back handle. Heartbeat stayed null (Verified).
- **Live worker / queue consumer:** the preflight refuses on a heartbeat younger than 60 s or on read messages in
  `pgmq.q_notification_events` (heuristic, §12).
- **Parallel execution:** the design does not support it (review §5.9), so it was **not tested**.
