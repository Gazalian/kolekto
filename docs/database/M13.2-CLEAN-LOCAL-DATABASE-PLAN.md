### ⚠️ The one real hazard: the CLI is linked to staging

`supabase/.temp/` is git-ignored (and CI asserts it is never tracked), so the link will not
be committed. **But the live CLI on this machine is linked to the "kolekto staging"
project.** Any `supabase` command run with `--linked` or a remote/`--db-url` flag would hit
**staging**, not local. Mitigation for every destructive step:

- Use only local-targeting commands: `supabase db reset`, `supabase migration up --local`,
  `supabase test db` (all operate on the local container).
- **Never** pass `--linked`, `--db-url <remote>`, `--project-ref`, or run `supabase db push`.
- Do **not** run `supabase link` / change linkage (not approved; not needed).

## 2. Options considered

### Option 1 — Fresh local DB from the existing complete migration history ✅ RECOMMENDED

Replay all 108 migrations from scratch into the local container via the repository's
documented workflow, then apply `seed.sql`, then run pgTAP.

- **Reproducibility:** already enforced — CI's `database` job does exactly this on every PR
  (`supabase db reset --debug` → `supabase test db` → zero-drift `db diff`).
- **Compatibility:** identical schema the app and worker already target; no divergence.
- **Isolation:** local container only; loopback URLs; no cloud link used.
- **Maintenance:** zero new surface — it *is* the existing discipline.
- **Cost:** destroys local-only developer data → requires backup + explicit confirm (built
  into `npm run db:reset`).

### Option 2 — Separate "M13.2-only" minimal-baseline database ❌ REJECTED

Rejected: M13.2 is **not** separable. Notification tables FK/depend on `auth.users`,
`public.users`, `public.communities`, and the `app` helper schema from the foundation
block (proven by every notification pgTAP fixture). A minimal baseline would either
re-create those tables (a second, drifting source of truth — explicitly forbidden) or fail
to run the app/tests. It also could not satisfy "must run the application or its tests
correctly."

### Option 3 — New / linked hosted project ❌ REJECTED (and out of bounds)

Out of scope by the safety rules (no `supabase link`, no hosted project without approval).
Isolation is already achieved locally by ADR 0007; a hosted project adds remote-destructive
risk for zero benefit here.

## 3. Recommendation

**Adopt Option 1.** The clean local database = the existing migration chain replayed from
scratch into the local container. No migration files are deleted, rewritten, or
re-baselined. The temporary pause on *new* migration creation stays in effect until this
plan is approved.

## 5. Safety preconditions before any local reset

A reset is destructive to local developer data. **Do not run it until all are true:**

1. Target is the **local** container (`supabase_db_kolekto`, port 54322). ✅ configured.
2. No production/staging URL or `--linked` flag involved. (Operator must not add them.)
3. Local data is disposable / already backed up — `npm run db:reset` **takes a backup first
   and refuses without `KOLEKTO_CONFIRM_RESET=yes`.**
4. Migration files and `config.toml` preserved (unchanged by this task). ✅.
5. Git work, stashes (`stash@{0}` M12A), backup branches (`backup/m13.2-p5-1-pre-rewrite`)
   untouched. ✅ — none modified.
6. Recovery path exists: `npm run db:restore` from the pre-reset backup.

## 6. Recovery plan

- **Before reset:** `npm run db:reset` auto-runs `scripts/db/backup.mjs` into `backups/`
  (gitignored). If that backup fails, the reset aborts.
- **After reset:** restore local app data with `npm run db:restore`.
- **Schema recovery:** the migration files themselves are the source of truth; a reset
  reconstructs the schema deterministically.
