## 14. Unexpected issues and blockers

1. **First start failed on a health-check timeout.** All 120 migrations applied, then the CLI reported
   `supabase_storage_kolekto-itest … unhealthy` and tore the stack down (containers and volumes removed —
   verified nothing was left). On the immediate retry with `--ignore-health-check` storage reported `healthy`
   within ~40 s. Cause (inference): the Docker VM has 3.77 GiB and the developer stack already uses ~1.2 GiB,
   so storage starts slower than the CLI's fixed wait. **Fix:** `itest:up` now starts with
   `--ignore-health-check` and runs its own bounded wait (240 s) until every container with a health check is
   `healthy`; otherwise it refuses and leaves the stack for inspection. The patched path was exercised by the
   down/up cycle (step 13). Step 5 bypassed the wrapper once (same flags and `--workdir`, sanitised
   environment); the wrapper then verified that stack in full before bootstrapping.
2. **Published ports bind to all interfaces** (`HostIp ""`), exactly like the developer stack. CLI 2.109.1 has
   no loopback-binding option. The DB needs the random test password; Mailpit UI/API (55424) and kong (55421,
   CLI demo keys) are reachable from the local network while the stack runs. Same exposure as the developer
   stack; not changed.
3. The Mailpit container performs its own release check (`LatestVersion` in `/api/v1/info`); the CLI prints
   an update notice for v3.0.0. Neither was acted on; the CLI stays pinned at 2.109.1.
4. **`itest:reset` is untested.** In particular whether `supabase db reset` keeps the cluster-level
   `kolekto_itest` role is unknown; the script handles both cases (alter vs create) but neither was run.
5. The probe driver lives in the session scratchpad, not the repository (Phase 3 scope named only the four
   wrappers). Phase 4's real integration files run the same gate path, so no repository copy is needed for
   them.
6. Carried over: Phase 1b's file relocation and all P6–P8 / Phase 1a–1c / Phase 3 work are uncommitted; the
   `KOLEKTO_SESSION_SECRET` transcript-exposure decision (Phase 1b §8) is still open. This session's agent
   process environment still holds developer and secret variables; only their names were listed.
