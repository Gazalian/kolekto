## 2. Test Harness Architecture (Phase C)

### Isolation strategy

The P8 test harness exercises the sender pipeline (from delivery claim through to
Mailpit receipt and state settlement) without enabling the `email_sending_enabled`
pause switch. The key architectural insight:

- **`sendOneClaimed(sql, opts)`** does NOT check the pause switch. It directly claims
  the next pending delivery, reserves an attempt, calls the provider, and settles.
- **`runSenderTick(sql, opts)`** is the only function that gates on `isEmailSendingEnabled`.
  It calls `sendOneClaimed` internally when the switch is ON.

By calling `sendOneClaimed` directly with a real `MailpitEmailProvider`, the test
exercises the full path — claim → reserve → template render → SMTP send → Mailpit
delivery → state settlement — while the pause switch remains `false` throughout.

This is NOT a workaround or bypass. The existing `notification-sender.integration.test.ts`
uses the same pattern: it calls `sendOneClaimed` directly for all its delivery tests.
The architecture separates the "should we send?" decision (`runSenderTick`) from the
"how to send" mechanics (`sendOneClaimed`), and the test targets the mechanics.

### Safety properties maintained

| Property | Verification |
|---|---|
| `email_sending_enabled` remains `false` | Asserted at start and end of every test |
| No external SMTP | `MailpitEmailProvider` rejects non-loopback hosts at construction |
| Adapter validates messages | `assertValidEmailRequest` runs before every send |
| No real recipients | All addresses are synthetic (`@kolekto.test`) |
| Synthetic data only | All fixtures use dedicated UUID ranges (`e8xxxxxx-...`) |
| Full cleanup | Every test cleans up its fixtures in `finally` blocks |
| No database mutations persist | Tests commit for the claim path, then delete in cleanup |

### Environment gate

Tests run only when ALL conditions are met:
- `KOLEKTO_WORKER_INTEGRATION=1`
- `SUPABASE_DB_URL` points at a loopback host (127.0.0.1, localhost, ::1)
- `EMAIL_SMTP_HOST` and `EMAIL_SMTP_PORT` point at local Mailpit SMTP
- `MAILPIT_API` points at local Mailpit HTTP API

Command to run:
```
KOLEKTO_WORKER_INTEGRATION=1 \
SUPABASE_DB_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres \
EMAIL_SMTP_HOST=127.0.0.1 \

MAILPIT_API=http://127.0.0.1:54324 \

```

### Key factual correction

The P6/P7 report stated that the full sender-to-Mailpit round-trip "requires enabling
the pause switch in a controlled test harness." This is factually incorrect. The sender
architecture has a clean separation:

- **`runSenderTick`** checks `isEmailSendingEnabled` and only calls `sendOneClaimed`
  when the switch is ON.
- **`sendOneClaimed`** performs the actual delivery mechanics (claim → reserve → template
  → provider → settle) and does NOT check the pause switch.

The existing `notification-sender.integration.test.ts` already called `sendOneClaimed`
directly for all its delivery tests, demonstrating this pattern. P8 extends it to use
a real `MailpitEmailProvider` and verifies Mailpit receipt.

### 7.1 Outstanding integration enhancement: processor-to-sender happy-path test

The following integration test would close the remaining coverage gap between the
processor and sender layers. It is an enhancement, not a condition for the current
P8 acceptance decision.

A processor-to-sender happy-path test should ideally:

1. Construct a valid, fresh, watched audit event (e.g. `member.create`).
2. Invoke the real `processNotificationMessage()` function.
3. Allow the processor to create the notification event and eligible delivery.
4. Verify that the delivery has the expected recipient and payload.
5. Pass that processor-created delivery to the actual sender (`sendOneClaimed`).
6. Verify template rendering and Mailpit receipt.
7. Verify the final delivery state (`sent`, correct `provider_message_id`).
8. Verify that no duplicate message is produced on replay.

This test would exercise the complete path from audit event through to Mailpit
in a single test function, confirming that processor-created deliveries are
correctly consumed by the sender — a handoff currently covered by separate tests
but not by one end-to-end integration test.

## 9. P8 Acceptance Decision

### CONDITIONALLY ACCEPTED

Accepted after independent review corrections (2026-11-03). No functional defects
were found. Documentation overclaims and misleading test names have been corrected.

#### What P8 verifies

P8 verifies the **sender integration pipeline** using real local infrastructure:

1. **Sender pipeline verified (D1, D2):** delivery claim → rate-limit reservation →
   send context loading → template rendering → `MailpitEmailProvider` → SMTP →
   Mailpit receipt → delivery state settled as `sent`. Subject, HTML body, plain text,
   from address, recipient address, member code, and community name all verified against
   Mailpit API. D1 and D2 seed rows directly via `addDeliveryWithEvent()`.
2. **Multiple templates verified (D2):** `officer_invitation.accept` template renders
   correct role and community name through to Mailpit.
3. **Context loading verified (D3):** `loadSendContext` returns correct event type and
   payload; `buildEmailMessage` selects the correct template and verb.
4. **No duplicates (D1, E4):** sent rows are terminal — `sendOneClaimed` returns `empty`
   on replay, and Mailpit receives exactly one message.
5. **Processor skip/reject decisions (E1–E3, E8):** unknown events, malformed messages,
   empty payloads, and stale events are correctly skipped by `processNotificationMessage`.
6. **Dead-letter threshold decisions (E5):** `shouldDeadLetter()` boundary values correct.
   Actual archival is covered by P6 tests, not P8.
7. **Terminal-state safety (E6, E7):** skipped and dead deliveries are never re-claimed.
8. **Adapter failure (E9):** unreachable SMTP is classified correctly, not silently swallowed.
9. **Pause switch state (E10):** confirmed OFF throughout. Does not test `runSenderTick`.
10. **Safety invariants (S1–S3):** pause switch off, non-loopback rejected, invalid
    messages rejected.
11. **Full regression passed:** 195/195 worker tests, 161/161 adapter tests, 1422/1422
    database pgTAP tests, build and typecheck clean.

#### What P8 does NOT verify

- **Processor happy path through D1/D2:** D1/D2 insert rows directly; they do not invoke
  `processNotificationMessage` to create the notification event and delivery.
- **Processor-to-sender happy-path handoff:** No single P8 test constructs a fresh audit
  event, invokes the real processor, allows it to create the delivery, and then passes
  that delivery to the sender through to Mailpit.
- **`runSenderTick` pause-switch behavior:** E10 confirms the switch is OFF but does not
  call `runSenderTick`.
- **Actual dead-letter archival:** E5 tests the threshold decision function only.
