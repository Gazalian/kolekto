## 1. Executive summary

The notification system is **well-built at the component level but is not end-to-end verified, and is not ready for M13.2 acceptance.**

- **Working [V]:** 146/146 worker unit tests pass (repeatable, sequential and parallel); worker typecheck clean; 22/22 web notification unit tests pass; the pause switch is `false` in the local DB; the Mailpit adapter refuses non-loopback hosts; `packages/config` refuses real providers in `local`; the four templates escape HTML, have plain-text parts and contain no UUIDs or "verified" claims.
- **The "four failing worker tests" could not be identified [V].** No log, report or artefact of a 191/195 run exists in the repository. The P8 report itself claims 195/195 sequential and "~5" concurrent failures — neither number has evidence. The 4 failures can only be among the 49 DB-backed integration tests (the other 146 are deterministic). Those tests were **not run** in this investigation because doing so would violate the safety rules (§3.3). Static analysis identifies a set of confirmed **test-isolation defects** that explain concurrent failures (§3.4), but the exact four remain **Unresolved**.
- **Not genuinely end-to-end [V].** No test (and no recorded manual run) exercises `pgmq.read → processNotificationMessage → delivery row → sendOneClaimed → Mailpit` in one path. The real event loop in `apps/worker/src/index.ts` is never executed by any test; P6 tests a hand-copied replica of it.
- **Product-level gap [V]:** zero of 5 local members are linked to an account and **no code path sets `members.user_id`** (D-LINK). Every member-targeted in-app notification — publish, publish-to-unpaid, post-publish reminders, membership confirmation in-app — therefore reaches **no one** in real use. The UI's recipient preview honestly reports this (it counts only linked members), but the host-facing features are functionally inert.
- **Documentation overstates acceptance [V].** P6 "FULLY ACCEPTED" relies on a manual, unrepeatable archival check; P8's describe block is titled "event → processor → sender → Mailpit" but never calls the processor; P8 E9 cannot fail; the claim "no test enables the pause switch" is false for `notification-sender.integration.test.ts`.

**Recommendation: NO-GO for M13.2 completion** (see §15). The remaining work is mostly test-harness and documentation work, plus one small template defect.

## 4. P6 — Dead-lettering assessment

### 4.1 Implementation [V]

- `apps/worker/src/dead-letter.ts`: `MAX_READ_CT = 5`; `shouldDeadLetter(readCt) = readCt > 5`.
- `apps/worker/src/index.ts` event stage: `pgmq.read('notification_events', 30, 10)` → for each message, if `shouldDeadLetter(read_ct)` → `pgmq.archive(...)` in its own try/catch, log, `continue`; else `processNotificationMessage` then `pgmq.delete`. A processing exception is logged and the message is left to reappear after the 30 s visibility timeout.

| Question | Answer |
|---|---|
| Max read count | 5 |
| Exact retry threshold | A message is **processed on reads 1–5** and **archived without processing on read 6**. So 5 processing attempts. |
| Archive behaviour | `pgmq.archive` moves the row to `pgmq.a_notification_events` (removes it from the queue). |
| Removal after archival | Yes — inherent to `pgmq.archive`. Confirmed historically (msg 77 in archive with read_ct 6, not in queue) [V]. |
| If archival fails | Error logged; message stays invisible for 30 s, then re-read with read_ct 7, archive retried. No crash. [V] |
| Healthy messages continue | Yes — `continue` per message, no batch-level abort. [V] |
| Can a poison message block the queue? | Not permanently. It consumes one of 10 batch slots per visit for ≤ 5 visits (~2.5 min), then is archived. [I] If archive fails persistently (e.g. permissions), it would be re-read forever, but still not block other messages. |
| Mixed healthy/failing batch tested? | Only in a **replica** of the loop (`simulateEventLoop` in `dead-letter.test.ts`). |

### 4.2 Gaps [V]

- **The real loop is untested.** `index.ts` calls `main()` at import, so the tests hand-copy its body. The comment claims "the test breaks if they diverge" — it does not; nothing ties the copy to `index.ts`.
- **No repeatable archival test exists.** The P6/P7 report §3 "pgmq integration verified against live local database" was a manual, one-off procedure (msg 77/78). No test file calls `pgmq.archive` against a real DB. The P8 report §4 E5 and §9 say "actual archival is covered by P6 integration tests" — **false**; there are none.
- No alerting/metric on dead-lettered messages beyond `console.error`. No replay tooling from the archive table. [V]
- `apps/worker/package.json` `start` now uses `--env-file=.env.local` and the build externalises `@aws-sdk/*`/`@smithy/*` — real runtime changes, described in the P6/P7 report as "No logic change (dependency version)". [V]

**Assessment:** implementation correct and simple; verification incomplete. *Accept implementation; do not accept "FULLY ACCEPTED" status until a real-loop test exists.*
