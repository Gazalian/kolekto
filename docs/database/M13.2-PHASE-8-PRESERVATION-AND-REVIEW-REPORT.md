### 5.1 R-1: a privilege gap dead-letters healthy messages

**Plain statement of the risk.** If the production worker role is missing any privilege the processor needs, or a migration has not reached that environment, every queue message will be moved to the dead-letter archive as poison within about 2.5 minutes. No one will be told, and no tool exists to replay them.

**Why (READ).** `isFatalDatabaseError` (42501, 42883, 42P01, 3F000 and others) is only consulted for the poll, in `index.ts:215`. In `queue-disposition.ts:152-167` a processing failure with one of those codes is not transient, so it gets no backoff and is simply retried at the 30 s visibility timeout. At read 6 it is archived. `pgmq.read` keeps working, so the fatal exit never fires. Phase 7's first attempt showed this exact failure mode: every event failed with 42501, because of a missing grant. Phase 8's backoff protects against locks, not against this.

**Why it matters now.** The hosted role is the one thing Phase 8 says is unproven until staging. The first staging start is exactly when this would happen.

**Suggested fix, not made:** in `handleQueueMessage`, treat a fatal database error from `process` as a worker fault and stop the process non-zero, leaving the message for later. The supervisor's crash-loop limit then stops the restarts, which also limits how far `read_ct` climbs. Messages are retained in the archive either way, so nothing is destroyed. This is a code change for the next phase.

## 6. Worker-role SQL: is it suitable for staging review?

**Verdict: yes for review, as a draft. No for applying.** The design is sound, and the grant list is what actually ran. It needs the changes below before anyone applies it, and nothing here should be read as approval to do so.

### 6.1 Queue privileges (the question you asked)

**Plain statement of the finding.** `grant select, update, delete on pgmq.q_notification_events` gives the worker role `UPDATE` on every column. Read live from the test stack's equivalent role: it **can** update `message`, `headers` and `enqueued_at`, and it **cannot** insert into the queue or read the whole archive. So a compromised worker credential can rewrite the body of a message waiting to be processed, and falsify its age. No test covers this: LP-3 has no such statement.

**What the worker actually needs.** Read from pgmq 1.5.1 in the live catalog and from `index.ts`. All are SECURITY INVOKER, so they run with the role's privileges.

| Operation | Columns written | Source |
|---|---|---|
| `pgmq.read` | `vt`, `read_ct` | Live function definition |
| `pgmq.set_vt` | `vt` | Live function definition |
| `markProcessed` | `headers` | `index.ts:163` |
| `park` | `vt`, `headers` | `index.ts:170` |
| `pgmq.archive`, `pgmq.delete` | None by `UPDATE` | Live function definition |

**`message`, `enqueued_at` and `msg_id` are never written by the worker.** So this should be enough, though it has not been run:

```sql
revoke update on pgmq.q_notification_events from kolekto_worker;
grant update (vt, read_ct, headers) on pgmq.q_notification_events to kolekto_worker;
```

The `revoke` matters. A column grant added beside a table grant removes nothing, and `workerRoleSql()` is grant-only, so re-running it on the test stack would leave the broad grant in place while appearing to succeed.

**How much this closes.** It protects the integrity of in-flight and dead-lettered bodies. It is **not** a complete containment, because the role also holds `INSERT` on `notification_events` and `notification_deliveries`, including `recipient_address` and `status` (read live). So a leaked worker credential can already queue mail to any address, subject to the pause switch, L1 to L5 and suppression. That is inherent to the current design, where the worker inserts rows directly. Moving those inserts behind a SECURITY DEFINER function would close it, and needs a migration. I recommend recording it as an accepted risk for now. A worker credential also sits beside the SES key in the same process.
