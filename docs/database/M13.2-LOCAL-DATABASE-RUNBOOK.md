# M13.2 — Local Database Runbook

> How any engineer reproduces the clean, isolated local database and validates it. Commands
> are the repository's existing `package.json` scripts and the Supabase CLI. Produced
> 2026-10-13, updated 2026-10-30. **Local development only** — never run these against staging or production.

## 0. Guardrails (read first)

- The CLI on this machine is **linked to the `kolekto staging` project** (`supabase/.temp/`,
  gitignored). Every command below targets the **local container only**. **Never** add
  `--linked`, `--db-url <remote>`, `--project-ref`, or run `supabase db push` / `supabase link`.
- `npm run db:reset` destroys **local** developer data. It backs up first and refuses unless
  `KOLEKTO_CONFIRM_RESET=yes` is set. Prefer `npm run db:migrate` when you only need schema.
- CLI version is pinned to **2.109.1** (config.toml is authored for it; `latest` fails to parse).

## 2. Start the isolated local stack

```bash
npm run db:start          # supabase start — Postgres :54322, API :54321, Mailpit :54324
```

Ports (from `config.toml`): DB 54322, API 54321 (serves `public` only), Studio 54323,
Mailpit UI 54324, Mailpit SMTP 54325.

> **Note — storage volume.** If `supabase start` fails its health check and cleans up
> containers, it also destroys the `supabase_storage_kolekto` Docker volume. Any local dev
> images (e.g. collection covers uploaded via the app) are lost. The volume and the
> `collection-covers` bucket are recreated automatically on the next successful start, but
> the files are gone. This is a CLI cleanup behaviour, not a bug in the application.

> **Note — Mailpit SMTP ownership.** Both Mailpit host ports are published by the
> Supabase CLI directly: `[local_smtp] port = 54324` (web UI / API) and
> `[local_smtp] smtp_port = 54325` (SMTP listener) in `supabase/config.toml`. The
> `smtp_port` line was added in commit `19f27f4` ("chore(supabase): publish Mailpit
> SMTP port for local and CI (M13.2 P1)") and takes effect on the next
> `supabase stop` / `supabase start`. An older Docker forwarder container named
> `kolekto-mailpit-smtp-forwarder`, which proxied host port 54325 to the Mailpit
> container's internal port 1025, was a workaround from before `smtp_port` was
> configured and is now obsolete. Do not recreate it and do not run it alongside the
> current configuration — both bindings would compete for host port 54325 and
> whichever started second would fail. Runtime confirmation (`docker ps` showing the
> Supabase Mailpit container exposing `0.0.0.0:54325->1025/tcp`, host listener
> inspection on 54325, and an SMTP smoke send into Mailpit) is still required before
> declaring the local environment fully validated.

## 3. Build the clean database

**Path A — fresh rebuild from scratch (clean DB, destroys local data):**

```bash
# Backs up to backups/ first, then replays all 120 migrations + seed.sql.
KOLEKTO_CONFIRM_RESET=yes npm run db:reset
```

**Path B — apply migrations, keep existing local data (usual choice):**

```bash
npm run db:migrate        # supabase migration up --local
```

Both replay the full migration history (120 files as of 2026-10-30).

## 4. Validate (Phase G)

Run from a clean rebuild. Report results honestly; never record an un-run step as passed.

| # | What | Command | Proves |
|---|---|---|---|
| 1 | Local stack up | `npm run db:start` | container reachable |
| 2 | Migrations replay from scratch | `KOLEKTO_CONFIRM_RESET=yes npm run db:reset` | all 120 apply in order |
| 3 | pgTAP suites (50 files) | `npm run db:test` (`supabase test db`) | schema, RLS, grants, notification claim/resolve, rate limits, backlog, retry-then-sent, quota controls, post-publish reminders |
| 4 | No schema drift | `npm run db:diff` on `public,app,private` (empty = pass) | files reproduce the schema |
| 5 | Typecheck + invariants + unit tests | `npm run verify` | TS build, 5 invariants, domain/unit tests |
| 6 | Reference concurrency | `npm run test:concurrency` | claim/lease & reservation concurrency |
| 7 | Browser E2E (optional, heavy) | `npm run test:e2e` | full-stack journeys (known to stall on constrained Windows box — QA-ENV-01) |

Integration/pgTAP DB URL: `postgresql://…@127.0.0.1:54322/postgres` (loopback, local). The
app's env guard (`packages/config/.../env.ts`) refuses anything non-loopback for
`KOLEKTO_ENV=local`.

### Targeted check — retry-then-sent regression only

```bash
supabase test db --help   # confirm single-file selection flags for the pinned CLI, then run test 39
```

Test 39 asserts: attempt 1 → `retry` sets `error_code`; attempt 2 → `sent` does **not**
violate `notification_deliveries_sent_has_no_error`; final state `sent`, `error_code` /
`error_message` NULL, `attempt_count = 2`.

## 5. Teardown / recovery

```bash
npm run db:restore        # restore local app data from a backups/ snapshot
npm run db:stop           # supabase stop
```

## 6. What NOT to do

- Do not `supabase db push`, `supabase link`, or pass `--linked` / remote `--db-url`.
- Do not delete or rewrite migration files to make the directory look clean.
- Do not disable RLS, constraints, triggers, or grants to make a test pass.
- Do not enable a real email provider or auto-release held notifications
  (`app.release_held_notifications` is operator-invoked, deliberately).
- Do not commit `.env*` (except `.env.example`) or `supabase/.temp/` — CI fails the build if
  you do.

## 7. Reproduce on a brand-new clone

```bash
git clone <repo> && cd kolekto
cp .env.example .env.local      # then fill local values; keep KOLEKTO_ENV=local, loopback URLs
npm ci
npm run db:start
KOLEKTO_CONFIRM_RESET=yes npm run db:reset   # fresh schema from the full history
npm run db:test && npm run verify
```

A fresh clone is **never** linked to any cloud project (ADR 0007): `supabase/.temp/` is
gitignored, so linkage is per-machine and must be created deliberately — which this runbook
never does.
