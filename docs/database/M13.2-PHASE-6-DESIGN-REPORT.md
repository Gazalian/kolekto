## 1. Executive summary

- **The pipeline is traceable end to end and every hop exists** (Verified, §2):
  domain RPC (`app.create_member`, …) → `app.write_audit_log` → `public.audit_logs` INSERT →
  trigger `audit_log_notification_enqueue` → `app.enqueue_notification_on_audit()` →
  `pgmq.send('notification_events', …)` → worker event stage (inline loop in `src/index.ts`) →
  `processNotificationMessage` → `notification_events` + `notification_deliveries` (email `pending`) →
  `sendOneClaimed` → `MailpitEmailProvider` → Mailpit.
- **Already proven today, in two separate halves** (Verified): the processor integration test drives the real
  RPCs, the real trigger and the real queue table and runs the real processor — inside one rolled-back
  transaction, stopping at delivery rows. The Mailpit tests (Phase 5) start from directly inserted rows.
  **Nothing joins them.** An E2E test has to *commit* (the sender's claim runs in its own transaction), so it
  is a new test class for this stack.
- **An E2E test is feasible without any source, migration or switch change** if it (a) commits the domain
  action, (b) processes only its own queue message, selected by its run-unique `community_id`, (c) sends with
  `sendOneClaimed` directly, and (d) matches Mailpit exactly (Inferred from §2–§6).
  It then proves every hop **except** the worker's inline event loop in `index.ts` and the
  `runSenderTick` gate in its ON state.
- **`runSenderTick` cannot send with the switch `false`, by design, and the switch may not be written**
  (Verified, §4). Proving "switch ON → tick drains" needs either an accepted gap (status quo, D-8) or a
  small, separately approved source refactor that extracts the drain loop and the event stage without adding
  any switch bypass (§4.4).
- **Safest first event: `member.create`** (one RPC, one queue message, one email row to a run-scoped supplied
  address). Next: `officer_term.end`, then `officer_invitation.accept`. `member.approve_join` last (§3).
- **Budget is the binding constraint right now** (Verified, §6): 131 of 180 transactional attempts in the
  last 24 h; the harness refuses a file above 140. A full `--with-smtp` lane costs 21 and would be refused
  until about **2026-11-05 15:53 UTC**, when 68 attempts leave the window.
- **New permanent residue:** `public.audit_logs` and `public.notification_events` are append-only (no-update /
  no-delete triggers), and the test stack holds **0** audit rows today. The first committed E2E run creates
  the first ones; only `itest:reset` removes them (§6.6).

## 4. Sender tick and pause-switch assessment

### 4.1 `sendOneClaimed` vs `runSenderTick` (Verified)

| | `sendOneClaimed` | `runSenderTick` |
|---|---|---|
| Reads pause switch | **No** | Yes, `app.email_sending_enabled()` every tick |
| Sends with switch `false` | Yes (test path used by Phase 5) | **Never** — returns `paused: true`, `steps: []` |
| Maintenance | No | Lease recovery, 72-h expiry, ledger purge (when `runMaintenance`) — all global |
| Writes `notification_sender_state` | No | Yes: `app.record_sender_heartbeat` on **every** tick |
| Batch | One row | Up to `maxBatch`, stops on `empty` / `halt` / `shouldContinue()` |

### 4.2 How the switch can be tested without enabling it

- **Paused half — already covered** (Verified): "paused: runSenderTick claims nothing and preserves the queued
  row" runs in `inRollback` (its heartbeat write rolls back).
- **Enabled half — cannot be done with the current code.** The only input to the gate is the database
  function; there is no injection point, and R11′ forbids writing the switch even in a rolled-back
  transaction. A rolled-back transaction would not work anyway: an enabled tick calls `sendOneClaimed`, which
  needs `sql.begin` on a base connection (Verified).
- **A committed tick in an E2E file would break the next file** (Inferred from code): the tick commits a
  heartbeat, and `runPreflight` refuses with `PREFLIGHT_LIVE_WORKER` while the heartbeat is < 60 s old.
  So E2E tests must not call `runSenderTick` committed.

### 4.3 What an E2E test can honestly claim with the current code

Trigger → queue → processor → email row → `sendOneClaimed` → Mailpit, with the switch `false`. It does **not**
prove the inline event loop in `index.ts`, the dead-letter archive in that loop, or the tick's gate in the ON
state.

### 4.4 Smallest safe design change (future phase, separate approval — `src/**`, Q5 rule 9)

1. **Extract the event stage** from `index.ts` into an exported
   `runEventStage(sql, { batchSize, visibilityTimeoutS })` with identical behaviour (read → dead-letter
   check → process → delete). `index.ts` calls it. A characterization unit test with fake SQL pins the current
   order and the `::bigint` casts first.
2. **Extract the drain loop** from `runSenderTick` into an exported `drainSendBatch(sql, opts)` (the existing
   `for` loop over `sendOneClaimed`). `runSenderTick` keeps the gate and calls it.
3. **Do not add any injectable switch, override GUC or "test mode".** The gate stays a single database read.
   `drainSendBatch` bypasses the switch no more than `sendOneClaimed` already does.

Result: the E2E test exercises the production event-stage and drain code; the gate itself stays covered by the
paused rollback test, the fake-SQL unit test and pgTAP 40. "Switch ON → drains" against a real database stays
an **accepted gap** (D-8) unless Q-B is reversed.

## 5. Retry / failure coverage matrix

Policy (Verified, `notification-backoff.ts`, `notification-send-claim.ts`, limits row): max 3 attempts; backoff
after attempt 1 = 5 min, after attempt 2 = 30 min, ±20 % jitter; 3rd failure → `dead/retries_exhausted`;
`permanent` → `dead/<code>` after one call; ambiguous + `idempotency: "none"` → `dead/outcome_unknown`, never
retried; ambiguous + `"provider"` → retry; `adapter_misconfigured` → halt. Mailpit adapter: refused connection →
transient `provider_unreachable`, unambiguous; 4xx → `provider_rejected_transient`; 5xx (any stage) →
`provider_rejected_permanent`; drop/timeout after DATA → transient, **ambiguous**.

### 6.3 Advisory lock and claim isolation (Verified, Phase 4 harness)

Session lock `(918273, 1)` per file on a reserved connection; `checkpoint()` before every test refuses unless
the whole database has 0 open email rows; `--test-concurrency=1`. Because the claim is unscoped, a test may only
ever claim its own row, and every test asserts the claimed `deliveryId`.

### 6.4 Queue isolation (the new problem)

- `pgmq.read` is as global as the claim. Today the queue is empty and nothing but harness tests writes audit
  rows to this stack (Verified: 0 audit rows, 0 messages).
- **Design:** extend the preflight/checkpoint with "queue length 0 and no read messages" (today it checks read
  messages only — Verified, `QUEUE_READ_SQL`). Then either (a) select the test's own message by
  `message->>'community_id' = <scope community>` (the processor test's method, no `src` change), or (b) after
  §4.4, call the real `runEventStage`, which can then only see the test's own message.
- **Acknowledgement:** the worker deletes a processed message (`pgmq.delete`). For a test, archiving its own
  `msg_id` (`pgmq.archive`) leaves evidence and is not a row deletion. Either is a new write the acceptance
  guard does not yet classify (Inferred: it has no `pgmq` rule) → needs a decision and a guard rule limited to
  the test's own `msg_id`.
- **Leftovers:** if a test fails between the domain commit and the acknowledgement, its message stays queued.
  `afterEach` must archive any queued message whose `community_id` is one of the file's tracked communities
  (quarantine equivalent), and `finish()` must assert the queue is empty.

### 6.5 Tagging and quarantine

- Ids created by RPCs (`uuid_generate_v7`, `next_member_code`) are not scope-issued. Ownership is therefore
  anchored on the scope-issued **community id** (Inferred: `buildQuarantineStatement` already quarantines by
  `community_id`, so it covers E2E rows unchanged).
- Every recipient is `scope.address()` (`itest+<runTag>-<n>@<file>.example.test`), which
  `app.email_address_usable` accepts (Verified, read-only call). Officer recipients are the fixture users'
  auth emails, also scope addresses.
- Mailpit: existing exact matcher — recipient + rendered subject + `expectedMessageId(deliveryId)`, where
  `deliveryId` is read from the processor-created row (by `notification_event_id` of the event whose
  `object_id`/`community_id` is the test's own).
- No broad cleanup or global deletion is needed (Inferred): everything committed is run-tagged; open rows are
  quarantined; the queue is acknowledged per message.

### 6.6 Residue (new class)

`audit_logs` (no update/delete/truncate), `notification_events` (no update/delete), `notification_send_attempts`
(no update/delete/truncate) are append-only (Verified, triggers). The first E2E run writes the first committed
audit rows on the stack; they are inert but permanent until `itest:reset`. This needs explicit acceptance.

## 7. Proposed E2E test architecture

New file `test/integration/notification-e2e-mailpit.integration.test.ts` (not the retired
`notification-pipeline` name), added to `INTEGRATION_MANIFEST` **and** `SMTP_INTEGRATION_FILES`; runs only with
`--with-smtp`. Gate, harness and `connectVerified` exactly as the Phase 4 contract.

Per test (example `member.create`):

1. `harness.checkpoint()` — 0 open email rows **and** (new) queue empty.
2. Committed fixture: `createCommunityFixture` (scope ids, run-scoped emails, owner term).
3. Committed domain action in one `sql.begin`: `set_config('request.jwt.claims', {sub: owner}, true)`,
   `set local role authenticated`, `app.create_member(..., p_email => to)`; commit.
4. Queue: wait (bounded poll, no fixed sleep) for exactly one message with this community id; assert its
   `action`, `object_id` (= returned member id), `actor_type`; no other message exists.
5. Event stage: `processNotificationMessage(sql, message)` (or `runEventStage` after §4.4) → `processed`,
   email `pending`. Acknowledge (archive or delete) this `msg_id` only.
6. Assert rows: one `notification_events` row (`event_key`), one email delivery `pending`, address `to`,
   assurance `unverified_supplied`, `send_class transactional`; payload carries no `@`.
7. `waitForL5Headroom(sql)`; `sendOneClaimed(sql, mailpitProvider)` (or `drainSendBatch` after §4.4) → `sent`
   for **that** delivery id; `providerMessageId === expectedMessageId(deliveryId)`.
8. Mailpit: `waitForExactlyOne({to, subject: buildEmailMessage(...).subject, messageId, runTag})`; content check.
9. Idempotency: replay the same queue message through the processor → no new event / delivery; a second
   `sendOneClaimed` → `empty`; still exactly one Mailpit message.
10. Switch read `false` before and after (gate already does it per file).
11. `afterEach`: quarantine open rows + archive leftover own-community messages; `finish()`: queue empty,
    0 open rows, mutex released.

Then `officer_term.end` (adds a second confirmed officer; asserts `verified_account` and the in-app row) and
`officer_invitation.accept` (token never logged). Optionally a negative E2E with no SMTP grant: member created
without an email → `skipped/no_recipient`, nothing sent (costs 0 grants).
