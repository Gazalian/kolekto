update public.notification_deliveries

## 6. Mailpit exact-match helper (`itest-mailpit.ts`)

**Matching contract.** An entry of `GET /api/v1/messages|search` (`{ messages: [...] }`) is ours only if
`To` has exactly one recipient equal to the expected address, `Subject` equals the expected subject,
and `MessageID` equals the expected Message-ID (`sha256(deliveryId)[0..32]@kolekto.invalid`, brackets
optional). The expected address must be a run-scoped `itest+<runTag>-…` address of this run; shared
addresses are refused. Content is checked afterwards on the full message (`checkMessageContent`). Field
names are those the existing file reads, plus `MessageID` [U: confirm on Mailpit v1.30.2, checklist D-5;
a different name fails closed].

**Ambiguity handling.** 0 matches → `MAILPIT_NO_MATCH` (counts only, no values); > 1 →
`MAILPIT_AMBIGUOUS` (duplicate send); expected Message-ID with another recipient/subject or on a
multi-recipient message → `MAILPIT_AMBIGUOUS`; any malformed list or entry → `MAILPIT_RESPONSE_INVALID`.
`total`/`messages_count` are never read; order is irrelevant; nothing clears the inbox.
`assertNoMessageTo()` gives the absence check by run-scoped recipient.

**Tests (10) [M].** Adapter derivation (known SHA-256 vector + the adapter and sender source pinned);
selection among other runs' and developer messages in any order with misleading totals; wrong
recipient (incl. a longer counter), wrong run, wrong subject (suffix, prefix), wrong Message-ID;
conflicting Message-ID (other recipient, other subject, subject containing the expected one, truncated
subject, recipient prefix, extra recipient); duplicates; secret-free no-match message; nine malformed
responses; seven invalid expectations; absence; content. Mutations "subject `includes`" and "recipient
substring" are each caught (1 fail each) [V].

## 7. Mutex helper (`itest-mutex.ts`)

**Behaviour.** `pollBounded(options, attempt)`: timeout 1 ms–120 s, interval 10 ms–10 s and ≤ timeout,
plain label, injected clock (`now`, `sleep`) — otherwise `POLL_OPTIONS_INVALID` before any attempt. At
most `floor(timeout/interval) + 2` attempts even with a frozen clock; a non-finite or decreasing clock is
`POLL_INCONCLUSIVE`; never sleeps longer than the interval or the time remaining; an attempt that throws
stops at once (`POLL_FAILED`/`MUTEX_FAILED`, SQLSTATE/errno only, no `cause`); timeout →
`PollTimeout`. `acquireSuiteMutex()` runs `select pg_try_advisory_lock(918273, 1) as locked` (non-blocking)
through it; only exactly `true`/`false` is accepted (`MUTEX_INCONCLUSIVE` otherwise); timeout →
`MUTEX_TIMEOUT` naming the holder's `application_name` when it is a safe token, else `unknown`.
`checkMutexHeld()` implements loss detection (`MUTEX_LOST` on 0). SQL constants for unlock, holder
(`pg_locks` `classid/objid/objsubid = 918273/1/2`) and own-session check. The dedicated long-lived lock
connection itself is Phase 4–5 work (it needs `itest-db.ts` and a live database).

**Tests (12) [M].** First-try success; success after releases with exact sleeps; timeout with exact

## 9. `.env.itest` loading (`itest-env-file.ts`, `runIntegrationEntry`)

### 9.1 How it works

`npm run test:integration` → `run-integration.ts` → `runIntegrationEntry(defaultEntryDeps())`:
(1) refuse if any `KOLEKTO_ITEST_*` variable is set in the shell (`ITEST_ENV_AMBIENT`, names only) —
before reading anything; (2) read exactly `<repository root>/.env.itest`; (3) strict parse: ≤ 4 KiB,
`KEY=value`/blank/`#` lines (CRLF and one BOM tolerated), only the four `KOLEKTO_ITEST_*` keys, no
duplicates, no quotes, no `export`; (4) merge the four values over the runner's environment and hand that
to the **unchanged** Phase 1b lane (static gate → manifest → allow-listed child → canary). `node
--env-file` was rejected: an already-exported variable silently wins over the file.

### 9.2 How fallback is prevented

Only one path is ever read (unit-tested with a read spy; `.env.local`/`.env` placed in the fake file
system are never opened). No developer variable is a source: a missing file is a refusal, an incomplete
file is refused by `parseIntegrationEnvironment` (`ENV_MISSING`), developer values present in the shell are
used only for the existing "must differ" comparison and are dropped from the child environment.
`.gitignore`'s `.env.*` covers the file (asserted).

### 9.3 Failure behaviour

Missing → `ENV_FILE_MISSING`; unreadable → `ENV_FILE_UNREADABLE` (errno only); malformed →
`ENV_FILE_INVALID` (line number/key, never a value); ambient → `ITEST_ENV_AMBIENT`. Each exits 1 before
any file is listed or any process spawned (unit-tested). Refusals never contain the password or stack ID
(message, `String`, `inspect`, JSON, stack checked).

### 9.4 Change to a Phase 1b test

The spawned entry-point test in `itest-gate.test.ts` previously ran `run-integration.ts` in a scrubbed
environment and expected `ENV_MISSING`. With file loading, that run would read the real `.env.itest` —
once Phase 3 creates it, `npm test` could have started a real integration run. It now spawns with an
ambient `KOLEKTO_ITEST_STACK_ID`, which is refused before the file is read, so the outcome is
independent of the file (expects `ITEST_ENV_AMBIENT`, exit 1, no TAP, value not echoed). The
missing-file path is covered in-process with an injected file system.
