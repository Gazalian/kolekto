## 1. Executive assessment

The plan's diagnosis is sound and well evidenced. Its core direction is right: stop deleting behind
disabled triggers, give every test run-unique identities, keep anything that does not need a commit inside
a rolled-back transaction, serialise the genuinely global resources, and move commit-requiring tests to a
disposable database that holds nothing else.

It is **not safe to implement as written**. Seven defects would each let a "protected" run still touch the
developer's stack, pass without running, or fail unpredictably:

1. **A skipped gate is a green run.** Every integration file uses `describe(..., { skip })`. An unmet
   precondition produces exit code 0. The plan's `integrationGate` keeps that behaviour.
2. **The Mailpit/SMTP endpoint defaults to the developer's ports.** A test database on the test stack with a
   forgotten `EMAIL_SMTP_PORT` sends real SMTP to the developer's inbox.
3. **The `kolekto.itest = 'on'` marker is a boolean that is trivially spoofed or mis-applied**, and it is
   lost by `db reset`. It does not identify *which* test stack is on the other end.
4. **Rollback-class tests are allowed to run on the developer database**, but the ones that expect a
   `granted` reservation read global, committed L3/L4/L5 state and take global advisory locks.
5. **Leftover rows stay claimable.** With "tests never delete", pending rows left by one test (an L5
   deferral is due again about one second later) are picked up by the next unscoped claim, by maintenance, or
   by pgTAP 37. The plan has no step that makes leftovers inert.
6. **The `SenderOptions.claim` production change is not needed** once leftovers are made inert and
   integration tests run only on the disposable stack. It widens a production type for test convenience.
7. **Committed filler rows poison the daily quota.** Ledger rows inserted without `send_class` default to
   `transactional` and count toward the global L3/L4/L5 limits. The plan correctly moves fillers into
   rollback; it must make that a rule, not a preference.

## 4. Answers to Q1–Q5

### 4.1 Q1 — Separate testing environment

**Recommendation: adopt DB-2 (a second local Supabase stack with its own Mailpit), with the hardening
below. Reject DB-1.**

**Why not DB-1.** A second database in the same cluster shares the container, the port 54322, the
credentials, the Mailpit and cluster-wide objects. The only difference between a safe and an unsafe URL is
one path segment. `create database … template` from the developer database would also copy developer data.
It cannot give the separate inbox the tests need.

**Can separate ports and Docker volumes be configured safely? Yes [V F17–F19, F21].**
The CLI scopes everything it creates by `project_id`. A test stack needs:

| Setting | Dev (verified) | Test (proposed) |
|---|---|---|
| `project_id` | `kolekto` | `kolekto-itest` |
| `[api] port` | 54321 | 55421 |
| `[db] port` / `shadow_port` | 54322 / 54320 | 55422 / 55420 |
| `[studio]` | 54323 | disabled (or 55423) |
| `[local_smtp] port` / `smtp_port` | 54324 / 54325 | 55424 / 55425 |
| `[db.pooler]` | disabled | disabled (session advisory locks are unsafe behind a transaction pooler) |
| Postgres major | 17 | 17 (same CLI → same image `17.6.1.166`) |

Avoid 54320–54329 (dev) and the Windows-excluded ranges (F21). Containers become
`supabase_<svc>_kolekto-itest`, the network `supabase_network_kolekto-itest`, volumes
`supabase_db_kolekto-itest` and so on.

**Can it start and stop independently? Yes**, through `--workdir <itest-dir>`. Start-up, stop and
`db reset` must always go through a wrapper that:

- passes `--workdir` explicitly and asserts the resulting container prefix is `supabase_db_kolekto-itest`;
- **never passes `--linked`, `--db-url` or `--all`**, and never calls `supabase stop --all`;
- refuses to run if `<itest-dir>/supabase/.temp` exists. The developer work directory is **linked to a remote
  project (F20)**. A test directory copied wholesale from it would inherit that link. It must be created
  from a clean template, not by copying the repo's `supabase/` folder;
- is separate from `npm run db:reset` / `db:stop`, which target the developer stack by default (F22).

**Sharing migrations [U].** The CLI expects `<workdir>/supabase/migrations`. Two options for the spike:
a Windows directory junction (`mklink /J`, no administrator rights) so there is one source of truth, or a
copy made at bootstrap and verified by directory hash against `supabase/migrations`. The junction avoids
drift; the copy avoids anyone running `supabase migration new` in the wrong tree. The spike decides.

**Services [U].** The test stack needs Postgres and the auth service (migrations insert into `auth.users`,
and the auth tables are created by GoTrue). Storage is probably needed. Studio, analytics, edge runtime,
vector and imgproxy are not. Start with `--exclude` for those and confirm all 120 migrations apply.

**Can the runner be guaranteed not to reach the developer database? Not by a flag.** A negative can only
be enforced in depth. Required layers, in order of strength:

1. **Credentials that do not exist on the dev stack.** Bootstrap creates a login role (for example
   `kolekto_itest`, superuser inside the disposable database only) with a random password written to a
   git-ignored `.env.itest` (`.env.*` is already ignored, `.gitignore:23`). The dev server has no such
   role, so a mis-pointed URL fails authentication instead of connecting. This is the only layer that works
   even if every other check has a bug.
2. **Distinct variable names with no fallback.** The integration harness reads only `KOLEKTO_ITEST_DB_URL`,
   `KOLEKTO_ITEST_SMTP_PORT`, `KOLEKTO_ITEST_MAILPIT_API`, `KOLEKTO_ITEST_STACK_ID`. It never reads
   `SUPABASE_DB_URL`, never loads `.env.local`, and refuses to start if any value equals its dev
   counterpart. The pipeline test's current defaults (`EMAIL_SMTP_PORT ?? 54325`, `MAILPIT_API ?? 54324`)
   must be removed (F17, defect 2).
3. **Port allow-list and deny-list.** Every endpoint (DB, SMTP, Mailpit API) must be on loopback, inside the
   configured test range, and outside 54320–54329. All four values come from one generated file so they
   cannot disagree (a test DB with a dev Mailpit is a split-brain configuration).
4. **Identity check on the live connection** (see the marker below), made on the connection the tests use.

**Is a `kolekto.itest` marker sufficient? No — not as `'on'`.**

- `current_setting('kolekto.itest', true) = 'on'` is a boolean. One mistaken
  `alter database postgres set kolekto.itest = 'on'` on the developer database turns every guard green.
  Any session can also `SET` the same name for itself.
- `supabase db reset` recreates the database, which discards a database-level setting. A reset without a
  re-apply silently removes the marker (the safe direction, but it makes the failure confusing).
- It cannot tell one test stack from another, or from a stale one.

**Recommended marker [P].** Bootstrap generates a random UUID, writes it to the database
(`alter database postgres set kolekto.itest_stack = '<uuid>'`) and to `.env.itest`
(`KOLEKTO_ITEST_STACK_ID`). The harness requires:
`current_setting('kolekto.itest_stack', true) = $KOLEKTO_ITEST_STACK_ID`, `current_user = 'kolekto_itest'`,
`inet_server_port()` equal to the configured port, and `current_database()` equal to the configured name.
Marker, credentials and ports then have to be wrong in the same direction at once. Bootstrap, reset and
marker-application are one script; there is no supported way to reset without re-marking.

**Should the runner refuse to start when any check is inconclusive? Yes, and it must fail, not skip.**
Inconclusive includes: variable missing, duplicated or malformed; connection refused or timed out;
`current_setting` NULL or mismatched; more than one row; role, port or database mismatch; the server not in
the expected state; Mailpit API unreachable or on a dev port; the pause switch row missing or `true`; any
claimable or unexpired-`sending` email row not owned by the harness; a sender heartbeat younger than 60 s.
All checks are read-only and run before the first write. A refusal exits non-zero with the reason. This
requires a mode in which an unmet precondition is an error: `npm run test:integration` sets
`KOLEKTO_ITEST_REQUIRED=1`; plain `npm test` never touches a database at all (§6, R2).

**Safest setup, in one paragraph.** A separate `kolekto-itest` Supabase stack in its own work directory
(clean of `.temp`), ports in 55420–55429, its own Mailpit, a generated `.env.itest` holding a role
password, a stack-identity token and all endpoints, scripts `itest:up | down | reset | status` that wrap the
CLI with the guards above, and an integration harness that reads only those variables, fails closed, and
holds a database-level mutex. Integration tests never run against the developer stack.

### 4.2 Q2 — Tests that commit

**Legend.** *Why commit*: **K1** two independent sessions must see the same committed state;
**K2** production code commits by design before an external call (F1);
**K3** a non-transactional external side effect (SMTP, TCP);
**K4** needs real wall-clock progress, which `now()` frozen at transaction start cannot give (L5's 1 s
window, retry delays).

**Limitations of rollback that apply to every "R" below [V/I].**

- `now()` is the transaction start time. Timestamps manipulated relative to `now()` still work (a lease set
  to `now() - 1 second` is expired, a row aged `now() - 73 hours` is stale). Two *granted* reservations in
  one transaction cannot both succeed under L5, and nothing "waits for the next second".
- The transaction sees committed foreign state (global counters, `claim_next`) but nothing foreign sees it.
  R tests are therefore insensitive to their own side effects and **sensitive to everyone else's committed
  rows**.
- Global advisory locks `(3,0)`, `(4,class)`, `(5,class‖daily)` (F4) are held until rollback. A hung R test
  blocks every other reservation in the database.
- An error aborts the transaction. An expected error (the 42501 tests) needs a savepoint.
- No external side effect may happen inside an R test. A real SMTP send inside a transaction that is rolled
  back yields a delivered email with no database record — the ambiguous state the design works to avoid.
- `sendOneClaimed` and a sending `runSenderTick` cannot run inside a transaction (F1). A paused tick,
  `recoverExpiredLeases`, `expireStaleDeliveries` and `readSendHealth` only use tagged templates and *can*
  run on a transaction handle (cast required by their `BaseSql` type; test-side only). [V by reading; U by
  running]
- The pool must not be used from inside `begin(...)` with `max: 1`; use `tx` only, or the test hangs.

**Guarded enable (revision to the plan).** The plan bans every committed switch change. That leaves the
operator-critical path "switch on → `runSenderTick` → drains" unproven against a real database: F1 makes it
impossible inside a transaction, and a fake-SQL unit test proves only that a claim is *attempted*. On the
disposable stack, with the mutex held and no live worker, one test may enable the switch inside a harness
helper `withSwitchEnabled()` that restores `false` in `finally`. A crash between enable and restore leaves
the switch `true`; the next run's preflight refuses to start (it requires `false`), and recreating the
disposable stack clears it. On the developer database this is physically excluded because integration
tests cannot target it. **[Q-B]** — recommended yes; if declined, record that this path has no integration
coverage.

### 4.5 Q5 — `SenderOptions` change

**Does it change production behaviour?** When omitted, no: `opts.claim ?? claimNextDelivery` evaluates to
the same function with the same arguments `(tx, SEND_LEASE_SECONDS)` [V]. It changes the **type surface**
of `SenderOptions` and, through `TickOptions extends SenderOptions` (F2), of `runSenderTick`.

**Does the production sender keep its default claim path?** Yes. `index.ts` passes a literal with no
`claim` (F2).

**Can runtime configuration enable it?** No. The field is a function value; nothing in `loadConfig`,
`loadEmailConfig` or `index.ts` can construct one. It can only be enabled by a code edit. The residual risk
is a future caller passing a strategy that claims a row the caller chose. The database limits the damage
(`reserve_email_attempt` raises `RESERVE_PRECONDITION` unless the row is `sending`; settling is
lease-token-gated), but a strategy that claims an arbitrary production row and then reaches a **real
provider** is precisely the capability the seam adds to the send path.

**Is it needed?** No. Its only job is to stop a test claiming another test's row. That is already solved by
(a) serialising every integration file, (b) running only on a disposable database, and (c) making each
test's leftover rows inert. With those in place the default claim path is correct, and it is the more
faithful test (it exercises the production claim function rather than a replacement).

**Is a better seam available?**

| Option | Production change | Verdict |
|---|---|---|
| S1 Environment isolation + preflight "no foreign claimable rows" + per-test quarantine (UPDATE own non-terminal rows to `dead/itest_quarantined`, F9) | **None** | **Recommended.** |
| S2 Export a lower-level `sendClaimed(sql, opts, claim)`; `sendOneClaimed` calls it with `claimNextDelivery` | One new export; `SenderOptions` untouched | Acceptable fallback if a measured need appears. Cannot scope `runSenderTick`. |
| S3 `SenderOptions.claim` (plan B-1) | Widens an exported type reachable from the production loop | **Rejected for now.** |
| S4 Tests wrap `sql` in a Proxy that rewrites the claim SQL | None | Rejected: replicates SQL text; the same replica defect as P6's `simulateEventLoop`. |
| S5/S6 New RPC parameter or scoped RPC (plan B-2, B-3) | Migration to a security-definer function | Rejected (agree with the plan). |

**Can it be tested without changing the production API?** Yes. The default path is covered by the existing
public API on the disposable stack, and a unit test using a fake `sql` with a `begin` that answers only the
claim and reserve queries proves the outcome mapping. The plan's proposed unit test ("injected claim is
used; default is `claimNextDelivery`") would not be needed.

**Decision: do not approve B-1.** Revisit only if, after S1 is in place, a concrete requirement remains
(for example running integration files in parallel). Even then prefer S2.

## 5. Additional technical checks

**5.1 Advisory-lock lifetime and release on failure.**
A session-level `pg_advisory_lock` is released when its session ends. A test failure alone does not end the
session, so the release must be explicit, and the process exit closes the socket as a backstop [I]. The
plan's sketch (`pg_advisory_lock`, blocking) has these gaps:

- Blocking acquisition can wait forever behind a stuck run. Use `pg_try_advisory_lock` in a bounded poll
  (for example 60 s) and fail with the holder's `application_name` from `pg_stat_activity`.
- The lock must live on a **dedicated** connection (`postgres(url, { max: 1, idle_timeout: 0,
  max_lifetime: <large>, connection: { application_name: 'kolekto-itest-lock' } })`). With defaults,
  postgres.js recycles connections after 30–60 minutes (F24) and a recycled connection silently drops the
  lock.
- Detect loss: at each test boundary confirm the lock is still held (`pg_locks` for the lock connection's
  pid); abort the file if not.
- Release in `after` and also on `process.on('exit')` where possible. A hard kill is covered by connection
  close. Advisory locks are per database, which is the right scope on the test stack.
- Never run it through a transaction pooler (`[db.pooler]` is disabled, `config.toml`) — gate on that.
- Key `(918273, 1)` does not collide with `(1..5, …)` (F4). Document it next to the migrations' lock order.

**5.2 Connection pooling and transaction/session lock behaviour.**
`reserve_email_attempt` takes transaction-level locks that are released when Phase 1 commits, before the
provider call (F1, F4); the L5 window therefore measures reservation time, not send time. Rules:

- Inside `sql.begin`, use only `tx`. With `max: 1`, a stray `sql\`…\`` inside the callback deadlocks.
- Give every test connection `connection: { application_name, lock_timeout, idle_in_transaction_session_timeout }`
  and every test a node `timeout`. A hung R test otherwise holds global advisory locks (F4) and blocks
  every other reservation until the client dies.
- Mix of pooled and session state: the mutex connection is never used for test queries.

**5.3 Test-run identifiers and uniqueness.**
Use `crypto.randomUUID()` for every entity id (community, user, event, delivery, audit id) — never a fixed
prefix plus a counter (F16). Keep a short run tag (8 hex) only in human-visible strings: slug
`itest-<tag>-<n>`, `event_key`, address `itest+<tag>-<n>@<file>.example.test` (plus-addressing already
passes `assertValidEmailRequest`; sender test uses it). Check the slug against `reserved_community_slugs`
and the address-length limits [U]. Log the run tag at start and set it as `application_name` so residue and
connections are attributable. Because Message-ID derives only from the delivery id (F15), random delivery
ids make Message-IDs unique across runs.

**5.4 Mailpit search and Message-ID matching.**
- Expected Message-ID for a delivery is `sha256(deliveryId).hex[0..32] + "@kolekto.invalid"`; it equals the
  stored `provider_message_id` (F15). The plan's formula must include the domain.
- Mailpit is `v1.30.2` (F17). Search operators (`to:`, `message-id:`) and the JSON field names for the
  Message-ID are **[U]** — confirm against the running version. **Do not rely on search semantics for
  correctness.** Use search to narrow, then filter client-side for an exact `To` address and exact
  Message-ID, and assert an exact count.
- Delete-all and `inbox.total` assertions must go (the plan agrees). Absence assertions ("skipped row sends
  nothing") are best made with `FakeEmailProvider.attempts === 0`; if Mailpit is used, filter by the run's
  unique recipient.
- Mailpit may cap stored messages [U]; correlation by unique id makes pruning harmless.
- Replace fixed `sleep(500)` with a bounded poll on the unique key.

**5.5 Rate-limit isolation without deleting ledger records.**
- Unique address and community per test make L1 and L2 independent across tests and runs.
- L3, L4 and L5 are global by design. The mutex serialises them; real pacing replaces ledger deletes:
  `waitForL5Headroom` polling the **server** clock (the existing code notes JS/DB clock skew of hundreds
  of ms).
- Filler rows never commit (F6). Make it a checked rule: a unit test greps for `insert into
  public.notification_send_attempts` outside an R helper.
- **Budget.** A full committed run grants roughly 20–30 transactional reservations by my count of the
  current tests (the plan says ≈19; [I] either way). At 180 per 24 h that is about six runs a day before
  `provider_daily_limited`. A preflight headroom check is right; the operator remedy is `itest:reset`, not
  a limit change (limits change only by reviewed migration, F5).
- Rate-limit test 2 (two concurrent workers) needs L5 headroom before it starts, otherwise its "granted"
  worker may be deferred.

**5.6 Queue isolation and real worker behaviour.**
- Only the processor integration tests touch pgmq today, and only inside rolled-back transactions.
- Any committed code path that inserts into `audit_logs` fires `enqueue_notification_on_audit` into the
  shared `notification_events` queue (`20261007100000…sql:378`). On the disposable stack nothing consumes
  it. A real worker pointed at the test stack would.
- The plan's R-4 mitigation (refuse if a sender heartbeat is younger than 60 s) misses a worker that has no
  email provider: it consumes the queue and writes **no heartbeat** (F27). Add a queue check: refuse when
  `pgmq.metrics('notification_events')` shows messages being read (`queue_visible_length` changing, or any
  message with `read_ct > 0` that the harness did not create) [U on metric names], and document that no
  worker may run against the test stack.
- Future queue tests use a per-run queue (plan §H) because `index.ts` reads the literal queue name
  (`index.ts:112`). Importing `index.ts` runs the loop (F25); the extraction in Phase 5 is required, and a
  spawned worker must receive an explicit environment — never `--env-file=.env.local` (the `start` script
  does exactly that).

**5.7 Expiry, lease recovery and heartbeat (global operations).**
`recoverExpiredLeases`, `expireStaleDeliveries`, `purgeStaleSendAttempts` and `recordSenderHeartbeat` act on
all rows. On a shared database they would expire a developer's old pending rows, reclaim a live worker's
lapsed lease and overwrite the real heartbeat. Handling:

- Prefer running them in R (their effects roll back, and the heartbeat write never lands).
- Where they must commit, run only on the test stack, under the mutex, asserting on own ids (the current
  `>= 1` assertions are fine).
- Rows left `pending` by an earlier failed test would be expired or recovered by a later one. Quarantine
  makes them terminal first (§4.5 S1).

**5.8 Safe cleanup with existing foreign keys and triggers.**
- No test deletes from ledger, events, deliveries, communities, users, officer terms or `auth.users`. The
  FKs (F8, F10) and triggers (F7, F8, `officer_terms_assert_owner`) make that impossible without a bypass,
  and the plan is right that recreating a disposable database is a lifecycle operation, not a bypass.
- Per-test `finally`: **quarantine**, not delete — `update notification_deliveries set status='dead',
  error_code='itest_quarantined', send_lease_token=null, send_lease_expires_at=null where community_id =
  $scope and status in ('pending','sending')`. Allowed by F9. It must not fail the test or mask the test's
  own failure; log errors, and have `after` assert the scope has no `pending`/`sending` rows.
- Preflight on each file: zero email rows that are claimable or `sending` outside the harness. Fail closed.
- R tests leave nothing and need no cleanup.

**5.9 Parallel execution.**
Do not parallelise the integration lane. C tests contend for global counters and the global claim. R tests
that expect `granted` or `empty` read global state and take global advisory locks, so they are not safely
parallel with C tests either, and a mix gives flaky L5 outcomes. Run the whole integration lane with
`--test-concurrency=1` **and** the database mutex (the mutex also covers two shells). Unit tests stay
parallel. Estimated cost: tens of seconds of L5 pacing plus normal runtime — acceptable [I].
