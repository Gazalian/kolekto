## 0. Summary

The worker integration tests share one database, one Mailpit inbox and one sender-state row with
each other **and with the developer's local application data**, and they repair the damage by
deleting rows behind disabled append-only triggers. Serialising them would hide some symptoms but
would not stop them from stealing local dev deliveries, burning the global daily send quota,
wiping the inbox or committing the pause switch ON.

The recommended architecture has six layers, each addressing a distinct cause:

| Layer | What | Fixes |
|---|---|---|
| L-A Ownership | Every test owns a run-unique community, delivery/event ids and recipient addresses (`TestScope`) | ISO-1, ISO-3, ISO-5, residue collisions |
| L-B Scoped claim | Tests drive the **real** `sendOneClaimed` / `runSenderTick` with an injected claim strategy restricted to the test's community; production default unchanged | ISO-1 |
| L-C Rollback-first | Anything that does not need a commit (reservations, deferrals, processor, context load) runs inside a rolled-back transaction, as `notification-processor.integration.test.ts` already does | ISO-2, ISO-3 (fillers never commit) |
| L-D Global-state mutex + realistic L5 pacing | One session-level advisory lock serialises DB-backed integration files; sends wait for the real 1 s L5 window instead of deleting the ledger | ISO-2, ISO-6 |
| L-E No protection bypass | Tests never disable triggers, never delete ledger/event rows, never commit a pause-switch change, never delete-all Mailpit | ISO-3, ISO-4, ISO-5 |
| L-F Disposable test database | Commit-requiring tests run only against a dedicated, marker-guarded local test database that is recreated wholesale, never against the dev database | Residue, global quota exhaustion, dev-data interference |

No database migration is required by the recommended path. One small, default-preserving
production-code change is proposed (an optional claim strategy on `SenderOptions`, §5.2).

### 1.3 Additional global-state findings not in the diagnostic [V]

- **ISO-7 — global maintenance calls.** `expireStaleDeliveries(sql, 72)` (sender test "72-hour expiry…") marks *every* pending email row older than 72 h dead — including other tests' rows (the sender file's own 73 h/80 h rows across parallel runs) and any dev row. `recoverExpiredLeases` returns *any* expired lease to pending or dead — including a lease another test expired on purpose. Both are global by design.
- **ISO-8 — heartbeat writes.** `runSenderTick` always calls `app.record_sender_heartbeat`, so tests overwrite the operational heartbeat the health snapshot reports (diagnostic §2.4 shows a heartbeat from test runs).
- **ISO-9 — cross-run address reuse.** Sender and pipeline files derive addresses from a per-process counter or a constant (`synthetic-recipient@kolekto.test`), so once ledger rows stop being deleted, L1 (3/address/24 h) would trip on the fourth run of the day.
- **ISO-10 — full cleanup is structurally impossible without a bypass.** Because events are append-only with no sanctioned delete and FKs are `restrict`, no test can remove a committed community, its events, its deliveries that have ledger rows, or its owner user without disabling a trigger. *Any* plan that keeps committing to the dev database must either keep the bypass or accept permanent residue.
- **ISO-11 — `now()` is frozen inside a transaction.** Postgres `now()` returns the transaction start time [V: Postgres semantics]. All L-window counts, lease expiry and the 72 h rule use `now()`. A sender test wrapped in one outer transaction would see a frozen clock: L5 would defer every second send forever and leases could never expire. This rules out "wrap the whole sender runtime in a rollback transaction" (§3.3).

## 2. Root cause of each defect

| # | Defect | Root cause [V] | Why it bites [I] |
|---|---|---|---|
| ISO-1 | Tests claim another test's delivery | `claim_next_notification_delivery` has no scope parameter and is correct for production (fairness across communities). The test harness uses the production entry point with no way to restrict it, and every file seeds claimable rows in the same table. | Parallel files, leftovers from crashed runs, and dev rows are all candidates; `step.deliveryId` mismatch or unexpected `empty`. |
| ISO-2 | Per-second / daily limits are global | L3/L4/L5 counts filter only by time (and class), by design — they model provider quotas. Tests assume their reservation is the only one in the window. | A send in another file within 1 s → `provider_rate_limited`; the L4 test's 180 committed fillers → `provider_daily_limited` for every concurrent transactional reservation until cleanup. |
| ISO-3 | `clearSendLedger()` deletes the whole ledger | Written to defeat ISO-2 between two sends in one test (comment at sender:161–167 says so). Implemented by disabling the append-only trigger table-wide. | Deletes other files' fillers mid-test and any dev ledger rows; while disabled, the trigger is off for **every** session. |
| ISO-4 | Tests change the shared pause switch | The only way the sender test can show "switch on → sends" is to commit the real switch. `cleanup()` also writes `false` every time. | Crash/kill between line 530 and `finally` leaves sending ON; while ON, the tick drains any due row in the DB with a fake provider; a dev worker would drain to Mailpit. `cleanup()` silently overwrites a switch the developer set deliberately. |
| ISO-5 | Global Mailpit delete and count | Helper `mailpitDeleteAll()` + `inbox.total === 0` (E6) instead of correlating by recipient or Message-ID. | Any concurrent SMTP send breaks E6; one test's delete removes another's message before it is asserted. |
| ISO-6 | Files run concurrently | `node --test` runs files in separate processes in parallel by default; no `--test-concurrency` flag in the script [V script; parallel default per Node 22 docs]. | Turns ISO-1…5 from latent into actual failures. Not itself a bug; a multiplier. |

## 3. Options considered

### 3.1 Per-test unique community and identifiers — **adopt** [P]

Generate a `runId` per process (e.g. 8 hex chars from `crypto.randomUUID()`), and per test a fresh
community id, event/delivery ids (`randomUUID()`), slug `itest-<runId>-<n>` and addresses
`itest+<runId>-<n>@<file>.example.test` (plus-addressing already passes `assertValidEmailRequest`:
the sender test uses `member+…@sender.example.test` [V]).
Fixes L1/L2 cross-run accumulation, gives every row a scope key, gives Mailpit a correlation key.
Does **not** fix L3/L4/L5 or the claim RPC on its own.

### 3.2 Per-test schemas or isolated databases

- *Per-test schema:* not viable [V]. All functions are `security definer set search_path = ''` and
  reference `public.*`/`app.*` explicitly; a cloned schema would still call the originals.
- *Per-test database:* not viable — 120 migrations and Supabase-managed `auth`/`pgmq` per test.
- *One disposable database per suite run* — **adopt for commit-requiring tests** (§4.6). Options:
  - **DB-1** second database in the same local cluster (`kolekto_itest`), built from a schema dump
    of the migrated `postgres` database. Cheap; fidelity risk around Supabase-owned schemas,
    extension ownership and event triggers [U].
  - **DB-2** second Supabase local stack (different `project_id`, ports e.g. 6432x) with its own
    Postgres **and its own Mailpit**. Full fidelity, `supabase db reset` is safe there by
    construction. Cost: ~1–2 GB RAM, start-up time, keeping its migrations directory identical to
    the main one [U: whether the CLI can share `supabase/migrations` across two project ids without
    copying].
  - **DB-3** reset the main local DB before each run — **rejected** (destroys dev data; forbidden).
  Choice between DB-1 and DB-2 is decision **[Q-1]**; recommendation DB-2 after a spike.

### 3.3 Transaction-based isolation — **adopt where no commit is needed** [V precedent, P extension]

`notification-processor.integration.test.ts` already proves the pattern. Everything inside a
rolled-back transaction is invisible to other sessions and disappears on failure or crash
(connection loss = rollback) — including fillers and even a pause-switch change.

Limits [V/I]:
- `sendOneClaimed` calls `sql.begin` on a base connection and commits the claim before the
  provider call **by design**; it cannot run inside an outer transaction (postgres.js
  `TransactionSql` has `savepoint`, not `begin`).
- ISO-11: inside one transaction `now()` is frozen, so time-window behaviour is unrealistic.
- Concurrency tests need two committed sessions.
- Advisory `xact` locks taken by `reserve_email_attempt` (keys `(3,0)`, `(4,class)`, `(5,class|daily)`)
  are held until the outer rollback, briefly serialising other reservations — acceptable.

So: reservations, deferrals (L2/L4/L5), suppression, processor, `loadSendContext` → rollback.
Sender runtime (send, retry, exhaustion, lease recovery, Mailpit) → commit, in the disposable DB.

### 3.4 Explicit test ownership identifiers — **adopt via 3.1** [P]

No schema change: the community id *is* the ownership key for every notification table
(`community_id` on events, deliveries and ledger [V]). A `test_run_id` column would be a production
schema change for test convenience — rejected.

### 3.5 Scoped cleanup — **adopt for mutable rows only** [P]

Cleanup may delete only rows that are (a) inside the test's own community / ids and (b) in tables
without append-only protection. Append-only rows are never deleted by tests (§4.5, ISO-10).

### 3.6 Serial execution — **adopt as one layer, not the solution** [P]

Serialising fixes concurrency between files but not: dev-data stealing (ISO-1 against dev rows),
cross-run residue (ISO-9), daily-quota burn (ISO-2/L4), switch commits (ISO-4), inbox wipes (ISO-5),
global maintenance (ISO-7). It is necessary for the genuinely global counters (L3/L4/L5, sender
state, maintenance) and is implemented as a DB advisory lock (works even if someone runs
`npm test` with the env flag) plus `--test-concurrency=1` in a dedicated script.

### 3.7 Separate Mailpit or message correlation — **adopt correlation; separate instance comes free with DB-2** [V/P]

The Mailpit adapter sets `Message-ID: <sha256(idempotencyKey)[0..32]>` and returns that value as
`providerMessageId`; it also sets `X-Kolekto-Idempotency-Key: <deliveryId>` [V,
`packages/adapters/src/mailpit-email-provider.ts:89–153`]. With a run-unique recipient, a test can
assert on exactly its own message without touching anything else.

### 3.8 Dedicated test-only sender state — **reject as a schema feature** [P]

A second state row or a "test mode" flag would add production surface. Instead: no committed switch
writes (§4.5); the enabled path is covered by a unit test plus a disposable-DB test.

### 3.9 Scoped claim — options (Investigation B)

| Option | Change | Prod semantics | Verdict |
|---|---|---|---|
| B-1 Inject a claim strategy into `SenderOptions` (default `claimNextDelivery`) | Worker TS only | Unchanged when omitted (production `index.ts` never passes it) | **Recommended** |
| B-2 Add `p_community_id uuid default null` to the RPC | Migration | A defaulted extra parameter creates an overload; `claim_next_notification_delivery(integer)` calls become ambiguous unless the old signature is dropped → touches a security-definer function used by production | Rejected |
| B-3 New `app.claim_next_notification_delivery_scoped(...)` | Additive migration | Unchanged, but adds a test-only privileged function to production | Rejected |
| B-4 Tests call `claimDeliveryById` and reimplement the rest of the send step | Tests only | — | Rejected: a replica, the same defect as P6's `simulateEventLoop` |

B-1 detail [P]: the test strategy selects one candidate in the test's community and then calls the
**production** `app.claim_notification_delivery(id, lease)`, which re-checks every eligibility rule
itself — email channel, not terminal, `pending`, `attempt_count < 3`, due (`next_retry_at <= now()`)
[V, `20261013100000…sql:148–223`]. Drift in the test's candidate query can therefore only cause a
missed claim (test fails loudly), never an ineligible claim.

```ts
// test/support — sketch, not final code
select id from public.notification_deliveries
 where community_id = $scope and channel = 'email' and status = 'pending'
   and attempt_count < 3 and (next_retry_at is null or next_retry_at <= now())
 order by created_at, id limit 1 for update skip locked;
-- then: claimDeliveryById(tx, id)   (same transaction, before reserveEmailAttempt)
```

Cross-community ordering ("oldest first across all communities, no starvation") remains covered by
pgTAP `37_notification_send_claims.sql` [U: confirm it asserts ordering] and one disposable-DB test
that uses the unscoped default.

## 4. Recommended architecture

### 4.1 Test classes [P]

| Class | Definition | Where it may run |
|---|---|---|
| **U** unit | No DB, no SMTP | Anywhere, parallel |
| **R** rollback | All DB writes inside one rolled-back transaction; no SMTP | Dev DB or disposable DB |
| **C** commit | Commits rows (sender runtime, races, lease recovery, Mailpit sends, worker loop) | **Disposable DB only**, under the file mutex |

### 4.2 Harness module `apps/worker/test/support/itest.ts` (new) [P]

Not matched by `test/*.test.ts`, so never executed as a test file.

- `integrationGate(kind: "R" | "C")` → skip reason or `false`. `C` additionally requires
  `KOLEKTO_ITEST_DB_URL` (distinct from `SUPABASE_DB_URL`), loopback, **and** a marker check
  `select current_setting('kolekto.itest', true) = 'on'` (set once by `alter database … set kolekto.itest = 'on'`
  on the disposable DB only). The dev DB never carries the marker, so a C test cannot run there
  even if misconfigured.
- `preflight(sql)` (in `before`): assert `email_sending_enabled = false`; abort the file if true
  (fail closed, never "fix" it). `postflight(sql)` (in `after`): assert it is still false.
- `acquireSuiteLock(url)` → dedicated connection holding `pg_advisory_lock(918273, 1)` for the file's
  life (two-int key space distinct from the reserve function's `(1..5, …)` [V]); released on
  `after` or automatically when the process dies.
- `newScope(sql, label)` → creates owner (`auth.users` + `public.users`), community and returns
  `{ runId, communityId, ownerId, id(), address(n), tag }`.
- `scopedClaim(communityId)` → B-1 strategy above.
- `waitForL5Headroom(sql, class = 'transactional', timeoutMs = 5000)` → polls
  `count(*) … where send_class = $1 and attempted_at > now() - interval '1 second'` on the
  **server** clock until 0 (avoids JS/DB skew noted at sender:401–406 [V]).
- `inRollback(sql, fn)` → generalises the processor file's `Rollback` sentinel.
- Mailpit: `mailpitFind({ to, messageId }, { expect, timeoutMs })` — polls `GET /api/v1/search?query=to:"…"`
  (and/or `message-id:"…"`) until exactly `expect` messages or timeout; no `sleep(500)`.
  [U: confirm search operators for the bundled Mailpit version.]
- `readDelivery`, `addDeliveryWithEvent(scope, opts)` shared instead of duplicated per file.

### 4.3 Queue and sender isolation [P]

- `SenderOptions.claim?: (tx, leaseSeconds) => Promise<NextDeliveryClaim>`; `sendOneClaimed` uses
  `opts.claim ?? claimNextDelivery`. `TickOptions extends SenderOptions` [V], so `runSenderTick`
  inherits it with no further change.
- Every C test passes `claim: scopedClaim(scope.communityId)`. Exactly one test (disposable DB,
  under the mutex, after asserting no non-terminal email rows exist outside its scope) uses the
  default to prove the unscoped path.
- `recoverExpiredLeases` / `expireStaleDeliveries`: kept global (production behaviour); only called
  in C tests in the disposable DB under the mutex; assertions restricted to the test's own ids
  (they already use `>= 1` counts [V]).

### 4.4 Rate-limit isolation (realistic behaviour preserved) [P]

- **No ledger deletes.** The "send, clear ledger, send again" pattern is replaced by
  "send, `waitForL5Headroom`, send again" — the real 1/s limit is exercised, not bypassed.
  Replay steps after a `sent` row do not need either: `sendOneClaimed` returns `empty` before
  reserving when nothing is claimable [V, `notification-sender.ts`].
- **Filler tests become R.** "L2 community deferral", "L5 per-second", "L4 daily" move into
  `inRollback`: insert fillers, `claimDeliveryById` + `reserveEmailAttempt` in the same transaction
  (the pattern of `notification-rate-limit.integration.test.ts:118–121` [V]), assert reservation,
  `next_retry_at`, unchanged `attempt_count`, kept address, then roll back. The 180 L4 fillers never
  become visible to any other session.
- The TS mapping "deferred reservation → `outcome: "deferred"`, no provider call" becomes a unit
  test with a fake SQL (extend `notification-sender.test.ts`'s `fakeSql`).
- Per-run unique addresses/communities make L1/L2 independent across tests and runs.
- L3/L4/L5 are global by design; the suite mutex plus L5 pacing make them deterministic. Budget:
  ≈19 granted transactional reservations per full C run [I, counted from current tests]. A
  `preflight` check refuses to start if the disposable DB's 24 h transactional count is above
  `180 − 40`, telling the operator to recreate the test DB.

### 4.5 Ledger, events, pause switch — protections stay on [P]

- Tests never `alter table … disable trigger`, never use `app.send_attempts_purging`, never delete
  from `notification_send_attempts` or `notification_events`.
- R tests leave nothing behind. C tests leave tagged residue (`itest-<runId>`) in the disposable DB,
  which is recreated wholesale (DB-2: `supabase db reset` against the test stack only; DB-1: drop
  and rebuild `kolekto_itest`). Recreating a disposable database is a lifecycle operation on a
  database that holds nothing else — not disabling a protection.
- Mutable rows (`communities`, `users`, `auth.users`, `officer_terms`) are **not** deleted either
  in C tests: FKs `restrict` from events make it impossible [V]. Cleanup code is removed.
- **Pause switch:** no test commits a switch change, and `cleanup()` no longer writes `false`.
  - Paused path: C/R test reads the real switch (preflight guarantees `false`) and proves
    `runSenderTick` claims nothing, preserves the row and makes no provider call.
  - Enabled path: unit test with `fakeSql(true)` asserting a claim is attempted (today only
    `allowSend:false` with the switch on is unit-tested [V, sender.test.ts:100–111]).
  - Real-switch round trip (optional, disposable DB only): `inRollback` → `set_email_sending_enabled(true)`
    → `app.email_sending_enabled()` reads true → rollback. A crash rolls the change back
    automatically; no session ever sees it. `set_email_sending_enabled` semantics stay covered by
    pgTAP 40 [V file exists; U: assertions].

### 4.6 Mailpit isolation [P]

- Remove `mailpitDeleteAll()` and every `inbox.total` assertion.
- Correlate by run-unique recipient **and** `providerMessageId` (= `Message-ID`), assert exact counts
  for that recipient (`=== 1` after send, still `=== 1` after replay).
- E6 ("skipped row produces no message") asserts `mailpitFind({ to: scope.address(n) }, { expect: 0 })`
  after a bounded wait.
- With DB-2 the test stack has its own Mailpit, so dev mail and test mail never mix.

### 4.7 Why this is the safest, most maintainable option [I]

- It fixes causes, not symptoms: every global-state interaction is either scoped (A, B), never
  committed (C), serialised deliberately (D), or confined to a database that holds nothing else (F).
- It changes no SQL and no production behaviour; the single production-code change is an optional,
  default-preserving parameter.
- It reuses two patterns already in the repo (rollback sentinel; claim-by-id + reserve in one
  transaction), so the harness is familiar.
- It removes code (per-file `cleanup`, `clearSendLedger`, duplicated helpers) rather than adding
  per-test repair logic.

## 8. Test execution strategy [P]

| Command | Runs | Concurrency | Target |
|---|---|---|---|
| `npm test --workspace apps/worker` | U (+R if `KOLEKTO_WORKER_INTEGRATION=1`) | default (parallel) | dev DB for R only |
| `npm run test:integration --workspace apps/worker` | R + C | `--test-concurrency=1` + suite advisory lock | `KOLEKTO_ITEST_DB_URL` (disposable, marker-checked) |

Run order for acceptance: recreate test DB → `test:integration` ×3 consecutive, output captured to
a file → `test` ×3 (parallel) → typecheck. Any C test seen running against a DB without the marker
is a harness bug.

R tests are safe in parallel with each other because they commit nothing; their transient advisory
`xact` locks only serialise reservations briefly [I].

## 9. Rollback considerations

- All changes are in tests, one optional TS parameter and one script — revert by reverting the
  commit(s); no data or schema rollback is needed [I].
- The disposable DB is independent: deleting it (or stopping the DB-2 stack) restores today's state.
- If the B-1 parameter is reverted, scoped tests stop compiling — a loud failure, not a silent
  semantic change.
- During migration of each file, keep the old file content in Git history only; do not keep two
  copies of a test running in parallel.
