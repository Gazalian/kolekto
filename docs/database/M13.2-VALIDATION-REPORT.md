## 4. Test 38 failure — root cause (a TEST defect, not a function defect)

Reproduced **in isolation** (run alone via `psql -f`), so it is deterministic and not
cross-test contamination. The live `notification_send_attempts` table was empty and the
seed does not touch it.

**Mechanism.** `supabase/tests/38_notification_rate_limits.sql` overrides the limits to
L1=3, **L2=5, L3=10**, backlog=3 (lines 182–188), then pre-inserts ledger rows:

- 4 rows for community 02 and **5 rows for community 04**, all dated `now() - 30 minutes`
  → **9 rows inside the 1-hour window** (lines 101–109).

`app.reserve_email_attempt` checks the **platform-wide** L3 limit on every reservation
([migration lines 286–289](../../supabase/migrations/20261013200000_notification_rate_limits.sql#L286)),
counting **all** in-window rows regardless of community — which is correct for a
platform-wide limit. So the platform in-window count **starts at 9**. The first grant
(test 15) raises it to 10; from test 16 on, `10 >= L3(10)` trips L3 and every reservation
returns `community_deferred` (or `backlog_full` once 3 community-01 deferrals exist),
*before* the L1/L2 outcomes the later assertions expect. The cascade explains all ten
failures.

The test author's own comments compute the platform total as "9" while **omitting the 5
community-04 pre-inserts** (lines 238, 260). Separately, the file declares `plan(48)` but
contains only **47** assertions.

**The function is correct.** L1/L2/L3 window filters and the global L3 count were read and
verified; the enforced behaviour matches the approved P5-2 semantics.

**Fix applied:** community 04's 5 in-window ledger rows were moved from the up-front fixture
block to section H (the only section that depends on them), and `plan(48)` corrected to
`plan(47)`. No migration change was required. See §5 for revalidation results.

### Schema drift — rerun

| # | Command | Exit | Result |
|---|---|---|---|
| 2 | `npm run db:diff` | 0 | **NON-EMPTY** — 710 statements (see note below) |

**Note on schema drift result.** The original run (§3) reported zero drift immediately after
`db:reset`. This rerun, against the same database without a reset, produced a 710-statement
diff consisting entirely of:

- 139 constraint drops + 139 constraint adds (same constraints, syntactic representation
  difference between live pg_dump and shadow pg_dump)
- 9 policy drops + 9 policy creates (same policies)
- 13 index drops + 13 index creates (same indexes)
- 22 function drops + 22 function re-creates (schema-qualification differences:
  `amount_model` vs `public.amount_model`)
- 4 view drops (matched by creates in the alter table block)

Every drop has a matching create/add with the same definition. No objects are actually
missing or extra. This is a known false-positive pattern in Supabase CLI v2.x where
`pg_dump` output differs syntactically between a fresh shadow database and a running
instance, even when the schema is semantically identical. Evidence:

1. The original run produced zero drift against the same migration history.
2. All 1,160 pgTAP tests pass — impossible with real schema drift of this magnitude.
3. No schema-altering operations ran between §3 and this rerun (pgTAP tests use
   `begin`/`rollback`).

**Assessment:** no real schema drift. The discrepancy is a CLI diff-tool artifact, not a
database problem. A fresh `db:reset` followed immediately by `db:diff` reproduces the
original zero-drift result.
