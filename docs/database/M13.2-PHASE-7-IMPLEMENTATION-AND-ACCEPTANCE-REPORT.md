### 3.2 Why each partial item stopped where it did

**F-1, production role.** Requires a new migration and a new credential in each environment. Stopped before applying. The content is proven by `workerRoleSql()` in `itest.mjs`. Rollback would be: repoint `SUPABASE_DB_URL` to the previous credential, then drop the role and its policies.

The rehearsal corrected the design's §5.2 privilege list. Three things it missed were found only by running the real worker:

| Missing privilege | Needed by | How it showed |
|---|---|---|
| `app.uuid_generate_v7()`, plus `USAGE` on `extensions` and `extensions.gen_random_bytes` | The `id` default on both tables | Every event failed with 42501 in attempt 1 |
| `app.strip_banned_payload_keys`, `app.payload_has_banned_key` | Sanitiser trigger and CHECK constraint | Found by reading the migration before the first run |
| `SELECT (msg_id)` on `pgmq.a_notification_events` | `RETURNING` inside `pgmq.archive` | Dead-lettering failed with 42501 in attempt 2 |

**F-3, database enforcement.** `sendOneClaimed` and the `claim`, `reserve` and `resolve` functions do not read the switch. Only `runSenderTick` does. Having the database refuse a claim while paused needs a migration, and would also break the direct-sender tests that rely on this. Not applied.

**F-6, durable record.** A table for skipped messages needs a migration. Archiving skips would mix them with dead letters, since the archive is the dead-letter store. The log line is the smallest honest step. Its durability depends on log retention, which is not yet chosen.

## 4. Actual worker runtime architecture and execution path tested

```
real RPC, committed, as an authenticated user
  → public.audit_logs → trigger → pgmq notification_events
  → node dist/itest/index.js   (the esbuild bundle of src/index.ts, sha256 074f4492…dd00c5)
      connected as kolekto_itest_worker
      pgmq.read → processNotificationMessage → pgmq.delete, or at read_ct 6, pgmq.archive
      runSenderTick: maintenance → app.email_sending_enabled() → claim + reserve → provider → resolve → heartbeat
  → MailpitEmailProvider → 127.0.0.1 → test Mailpit (directly or through the fault proxy)
```

The tests watch the worker from outside: database rows, `pg_stat_activity`, its logs and Mailpit. They never import worker logic into the test process for these checks.

- **Environment:** built from nothing. Only OS essentials are copied. `KOLEKTO_ENV=local`, so the config layer refuses a real provider. A unit test proves `AWS_*`, `EMAIL_API_KEY`, `NODE_OPTIONS`, `PG*` and `SUPABASE_DB_URL` cannot reach the child.
- **Target proof:** a session with the worker's `application_name` and exactly the worker role must appear, or the child is killed and the test fails.
- **Credential:** a random password, sent as a SCRAM verifier, valid for 90 minutes and removed at file end. Final read: `PASSWORD_SET=false`.
