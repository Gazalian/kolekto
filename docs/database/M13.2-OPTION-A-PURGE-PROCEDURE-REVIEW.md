## 1. Conclusion

**On the current evidence, the procedure can guarantee that it deletes exactly the 131 inventoried rows or nothing, subject to the assumptions and untested steps in §7.** Those rows are demonstrably test-only.

Three facts shape the procedure:

1. **It cannot run yet.** At 15:01:59 UTC no row is older than 48 hours. The transaction refuses until **2026-11-06 16:23:52 UTC**, when all 131 are eligible, and refuses again from **2026-11-07 16:11:13 UTC**, before the next 22 rows age in.
2. **`app.purge_stale_send_attempts()` cannot be limited to chosen rows.** It deletes by age alone. The guarantee comes from proving, under a lock and in one snapshot, that the rows matching its age test are exactly the verified set.
3. **The steps that change data have never run.** The lock, the suite mutex, the real purge call and the commit could not be rehearsed read-only. Each of them fails safe, because any failure before commit rolls everything back.

## 2. Corrections to the previous proposal

The previous SQL should not be used. Its weaknesses were more than the NULL handling you identified.

| # | Weakness in the previous proposal | Correction |
|---|---|---|
| 1 | `if n <> 131 or bad <> 0 or fp <> '…'`: a NULL comparison is not true, so a NULL could pass that test | Every condition is written `(…) is not true`, so NULL refuses |

## 5. Deliverable C: review of the purge function

Read live with `pg_get_functiondef`. It appears in one migration only, `20261013200000_notification_rate_limits.sql`, and has no later redefinition.

```sql
perform set_config('app.send_attempts_purging', 'true', true);
delete from public.notification_send_attempts where attempted_at < now() - interval '48 hours';
get diagnostics v_deleted = row_count;
perform set_config('app.send_attempts_purging', 'false', true);
return v_deleted;
```

| Question | Finding |
|---|---|
| **Which rows does it delete?** | Every row with `attempted_at < now() - 48 hours`. It has no community, class or address filter |
| **Can it delete rows outside the verified set?** | **Yes, on its own.** Any row meeting the age test is deleted, including a non-test one. Only the surrounding gate prevents this |
| **Which clock?** | `now()`, the transaction start. It is the same value inside the function as in the gate |
| **Which role?** | `SECURITY DEFINER`, owner `postgres`, `search_path` empty |
| **RLS?** | The table forces RLS with no delete policy, but `postgres` has `BYPASSRLS`. If that were lost, the function would delete 0 rows without error. The gate checks the owner, and the count check would refuse |
| **Triggers?** | Three `BEFORE` triggers on one function, all enabled. `DELETE` proceeds only while the transaction-local flag is `'true'`. `UPDATE` and `TRUNCATE` always raise. No `AFTER` trigger |
| **Flag?** | Local to the transaction, and reset by the function. It cannot outlive the transaction |
| **Cascades?** | None. Nothing references the ledger, and there are no rules or subclasses. Deliveries, events and communities are untouched |
| **Other effects?** | None. All rate limit windows are 24 hours or shorter, so rows older than 48 hours affect no limit |
| **Has it ever really deleted?** | **No.** Phase 8 found it has never deleted a row. This is its first real deletion |

**Security observation, separate from this purge:** the append-only trigger trusts only the flag. Any role with `DELETE` on the table can set the flag itself: `postgres`, `supabase_admin` and the test role `kolekto_itest`. The worker role has no direct `DELETE`, only `EXECUTE` on the function, and client roles have neither. It is worth checking when production roles are reviewed. I have not changed it.

## 6. Concurrency

| Possible interference | Can it occur? | Protection |
|---|---|---|
| New rows from `app.reserve_email_attempt` | Only if a worker or harness is running. These rows use `now()`, so they are never old enough | Table lock, session check |
| Backdated rows | Only `insertLedgerFillers`, which runs in a rolled-back transaction, or a privileged role by hand | Table lock, and the exact ID match |
| Another purge in progress | The worker calls it each maintenance pass, if a worker is running | Table lock. Earlier purge: count mismatch, refuse |
| Rows ageing in during the run | **No.** Within one transaction the cutoff is fixed. No row ages in anywhere in the window | Same `now()`, window check |
| A writer mid-transaction at the start | Possible if something is running | `lock_timeout` of 5 s, then refuse |
| A lane starting during the run | It polls the suite mutex | `pg_try_advisory_xact_lock(918273, 1)`, refuse if held |
| A change to a delivery, event or community after the check | It cannot change which rows are deleted. Ledger rows cannot be updated, and the delete is by ledger age | Not locked, on purpose. Same snapshot for all checks |
| Deadlock | **No.** The purge transaction takes the table lock first and otherwise reads and uses non-blocking try-locks | |

**Required protection, in order:**

1. `BEGIN ISOLATION LEVEL REPEATABLE READ`.
2. `LOCK TABLE … IN SHARE ROW EXCLUSIVE MODE`, **before any query.** This blocks every insert, update, delete and truncate on the ledger and every other locker, and still allows reads.
3. The snapshot is taken at the first query after the lock, so it includes every writer that finished before the lock.
4. The gate and the function's `DELETE` use that same snapshot and the same `now()`.

**Why this gives set equality:** the `DELETE` matches the rows visible in the snapshot with `attempted_at` below the cutoff. The gate proves that this exact set equals the 131 IDs. No writer can change the table until commit. The post-checks then confirm the outcome.

Holding the lock briefly delays any writer, and nothing should be writing. Every other table is read without a lock.

## 8. Deliverable E: risks and rollback

| When | What happens | Recovery |
|---|---|---|
| **Any failure before commit** | **Complete automatic rollback.** Includes a refused gate, a failed check, a timeout, a lost connection or a psql exit | Nothing to recover. Read the refusal, and do not adjust the gate to pass |
| **After commit** | **The deletion is permanent. There is no undo command** | See below |

## 9. Deliverable F: can only verified test-only records be deleted?

**Yes: exactly these 131 rows, or none, under these assumptions.**

**The guarantee follows from:**

1. The purge's age test is evaluated with the same `now()` and against the same snapshot as the gate.
2. The gate proves that the set matching that test equals the 131 inventoried IDs, by count, by exact ID array and by fingerprint.
3. The lock prevents any change to the ledger until the transaction ends.
4. Any difference raises an exception, which rolls everything back.
5. Post-checks independently confirm 131 deleted, none remaining, and every other row unchanged.

**Assumptions:**

- PostgreSQL honours `REPEATABLE READ`, table locks and transaction atomicity as documented.
- The script runs unmodified, in `execute` mode, as `supabase_admin`, against this container.
- The window and the live checks hold at that moment. If not, it refuses.

**What it cannot guarantee:**

- **That "test-only" is absolute.** It is strong evidence, not attestation. Slugs, reserved-domain addresses, agreeing run tags and linked records show that these rows came from the test harness. Someone with superuser access could forge rows to match, though the exact IDs and the fingerprint would catch any change after this inventory, and the whole stack contains no non-test community or user.
- **That the purge will succeed.** It can only guarantee a clean refusal if it does not.
- **That the deletion can be undone** by anything other than the untested re-insert.
- **That the target check would refuse the ordinary development database.** It relies on `kolekto.itest_*` settings being absent there. I did not test this, because that database is off limits.
