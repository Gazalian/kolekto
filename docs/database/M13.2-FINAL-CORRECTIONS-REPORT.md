### 2.5 Queue dead-lettering (R-1)

**Confirmed from the code before changing it:** a processing failure with 42501 got no backoff, was retried at the 30 s timeout, and was archived at read 6, while `pgmq.read` kept working, so the fatal exit never fired. **Plainly: a missing privilege would have dead-lettered every healthy message in about 2.5 minutes.**

**A plain "exit on a fatal error" would not have been enough.** `pgmq.read` raises `read_ct` on all ten messages in a batch, on every restart, whether or not they are attempted. A restart loop would still have reached read 6, and then the dead-letter branch runs *before* processing. So there are two layers:

| Layer | What it does |
|---|---|
| **Startup preflight** | Reads the catalog after the timeout check and before the first `pgmq.read`. Missing what processing needs: `worker_privileges_refused`, exit 1, **queue not read, so `read_ct` cannot climb** |
| **Worker fault** | A fatal code during processing, or a fatal failure of the mark after a failed delete, is not counted against the message. It logs `notification_event_worker_fault`, writes `kolekto_fault_reads`, `kolekto_fault_code` and `kolekto_fault_at` into the message's headers, records the rest of the batch as `batch_abandoned`, and exits 1 |

Dead-lettering now uses `read_ct - kolekto_fault_reads`. A malformed header counts nothing, so it cannot accidentally keep poison in circulation. `42703` and `42704` joined the fatal list, since a migration gap could otherwise dead-letter too.

**A 42501 cannot be one message's own fault.** The processor calls `app.evaluate_email_eligibility` and `app.resolve_collection_audience`, and neither raises it, nor calls `require_permission`. I checked this because the design would otherwise loop on it. **READ**

**No replay.** Recovery is the same message, still in the queue, read at its visibility timeout. Nothing is copied or re-queued. Processing is idempotent, as EV-1's replay test shows.

**Acknowledgement problems.** The proven F-15 path is unchanged: mark, retry only the delete, park at read 8, never dead-letter. A worker missing DELETE or archive INSERT therefore **starts and logs `worker_privileges_degraded`** rather than refusing. That is a judgement call: it keeps F15-ACK's restart-under-revocation behaviour, and those failures are non-destructive, but a refusal would be louder. Tell me if you want a refusal, and F15-ACK and F15-ARCHIVE then need rewriting.

**Diagnostics and recovery:** runbook §7.2 and §7.3, alerts A10 to A12, and a new `worker_faults_total` on the health line.

**Tests.**

- **VERIFIED, with fakes, in `queue-disposition.test.ts` and `worker-guards.test.ts`:** six fatal codes, poison still dead-lettering, 12 consecutive faults then exactly one processing, batch abandonment, the preflight's tiers.
- **NOT TESTED:** new `R1-FAULT` in the reliability file, which takes a real privilege from the role, proves exit 1, the durable header, an unmoved `read_ct` across a restart, and recovery with one event and one delivery. It costs 0 grants, about 1 minute, and is blocked by the ledger guard (§10).
