## 3. F-13 remediation and evidence

### What was found

Read from the catalog only, `f13/catalog-before.txt`. No request was sent, and the queue and response tables held 0 rows before and after.

**Why it needs a PUBLIC revoke.** Postgres has no per-role deny. While PUBLIC holds a privilege, every role holds it, so no worker-role design can close this.

- ADR 0005 plans `pg_cron` → `pg_net` → route handler for later. `pg_cron` jobs would run as `postgres`, so `postgres` keeps `http_get` and `http_post`.
- The pg_net background worker runs as superuser and is unaffected. It stayed up: its backend was present before the change, and no request was issued.

## 4. F-14 remediation and evidence

### The worker's real SQL and where it can wait

| Operation | Transaction | Can it wait on a lock? | Result on timeout |
|---|---|---|---|
| `pgmq.read` | Own | Row locks skipped (`SKIP LOCKED`). A table lock blocks it | Poll failure; bounded by the existing 30-failure exit |
| Processing (reads, event and delivery inserts) | One | **Yes:** the unique key on `event_key`, the dedupe key | Rolls back, nothing committed |
| `pgmq.delete`, `pgmq.archive` | Own | **Yes:** row and table locks | Acknowledgement or archive failure (§5) |
| Claim + reservation | One, committed before the provider call | **Yes:** five advisory locks in `reserve_email_attempt` | Rolls back, claim and attempt undone |
| Provider call | **None** | Not database | The provider's own timeout |
| Settle, after the provider call | Own | **Yes:** the delivery row | **Retried, see below** |
| Heartbeat, maintenance | Own | Yes: the sender-state row | Tick error logged; loop continues |

### The bounds, and why these numbers

Measured from `pg_stat_statements` over about 8,000 worker statements (`phase-a/worker-statement-timings.txt`). Every statement that was not deliberately blocked finished in under 1 s: the slowest were `pgmq.archive` at 979 ms and `pgmq.read` at 592 ms. Most averaged under 20 ms. This is a Windows Docker VM, not production hardware.

| Setting | Value | Impact on normal processing |
|---|---|---|
| `lock_timeout` | **5 s** | None seen: five times the slowest unblocked statement. A wait this long means someone is holding something |
| `statement_timeout` | **15 s** | None seen. Deliberately longer than `lock_timeout`, so a lock wait always reports as 55P03 and not 57014 |
| `idle_in_transaction_session_timeout` | **30 s** | None: no worker transaction waits on anything but the database |
| `connect_timeout` | 10 s (existing) | Unchanged |
| Startup probe, client-side | **15 s**, up to 5 attempts | Bounds a server that accepts a connection and then never answers. UNIT ONLY |

They are sent as startup parameters. **At startup the worker reads them back from the server and refuses to run if any is missing**, because a transaction-mode pooler can drop startup parameters silently, and that would bring F-14 back unnoticed. Every run logged `worker_database_timeouts` with the applied values.

**Queue processing worst case.** One message: about 5 s if it hits a lock, since the first timeout aborts the transaction. A batch of 10: about 50 s, which exceeds the 30 s visibility timeout. That is safe with one worker, because only this worker reads, and the replay is idempotent regardless.

### Two changes the timeouts made necessary

**Backoff.** See §1 item 3. `queue-disposition.ts` calls `pgmq.set_vt` after a transient failure. Measured: 30 s, then 60 s (test F14-LOCK). The longer steps are UNIT ONLY.

**Settle retry.** Before this phase a settle after the provider accepted would simply wait. With a timeout it could fail, leaving a row `sending` until its lease lapsed and then `dead/outcome_unknown`, even though the outcome was known. It now retries a transient failure up to 3 times, about 17 s at most, well inside the 300 s lease. This is safe to repeat because the database function is gated on the lease token.

File: `test/integration/notification-worker-reliability.integration.test.ts`. All passed in 3 of 3 runs.

| Your requirement | Test | Evidence |
|---|---|---|
| 1. Hold a relevant lock | F14-LOCK event key; F14-ACK queue row; F14-SEND reservation advisory lock; F14-SETTLE delivery row | Held by the test, always rolled back |
| 2. Start the real worker | All four | The esbuild bundle, as `kolekto_itest_worker` |

| 4. Sanitised failure | Asserted exactly `{"name":"PostgresError","code":"55P03","severity":"ERROR"}` | All 52 stored worker logs passed the scan |

Also proven: while the lock is held **the loop keeps running and the heartbeat advances**, which is the actual defect in F-14. A timed-out reservation uses no attempt, no grant and sends no mail.

**Not proven:** `statement_timeout` and `idle_in_transaction_session_timeout` were confirmed as applied, but **neither was made to fire** at runtime. Only `lock_timeout` was. There is no transaction-wide limit either: a transaction of many slow statements could run longer, each bounded to 15 s.

**A remaining gap:** after startup, a connection that stops answering, such as a network black hole, is not bounded by any of this. The server-side timeouts cannot fire and the driver has no query timeout. The worker would stall silently until TCP gives up. Alert A4 (stale heartbeat) would see it. Not fixed.

## 5. F-15 remediation and evidence

### The three failures are now separate

`apps/worker/src/queue-disposition.ts` (new) decides what happens to each message. `index.ts` only supplies the database operations.

| | Processing failed | Acknowledgement failed | Archive failed |
|---|---|---|---|
| **What is true** | Nothing committed | **Processing committed**, delete failed | Poison, and the move failed |
| **Next read** | Process again | **Delete only.** Never reprocessed | Archive again |
| **Is it poison?** | At read 6 | **Never** | Already was |
| **Bound** | 5 attempts, then archive | Read 8, then park | 3 archive attempts, reads 6 to 8, then park |
| **Log** | `Failed to process…` (unchanged) | `notification_event_ack_failed` | `notification_event_archive_failed` |
| **Counter** | `failed_total` | `ack_failures_total` | `archive_failures_total`. `dead_lettered_total` does **not** rise |

**How the worker remembers across restarts.** After a failed delete it writes `kolekto_processed_at` into the message's own `headers`. If that write also fails, the next read processes again, which is idempotent (F14-ACK proves this path).

### The durable outcome: parking

When attempts run out, the message is **parked**. It stays in `pgmq.q_notification_events` with its body untouched, its visibility moved 10 years ahead, and `kolekto_parked_reason` (`ack_failed` or `archive_failed`) and `kolekto_parked_at` in its headers.

| Your requirement | How it is met |
|---|---|
| No indefinite retry | Parked messages are not read again. Asserted: `read_ct` unchanged past a whole visibility timeout |
| No silent delete | Parking never deletes. Asserted: the row and body are intact |
| Recoverable | `select pgmq.set_vt('notification_events', <msg_id>, 0)` gives one more attempt. Tested end to end. The procedure is in runbook §7.1 |
| Idempotent, no duplicate delivery | One event and one delivery throughout, including across a worker restart |
| Durable and independently observable | It is in the row, readable with SQL with no worker running. Also `queue_parked` and `parked_total` on the health line |
| Not confused with poison | The reason says which it was. An acknowledgement-failed message is deleted on release and never archived. Asserted |

**No migration was needed.** `headers` is a pgmq 1.5 column, and the worker already holds `UPDATE` on the queue table. `pgmq.archive` carries headers across, so a released message's history stays with it. Verified: archived with its reason, 3 rows.

**If parking itself keeps failing**, the worker exits non-zero at read 11 rather than retry for ever. **UNIT ONLY:** a real persistent failure of that one `UPDATE` is hard to produce, because `pgmq.read` needs the same privilege and would fail first, which already ends the process.

### Tests with real, injected failures

The worker role really loses `DELETE` on the queue, or `INSERT` on the archive, for the length of the test, and gets it back. Each test then reads the grant back. If the process dies in between, both files refuse to start until `npm run itest:worker-role` restores it.

| Test | What it proved, 3 of 3 runs |
|---|---|
| F15-ACK | Processed once. Delete fails with 42501 on reads 1 to 8, **across a worker restart**. No `Failed to process`, no `Dead-lettering`, no second `processed` line. Parked at read 8 as `ack_failed`, not read again. Released: `ack_recovered` at read 9, queue empty, 1 event, 1 delivery, archive unchanged |
| F15-ARCHIVE | Exactly 5 processing attempts (22P02), so ordinary poison handling is unchanged. Exactly 3 failed moves at reads 6, 7, 8 (42501). Parked as `archive_failed`, body byte-identical, `dead_lettered_total` 0, a healthy message unaffected, the sentinel value absent from logs. Released: archived once at read 9 with its reason, `dead_lettered_total` 1, nothing created |

RC-5, the Phase 7 poison test with no injected failure, still passes: 5 attempts, archived at read 6.

## 11. Proposed production migration and deployment plan

**Design and review only. Nothing here was applied, created, accessed or deployed.** Neither proposal has been executed anywhere, including the test stack. Both sit outside `supabase/migrations`, because the test stack refuses to start if that directory differs from its copy.

**Order.** Staging, under its own approval, then production, under a separate one. The rollback for each step is stated with it. A staging result does not imply production is safe.

### 11.1 Least-privilege role and grants, and RLS policies

`M13.2-P8-worker-role.proposed.sql`: role `kolekto_worker`, the same grants and 10 policies that ran on the test stack, 17 functions, and post-apply checks. Unproven until staging: running under the hosted migration role.

### 11.2 F-13 in staging and production: decision needed

**Read the ACLs first**, read-only, under approval. The proposal lists the queries. **Do not issue a worker credential while `has_schema_privilege('kolekto_worker', 'net', 'USAGE')` is true**, because that credential could send arbitrary outbound HTTP from inside the database.

|---|---|---|

### 11.4 Credentials: provisioning, rotation, revocation

| Step | Plan |
|---|---|
| **Provision** | One credential per environment, generated by the operator's secret store, set with `ALTER ROLE … PASSWORD` over an approved session. Prefer sending a SCRAM verifier, so plaintext never reaches the server logs. Inject at process start. Never the same value in two environments, never the owner credential |
| **Rotate** | Issue a new password, update the secret store, restart the worker with the §5 pause sequence, and confirm a session as `kolekto_worker`. Rotate on a schedule you choose, and on any suspected exposure |
| **Revoke, emergency** | `ALTER ROLE kolekto_worker NOLOGIN`, then `pg_terminate_backend` for its sessions. The worker exits 1 on the failed reconnect (proven by CFG-REVOKED), and the restart policy stops on a crash loop. No email goes out meanwhile; queue messages and deliveries wait |

### 11.5 Connection limits

The role limit is 5. The worker's loop is sequential and normally holds one connection. **Use a direct or session-mode connection, not transaction mode:** the worker needs its startup parameters, and refuses to start without them. The driver's default pool of 10 is above the role limit but is not reached by a sequential loop. Setting `max` explicitly is a small follow-up. The proposal also sets the timeouts on the role as a second line of defence.

### 11.6 Health checks and alerting

Log-based liveness: no `notification_event_health` line for 2 minutes means restart. The runbook's alerts A1 to A5, plus the new A6 parked message, A7 archive or acknowledgement failures, A8 oldest message over 20 minutes, A9 timeouts refused. **None of these is built.** Each must be fired once with a synthetic value in staging before activation. Log retention must be chosen: 30 days is proposed. A6 and A8 can also run as SQL, independently of the worker.

## Final statement

**What is now proven, on the isolated test stack, on Windows, with this bundle:**

- The worker role cannot initiate outbound HTTP through `net`, by catalog and by refusal. Only `postgres` (and so the harness role, its member), `supabase_functions_admin` and the owner retain the HTTP functions. No request was sent.
- A held lock fails in about 5 s with a sanitised 55P03 at all four places the worker can wait. The loop keeps running, the message stays recoverable, and recovery creates no duplicate delivery.
- The worker refuses to run if its timeouts are not applied on the server.
- An acknowledgement failure is distinguished from a processing failure and from poison, across a restart.
- A message whose acknowledgement or archive keeps failing stops retrying at a fixed bound, is kept intact with a durable reason, and can be released to finish exactly once.
- The Phase 7 worker-runtime file still passes on this code, 23 of 23 in one pass, with RC-LOCK, RC-2 and LP-3 deliberately updated (§1).

**What remains unsafe:**

- **F-13 is open or unknown on staging and production.** Neither was read. A least-privilege role does not close it.
- **There is no production worker role or credential.** As documented, the worker would run as the owner.
- **The pause switch is enforced in one place only**, not by the database (F-3).
- **Nothing alerts anyone.** A parked message, a stale heartbeat and an exit are log lines and rows until someone builds the alerts. There is no dead-letter replay tool.
- **A connection that stops answering after startup is not bounded.**
- **`statement_timeout` and `idle_in_transaction_session_timeout` have never fired in a test.**
- **A lock held more than about 15 minutes dead-letters healthy messages** into the archive, with no replay tool.
- **Not tested:** real SIGTERM on Linux, the deployment image, SES and real sending, two workers, the 7 older files on this code, and the hosted migration role.
- **All of this is uncommitted.**

**Is M13.2 complete?** **No.** The reliability defects found by Phase 7 are closed on the test stack. The production prerequisites in §12 are not met.

**Is production notification activation authorised?** **No.** Nothing in this phase authorises it, and these isolated tests passing is not evidence of production readiness. `email_sending_enabled` stayed false at every reading outside the guarded test windows, and ends false.
